# 代码库内交接原型

**与相近工作流的区别：** 最接近的是 AWF-0007 从反馈到原型（Feedback to prototype）：该工作流把反馈聚类成 PRD，做出多个原型变体，并用 5 次用户测试验证。本工作流的交付物是交给工程团队的单个仓库内分支，关卡是边缘状态审阅和开发交接，没有用户测试环节。它也不同于新的“设计师提交的 UI PR”（Designer-authored UI PR）：那里设计师自己的 PR 经工程审阅后合入生产环境，而这里是开发者基于原型分支编写上线代码。
**工具变体：** `claude-code`

## 步骤

1. 一次性准备：一个由开发者组成的突击小组花六周时间，把生产仓库改造成设计师可以安全、高效做原型的地方。准备工作是一份设计师配置和三个 Claude Code 技能文件 [[1]](#sources)。
2. 每个功能，设计师直接在生产代码库的一个 git 分支上做原型，使用真实的设计系统组件。这取代了单独的 Figma 样稿和 Lovable 交互原型 [[1]](#sources)。
3. 范围受代码中已有内容的限制。可行性问题在设计师做原型时就会暴露，而不是等到开发后期 [[1]](#sources)。
4. 设计师在规格中补上空状态、错误状态和加载状态。🛑 **审阅**：这些边缘状态在交接前被标出来供审阅 [[1]](#sources)。
5. 🛑 **接手**：开发者基于交接分支构建生产功能，管理层也在同一处查看进展 [[1]](#sources)。

**产出：** 生产仓库 git 分支上的一个原型，加上涵盖边缘状态的规格，开发者以此作为上线功能的起点。
**失败模式 → 防护：** 样稿空想而不可行，缺失的边缘状态由开发者自己补上 → 在代码库约束内用真实组件做原型，并在交接前标出边缘状态供审阅。多个工具之间版本混乱 → 一个分支上只有一份产物。
