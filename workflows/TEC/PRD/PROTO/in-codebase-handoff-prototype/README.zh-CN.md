# 代码库内交接原型

**工具变体：** `claude-code`

## 背景

设计师需要展示一个功能如何交互，开发者则需要符合现有应用、确实可行的起点。独立样稿转成代码时容易丢失细节，尤其是页面没有数据、正在加载或发生错误的时候。本工作流用真实组件把原型放在仓库分支上，并同时记录这些状态。智能体帮助设计师在准备好的环境中修改和测试交互。开发者仍负责把交接成果做成生产代码，并判断是否达到发布要求。

**术语：**
- **代码库 / 仓库 / git 分支**：应用源码、保存其版本的地方，以及一条隔离的修改线。
- **设计系统 / 组件**：共享的界面规则，以及可复用的界面元素。
- **空 / 错误 / 加载状态**：没有数据、发生故障或等待时，用户看到的内容。
- **规格 / 交接（spec / handoff）**：行为说明，以及把工作移交给实施开发者。
- **PR / LLM**：pull request，以及驱动编码智能体的大语言模型。

## 用智能体搭建

**形态：** `project`。依赖事先准备好的仓库、长期的组件知识，以及限制设计师修改范围的强制边界。

**需要：** 准备好的仓库与设计师指令；可复用组件及本地预览命令；原型分支；获批的示例数据。用 `CLAUDE.md` 保存约定，用 Skill 保存原型流程。Hook 或 Permission rule or mode 必须阻止生产部署，以及修改密钥或受保护的后端区域。

| 步骤 | 搭建方式 |
|---|---|
| 开发者准备仓库 → 功能想法 | 开发者配置 `CLAUDE.md`、Skills、参考资料和编辑边界；设计师提供功能意图。 |
| 设计师在一个分支上提示 → 原型 ⟲ 可行性 | Skill 读取真实组件，修改原型分支，并使用项目的预览及构建命令暴露可行性问题。 |
| 规格涵盖空 / 错误 / 加载状态 → 🛑 review | Skill 写出状态说明，把缺失行为标出来供设计师和开发者审阅。 |
| 🛑 handoff | Skill 整理分支、预览说明和未决问题；开发者接手实施。 |

**检查点：** `review`：交接前，设计师和开发者检查交互及状态覆盖。`handoff`：开发者收到分支与规格；智能体没有生产合并或部署凭据。Hooks 保护设计师环境不得修改的仓库区域。

**与来源相比：** 来源出自 2026-05，已于 2026-11 打开。检索发现 [Nate Parrott 的 2026-07 实践](https://claude.com/resources/articles/how-the-product-designer-who-built-claude-design-uses-it-to-explore-ideas-before-building-them)，已于 2026-11 打开，介绍较新的视觉原型方式及对已有代码背景的利用。这是相邻的选择，不能证明 Knak 基于准备好仓库的交接方式已经过时。通用智能体提供代码编辑与 Skills；仓库准备、组件知识，以及由开发者负责上线实现，仍不可少。来源报道的是智能体辅助设计师的工作流，并非自主交付功能。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 一次性准备：一个由开发者组成的突击小组花六周时间，把生产仓库改造成设计师可以安全、高效做原型的地方。准备工作是一份设计师配置和三个 Claude Code 技能文件 [[1]](#sources)。
2. 每个功能，设计师直接在生产代码库的一个 git 分支上做原型，使用真实的设计系统组件。这取代了单独的 Figma 样稿和 Lovable 交互原型 [[1]](#sources)。
3. 设计师把范围限制在代码中已有的内容内。可行性问题在设计师做原型时就会暴露，而不是等到开发后期 [[1]](#sources)。
4. 设计师在规格中补上空状态、错误状态和加载状态。🛑 **审阅**：这些边缘状态在交接前被标出来供审阅 [[1]](#sources)。
5. 🛑 **接手**：开发者基于交接分支构建生产功能，管理层也在同一处查看进展 [[1]](#sources)。

**产出：** 生产仓库 git 分支上的一个原型，加上涵盖边缘状态的规格，开发者以此作为上线功能的起点。
**失败模式 → 防护：** 样稿空想而不可行，缺失的边缘状态由开发者自己补上 → 在代码库约束内用真实组件做原型，并在交接前标出边缘状态供审阅。多个工具之间版本混乱 → 一个分支上只有一份产物。

**与相近工作流的区别：** 最接近的是 AWF-0007 从反馈到原型（Feedback to prototype）：该工作流把反馈聚类成 PRD，做出多个原型变体，并用 5 次用户测试验证。本工作流的交付物是交给工程团队的单个仓库内分支，关卡是边缘状态审阅和开发交接，没有用户测试环节。它也不同于新的“设计师提交的 UI PR”（Designer-authored UI PR）：那里设计师自己的 PR 经工程审阅后合入生产环境，而这里是开发者基于原型分支编写上线代码。
