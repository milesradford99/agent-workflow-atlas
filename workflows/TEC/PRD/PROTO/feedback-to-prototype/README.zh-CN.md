# 从用户反馈到原型

## 背景

产品团队收集客户的抱怨与建议，但这些消息本身并不能说明哪个问题值得解决。原型把一种可能的方案变成可操作的东西，让人们在团队决定正式开发前先试用。本工作流让智能体归纳反馈、起草需求，并实现不同的交互方案。产品经理选择问题，设计师在用户测试前审阅原型。方案是否满足需求，仍需要真实用户提供证据。

**术语：**
- **PRD / PM**：产品需求文档，以及决定优先级的产品经理。
- **NPS 原话**：净推荐值调查中一并收集的书面评论。
- **主题聚类 / 带来源的引述**：归到一起的相关反馈，以及可追溯到原始记录的原话。
- **红队质疑**：主动寻找提案的薄弱环节。
- **设计令牌 / 原型**：可复用的视觉设置，以及可用于测试的交互模型。

## 用智能体搭建

**形态：** `skill`。一位产品负责人在对话中推动一次探索循环；Skill 可保存流程，并调用内置的并行检查。

**需要：** 经批准的反馈与转写，带原始记录标识；产品约束、设计参考和保存原型文件的沙盒。模型访问前移除无关客户标识。原型使用合成数据；智能体不能调用客户消息、招募或生产发布工具。

| 步骤 | 搭建方式 |
|---|---|
| 反馈 → 主题聚类 + 引述 → 🛑 plan | Skill 整理反馈、链接引述，并展示不同的问题表述；由产品经理选择重点。 |
| PRD → 红队质疑 | Skill 起草需求；只读 Subagent 对照所给证据检查假设和遗漏。 |
| 每个方案：做原型 → 迭代 → 🛑 review | Skill 使用获批组件或编码环境写入独立原型文件；由人比较交互并提出修改。 |
| 5 次用户测试 → 回到反馈 | 人组织测试并提供转写；Skill 将观察结果补充到证据集合中。 |

**检查点：** `plan`：Skill 交出主题、证据和不确定性后停下，等待选题才起草方案。`review`：交出原型及方案差异供设计审阅。智能体不能招募或联系客户、发布原型或修改生产系统；测试和发布由人控制。

**与来源相比：** 公开记录出自 2025-08，已于 2026-11 打开。它采访了使用 AI 原型工具的团队，并非由智能体运行完整序列，也不能证明普遍需要 5 次测试。检索发现 [Nate Parrott 的第一手原型实践](https://claude.com/resources/articles/how-the-product-designer-who-built-claude-design-uses-it-to-explore-ideas-before-building-them)，出自 2026-07，已于 2026-11 打开，介绍了结合代码背景反复探索视觉方案。通用编码 Skill 现在可以直接制作原型文件；搭建不要求使用历史步骤中列出的特定生成工具。用户反馈与是否投入开发的决定仍不属于自动生成。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 智能体把工单、通话记录和 NPS 原话聚类成主题，每个主题附计数和带来源链接的引述。
2. 🛑 **计划**：产品经理选定要解决的问题。
3. 智能体起草 PRD：问题、用户、非目标、指标、用户故事、边界情况。由一个评审者做红队质疑（“工程团队会反对什么？”）。
4. 智能体根据 PRD 和设计令牌做 2–3 个原型方案（v0、Lovable、Bolt、Figma Make、Claude artifacts）。
5. 产品团队与智能体一起迭代。
6. 🛑 **审阅**：设计师审阅原型。
7. 产品团队进行 5 次用户测试，并把转写内容回流到第 1 步。

**产出：** PRD 和原型成为 AWF-0001 或 AWF-0008 的输入。
