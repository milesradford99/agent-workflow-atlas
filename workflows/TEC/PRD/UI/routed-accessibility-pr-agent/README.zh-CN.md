# 分流式无障碍 PR 助手

**工具变体：** `github-copilot-cli` · `axe-core` · `accessflow-code-agent`

## 背景

无障碍专家帮助团队让不同视觉、听觉、行动和交互方式的人都能使用界面。代码可以暴露部分障碍，但通过自动检查的组件在真实使用中仍可能失败。本工作流让智能体审查提议的前端变更，提出范围受限的修复，并把困难模式转给专家。工程师决定是否接受每项修复，无障碍团队则抽查智能体输出。人工角色不可省去，因为许多无障碍判断依赖具体场景与交互。

**术语：**
- **WCAG / A 和 AA**：Web 内容无障碍指南，以及对成功准则分组的符合级别。
- **PR / CLI**：提议的仓库变更，以及按需发起请求的命令行界面。
- **审查者 / 实现者 / schema**：分开的检查与编辑角色，以及报告的固定格式。
- **Toast / 树形视图 / 数据表格**：短暂的状态消息、分层列表，以及可交互的表格。
- **重新审计**：修改之后，再检查所提的修复。

## 用智能体搭建

**形态：** `service`。前端 PR 事件自动启动运行，专家定期审计；人收到修复建议、升级案件和抽检样本。

**需要：** PR 事件与限定范围的仓库访问；机构内部已审计的示例；当前无障碍参考资料、复杂度脚本和风险模式规则；隔离预览及测试脚本；持久的审阅与审计队列。使用合成或获批测试数据。使用 Permission rule or mode 禁止 commit、合并与生产部署。

| 步骤 | 搭建方式 |
|---|---|
| PR 或提问 → 复杂度评分 → 🛑 handoff | 无界面 Skill 调用复杂度脚本；阈值或已知高风险模式要求仅提供指导时，由 Hook 阻止编辑。 |
| 审查者调研 → 审计 → 结构化发现 | 只读 Subagent 使用固定审查 schema，返回准则引用、代码位置及升级触发条件。 |
| 主智能体过滤 → 指导或实现者 → 验证 → 重新审计 | Skill 仅对获准情况把过滤后的发现交给独立的编辑 Subagent，再运行测试及新一轮检查；worker 不直接互通。 |
| 🛑 review · 定期 🛑 sample | 服务把建议 diff 和指导写入 PR 审阅队列，按规则保留样本供无障碍团队检查。 |

**检查点：** `handoff`：复杂或高风险情况交付证据及供无障碍团队处理的问题，不生成补丁。`review`：工程师看到建议 diff、准则引用与验证局限，只提交接受的修复。`sample`：无障碍团队定期审计保存的输出和反馈。权限规则及阻止编辑的 Hook 强制执行仅给指导的限制；服务不能合并。

**与来源相比：** 来源出自 2026-05，已于 2026-11 打开。检索发现 [accessFlow 的 Code Agent 公告](https://support.accessibe.com/hc/en-us/articles/39152427368466-2026-09-17-accessFlow-Code-Agent-brings-AI-powered-accessibility-checks-to-GitHub)，出自 2026-09，已于 2026-11 打开，介绍了 PR 检查与改进建议。这是仍在提供的产品选择，不能证明专家分流或人工检查已经过时。通用无界面智能体可以用 Skills、Subagents 和 Hooks 完成分流，已有检查器仍作为外部工具。保留来源中固定顺序、分开的审查者和实现者；工具通过或另一个模型批准，都不能证明完整的无障碍符合性。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 代码托管平台在修改前端代码的 PR 上自动触发智能体；开发者也可从 CLI 或编辑器按需调用 [[1]](#sources)。
2. 由 shell 脚本给代码的复杂度打分。超过阈值时，智能体不做任何代码改动。🛑 **接手**：它提示用户去咨询无障碍团队 [[1]](#sources)。
3. 只读的审查子智能体调研 WCAG 准则、审计代码、标记升级触发条件（例如多个高严重度失败），并按模板格式返回发现 [[1]](#sources)。
4. 主智能体验证并过滤这些发现。对于高风险模式（拖放、toast 提示、富文本编辑器、树形视图、数据表格），它把实现者切换为仅给指导。否则由实现者提出并验证代码改动，主智能体运行重新审计的循环 [[1]](#sources)。
5. 🛑 **审阅**：由人决定是否提交每项建议的修复。🛑 **抽检**：无障碍团队定期检查智能体输出的准确性，并跟踪 PR 审阅人的反馈情绪 [[1]](#sources)。

**产出：** 前端 PR 上的 WCAG 发现和建议修复；对复杂模式则是一份指导文档加转交。
**失败模式 → 防护：** 约 36% 的 A 级和 AA 级准则无法被自动发现 → 智能体升级并给出指导，而不是声称已全面覆盖。对难处理的控件给出自信的修复 → 高风险模式的拒绝清单加复杂度阈值。经验较少的用户不加质疑地接受输出 → 由无障碍团队定期审计 [[1]](#sources)。

**与相近工作流的区别：** 最接近的是 AWF-0062（受规格约束的界面方案），那是由设计师把关、生成新界面的流程。本工作流在每个 PR 上审计并修复已有的前端代码。它按复杂度和风险分流，决定是修复、给指导还是转交，并增加专家抽检审计。
