# 依据规格的界面方案

**工具变体：** `figma-api` · `figma-mcp` · `claude-code`

## 背景

产品设计师把需求变成符合产品共同视觉语言的界面。工单、对话和现有代码可能互相矛盾，精致的界面也可能意外加入无人要求的行为。本工作流让智能体收集资料、指出冲突，先提出几个克制的布局方案，再完成被选中的设计。设计师选择方向并检查最终界面。人工判断仍然必要，因为结构检查不能证明界面是否表达清楚，或是否实现了真实需求。

**术语：**
- **灰度线框 / hi-fi**：尚未完成视觉样式的布局，以及细节完整的高保真界面。
- **组件库 / 已发布实例**：共享的组件定义，以及放在界面上并与其关联的副本。
- **语义令牌 / 基础值（primitive）**：表达用途的命名样式，以及其底层数值。
- **规格 / 记忆 / QA**：有版本的设计规则、记录的修正，以及质量检查。
- **API / MCP**：程序接口，以及把其工具连接到智能体的协议。

## 用智能体搭建

**形态：** `project`。持久的设计规则与修正记录，加上只能使用组件库的写入边界，必须适用于每个任务。

**需要：** 工单及关联资料；组件库和工作文件；`DESIGN.md` 与已审阅的修正记录；获批且具备所需读写权限的 Figma MCP server (connector) 工具。Skill 在开始时加载规则，`CLAUDE.md` 说明资料优先级。保护客户材料与生产数据；只在获批设计文件中工作，并标记示例内容。

| 步骤 | 搭建方式 |
|---|---|
| 工单 + 资料 → 列出冲突 → 🛑 plan | Skill 读取资料与设计规则，列出矛盾及未决问题，不修改产品负责人的工单。 |
| 2-3 个灰度方案 → 🛑 review | Skill 通过 MCP server (connector) 工具用组件库实例生成方案；设计师选定或组合，并记录原因。 |
| 工作文件中做 hi-fi；新组件先入库 | Hook 在写入前检查目标文件和组件来源。新增库组件等待人工发布，之后才用于工作文件。 |
| 视觉 QA → 🛑 review → 修正写回规格与记忆 | Skill 导出截图，把受影响实例与源组件比较；获批修正以有版本的规则及记录修改提案保存。 |

**检查点：** `plan`：Skill 绘制之前先交出来源冲突与问题并停下。`review`：设计师选择方案，QA 之后再检查详细界面。MCP 权限不允许智能体发布组件库或上线；Hook 阻止在工作文件中创建未经批准的本地组件。设计规则与修正记录的修改由人审阅。

**与来源相比：** 来源出自 2026-10，已于 2026-11 打开。检索发现 [Figma 当前工具文档](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/)，已于 2026-11 打开，记载了原生读写工具。因此设计文件访问可以通过 MCP server (connector) 提供，不必假设需要定制 API 包装器，但仍取决于账号可用的工具和额度。来源中的先入库、来源冲突审阅和人工视觉检查仍然适用。修正记录与 `CLAUDE.md` 本身都不是强制约束；写入限制需要连接器权限或 Hooks。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 设计师维护两个 Figma 文件（一个组件库，一个只用已发布实例搭建的工作文件）、一份带版本的 DESIGN.md 规格，以及一份记录过往修正的智能体记忆。智能体在执行任何任务前都先加载这些内容 [[1]](#sources)。
2. 智能体读取 Jira 工单及其关联的用户故事、Confluence 页面、代码规格和通话转录。它只设计这些资料所描述的内容 [[1]](#sources)。
3. 🛑 **计划**：动手画之前，智能体先列出用户故事、看板和代码之间有哪些不一致，以及以哪个来源为准。未决问题退回给产品负责人 [[1]](#sources)。
4. 智能体用组件库实例搭出 2-3 个灰度线框方案，并排放在评审画板上 [[1]](#sources)。
5. 🛑 **审阅**：设计师选定或组合方案，并说明理由 [[1]](#sources)。
6. 智能体用真实内容把选定方案做成高保真。任何新组件都要先入库并发布，界面才能使用它 [[1]](#sources)。
7. 批量修改之后由智能体做视觉 QA：把每个实例与其主组件比对，截取修改前后的截图，检查裁切和重叠，并逐项过一遍检查清单 [[1]](#sources)。
8. 🛑 **审阅**：设计师检查界面。每处修正都写进规格和记忆，避免再次出现 [[1]](#sources)。

**产出：** 基于已发布设计系统构建的、经过审阅的高保真 Figma 界面，加上更新后的规格和记忆。随后进入开发交接。
**失败模式 → 防护：** 智能体凭空造出产品里并不存在的组件 → “只能用组件库实例”的规则加规格约束。同样的错误每周重犯 → 把修正持久化到记忆（约 70 条），并以规格为准。结构有效但视觉有误的界面 → 即使 QA 脚本报告零错误，设计师仍要亲自查看 [[1]](#sources)。

**与相近工作流的区别：** AWF-0008 设计到代码是把已批准的设计转成代码。AWF-0007 反馈到原型是根据反馈构建原型。本工作流则从工单出发，产出经过审阅的设计工具界面，并设有选定方案的关卡。
