# 依据规格的界面方案

**与相近工作流的区别：** AWF-0008 设计到代码是把已批准的设计转成代码。AWF-0007 反馈到原型是根据反馈构建原型。本工作流则从工单出发，产出经过审阅的设计工具界面，并设有选定方案的关卡。
**工具变体：** `figma-api` · `figma-mcp` · `claude-code`

## 步骤

1. 维护两个 Figma 文件（一个组件库，一个只用已发布实例搭建的工作文件）、一份带版本的 DESIGN.md 规格，以及一份记录过往修正的智能体记忆。智能体在执行任何任务前都先加载这些内容 [[1]](#sources)。
2. 智能体读取 Jira 工单及其关联的用户故事、Confluence 页面、代码规格和通话转录。它只设计这些资料所描述的内容 [[1]](#sources)。
3. 🛑 **计划**：动手画之前，智能体先列出用户故事、看板和代码之间有哪些不一致，以及以哪个来源为准。未决问题退回给产品负责人 [[1]](#sources)。
4. 用组件库实例搭出 2-3 个灰度线框方案，并排放在评审画板上 [[1]](#sources)。
5. 🛑 **审阅**：设计师选定或组合方案，并说明理由 [[1]](#sources)。
6. 用真实内容把选定方案做成高保真。任何新组件都要先入库并发布，界面才能使用它 [[1]](#sources)。
7. 批量修改之后由智能体做视觉 QA：把每个实例与其主组件比对，截取修改前后的截图，检查裁切和重叠，并逐项过一遍检查清单 [[1]](#sources)。
8. 🛑 **审阅**：设计师检查界面。每处修正都写进规格和记忆，避免再次出现 [[1]](#sources)。

**产出：** 基于已发布设计系统构建的、经过审阅的高保真 Figma 界面，加上更新后的规格和记忆。随后进入开发交接。
**失败模式 → 防护：** 智能体凭空造出产品里并不存在的组件 → “只能用组件库实例”的规则加规格约束。同样的错误每周重犯 → 把修正持久化到记忆（约 70 条），并以规格为准。结构有效但视觉有误的界面 → 即使 QA 脚本报告零错误，设计师仍要亲自查看 [[1]](#sources)。
