# 设计师提交的 UI PR

**工具变体：** `cursor` · `claude-code`

## 背景

产品设计师通常先描述界面，再交给工程师转成应用代码。小交互在交接中可能丢失细节，大改动则可能受到样稿里看不到的技术约束。本工作流让设计师直接在产品仓库中使用智能体，一边修改一边预览。工程团队仍审阅每项提议的变更，因为外观不能证明可维护性、性能或无障碍质量。有些实验本就应该被舍弃，而不是上线。

**术语：**
- **UI / 前端 / 后端**：用户界面、在用户应用中运行的部分，以及提供支持的服务端行为。
- **PR / 分支 / CI**：pull request、一条隔离的修改线，以及对提议变更运行的自动检查。
- **Linter / 预览应用**：检查代码规则的工具，以及供发布前查看的运行构建。
- **状态 / 跨领域架构**：应用在交互之间保存的信息，以及影响多个系统部分的结构。

## 用智能体搭建

**形态：** `project`。设计师的 Skill 之外，还需要事先准备的仓库约定、受保护的编辑边界和必需的工程审阅。

**需要：** 仓库、获批界面组件和预览及构建命令；`CLAUDE.md` 中的设计师指令；实现和检查用的 Skill。使用专用分支与示例数据。用 Hook 或 Permission rule or mode 限制后端和密钥文件编辑；不提供合并及生产部署工具。

| 步骤 | 搭建方式 |
|---|---|
| 想法或草图 → 设计师提示智能体 → 调整 ⟲ 预览 | Skill 读取组件约定并提出范围计划，开发者先批准再编码。随后 Skill 起草修改，并调用项目脚本运行预览。设计师推动迭代。 |
| 开 PR，附背景与文档 → linter、CI、测试、预览 | Skill 准备 diff 和说明；Hook 运行必需的本地检查，代码托管平台运行常规 CI。 |
| 🛑 review → 合并或关闭 | 智能体交出可审阅 PR 后结束；工程团队决定合并、要求修改，或关闭并记录下一次尝试的经验。 |

**检查点：** `review`：开发者先批准范围计划，之后工程师对照产品请求检查运行预览、diff、测试结果及范围。仓库权限阻止智能体合并或部署；受保护分支要求工程审阅。超出约定前端范围的修改，应先交还工程师再继续实施。

**与来源相比：** 来源出自 2025-08，已于 2026-11 打开。检索发现 [Plotly 的工程团队后续记录](https://plotly.com/blog/what-i-learned-integrating-designers-wielding-llms-into-our-codebase/)，出自 2025-10，已于 2026-11 打开。它把适用情况收窄到受限的变更，并说明编码前要先由开发者批准计划，之后仍有 PR 审阅。本设计保留仓库和审阅边界，不把编码加快解释为自主交付；编码前先由开发者批准计划，沿用的正是后续记录。来源中的百分比仍是历史结果，不是对本搭建的预期。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 产品设计师从 Figma 中的想法或勾勒的交互模式出发。他们不写规格说明，而是打开带仓库集成助手（Cursor 或 Claude Code）的代码编辑器，用提示词让它在真实的产品代码库里构建这个体验 [[1]](#sources)。
2. 设计师在代码库内调整样式、修改行为、尝试布局，并在运行中的应用里预览每处改动。工作在带预览环境的专用功能分支上进行 [[1]](#sources)。
3. 对于前瞻性工作或大型交互探索，设计师会有意先在仓库之外做一个一次性原型，比较方案，判断这个想法是否值得完整实现 [[1]](#sources)。
4. 满意后，设计师提交一个带背景说明和文档的 pull request。防护措施（linter、CI、预览应用、自动化测试、必需的审阅）随之运行 [[1]](#sources)。
5. 🛑 **审阅**：工程团队按与其他代码相同的评审流程，审阅每一份设计师的贡献，看质量和一致性。常见的驳回原因有偏离设计系统、性能或无障碍缺口、可维护性问题 [[1]](#sources)。
6. 交付系统将合并的 PR 上线。关闭的 PR 把经验带入下一轮。只改前端的变更最容易落地，复杂功能则与工程师结对完成 [[1]](#sources)。

**产出：** 一个由设计师编写、合入生产代码的前端 pull request，无需 Figma 到工程的交接。
**失败模式 → 防护：** PR 偏离设计系统、留下性能或无障碍缺口，或触及跨领域架构和临时状态 → 必需的工程审阅，加上 linter、CI、预览应用和测试。约 30% 的 PR 未合并即被关闭。涉及后端的改动落地效果差 → 设计师的 PR 只限前端，复杂功能与工程师结对。

**与相近工作流的区别：** 最接近的是 AWF-0062 依规格出界面方案（Spec-bound screen options）：那里的交付物是 Figma 工作文件中的高保真设计，由设计师审阅。本工作流的交付物是上线的代码，关卡是工程团队的 PR 审阅。AWF-0121 是针对工程师 PR 的无障碍审阅与修复智能体：交付物不同，并且转给无障碍团队处理。
