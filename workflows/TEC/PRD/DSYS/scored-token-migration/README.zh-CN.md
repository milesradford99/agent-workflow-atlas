# 打分式设计令牌迁移

**工具变体：** `claude-code` · `regex-codemod` · `ambrook-agent-graph-migration` · `figma-mcp`

## 背景

设计令牌给界面的颜色和样式命名，用名称表达用途。把已有应用迁移到新令牌系统时，不能只匹配色值：同一种灰色可能用于背景、禁用文字或边框，在另一种主题里这些角色又可能分开。本工作流先从小范围的已审阅示例中整理映射规则，再区分机械替换与含糊选择。智能体可以提出依赖上下文的映射。设计师和工程师仍需检查结果，因为代码检查无法确定全部视觉意图。

**术语：**
- **工具类 / 语义 / 主题令牌**：按原始值、用途或视觉主题中的角色命名的样式。
- **UX / 十六进制色值（hex value）**：用户体验，以及用数字表示的颜色。
- **Codemod / regex**：自动修改源代码的程序，以及机械替换使用的文本模式匹配。
- **打分矩阵 / lint 关卡**：排列候选映射的标准，以及拒绝不合规代码的自动规则。
- **快照 / 浅色和深色主题**：保存下来用于比较的渲染结果，以及同一界面的不同视觉配色。

## 用智能体搭建

**形态：** `project`。需要跨多个切片与审阅保持共用的评分规则、受保护的迁移说明和 lint 关卡。

**需要：** 令牌词汇表与映射表；切成可审阅小块的代码库；有版本的 Skill 与 `CLAUDE.md`；codemod 和 lint 脚本；覆盖两种主题的预览构建。给智能体迁移分支，不提供生产合并或发布工具。

| 步骤 | 搭建方式 |
|---|---|
| 共用词汇表 → 切分代码库 → 试点迁移 | Skill 加载双方同意的令牌并修改试点切片；脚本枚举全部切片，防止文件悄悄从任务清单中消失。 |
| 🛑 review → 解释遗漏 → 更新 skill ⟲ 重复 | 研发与 UX 审阅 diff 和渲染；Skill 把获批规则修改及原因记入有版本的文件。 |
| 锁定 3 维矩阵 → codemod 或 AI 映射 | Skill 用固定规则处理含糊情况；脚本处理精确映射。Hook 在正式迁移期间阻止修改获批评分规则。 |
| 先迁移浅色主题 → lint 关卡 → 🛑 review → 人工修复 | Hook 运行迁移 lint 检查；Skill 提供覆盖两种主题的界面及状态清单，供人工审阅并记录修正。 |

**检查点：** `review`：大范围迁移前，试点审阅人批准规则；最后的审阅人查看两种主题中的所有相关界面与状态。智能体没有发布工具。Lint 发现不允许的令牌族，语义含义是否选对则由人判断。

**与来源相比：** 条目引用日期为 2026-10；2026-11 打开的原页面显示 2026-07，这一日期差异需要证据复核。检索发现 [Ambrook 的设计系统迁移记录](https://ambrook.com/engineering/ai/migrating-fast-with-agent-graphs-design-system-material-ui-base-ui)，出自 2026-08，已于 2026-11 打开，结合了智能体编写的小 PR、测试、codemod 和人工审阅。这是相邻的组件迁移，不会取代本条目的打分规则。搭建保留用确定性 codemod 处理精确映射，用已审阅 Skill 处理含糊映射的分工。当前智能体的上下文容量不能成为取消切片跟踪或人工主题检查的理由。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 研发与 UX 就共用的令牌词汇表达成一致。团队把代码库切分成小的组件切片 [[1]](#sources)。
2. 试点循环：AI 迁移一个切片。🛑 **审阅**：研发和 UX 一起审计结果。每遇到一处错误替换，就让 AI 解释其理由，然后把这一缺口补进集中的规则与 skill 文件。重复直到规则稳定 [[1]](#sources)。
3. 团队锁定打分矩阵。每个候选令牌按十六进制色值匹配、上下文契合度和主题一致性三项各打 0–3 分 [[1]](#sources)。
4. 正式运行：正则 codemod 处理简单的一对一映射。含糊或多重意图的令牌走 AI 打分矩阵。先迁移浅色主题，这样即使选错，线上渲染的颜色也不变 [[1]](#sources)。
5. 团队加上 lint 关卡，让迁移成果保持下去。🛑 **审阅**：人工点遍每个界面和每种状态，两种主题都要看（没有快照工具）。人工修复剩余的错误选择 [[1]](#sources)。

**产出：** 一个从工具类令牌迁移到语义化、支持主题的令牌的代码库，可以直接上深色模式。
**失败模式 → 防护：** 对整个代码库下提示词会漏文件，并把不同文件的逻辑混在一起 → 分块，并把简单映射分流给 codemod。意图含糊 → 用经审计的试点结果构建打分矩阵。隐蔽的错误选择 → 先迁移浅色主题，再人工检查两种主题 [[1]](#sources)。

**与相近工作流的区别：** 最接近的是 AWF-0008（设计稿到代码），它借助截图 diff 从 Figma 画框构建新界面。本工作流改写整个代码库中成千上万处已有的令牌用法。它增加了用于建立规则的试点与审计阶段、codemod 与 AI 之间的分流，以及发布前的全面人工检查。
