# 代理评测驱动的设计系统文档

**工具变体：** `sanity-design-system-eval-tool` · `sanity-ailf` · `mcp-server`

## 背景

设计系统维护者提供组件和使用说明，让产品界面保持一致。编码智能体仍可能误解这些说明，编造组件属性，或者做出能构建却不好用的界面。本工作流把智能体当作文档的测试用户：给它们同样的任务，测量构建结果，再比较版本。维护者根据失败决定哪些说明需要修正。人工解释仍然必需，因为智能体可以描述症状，却未必找对原因。

**术语：**
- **设计系统 / UI**：共享的界面规则与组件，以及它们组成的用户界面。
- **评测 / 测试框架（eval / harness）**：可重复的测试，以及执行测试并收集结果的软件。
- **API / MCP**：组件可调用的接口，以及向智能体提供外部工具和文档的协议。
- **视觉差异 / token 消耗**：渲染图像的比较，以及模型输入和输出的用量。
- **JSON schema / AILF**：结构化文档格式，以及 Sanity 内部的 AI Literacy Report 评测套件。

## 用智能体搭建

**形态：** `skill`。一位维护者在对话中运行一次文档实验；已有评测框架可以由 Skill 旁的脚本调用。

**需要：** 组件库及有版本的文档；固定任务提示词和模型设置；评测框架、隔离构建目录、无障碍检查及截图脚本；运行预算与基线结果。使用合成数据，不给评测 worker 生产发布凭据。

| 步骤 | 搭建方式 |
|---|---|
| 设计系统变更 → n 个智能体用同一提示词构建 | Skill 固定任务、模型设置和文档版本。旁边的脚本调用已有测试框架，每次试验使用独立工作区。 |
| 汇报构建、无障碍、视觉和用量结果 | Skill 汇总实测结果及智能体反馈，报告中保留失败运行与测试条件。 |
| 🛑 review → 编辑文档 ⟲ 重跑并对比 | 维护者选定一项文档修改。Skill 使用同一任务和设置重跑，并比较保存的两组结果。 |
| 发布变更 | Skill 准备文档 diff 和报告；维护者按常规仓库流程发布。 |

**检查点：** `review`：Skill 交出失败记录、截图、智能体反馈及评测条件后停下。维护者判断原因并选择修改。评测智能体不能修改或发布源文档；协调智能体没有合并或发布工具。

**与来源相比：** 来源出自 2026-08，已于 2026-11 打开。针对更新实例及所列工具的检索，截至 2026-11 未找到更新实例。已有评测框架仍然有用；通用智能体的 Skills 只协调运行并解释输出。来源提醒，可复用代码块与 lint 辅助可能掩盖文档缺陷，因此只比较文档时必须关闭这些辅助，另外测试辅助本身的影响。构建成功或智能体自述不能证明文档变好；保留下来的前后实测结果才是证据。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 维护者定义一项评测：哪个设计系统、安装说明、训练材料（markdown 或 MCP 服务器）、模型，以及自定义或由智能体生成的提示词 [[1]](#sources)。
2. 测试框架用同一个提示词启动 n 个智能体；每个都构建界面。测试框架衡量到成功构建所需的尝试次数、无障碍问题、代码行数、性能、每次迭代的视觉差异和 token 消耗；汇总智能体对哪里让它们困惑的反馈 [[1]](#sources)。
3. 维护者在每次发布组件、API 变化或文档更新时运行；3–5 次迭代通常就能给出信号，10 次可得到更确切的结果 [[1]](#sources)。
4. 🛑 **审阅**：维护者阅读报告；智能体的反馈 "more like a smoke detector than a dentist"（只有症状，没有原因），所以由人把它转化为具体的文档修改 [[1]](#sources)。
5. 维护者修复文档（Sanity 从 markdown 换成了 JSON 文档 schema），重跑，并衡量前后变化 [[1]](#sources)。
6. 团队用第二套测试框架交叉验证：Sanity 内部的 AILF 套件分别测试没有文档、提供文档、以及自己查找文档这三种情况下的智能体 [[1]](#sources)。

**产出：** 设计系统文档（以及组件/API），附每个模型实测的智能体成功率，外加每次变更的前后对比报告。
**失败模式 → 防护：** 让智能体根据自己的反馈持续改写文档会失控（作者试过）→ 保留由人来转化反馈 [1]。在大规模运行上烧钱 → 少量迭代，跟踪 token/成本 [1]。

**与相近工作流的区别：** AWF-0008 设计转代码（Design to code）和 AWF-0122 带评分的 token 迁移（Scored token migration）交付的是产品代码。这里智能体是一群被测试对象，产出是经反复的智能体构建来衡量的、改进后的设计系统文档，人工检查点是把评测反馈转化为文档修复。
