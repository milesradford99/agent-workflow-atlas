# 基于性能剖析的优化

**工具变体：** `uber-perfinsights` · `optix`

## 背景

软件运行的成本与它消耗的计算量成正比，所以工程师会定期寻找浪费计算的代码。他们用剖析器（profiler）对运行中的系统采样，记录处理器时间和内存都花在了哪里，找出用得最多的那几个函数（热点函数），再改写其中浪费的部分。在几百个服务上手工做这件事既慢，又需要专家。这里由智能体从实测的热点函数出发，把每个函数对照一份已知的浪费写法清单，起草一个带置信度评分的修复。每个 diff 仍由开发者审阅，因为只有代码的负责人才能判断更快的版本是否保留了服务所依赖的行为，而且模型可能报告一个并不存在的问题。

**术语：**
- **剖析（profile）**：对运行中服务的采样，显示处理器时间和内存花在哪些函数里。
- **flat CPU**：函数自身花费的处理器时间，不含它所调用函数的时间。
- **热点函数**：占用处理器时间最多的那些函数。
- **反模式（antipattern）**：一种已知的、浪费资源的写法，在目录中与更好的替代写法一起记录。
- **monorepo**：一个存放许多服务代码的仓库。
- **runtime.mallocgc**：Go 运行时的内存分配器；CPU 中有很大比例花在这里，说明代码很耗内存。
- **少样本示例**：放进提示词里的示范，向模型展示想要什么。
- **LLM 陪审团**：几个独立的模型检查，必须一致同意才保留某个发现。
- **误报**：报告了一个并不存在的问题。
- **LLMCheck、Optix**：Uber 对模型发现做基于规则校验的工具，以及它的持续代码优化工具。

## 用智能体搭建

**形态：** `service`。由每日的定时计划启动，键盘前没有人，开发者只看到带评分的建议。

**需要：** 通过脚本或 MCP 服务器读取剖析器每日输出的权限；对代码仓库的读取权限；一份带改动前后示例的反模式目录，作为参考文件保存；一份要排除的函数清单（开源库和运行时代码）；用于检测规则的校验脚本；建议的落点，例如草稿拉取请求或工单队列；没有合并权限。

| 步骤 | 搭建方式 |
|---|---|
| 每日全机群 CPU/内存剖析 → 每个服务取前 30 个热点函数 → 静态过滤 | 一个定时脚本拉取剖析数据，每个服务按 flat CPU 保留前 30 个，当 `runtime.mallocgc` 超过 CPU 的 15% 时加入内存剖析，并剔除开源库和运行时函数。 |
| 每个函数：对照目录检测反模式 | skill 把每个函数的完整源码和目录交给一个子智能体，由它指出存在的反模式，并起草带置信度评分的修复。 |
| LLM 陪审团 + 基于规则的校验器 → 置信度评分 + 建议修复 | 各自独立的子智能体分别检查反模式是否存在、修复是否有效；随后由脚本做基于规则的检查并记录结果。 |
| 🛑 review (开发者) | 每个留下来的建议都以草稿 diff 的形式连同评分发给代码负责人。 |
| 合并 diff | 开发者在代码托管平台上合并。 |

**检查点：** `review`：智能体只能读取和提出建议，没有合并工具；建议只以草稿 diff 或队列条目的形式离开这次运行。由开发者逐条决定。被拒绝的建议会被记录下来，便于人去修订目录和检查规则。

**与来源相比：** 唯一的来源和公开实例，即 Uber 的博客文章，出自 2025-07；本条目的来源都早于 2025-11。文章报告的是一条带陪审团和规则校验器的模型调用流水线；搭建方式把它保留为 skill、子智能体和脚本，而不是一个自行决定步骤的智能体。2026-11 的搜索没有找到 Uber 的更新记述，只有对同一篇文章的转述。搜索确实找到了 2026 年关于智能体依据线上剖析工作的会议演讲，例如 Netflix 一场关于 CPU 剖析和共享反模式目录的演讲（[演讲页面](https://www.ai.engineer/talks/CgsWxRUY5Eo-ai-agents-performance-ship-faster-pay-less)；月份未显示）。它只在搜索结果中看到，没有打开阅读。来源页面本身在本次检查中无法打开（会话网络屏蔽了该站点）。搭建方式没有包含每日剖析器和全机群规模，它们取决于各公司自己的工具。

## 步骤

*以下按来源所述。*

1. 从每日运行的全机群剖析器获取 CPU 和内存剖析数据，采样于流量高峰期。[[1]](#sources)
2. 每个服务按 flat CPU 保留前 30 个函数。当 runtime.mallocgc 超过 CPU 的 15% 时，加入内存剖析。用静态过滤剔除开源库和运行时函数。[[1]](#sources)
3. 对每个热点函数，把完整源码和一份精选的反模式清单发给 LLM。提示词采用少样本示例、角色设定，要求修复可运行，并要求给出置信度评分。[[1]](#sources)
4. LLM 陪审团独立检查反模式是否存在、修复是否有效。随后 LLMCheck 基于规则的校验器捕获误报，并记录检测准确率。[[1]](#sources)
5. 🛑 **审阅**：diff 合入 Go monorepo 之前，由开发者审阅带评分的建议。经验证的建议还会输入 Uber 的持续优化工具（Optix）。[[1]](#sources)

**产出：** 合入 monorepo 的优化 diff，以及一份随时间跟踪的热点代码中反模式数量。
**失败模式 → 防护：** LLM 的误报和幻觉损害工程师的信任 → 陪审团校验加 LLMCheck（误报率 'from over 80% to the low teens'）。时间花在冷代码上 → 先用基于剖析的热点路径过滤。
**与相近工作流的区别：** AWF-0002 扇出式代码迁移：AWF-0002 在各处应用同一项事先规划好的重构，并由试点计划把关。本工作流由生产环境的剖析数据决定改什么，每个 diff 是不同的修复，关卡是开发者对照实测热点路径逐个 diff 审阅。

## 公开实例

- [Uber, PerfInsights](https://www.uber.com/us/en/blog/perfinsights/) (2025-07-22)。已在顶级 Go 服务中投入生产；合入了数百个 diff。每个问题 "from 14.5 hours to almost 1 hour of tool runtime"；"93.10% time savings"。*第一手：是；可信度：高。*
