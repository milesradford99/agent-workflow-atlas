# 批量代码迁移

**参考实例：** Airbnb 的 Enzyme → React Testing Library 迁移 [[5]](#sources)。约 3.5k 个测试文件在大约 6 周内迁移完成，而人工估算需要 1.5 年。每个文件一个步骤状态机，带着错误反馈重试。约 75% 的文件在数小时内通过，剩余约 900 个获得更丰富的上下文和更多次重试。不到 100 个由人工收尾。

## 背景

大型代码库经常需要在成百上千个文件里做同一种改动：把测试迁到新的测试库、把某个数字类型放宽、替换一个已弃用的调用。工程师把这叫作迁移，把执行迁移的脚本叫作 codemod。手工做要花上几个月重复劳动；普通脚本能处理简单的情况，碰到少见的写法就失灵。在这里，智能体对每个文件单独、并行地做迁移，每个文件都必须通过项目的自动检查才算完成；没通过的文件补充更多上下文后再试一次。人在几个文件上试跑之后定下规则，随机抽查一部分，找出测试发现不了的语义变化，最后由代码负责人评审结果。测试通过并不能证明一个文件仍然在测原来要测的东西，而各部分代码由各自的负责人负责。

**术语：**
- **迁移**：在大量文件中，把代码库从一种库、语言特性或写法换成另一种。
- **codemod**：自动改写代码的程序；AST codemod 作用于代码解析后的结构，而不是文本。
- **Enzyme → React Testing Library（RTL）**：两个用于测试网页界面组件的库；参考实例是把测试从前者迁到后者。
- **试点**：在一小批有代表性的文件上试跑，在全面运行之前调好指令。
- **提示词包（规则手册）**：每个 worker 都使用的、已冻结的指令、改动前后示例和成功标准。
- **少样本示例**：放进提示词里的示范，向模型展示预期的改动。
- **lint、类型检查、测试**：按顺序进行的自动检查：代码风格和简单错误、类型错误，然后是行为。
- **状态机**：每个文件一份记录，标明已通过哪一步，这样失败的步骤可以单独重跑。
- **重试预算**：每一步或每个文件最多可以尝试的次数。
- **长尾**：前几轮都没通过、需要更多上下文或人工处理的少数文件。
- **语义保真**：迁移后的文件是否仍然检查与原文件相同的行为。
- **代码负责人**：登记为负责某部分代码的人或团队（`CODEOWNERS`）。
- **无头 worker**：由脚本启动、对话中没有人的智能体运行。

## 用智能体搭建

**形态：** `project`。扇出需要自定义的并行工作者，而且有两条规则对每个工作者都必须成立（只改分配给它的文件；绝不编辑已冻结的提示词包），这要靠钩子。[套件](variants/claude-code.md)把这套搭建方式写成了文件，其中用一个启动无头 worker 的 shell 脚本代替了动态工作流。

**需要：** 一个迁移分支；可以并行运行、或在各自 worktree 中运行的 lint、类型检查和单文件测试命令；一份写明这些命令和禁改路径的 `CLAUDE.md`；一个存放规则手册、示例和成功标准的 `migration/` 文件夹；一个 `CODEOWNERS` 文件；`gh` 命令行工具。

| 步骤 | 搭建方式 |
|---|---|
| 在 10–20 个文件上试点 → 🛑 plan | 一个编排 skill 在主对话中对试点文件逐个运行单文件 skill，写出规则手册、示例和成功标准，然后停下等待批准。 |
| 每个文件：(重构 ⟲ lint → 类型 → 测试) | 一个动态工作流，把每个文件交给各自的子智能体运行单文件 skill：先重构，再依次过 lint、类型和测试，每一步根据校验器的输出修复，不超出重试预算。用 `PreToolUse` 钩子拦住对所分配文件之外任何文件以及对 `migration/` 的修改。 |
| 为失败项补充上下文 → 每个失败项：(重试 ⟲ 检查) | skill 根据工作流的结果对失败项聚类，并提出对规则手册的修补；经人同意后，第二个动态工作流带上同级文件、被测代码和更多示例，重跑失败的文件。 |
| 🛑 sample | skill 从已通过的文件中随机抽取一部分，逐个展示改动前后的 diff。见“检查点”。 |
| 分批提 PR → 🛑 review | skill 按 `CODEOWNERS` 把已通过的文件按负责人分组，每组准备一个拉取请求。`git push` 和 `gh pr create` 之前由权限规则询问；代码负责人在代码托管平台上评审。 |

**检查点：** `plan`：试点结束后 skill 停下，在人批准提示词包之前不会开始扇出；之后由钩子保持提示词包冻结。`sample`：动态工作流在运行中途不能接收输入，所以抽检放在它之后：skill 展示随机抽取的一部分迁移文件及其 diff，等待人对保真度的判断；如果人发现语义变化，就修补规则手册并重跑受影响的文件。`review`：每个负责人分组一个拉取请求，只有经询问规则确认后才创建，智能体没有合并权限。

**与来源相比：** 来源 5 出自 2025-03；公开实例出自 2024-05 到 2026-07。来源 5 报告的是一条由逐文件状态机驱动的模型调用流水线，而不是一个自行决定步骤的智能体。最新的公开实例，即 Anthropic 2026-07 的记述，用智能体描述了同样的做法：先写规则手册，在 3 个文件上做压力测试并丢弃其产出，然后由实现智能体分批工作，配两个在各自上下文中工作的审阅者和阶段关卡，并使用动态工作流运行。上面的搭建方式用动态工作流做扇出；在用不了这项功能的地方，套件里启动 `claude -p` worker 的 shell 脚本仍然可用。来源 5 针对长尾、用大量相关文件扩充提示词的做法，在这里保留为第二轮；本搭建方式没有规定提示词的大小。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 团队在 10–20 个有代表性的文件上试点，调整提示词和示例。🛑 **计划**：由人冻结提示词、少样本示例和成功标准。
2. 系统为每个文件运行一个状态机：重构 → 修复 lint → 修复类型 → 修复测试。每一步都是一次 LLM 调用，并接收对应验证器的输出。由 N 个并行的无头 worker（`claude -p`、Codex exec、Agent SDK）运行，每个都有重试预算。
3. 针对长尾，团队补充上下文（同级文件、组件源码、更多示例）后重跑。他们对失败项聚类并修补提示词 [[5]](#sources)。
4. 🛑 **抽检**：由人随机抽样检查语义是否保真，不能只看“测试通过”。
5. 系统按负责人分批提 PR。🛑 **审阅**：代码负责人评审。其余遗留项由工程师人工修复。

**产出：** 迁移完成的代码库、失败日志，以及可复用的迁移提示词包。

## 公开实例

覆盖度（截至 2026-11-06）：**充分**：有详细的第一手实例，与流程的大部分环节一致。来自 [Where are the real runs?](../../../../../research/2026-11-real-runs.md)；每个数字都已对照原页面复核。

- [Sergii Gorbachov, Slack Engineering](https://slack.engineering/balancing-old-tricks-with-new-feats-ai-powered-conversion-from-enzyme-to-react-testing-library-at-slack/) (2024-05-22)。AST codemod 加带 DOM 上下文的 LLM；用评分标准检查样本文件；由人验证。"80% of the content within these files was accurately converted"；"saving of 22% of developer time"。*第一手：是；可信度：高。*
- [Ziftci et al., Google, arXiv 2504.09691](https://arxiv.org/abs/2504.09691) (2025-04-13)。39 个 int32→int64 迁移，逐文件编辑并验证；失败项交给人处理。"74.45% of the code changes and 69.46% of the edits were generated by the LLM"。*第一手：是；可信度：高。*
- [Anthropic, *How Anthropic runs large-scale code migrations*](https://claude.com/blog/ai-code-migration) (2026-07-16)。规则手册 → 用 3 个文件做一次性压力测试 → 扇出式实现-评审-修复 → 阶段关卡。"fanned out across all 1,448 files"；"Nineteen regressions surfaced after merge"。*第一手：是（自家产品）；可信度：中。*
- [Charas & Bruggmann, Spotify Engineering](https://engineering.atspotify.com/2025/11/spotifys-background-coding-agent-part-1) (2025-11-06)。在容器中做批量迁移，并用 LLM 评判；由各团队评审 PR。"merged more than 1500 pull requests"；"60–90%" 的时间节省。*第一手：是；可信度：高。*
