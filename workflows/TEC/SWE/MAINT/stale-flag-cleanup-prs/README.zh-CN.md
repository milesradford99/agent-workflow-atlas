# 过期开关清理 PR

**工具变体：** `google-adk` · `claude-opus` · `github-copilot-agent-tasks` · `github-actions`

## 背景

软件团队会用功能开关：代码里的一个开关，可以对一部分用户或全部用户打开某项新功能。功能全面上线之后，这个开关就不再需要了，但它背后的旧代码路径通常还留着，开关越积越多，让代码更难读、更难改。清理一个开关，就是找出它在哪里被用到，只保留开关最终取值对应的代码，并更新测试。这里由智能体为每个过期开关做这些工作，并为每个开关提一个拉取请求（PR，供人评审的拟议改动）。开关最终取哪个值必须由人确认，因为保留错误的分支会悄悄改变用户得到的东西；开关的负责人必须评审并合并这个 PR，因为这段代码由他负责。

**术语：**
- **功能开关（feature flag）**：代码里的一个开关，不需要新版本就能打开或关闭某项功能，或只对一部分用户打开。
- **过期开关**：很久没有变动、但仍留在代码里的开关。
- **发布（rollout）/ 部分发布**：当前能用到该功能的用户比例；部分发布指中途被放弃的发布，例如停在 60%。
- **目标取值**：清除开关代码时，开关应被固定成的值。
- **实验平台**：保存每个开关在线状态的系统。
- **PR（pull request，拉取请求）**：一项提议的改动，先发布出来供人评审，再合并进共享代码。
- **Git worktree**：仓库的一个独立工作副本，可以让几项改动同时进行。
- **补丁覆盖率**：被改动的行中有多大比例被测试执行到。
- **linter**：标出代码风格和简单错误问题的工具。
- **归档开关**：在开关服务中停用该开关，使其不能再被使用。

## 用智能体搭建

**形态：** `service`。由每日的定时计划启动，没有人在场，人只看到报告、接手请求和做好的 PR。

**需要：** 每日触发器（云端定时任务，或自己的调度器启动 `claude -p`）；列出过期开关的办法，可以是确定性的查询或工单流；通过 MCP 服务器对实验平台的只读访问；每个仓库的检出副本，其构建、测试、覆盖率和 lint 命令写在 `CLAUDE.md` 中；一份绝不触碰的开关排除名单；存放报告的队列或工单系统。不要给智能体实验平台的写权限，也不要给合并权限。

| 步骤 | 搭建方式 |
|---|---|
| 定时任务 (每日): 过期开关工单 | 一次定时运行读取工单或确定性的过期开关清单，分配给各开关的创建者。 |
| 编排器: 发布状态 + 目标取值 + 代码引用 → 报告 | 一个 skill 向平台查询每个开关的发布百分比和目标取值，在仓库中搜索引用，并写出提出目标取值的报告。运行到此结束。 |
| 部分发布：🛑 handoff / 🛑 review (工程师确认目标取值) | 报告通过工单发给开关负责人或一位工程师。部分发布交回负责人去完成或跳过；确认后的目标取值记录在工单里，由下一次运行接着处理。 |
| 每个开关：(在 worktree 中编辑 ⟲ 构建 + 测试 + 补丁覆盖率 + lint) | 对每个已确认的开关，一个子智能体在各自的 git worktree 中移除开关，并循环到构建、测试、补丁覆盖率（至少 95%）和 lint 都通过为止，有时限。每个仓库同时最多运行 4 个。 |
| 向开关负责人提 PR | 由一个脚本在检查通过之后才创建 PR，并分配给开关负责人。 |
| 🛑 review (负责人合并) | 负责人在代码托管平台上评审并合并。 |
| 归档开关 | 部署之后由负责人或另一个任务完成；智能体没有这方面的工具。 |

**检查点：** `handoff`：部分发布绝不编辑；报告连同发布状态转给负责人，在负责人回答之前智能体不再做任何事。`review`：有两处停顿，都靠智能体缺少相应工具来保证。清除步骤只对人已经记录了目标取值的开关运行，所以智能体不能以自己提出的取值为起点；智能体也没有合并或归档的工具，所以由负责人合并，开关在此之后才退役。如果漏掉一次停顿会改变面向用户的行为，还可以用 `PreToolUse` 钩子拦住对任何未标记为已确认的开关的编辑。

**与来源相比：** 来源出自 2025-12 到 2026-08。来源 1 报告的是由编排器驱动的两阶段智能体系统，来源 2 报告的是一个为每个开关启动一个云端智能体任务的 GitHub Actions 工作流；搭建方式保留了来源 1 的两个阶段，并把两阶段之间的停顿明确为一次运行的结束。来源 2 完全确定性的资格过滤，保留为列出过期开关的办法。本次检查中两个来源都没有打开（会话网络屏蔽了它们的站点），所以这里所述依据的是本条目的步骤。搭建方式没有设定成本或时间数字，也没有照搬来源 1 的 1 小时超时，只是说明应当设一个时限。正如来源 2 所述，机器人开的 PR 默认可能不跑 CI；请查看你的代码托管平台如何对待它们。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 每日定时任务为每个过期开关创建一张工单：90 天内未修改、代码中仍有引用、未归档、不在排除名单上。工单分配给开关的创建者 [[1]](#sources)。
2. 阶段 1：编排智能体获取工单。它通过 MCP 向实验平台查询开关的 UUID、发布百分比和目标取值，然后在仓库中搜索所有引用。它写出一份报告，提出目标取值并列出受影响的文件 [[1]](#sources)。
3. 🛑 **审阅**：工程师核对报告并确认目标取值。🛑 **接手**：部分发布（例如在 60% 时被放弃）交回给用户，由其完成发布或回滚，或跳过清理 [[1]](#sources)。
4. 阶段 2：每个已确认的开关对应一个清除智能体，各自在独立的 git worktree 中运行，每个仓库同时最多 4 个。每个智能体找出常量、封装和调用点，简化条件分支并更新测试。它循环执行，直到构建通过、测试通过、补丁覆盖率至少 95%、linter 无告警。它有 1 小时超时，检查通过前不得开 PR [[1]](#sources)。
5. 🛑 **审阅**：PR 分配给开关负责人，由其审阅并合并。在变体中，部署后开关会在开关服务中归档，工单关闭 [[1]](#sources)[[2]](#sources)。
6. 变体：资格过滤完全是确定性的（布尔开关、超过 3 个月、仍在代码中）。每个开关触发一个云端智能体任务，PR 带标签以便跟踪，由常规 CI 加必需的人工评审把关合并 [[2]](#sources)。

**产出：** 每个过期开关一个可直接合并的 PR，分配给开关负责人，随后归档该开关。
**失败模式 → 防护：** 硬编码错误的值会悄悄改变行为 → 在线发布状态取自平台而不是代码，并由人确认。调用链深处清除不彻底 → 覆盖率和 linter 检查，然后重新提示。50 次运行中的 5 次人工干预全都是调用链深度问题，而不是 bug。机器人 PR 默认不跑 CI → 手动批准 CI 运行 [2]。
**与相近工作流的区别：** AWF-0002 扇出式代码迁移（Fan-out codemod）在大量文件上应用同一种改写，先试点再抽检。这里的单元是开关，其目标取值来自在线平台。任何编辑之前都由人确认该取值，每位负责人拿到的是按开关拆分的 PR。AWF-0130 基于性能剖析的优化（Profile-led perf fixes）根据剖析结果瞄准热点函数。产出物和检查点安排都与这两者不同。

## 公开实例

覆盖度（截至 2026-11-13）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [DoorDash, Automating Feature-Flag Cleanup at Scale with a Multi-Agent LLM System](https://careersatdoordash.com/blog/automating-feature-flag-cleanup-at-scale-with-a-multi-agent-llm-system/) (2026-08-24)。处理最近的 50 个过期开关；并行清理智能体之前有一个人工检查点。"produced usable PRs for 45 of them at an average cost of $4.79 and 13.8 minutes per flag"。*第一手：是；可信度：高。*
- [Glovo, How We Use AI to Keep Feature Flags Under Control](https://tech-blog.glovoapp.com/blog/how-we-use-ai-to-keep-feature-flags-under-control/) (2025-12-10)。GitHub Actions 工作流为每个符合条件的开关触发一个 Copilot 智能体任务；必须经人工评审。"600+ feature flags older than a year"。*第一手：是；可信度：中。*
