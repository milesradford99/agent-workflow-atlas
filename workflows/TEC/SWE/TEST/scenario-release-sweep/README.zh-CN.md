# 发布前场景巡检

**工具变体：** `claude-code-skills` · `xcode-mcp` · `adb`

## 背景

手机应用发布之前，团队会停止加新功能（代码冻结），再由人手工试用应用，找出自动化测试漏掉的 bug。这意味着要在不同尺寸的手机上、不同的设置下（深色模式、特大字体、从右到左的语言等）反复走一遍主要界面。这件事又慢又重复，难免有角落被跳过。在这里，智能体在模拟出来的手机上按书面场景逐个操作，并报告看起来不对的地方。自动运行也会报出并非 bug 的东西，所以由开发者阅读报告、判断哪些是真问题并登记，是否发布仍由团队决定。

**术语：**
- **代码冻结（code freeze）**：发布前的某个时间点，此后只改缺陷，不再加新功能。
- **模拟器（simulator / emulator）**：行为像一部手机的程序，不用真机就能试用应用。
- **场景（scenario）**：用日常语言写的“应用里什么必须成立”（例如“用户可以重置密码”），不写检查所需的点击步骤。
- **预置测试账号**：测试后端上的登录账号，里面有已知数据，并在每个批次前重置，因此删除数据的场景也不会造成损害。
- **RTL**：从右到左的版面，用于阿拉伯语、希伯来语等语言。
- **探索式测试**：自由试用应用并记下任何看起来不对的地方，而不是照脚本走。
- **误报**：被报告出来、其实不是问题的问题。
- **分诊（triage）**：逐条阅读报告的问题，判断是否属实、严重程度，以及交给谁。
- **跟踪器**：团队登记和跟踪问题的系统。

## 用智能体搭建

**形态：** `skill`。开发者在每次冻结前启动这次巡检，之后再读报告，所以一个装有流程的 skill 加上操作模拟器的子智能体，就是够用的最小形态。来源作者自己也是用 skill 搭的。

**需要：** 能为模拟器或仿真器构建的应用；放在 skill 旁边的 Markdown 场景文件；一个创建全新模拟器的脚本，以及另一个在测试后端（绝不能是生产环境）上预置并重置测试账号的 skill 或脚本；所用平台提供的模拟器操控工具（iOS 用 Xcode 的 MCP 工具，Android 用 `adb`）和录屏；对问题跟踪器的只读访问，用来查重，运行期间没有创建问题的工具；上一次运行的报告副本，用来对比。

| 步骤 | 搭建方式 |
|---|---|
| 代码冻结 → 全新模拟器 + 预置测试账号 | 开发者按名字启动这个 skill。脚本创建模拟器，并让每台登录各自的测试账号，账号在每个批次前预置并重置。每台模拟器都录屏。 |
| 每个批次（3 个场景）：智能体操作应用 + 标记任何异常 | 内置子智能体每 3 个场景一个，通过设备操控工具操作模拟器。每个子智能体还被要求标记其他看起来不对的地方。下一个批次交给全新的子智能体，使每个上下文保持较小。可以用动态工作流脚本把批次分配到各台模拟器上。 |
| 设置扫描（深色、大字体、RTL、语言区域） | 同样的子智能体在 skill 旁边参考文件列出的组合设置下，重复检查主要界面。 |
| 验证智能体：确认 + 在代码中找原因 + 与问题跟踪器去重 | 另一个子智能体复核每个候选问题，阅读代码找原因，并通过只读连接器在跟踪器中搜索。 |
| 与上次运行对比的 HTML 报告 | skill 写出一份 HTML 文件，并与上次运行保存的报告对比。 |
| 🛑 review → 误报：更新场景 | 见“检查点”。 |

**检查点：** `review`：skill 最后呈现报告，然后停下。运行期间有一条权限规则拒绝使用跟踪器的创建问题工具，所以没有开发者的操作，任何内容都到不了跟踪器。开发者先分诊，再启动另一个 skill，把选中的问题连同视频片段和截图登记进去，并修改产生误报的场景。

**与来源相比：** 唯一的来源和公开实例的日期是 2026-11-10。来源作者就是用 skill 和子智能体搭建的，这与这里选定的形态一致，所以变化很小。2026-11 打开了来源页面，与步骤中的数字、设置扫描、验证和分诊环节相符；步骤中的命令名和数字是作者的，不属于本搭建方式。来源指出每次运行的结果会有差异，所以这套搭建方式是发布检查，而不是合并代码的门槛。它只在模拟器和仿真器上运行，因此测不了真实网络或购买。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 开发者用 Markdown 写场景，说明什么必须成立，而不是如何检查。可选的准备钩子（仅限 DEBUG 的启动夹具）可以跳过导航。这次运行共有 13 个领域的 104 个场景 [[1]](#sources)。
2. 每次代码冻结之前，一条命令（`/pocket-qa ios full`）创建全新的模拟器（4 台 iPhone 和 1 台 iPad）。每个模拟器登录各自的测试账号，由另一个 skill 在每个批次前预置并重置，因此破坏性场景也无妨。每个模拟器都录屏 [[1]](#sources)。
3. 智能体通过 Xcode 的 MCP DeviceInteraction 工具操作应用（Android 上用 adb）。每个智能体跑 3 个场景，然后交给一个全新的智能体，以控制上下文成本。智能体也会像探索式测试人员那样，标记其他看起来不对劲的地方 [[1]](#sources)。
4. 智能体会在组合设置下扫描主要界面（深色模式 + 增强对比度、最大字体 + 粗体、RTL + 长字符串、德语 + 减弱动态效果）。这些扫描约占全部测试用例的一半 [[1]](#sources)。
5. 验证智能体检查每个候选问题，收集证据（包括代码中的原因），并在 Linear 中查找重复项 [[1]](#sources)。
6. 智能体把所有内容汇入一份 HTML 报告，含结论、主要问题、共用每项检查的测试用例，以及与上次运行的对比 [[1]](#sources)。
7. 🛑 **审阅**：不会自动向 Linear 提交任何内容。开发者对报告分诊，并通过另一个 skill 附上视频片段和截图登记问题。误报会促成场景更新 [[1]](#sources)。
8. 按 PR 的变体：`verify` 只测试 diff 涉及的内容及其相邻部分 [[1]](#sources)。

**产出：** 每次发布一份 HTML QA 报告，加上登记在跟踪器中的已分诊问题。它为发布的放行/不放行决策提供依据。
**失败模式 → 防护：** 结果不确定，因此不能作为合并的门槛 → 单元测试保留。运行很慢（9 个智能体小时）→ 分片到 5 个模拟器上，压缩到约 2 小时，按 PR 的模式保持窄范围。只在模拟器上运行 → 没有真实网络或购买。误报 → 验证智能体加人工分诊。
**与相近工作流的区别：** AWF-0069、AWF-0131 和 AWF-0132 产出的都是合入仓库的测试代码或修复。本工作流不产出测试代码：智能体针对运行中的应用执行自然语言场景，交付一份经分诊的发布 bug 报告。产出物和人工检查点（登记前先分诊）都不同。
