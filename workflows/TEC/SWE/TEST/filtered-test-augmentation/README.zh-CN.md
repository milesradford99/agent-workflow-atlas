# 筛选式测试补充

**工具变体：** `testgen-llm` · `meta-ach-mutation-guided` · `qodo-cover`

## 背景

单元测试是对一小段代码是否按预期工作的自动检查。团队想要更多测试，但写测试很慢；工程师被要求给一个已有测试的类补测试时，往往只覆盖显而易见的情形。智能体可以很便宜地提出大量补充测试，但其中多数没有价值：编译不过、运行失败、只是偶尔失败，或者没有测到已有测试之外的任何东西。所以每个提出的测试都要实际运行，过不了筛选就丢掉；而留下来的测试最终进不进代码库，仍由代码的负责工程师决定，因为只有负责人知道一个测试检查的是重要的事，还是只是把代码复述了一遍。

**术语：**
- **单元测试（unit test）**：对一小段代码的自动检查。
- **类（class）**：许多编程语言里把数据和行为组织在一起的单位；测试通常按类来写。
- **覆盖率（coverage）**：测试至少运行过一次的代码行占程序全部代码行的比例。
- **不稳定测试（flaky test）**：代码没有任何改动，却时而通过、时而失败的测试。
- **提示词策略**：向模型索要测试的固定方式，例如“扩充现有测试”或“覆盖边界情况”。
- **温度（temperature）**：控制模型输出多样程度的设置。
- **diff**：一次改动新增和删除的代码行；这里一个测试对应一个 diff，和其他改动一样接受评审。
- **代码评审**：同事阅读一项改动，在合并前决定接受还是拒绝。

## 用智能体搭建

**形态：** `skill`。一位工程师一次针对一个类，并且全程在对话中审看留下来的测试，所以一个带筛选脚本的 skill 就是够用的最小形态。

**需要：** 一个构建、测试和覆盖率命令都可用的仓库；目标类至少已有一个由人编写的测试类；放在 skill 旁边、运行这些命令的筛选脚本；写进 skill 旁边参考文件的提示词策略；创建分支或补丁文件的权限，没有推送或合并的权限。

| 步骤 | 搭建方式 |
|---|---|
| 挑选已有测试的类 | 由工程师指定这个类，或者 skill 取工程师最近一次改动涉及的测试目录。 |
| 每个提示词 × 温度：生成补充测试 | skill 的参考文件列出各种提示词策略。内置子智能体每个负责一种策略，以文件形式返回候选测试。 |
| 能编译 → 首次运行通过 → 5 次重跑都通过 → 提高覆盖率 | skill 旁边的脚本按这个顺序，对每个候选运行项目自己的构建、测试和覆盖率命令，在第一关不过时就丢弃。 |
| 每个留存测试一个 diff | skill 为每个留存的测试写一个补丁或分支，附摘要和测试计划，由工程师应用。 |
| 🛑 sample → 🛑 review | 见“检查点”。 |

**检查点：** `sample`：在来源中，工具的两位作者在工程师看到之前先审阅推荐结果。本搭建方式没有这一步，因为运行 skill 的工程师会在任何内容离开自己机器之前看到每个留存的测试。`review`：skill 最后列出每个留存测试及其覆盖率增量，然后停下。智能体没有推送或合并的工具，并且有一条设为“询问”的权限规则管着 `git push`，所以由负责该代码的工程师在常规代码评审中逐个接受或拒绝每个 diff。

**与来源相比：** 来源出自 2024-02（一篇论文，同时也是公开实例）。论文作者搭建的是一条专用流水线，运行在 Meta 自己的代码和模型上。现在用一个带筛选脚本的 skill 就能一次对一个类完成同样的事。本搭建方式省去了温度扫描和组合两个模型（论文把它们描述为工具提供的选项），也省去了 12 月由工具作者进行的审阅。2026-11 重新打开了这篇论文，它仍然支持这些步骤、5 次重跑的稳定性检查和 73% 这个数字。2026-11 的网络搜索没有找到可以打开的、关于这一做法的更新记录。有一条搜索结果提示，开源变体 `qodo-cover` 可能已不再维护；这一点没有打开核实，使用前请自行确认该项目的状态。

## 步骤

*以下按来源所述。*

1. 工程师（或工具代其）选定一个已有的、由人编写的测试类：工程师刚提交的改动所在目录，或最近有人补过测试的目录 [[1]](#sources)。
2. 智能体用多种提示词策略（extend_test、extend_coverage、corner_cases、statement_to_complete）生成补充测试用例。可选地在 0.0–1.0 之间扫描温度，或组合两个 LLM [[1]](#sources)。
3. 脚本依次过滤候选，任何一关不过就丢弃：必须能编译、首次运行通过、5 次重跑全部通过（不是不稳定测试），并且相对已有测试实测提高覆盖率。失败的测试一律丢弃，因为无法区分是真 bug 还是断言写错了 [[1]](#sources)。
4. 工具把每个留存的测试单独作为一个 diff 提交，附摘要和测试计划，进入正常的代码评审 [[1]](#sources)。
5. 🛑 **抽检**：在 12 月的几轮运行中，工具的两位作者先审阅推荐结果，再交给工程师 [[1]](#sources)。
6. 🛑 **审阅**：负责该代码的工程师逐个接受、拒绝或放弃每个 diff，最终合入什么由他们决定 [[1]](#sources)。

**产出：** 合入的单元测试 diff，每个都保证提高覆盖率且稳定通过，扩充了原有测试类。
**失败模式 → 防护：** 没有断言或断言写着 TODO 的测试、只测简单 getter 的测试、近乎重复的测试、依赖薄弱 mock 的测试 → 在评审时拒绝并去重；覆盖率过滤要严格。只有约 4–5% 的生成尝试能留存下来，所以要跑大量低成本的尝试 [[1]](#sources)。
**与相近工作流的区别：** AWF-0002 扇出式代码迁移（Fan-out codemod）是在大量文件上改写已有代码。本工作流只新增测试，以实测的覆盖率提升为门槛，每个测试一个小 diff。

## 公开实例

覆盖度（截至 2026-11-06）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [New workflows for empty categories](../../../../../research/2026-11-new-workflows.md)。

- [Meta, Automated Unit Test Improvement using LLMs at Meta](https://arxiv.org/abs/2402.09171) (2024-02-14)。Instagram 和 Facebook 的 test-a-thon 活动；每个过滤后的测试作为 diff 交给工程师接受或拒绝。"73% of its recommendations being accepted for production deployment by Meta software engineers"。*第一手：是；可信度：高。*
