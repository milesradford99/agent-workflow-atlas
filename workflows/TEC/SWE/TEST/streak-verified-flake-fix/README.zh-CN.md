# 连跑验证的不稳定测试修复

**工具变体：** `claude-code` · `devin` · `datadog-ci-visibility`

## 背景

大型软件项目对每一项提议的改动都会运行成千上万个自动化测试。其中有些测试只是偶尔失败，而代码并没有任何改动，这就是不稳定测试（flaky test）。每次不稳定的失败都会让工程师把整个作业重跑一遍，而随着不稳定测试增多，重跑排起长队，拖慢所有人。不稳定测试难修，是因为原因很少一目了然；也难证明修好了，因为对一个时有时无的失败来说，一次干净的运行什么也说明不了。智能体可以读失败日志、提出修复，并不知疲倦地连续重跑很多次测试。合并之前仍然要由人评审这项改动，因为即使重跑全部通过，智能体对原因的解释也可能是错的。

**术语：**
- **不稳定测试（flaky test）**：代码没有任何改动，却时而通过、时而失败的测试。
- **CI（持续集成）**：对每项提议的改动自动运行的构建与测试作业。
- **不稳定性看板**：CI 系统给出的报表，按间歇性失败的频率给测试排名；这里导出其中一个测试的数据，作为工作的起点。
- **连续重跑次数（rerun streak）**：修复要被信任之前，目标测试在 CI 中必须连续重跑多少次都不出现失败。
- **假设（hypothesis）**：智能体对测试为何不稳定提出的唯一一个说法。
- **PR（pull request，拉取请求）**：一份提议的改动，在合并进共享代码之前公开出来供评审。
- **CODEOWNERS**：一个文件，写明哪个团队负责哪部分代码，让评审请求发给合适的人。

## 用智能体搭建

**形态：** `skill`。一位工程师针对一个不稳定测试启动这个 skill（或每个测试一个会话）并读取结果，所以一个承载循环的 skill，加上负责修复和检查的子智能体，就是够用的最小形态。步骤中的 Timee 变体由检测事件触发，现场没有人，那样搭建就属于 `service`。

**需要：** 目标测试的不稳定性导出文件；对 CI 日志的读取权限，以及在某个分支上发起 CI 重跑的权限；一个智能体可以推送分支并开草稿拉取请求、但没有合并权限的仓库；连续重跑次数和最大尝试次数，在启动 skill 时作为输入给出。

| 步骤 | 搭建方式 |
|---|---|
| 不稳定性看板导出 → 下载近期失败日志 | skill 以导出文件为输入，用 CI 系统的命令行工具或连接器下载该测试近期失败的 CI 日志。 |
| 修复子智能体：假设 + 在分支上修复 | 一个子智能体阅读日志和源码，提出一个假设，向分支提交一处修复，并返回简短摘要。 |
| 验证子智能体重跑 CI，直到连续 N 次通过 | skill 每次重跑启动一个小型子智能体。每个子智能体启动 CI、轮询，只判断目标测试是否失败，忽略同一次运行里其他不稳定测试。 |
| (修复 ⟲ 验证) | 验证子智能体报告再次出现失败时，skill 把新日志和之前的修复摘要交给一个全新的修复子智能体。循环在达到尝试上限时结束。 |
| 达到最大尝试次数：报告失败 \| 连续通过：开 PR | skill 向工程师报告失败，或通过代码托管平台的命令行工具开一个草稿拉取请求。 |
| 🛑 review → 合并 | 见“检查点”。 |

**检查点：** `review`：PR 以草稿形式创建，智能体没有合并它的工具，所以由人阅读 diff 和修复子智能体的摘要，再合并、修改或关闭。对于多个不稳定测试，每个导出文件启动一个会话；各会话之间不共享状态。

**与来源相比：** 来源的日期从 2025-07 到 2026-06。Kong 的文章（2026-06）描述的是用 Claude Code 搭建的这个循环：一个负责编排的 skill 加两个具名的子智能体，与这里选定的搭建一致。它还报告修复和验证用的是不同的模型，本设计并不要求这样。Timee 的文章（2025-07）用的是 Devin 产品，由 GitHub Action 触发；其步骤已概括在步骤里，这里不搭建。两篇文章都在 2026-11 打开过，仍然支持这些步骤；最新的来源不到 12 个月，所以不需要再查更新的记录。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 工程师给编排器（一个 skill）输入一个不稳定测试从 CI 可见性看板导出的数据（Datadog CSV）。它下载该测试近期失败时的 CI 日志。[[1]](#sources)
2. 编排器派生一个修复子智能体。它阅读日志和源码，提出一个假设，向分支提交一处修复，并回报摘要。[[1]](#sources)
3. 编排器接着派生若干小型验证子智能体。每个重跑 CI，并判断这个测试是否失败，忽略同一次运行中其他不稳定测试。它不断重复，直到达到配置的连续重跑次数。[[1]](#sources)
4. 一旦再次出现失败，新的日志连同之前的修复摘要交给一个全新的修复子智能体。循环在达到尝试上限时结束，并报告失败。[[1]](#sources)
5. 连续通过后，编排器开 PR。多个不稳定测试并行运行，每个种子文件一个实例。[[1]](#sources)
6. 🛑 **审阅**：经过验证的 PR 在合并前要经过常规的人工代码评审。[[1]](#sources)
7. 变体（Timee）：不稳定测试检测触发一个 GitHub Action，把测试名和错误发给 Devin。PR 通过 CODEOWNERS 自动分配，🛑 **审阅**：团队修改、合并，或关闭误报。[[2]](#sources)

**产出：** 每个不稳定测试对应一个合并的修复 PR，经连续的干净重跑验证。智能体放弃的测试会回报给团队。
**失败模式 → 防护：** 对间歇性失败，一次重跑通过说明不了什么 → 可配置的连续重跑次数。多次尝试导致上下文膨胀 → 每个修复子智能体只做一处修复，向后传递摘要。其他不稳定测试被当成噪声 → 专门的验证子智能体只判断目标测试。假设错误的修复 → 人工 PR 评审；团队可以重写或关闭。
**与相近工作流的区别：** AWF-0071 先复现的缺陷修复：AWF-0071 从缺陷工单出发，无法复现时转交人工。本工作流的触发源是不稳定性看板，成功标准是 CI 重跑的统计性连续通过。智能体无人值守地运行数小时，唯一的人工关卡是最终的 PR。AWF-0069 生成新测试；本工作流修复已有的测试。
