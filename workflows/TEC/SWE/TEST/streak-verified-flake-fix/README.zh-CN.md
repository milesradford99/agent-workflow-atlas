# 连跑验证的不稳定测试修复

**与相近工作流的区别：** AWF-0071 先复现的缺陷修复：AWF-0071 从缺陷工单出发，无法复现时转交人工。本工作流的触发源是不稳定性看板，成功标准是 CI 重跑的统计性连续通过。智能体无人值守地运行数小时，唯一的人工关卡是最终的 PR。AWF-0069 生成新测试；本工作流修复已有的测试。
**工具变体：** `claude-code` · `devin` · `datadog-ci-visibility`

## 步骤

1. 给编排器输入一个不稳定测试从 CI 可见性看板导出的数据（Datadog CSV）。它下载该测试近期失败时的 CI 日志。[[1]](#sources)
2. 编排器派生一个修复子智能体。它阅读日志和源码，提出一个假设，向分支提交一处修复，并回报摘要。[[1]](#sources)
3. 编排器接着派生若干小型验证子智能体。每个重跑 CI，并判断这个测试是否失败，忽略同一次运行中其他不稳定测试。它不断重复，直到达到配置的连续重跑次数。[[1]](#sources)
4. 一旦再次出现失败，新的日志连同之前的修复摘要交给一个全新的修复子智能体。循环在达到尝试上限时结束，并报告失败。[[1]](#sources)
5. 连续通过后，编排器开 PR。多个不稳定测试并行运行，每个种子文件一个实例。[[1]](#sources)
6. 🛑 **审阅**：经过验证的 PR 在合并前要经过常规的人工代码评审。[[1]](#sources)
7. 变体（Timee）：不稳定测试检测触发一个 GitHub Action，把测试名和错误发给 Devin。PR 通过 CODEOWNERS 自动分配，🛑 **审阅**：团队修改、合并，或关闭误报。[[2]](#sources)

**产出：** 每个不稳定测试对应一个合并的修复 PR，经连续的干净重跑验证。智能体放弃的测试会回报给团队。
**失败模式 → 防护：** 对间歇性失败，一次重跑通过说明不了什么 → 可配置的连续重跑次数。多次尝试导致上下文膨胀 → 每个修复子智能体只做一处修复，向后传递摘要。其他不稳定测试被当成噪声 → 专门的验证子智能体只判断目标测试。假设错误的修复 → 人工 PR 评审；团队可以重写或关闭。

## 公开实例

覆盖度（截至 2026-11-06）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [Second collection pass](../../../../../research/2026-11-second-pass.md)。

- [Kong, How We Used Agentic AI to Fix Kong Gateway's Flakiest Tests](https://konghq.com/blog/engineering/how-we-used-agentic-ai-to-fix-kong-gateways-flakiest-tests) (2026-06-10)。针对最不稳定的 15 个测试运行；每个测试耗时 4–5 小时、100–200k 个 token。"It fixed 12 of them and gave up on 3"。*第一手：是；可信度：高。*
- [Timee, さよなら Flaky Test！](https://tech.timee.co.jp/entry/2025/07/16/100000) (2025-07-16)。Datadog 检测触发 Devin 提 PR，经 CODEOWNERS 审阅。"3件 の Flaky Test を修正する Pull Request が Devin によって作成されましたが、そのうち 2件 は開発者によって変更が加えられることがなくマージされました"。*第一手：是；可信度：中。*
