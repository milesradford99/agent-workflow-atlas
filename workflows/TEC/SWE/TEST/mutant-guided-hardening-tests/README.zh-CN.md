# 变异体驱动的加固测试

**工具变体：** `meta-ach`

## 背景

软件团队会担心某些特定类型的失败，比如泄露用户的隐私数据，并希望有测试能在代码哪天真的以这种方式出错时发现它。靠手工写这类测试，需要有人能想象出那些故障，而普通的覆盖率数字也无法说明一个测试能不能抓住这类故障。在这里，工程师用平实的话写下这个担忧；智能体设想出这一类的真实故障，把每个故障植入代码的一份副本，再写出在故障存在时会失败的测试。一个测试只有同时满足三点才保留：能编译、稳定通过、能抓住现有测试都抓不到的故障。工程师仍要审阅每个测试，因为只有人才能判断它守护的是不是所指定的关注点，还是只是增加了覆盖率。

**术语：**
- **变异体（mutant）**：代码的一份副本，里面故意植入了一处小的故障。
- **杀死变异体（kill）**：测试在原代码上通过、在变异体上失败，就说明这个测试能检测出那处故障。
- **等价变异体**：改动并不改变代码行为的变异体，任何测试都杀不死它；在它身上花的功夫是白费的。
- **变异体驱动（mutation-guided）**：用变异体而不是行覆盖率来决定哪些测试值得保留。
- **不稳定测试（flaky test）**：代码没有任何改动，却时而通过、时而失败的测试。
- **test-a-thon**：定期举行的集中评审活动，一组工程师一起审阅生成的测试。
- **精确率和召回率**：被过滤器判定丢弃的项目中，丢得对的比例；实际存在的等价变异体中，被找出来的比例。
- **回归测试**：防止某类旧故障再次出现的测试。

## 用智能体搭建

**形态：** `skill`。工程师提出一个关注点，并在对话中逐个类处理，所以一个 skill 加上负责逐类工作的子智能体就是够用的最小形态。这些步骤里没有哪一条是必须每次运行都成立的规则。

**需要：** 一个构建和测试命令可用的仓库；一种在不动工作区的前提下把植入的故障应用到某个类副本上的办法，例如应用并还原补丁文件的脚本；写成纯文本的关注点，可以含糊；创建补丁文件的权限，没有推送或合并的权限。

| 步骤 | 搭建方式 |
|---|---|
| 纯文本关注点 (如隐私) | 工程师在一开始说明关注点；skill 把它存成文件，之后每一步都读取。 |
| 每个类：生成针对该关注点的变异体 | 内置子智能体并行运行，每个类一个。每个子智能体以补丁文件形式返回几个针对该关注点的真实变异体。 |
| 等价变异体智能体过滤 | 另一个子智能体判断每个变异体是否改变行为，丢弃不改变的。项目能脚本化的简单预处理先行运行。 |
| 生成能杀死存活变异体的测试 | 每个存活的变异体由一个子智能体写一个旨在让它失败的测试。 |
| 能编译 → 稳定通过 → 能捕获现有测试都捕获不到的变异体 | skill 旁边的脚本先构建测试、重跑，再把现有测试集和新测试分别对每个变异体运行。 |
| 🛑 review | 见“检查点”。 |

**检查点：** `review`：skill 最后列出每个留存的测试，附它杀死的变异体和它增加的覆盖率，请工程师接受或拒绝，并把对关注点的相关性与有用性分开评定。智能体只写补丁文件，没有推送或合并的工具，所以没有工程师点头，什么都合不进去。

**与来源相比：** 来源出自 2025-01（一篇论文，同时也是公开实例）。论文报告的是一个专用的多智能体工具 ACH，在 Meta 的 7 个平台上运行，生成的测试在 test-a-thon 中评审；本搭建方式是同样的步骤，做成工程师逐个类运行的 skill。2026-11 重新打开了这篇论文，它仍然支持这些步骤和这里引用的数字（9,095 个变异体、571 个测试、73% 的采纳率、36% 的隐私相关性、等价变异体的精确率和召回率）。2026-11 的网络搜索只找到这篇论文和对它的转述，没有找到可以打开的、关于这一做法的更新记录。本搭建方式不包含 ACH 自己的模型和提示词，也不含针对它们报告的数字，不能假定 skill 能复现这些数字。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 工程师用纯文本写下关注点。论文中的例子是隐私类故障；文字可以含糊或不完整。[[1]](#sources)
2. 对每个被测类，工具（ACH）生成少量针对该关注点的真实变异体（模拟故障），而不是一大批通用的变异算子。[[1]](#sources)
3. 一个 LLM 智能体找出并丢弃等价变异体（单独使用时精确率 0.79、召回率 0.47，加上简单的预处理后升至 0.95 和 0.96）。[[1]](#sources)
4. 对每个仍然存活的变异体，工具生成一个旨在杀死它的单元测试。[[1]](#sources)
5. 每个测试必须通过三道硬性检查：能编译、稳定通过（不是不稳定测试），并且能捕获现有测试都捕获不到的故障。相关性和风格留给人工审阅。[[1]](#sources)
6. 🛑 **审阅**：工程师通过常规代码评审或 test-a-thon 审阅这些测试，并逐个接受或拒绝。他们还要评定隐私相关性。[[1]](#sources)

**产出：** 合入的回归测试，防范某一类指定的故障。变异体在代码库中的分布，也可作为各组件的风险代理指标。
**失败模式 → 防护：** 等价变异体浪费生成精力 → 等价判定智能体加预处理。测试有用但偏离既定关注点（只有 36% 被判定与隐私相关） → 审阅者把相关性与有用性分开评定。只带来微不足道覆盖率的测试会被拒绝 → 每个测试都附上覆盖率。
**与相近工作流的区别：** AWF-0069 筛选式测试补充：AWF-0069 的目标是为已有测试的类提高覆盖率。本工作流从一条书面的关注点和模拟故障出发，产出是能杀死特定变异体的测试。如果只按覆盖率过滤，它的 571 个测试中有 277 个会被丢弃。

## 公开实例

覆盖度（截至 2026-11-06）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [Second collection pass](../../../../../research/2026-11-second-pass.md)。
