# 按准则审查设计文档

**工具变体：** `slack`

## 背景

在开发者动手实现一个新功能之前，很多公司会请安全团队读一读这个功能的设计文档，趁修改成本还低的时候指出风险。这就是安全设计评审。安全团队对照公司成文的安全准则检查设计，这类准则往往有上百条，同时凭经验找出清单覆盖不到的缺陷。团队人手少时，拿每条准则去对照每份文档很慢，评审人只好凭记忆，于是就有遗漏；而开发者交付得越快，排队的请求就越多。智能体先判断一份设计是否需要评审，再逐条对照准则检查，列出缺失或有问题的地方。每条发现在交给开发者之前，仍要由安全工程师核实，因为安全团队要为公司交付的产品负责，而错误地给出“没有问题”的结论代价最高。

**术语：**
- **安全设计评审（Security Design Review，SDR）**：在开始实现之前，由安全团队对设计文档做的评审。
- **设计文档**：开发者为一个功能写的书面计划：它做什么、怎么做、处理哪些数据。
- **准则**：公司编号成条的安全规则，例如如何认证用户、如何存放密钥，外加外部标准。
- **RFC**：已发布的互联网标准（Request for Comments），认证等协议常引用它。
- **分诊**：判断一个请求是否需要走完整评审。
- **漏报 / 误报**：评审没发现的真实问题 / 报告出来但其实不存在的问题。
- **上下文工程层**：决定每次调用模型时放入哪些准则、文档的哪些部分的那段代码。
- **基准评测**：一组带有专家结论的历史设计文档，用来衡量智能体的准确率。

## 用智能体搭建

**形态：** `skill`。安全工程师一次处理一个评审请求，并在同一段对话里核实发现，所以一个装有准则目录和流程的 skill 就够了。

**需要：** 作为参考文件放在 skill 旁边的准则目录和分诊规则；对设计文档的读取权限（文件，或连到文档库的 MCP 连接器）；只有在要让 skill 发出核实后的反馈时，才需要 Slack 连接器。设计文档可能描述尚未发布的产品和内部系统，所以要使用所在机构批准处理保密资料的环境。

| 步骤 | 搭建方式 |
|---|---|
| 开发者在 Slack 请求评审 → 分诊: 设计是否需要评审？ | skill 的第一条指令：读取请求，套用 `triage.md` 中的分诊规则。不需要评审时，说明理由后停下。 |
| 检索设计文档 + 相关准则 (160+) | skill 打开文档，从旁边的准则目录文件中挑出适用的准则。 |
| 逐条检查准则 + 标出缺失信息 | 内置子智能体各负责一组准则，返回一张表：准则、结论、文档原文引用、缺失信息。skill 要求它们把有疑问的地方都报出来。 |
| 发现 | skill 把各张表合并成一份发现清单。 |
| 🛑 review (安全团队核实) → 向开发者反馈 | 见“检查点”。 |

**检查点：** `review`：skill 列出发现清单后停下，不发出任何内容；安全工程师逐条确认、修改或删除。之后 skill 才起草给开发者的消息，并且只在工程师指示时才发出，或者由工程师用自己的账号发送。

**与来源相比：** 来源 1 及其公开实例出自 2026-02。来源把 Hayami 做成了一个独立服务，从现有的 Slack 请求流程启动，结果交给安全团队；它没有说明使用哪种智能体框架或模型。上面的搭建方式去掉了 Slack 触发和独立服务：由安全工程师对每个请求运行 skill。来源计划中的持续基准评测（第 6 步）不在本搭建方式之内；它需要一组带有专家结论的历史文档，放在 skill 旁边，在准则或模型变化时重新运行。如果团队希望每个请求在工程师接手之前就已分析完毕，可以把同一个 skill 以 `service` 的形态运行，把发现发到安全团队的队列。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 开发者在现有的基于 Slack 的流程中发起安全设计评审（Security Design Review）请求 [[1]](#sources)。
2. 智能体对请求做分诊：应用单独的内部准则，判断这份设计是否需要评审 [[1]](#sources)。
3. 智能体检索设计文档和相关的内部安全准则（160+ 条，外加 RFC 等标准），并交给上下文工程层处理 [[1]](#sources)。
4. 智能体对照每条准则检查设计，标出缺失的信息或明显的违规。它被调校得偏谨慎，宁可有些噪声（误报），也要做到零漏报 [[1]](#sources)。
5. 🛑 **审阅**：分析结果交给产品安全团队，由他们核实之后才反馈给开发者 [[1]](#sources)。
6. 安全团队以真实设计文档上的人类专家评审为基准评测智能体，并规划在准则和模型变化时持续做基准评测 [[1]](#sources)。

**产出：** 针对一份设计文档、逐条对照准则的安全发现清单，经安全团队核实后才交给开发者。
**失败模式 → 防护：** 结构混乱的设计文档会降低准确率 → 人和智能体在写得好的文档上都表现更好。准则不断演进 → 规划持续的基准评测。通用智能体会漏掉各组织特有的规则 → 用定制工具编码内部准则集。
**与相近工作流的区别：** AWF-0072 带护栏的设计规格（Guardrailed design spec）由智能体撰写规格。这里由人撰写设计文档，智能体对照庞大的准则目录进行审查，并设有安全团队核实的检查点。产出物是评审发现，而不是规格。
