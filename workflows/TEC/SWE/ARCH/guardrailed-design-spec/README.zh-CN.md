# 带护栏的设计方案

**与相近工作流的区别：** AWF-0001 计划把关式构建是在编码会话中批准每个任务的实现计划。这里的交付物是设计文档本身，在设计评审会上获批并经法务/隐私/安全签批，另有一个每周循环来更新架构规则。
**工具变体：** `claude-code-spec-tool` · `github-spec-kit` · `kiro` · `adr-skill-with-linter`

## 步骤

1. 由人写一份简短的概念文档或 PRD：问题、约束和代码指引。不需要打磨得很完整 [[1]](#sources)。
2. 方案工具加载仓库的系统文件（ARCHITECTURE.md、SECURITY.md、LEGAL.md、PLAN.md 模板、CLAUDE.md），并调研代码库和代码负责人 [[1]](#sources)。
3. 生成一份分为两部分的方案。上半部分给人看：问题陈述、Mermaid 图、关键决策、“我们不做什么”、干系人、隐私与安全。下半部分给智能体用：分阶段的指南，含文件路径、函数签名和验证清单 [[1]](#sources)。
4. 对照护栏文件检查计划，并引用其中被违反的条款。另一个子智能体再次评审，并核实所引用的每个文件路径确实存在 [[1]](#sources)。
5. 🛑 **审阅**：工程师在设计评审会上评审方案，先看问题陈述，这样错误的前提在大家细读细节之前就会被否决。会议全程录制 [[1]](#sources)。
6. 🛑 **签发**：法务、隐私和安全团队审批数据流 [[1]](#sources)。
7. 后台智能体按指南分阶段提交 PR 来实现，由人评审 [[1]](#sources)。
8. 每周，智能体读取已录制的评审、Slack 讨论串和抽样的 PR 评论，并提交一个更新系统文件的 PR。由人评审并批准，这样下一份方案就会纳入最新的决策 [[1]](#sources)。

**产出：** 一份存放在仓库或 Confluence 中、经过评审和签批的设计方案，同时也是智能体的实现契约；系统文件每周根据评审反馈更新。
**失败模式 → 防护：** “设计废话”（无视内部规范、选用非标准工具）→ 把规则写进系统文件，每次运行都检查。方案太长无法评审 → 面向两类读者的结构，问题陈述放在最前。知识在会议中流失 → 每周的系统文件更新 PR [[1]](#sources)。
