# 带护栏的设计方案

**工具变体：** `claude-code-spec-tool` · `github-spec-kit` · `kiro` · `adr-skill-with-linter`

## 背景

团队在对软件系统做一项较大的改动之前，通常要由一名工程师先写设计文档：要解决什么问题，各部分如何配合，会接触哪些数据，又刻意不做什么。同事在会上评审这份文档；凡是涉及客户数据流转的内容，还要由负责法务、隐私和安全的人批准。手写这类文档要花好几天，初稿还常常违背公司自己的规则（该用哪种数据库、数据可以存在哪里），评审人的时间就耗在一遍遍挑出同样的错误上。在这里，智能体根据一份简短的说明起草文档，对照公司成文的规则检查，并确认文档里对代码的引用确实存在。前提和设计是否正确，仍由工程师在评审会上决定；数据流仍由法务、隐私和安全的负责人批准，因为公司要为客户数据的处理方式承担责任。

**术语：**
- **设计方案（design spec，设计文档）**：一项改动的书面计划，在动手实现之前接受评审。
- **PRD（产品需求文档）**：产品经理写的说明，讲清一个功能必须做什么、为谁而做。
- **概念文档**：只有几行的粗略说明：问题、约束，以及指向相关代码的线索。
- **护栏文件（系统文件）**：放在仓库里、写明公司规则的文件：`ARCHITECTURE.md`（系统怎么搭）、`SECURITY.md`（怎么防护）、`LEGAL.md`（数据怎么处理），以及方案模板 `PLAN.md`。
- **数据流**：客户数据流向哪里、谁能读取、存放在何处。
- **代码负责人**：登记为负责某部分代码的人或团队，改动这部分代码时必须经他们评审。
- **PR（pull request，拉取请求）**：一份提议的改动，在合并进共享代码之前公开出来供评审。
- **分阶段 PR**：把实现拆成一连串较小的拉取请求，计划的每个阶段一个。
- **后台智能体**：无人值守、在自己的容器里运行、最后交回一个拉取请求的编码智能体。
- **Mermaid**：一种用文本描述图表的格式，可以直接在 Markdown 中渲染。
- **设计废话（design slop）**：来源对 AI 起草的、无视内部规范或选用非标准工具的设计的叫法。

## 用智能体搭建

**形态：** `project`。护栏文件是每次运行都必须读取的常驻项目知识，第二道检查需要一个没见过草稿的审阅者；这两点都要靠 project，单个 skill 做不到。每周更新是自行启动的，所以作为云端定时任务在 project 之外运行。

**需要：** 存有护栏文件和 `PLAN.md` 模板的仓库；一份指向这些文件的 `CLAUDE.md`；智能体可读的代码负责人数据（`CODEOWNERS` 文件或一个小脚本）；为了每周更新，还要通过 MCP 连接器读取评审会的转写稿和相关 Slack 频道。会议录音和内部讨论只能放在所在机构批准用于内部资料的环境里。不要给智能体合并权限。

| 步骤 | 搭建方式 |
|---|---|
| 概念文档或 PRD → 加载 ARCHITECTURE、SECURITY、LEGAL 文件和代码 | 一个方案 skill。它的第一条指令是读取说明、护栏文件和模板；内置的只读子智能体梳理受影响的代码及其负责人。 |
| 两部分的方案（给人看的一半，给智能体用的一半） | skill 按模板写出 `specs/<name>.md`：先写问题、图、关键决策、不做什么、干系人、隐私与安全；再写各个阶段，附文件路径、函数签名和检查项。 |
| 对照护栏文件检查 | skill 把每项决策与护栏文件对照，列出每一处冲突及其违反的规则。 |
| 新的子智能体核实文件路径 | 一个自定义的只读子智能体，只拿到方案和护栏文件，确认引用的每个路径都存在，并对冲突提出反驳。 |
| 🛑 review (设计评审会) → 🛑 sign-off (法务、隐私、安全审核数据流) | 见“检查点”。 |
| 分阶段的智能体 PR | 每个阶段单独搭建，例如按 [AWF-0001 Plan-gated build](../../FEAT/plan-gated-build/) 的方式。 |
| 每周的评审记录 → 系统文件更新 PR → 🛑 review | 一个云端定时任务每周运行一次，带着转写稿和 Slack 连接器，起草对护栏文件的修改并创建拉取请求。权限规则禁止合并。 |

**检查点：** `review`：方案 skill 最后先展示问题陈述、再展示整份方案，然后停下；工程师在设计评审会上审阅，不经过智能体。每周任务创建的拉取请求是第二个 `review`：由人合并或关闭，任务本身没有合并权限。`sign-off`：数据流由法务、隐私和安全的负责人亲自批准，在会上或在方案的拉取请求上进行。智能体没有记录批准的工具，也没有合并权限，所以任何方案都不会凭智能体一句话就往下走。

**与来源相比：** 来源 1 和唯一的公开实例都出自 2026-03。来源把方案工具做成了基于 Claude Code SDK 的命令行程序，配有一个录制每场设计评审的会议机器人，以及在容器里分阶段实现的后台智能体。上面的搭建方式以 Claude Code project 的形态完成同样的步骤；录制机器人和容器流水线不在其中，每周更新也假定转写稿已经存在。来源称团队已把模板和系统文件的写法作为开源的 Claude Code 插件（`spec-tool@abnormal-ai`）发布；本目录没有核查这个插件的内容。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 由人写一份简短的概念文档或 PRD：问题、约束和代码指引。不需要打磨得很完整 [[1]](#sources)。
2. 方案工具加载仓库的系统文件（ARCHITECTURE.md、SECURITY.md、LEGAL.md、PLAN.md 模板、CLAUDE.md），并调研代码库及其代码负责人 [[1]](#sources)。
3. 智能体生成一份分为两部分的方案。上半部分给人看：问题陈述、Mermaid 图、关键决策、“我们不做什么”、干系人、隐私与安全。下半部分给智能体用：分阶段的指南，含文件路径、函数签名和验证清单 [[1]](#sources)。
4. 智能体对照护栏文件检查计划，并引用其中被违反的条款。另一个子智能体再次评审，并核实所引用的每个文件路径确实存在 [[1]](#sources)。
5. 🛑 **审阅**：工程师在设计评审会上评审方案，先看问题陈述，这样错误的前提在大家细读细节之前就会被否决。会议全程录制 [[1]](#sources)。
6. 🛑 **签发**：法务、隐私和安全团队审批数据流 [[1]](#sources)。
7. 后台智能体按指南分阶段提交 PR 来实现，由人评审 [[1]](#sources)。
8. 每周，智能体读取已录制的评审、Slack 讨论串和抽样的 PR 评论，并提交一个更新系统文件的 PR。由人评审并批准，这样下一份方案就会纳入最新的决策 [[1]](#sources)。

**产出：** 一份存放在仓库或 Confluence 中、经过评审和签批的设计方案，同时也是智能体的实现契约；系统文件每周根据评审反馈更新。
**失败模式 → 防护：** “设计废话”（无视内部规范、选用非标准工具）→ 把规则写进系统文件，每次运行都检查。方案太长无法评审 → 面向两类读者的结构，问题陈述放在最前。知识在会议中流失 → 每周的系统文件更新 PR [[1]](#sources)。
**与相近工作流的区别：** AWF-0001 计划把关式构建是在编码会话中批准每个任务的实现计划。这里的交付物是设计文档本身，在设计评审会上获批并经法务/隐私/安全签批，另有一个每周循环来更新架构规则。
