# 按需告警调查

**工具变体：** `claude-agent-sdk` · `sentry` · `new-relic` · `slack-bolt`

## 背景

线上服务一出错，错误跟踪工具就会往团队的聊天频道发一条告警。接着得有人去弄清楚发生了什么：读错误详情，看错误率或响应时间有没有变化，查最近发布了什么，再找到相关的代码。这第一轮排查会占用手头计划好的工作时间，所以常被往后推，告警越积越多、无人查看。在这里，工程师让智能体去做这第一轮调查，拿回一份报告，每个假设都附有证据，还可以继续追问。修复是另一个单独的请求。要不要开始调查、要不要让它修、修得对不对，都由工程师决定，因为智能体的假设可能是错的，它做的任何改动都会进入客户在用的代码。

**术语：**
- **告警**：错误发生时自动发出的消息，这里由错误跟踪工具发到 Slack 线程里。
- **Sentry**：一种错误跟踪服务，把错误归并成 issue，每个 issue 有 ID、堆栈跟踪、发生频率和受影响的用户数。
- **堆栈跟踪**：出错时正在执行的函数调用链，可以据此找到相关代码。
- **指标、NRQL**：对运行中服务的测量，例如错误率和响应时间；NRQL 是 New Relic 监控服务的查询语言。
- **部署**：把新代码发布到线上服务。
- **grep**：在代码中搜索某个词或模式。
- **镜像仓库**：一份只读的代码副本，保持更新，供机器人搜索。
- **git worktree**：仓库的另一份独立工作副本，在里面改动不会影响主工作目录。
- **草稿 PR**：标为“未就绪”的拉取请求（一份公开出来供评审的改动提议），在有人把它标为就绪之前无法合并。
- **受保护路径**：智能体不得修改的文件：CI 配置（自动检查）、基础设施定义（以代码形式描述的服务器和网络）以及锁文件（记录每个依赖的确切版本）。
- **宿主**：运行智能体的程序；在来源中，推送代码的凭据由它而不是智能体持有。

## 用智能体搭建

**形态：** `project`。每次调查由一名工程师发起，并留下来追问，这一点 skill 就能承载；但修复这一步需要每次都必须成立的规则：不得修改受保护路径、改动量有上限、未经批准不得推送。这些要靠钩子和权限规则。

**需要：** 通过 MCP 连接器或放在 skill 旁边的小脚本，读取错误跟踪工具和监控服务；检出的仓库；一份 `CLAUDE.md`，列出受保护路径和改动量上限；作为 skill 参考文件的调查流程，包括要试哪些查询、按什么顺序。错误事件里可能含有客户数据；报告只能放在所在机构允许存放这类数据的地方，也不要把这些数据贴进拉取请求。

| 步骤 | 搭建方式 |
|---|---|
| Slack 线程中的错误告警 → 机器人发出调查按钮 → 🛑 action (工程师发起) | 工程师拿着告警里的 issue ID 运行调查 skill。见“检查点”。 |
| 获取事件 (堆栈、频率、用户) + 查询指标 + 最近部署 + 读取/grep 代码 | skill 按参考文件给出的顺序调用错误跟踪和监控的连接器，并阅读、搜索代码。内置的只读子智能体可以并行跑查询和代码搜索。 |
| 带证据的假设、影响、修复方向 (Slack 摘要 + HTML 报告) | skill 在对话里写一段简短摘要，另写一份详细报告文件，附查询结果和代码引用。 |
| (追问 ⟲ 深入查看) | 在同一段对话中进行：工程师提问，智能体再去查。 |
| 🛑 action (带确认的修复按钮，或明确请求) → 在一次性 worktree 中修复 | skill 交出报告后停下。只有明确的请求才会启动修复，skill 在新建的 git worktree 里修改。 |
| 大小 + 受保护路径防护 | 用 `PreToolUse` 钩子拦住对受保护路径的修改。skill 旁边的脚本统计改动的文件数和行数；超过上限时，skill 只出报告，不创建拉取请求。 |
| 宿主打开草稿 PR → 🛑 review (人工标记为就绪) | 权限规则设为在 `git push` 和 `gh pr create` 之前询问；拉取请求以草稿形式创建，正文注明由 AI 生成，并写明 issue 和请求人。禁止合并。 |

**检查点：** `action`：第一个是工程师启动 skill；告警本身不会触发任何运行。第二个是修复：skill 交出报告后停下，没人要求就不改代码，每次推送和创建拉取请求之前都由权限规则询问。如果像来源那样，推送凭据不能放在智能体手里，就禁止 `git push` 和 `gh pr create`，由工程师自己执行。`review`：拉取请求是草稿，智能体没有合并或标记就绪的权限；由人在代码托管平台上评审。

**与来源相比：** 来源 1 及其公开实例出自 2026-08。来源在 Claude Agent SDK 上做了一个 Slack 机器人，为错误跟踪和监控写了自己的 MCP 工具，每个 Slack 线程一个会话、追问时恢复会话，并由宿主程序推送代码，令牌不会到达智能体。上面的搭建方式在交互式 Claude Code 会话中完成同样的步骤，因为每次运行都由人发起，人也留下来追问。来源加上 Slack 按钮，是为了让大家记得有这个机器人；要有这个按钮，就得沿用来源自己的设计：在 Slack 应用背后跑一个 Agent SDK 程序。来源计划中的调查质量评测不在本搭建方式之内。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 当 Sentry 告警落入机器人所在的频道，并且能提取出 issue ID 时，机器人会在线程中发出使用说明和调查按钮 [[1]](#sources)。
2. 🛑 **操作**：工程师按下按钮或提及机器人。机器人把按钮替换为一条说明谁发起了调查的备注，以防重复运行 [[1]](#sources)。
3. 智能体获取事件详情（堆栈跟踪、频率、受影响用户），运行 NRQL 查询错误率、延迟和最近部署，并读取、grep 镜像仓库。调查步骤的顺序写在一份 Markdown 提示词模板里，随内部可观测性经验的积累而扩充 [[1]](#sources)。
4. 智能体给出报告：Slack 线程中的摘要，加一份带图表的详细 HTML 报告。证据包括查询结果和代码引用。会话保持打开，便于追问，例如要求对某个假设给出更多细节或换一个时间窗口 [[1]](#sources)。
5. 🛑 **操作**：由工程师启动修复，方式是带确认对话框的按钮，或明确提及（例如“fix it”）。没有关键词自动触发 [[1]](#sources)。
6. 智能体在每次请求专属的 git worktree 中编辑代码，用完即删。推送和调用 GitHub API 的是宿主而不是智能体，因此智能体的环境中没有令牌。超出文件数和行数限制的 diff 只出报告。CI 配置、基础设施定义和锁文件默认被屏蔽。PR 正文会注明由 AI 生成，并写明 Sentry issue 和请求人 [[1]](#sources)。
7. 🛑 **审阅**：PR 始终是草稿，不自动合并。由人审阅并标记为就绪 [[1]](#sources)。

**产出：** 告警线程中一份有证据支撑的根因报告，以及可选的、带防护的草稿修复 PR，供人工审阅。
**失败模式 → 防护：** 没人记得有这个机器人 → 每条告警都主动发出按钮。在无法分析的告警上白点 → 只有能提取出 issue ID 时才显示按钮。随提示词或模型变化，调查质量漂移 → 正在设计评测框架。
**与相近工作流的区别：** AWF-0071 先复现的 bug 修复（Reproduce-first bug fix）从 bug 工单一路走到修复 PR，且必须先复现。这里的主要产出是由人发起的对话式调查报告，修复是另一个需主动选择的步骤。自主程度是辅助，产出物是报告，并有两次明确的人工触发。
