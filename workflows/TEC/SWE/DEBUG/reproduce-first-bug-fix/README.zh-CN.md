# 先复现再修复的缺陷处理

**工具变体：** `claude-code` · `block-moneybot-autoheal` · `sentry-seer-cursor-agents` · `claude-agent-sdk-str-fix` · `claude-routines`

## 背景

用户报告软件产品出了故障，工程师就要把这份报告变成一个修复：弄清发生了什么，有意让故障再次出现，修改代码，再证明故障已经消失。难点往往不在改动，而在证明。一个只是偶尔出现的故障，碰巧跑通一次就可能看起来已经修好；一个从没亲眼见过故障就做的改动，修的可能是别的东西。在这个工作流里，智能体必须先复现故障才能动代码，在改动前后测量失败的频率，并把复现保留为一个永久测试。复现不了，它就停下来，把工单交给人。每一项改动仍由工程师评审并决定是否上线，因为产品的行为由他们负责，而合并意味着改动会直接到达客户面前。

**术语：**
- **工单**：在团队的工单系统（例如 Jira）里登记的故障报告，或错误跟踪工具（例如 Sentry）里的一个 issue 分组。
- **复现（repro）**：在受控条件下让报告的故障再次发生；repro 指做到这一点的测试或脚本。
- **基线**：改动之前复现失败的频率，通过多次运行测得。
- **非确定性（不稳定）故障**：有时出现、有时不出现的故障，在基于语言模型的产品中很常见。
- **评测用例（eval case）**：针对语言模型产品的测试，为整段对话打分，常由另一个模型充当评判。
- **fixture、合成数据**：固定的、编造的输入（固定的时钟、虚构的账户余额），让测试可以重复运行，而不用真实的客户数据。
- **staging**：用于测试的生产环境副本；一次性的 staging 为一张工单创建，用完即删。
- **git worktree**：仓库的另一份独立工作副本，修复时不会影响主工作目录。
- **回归测试**：保留在代码里的测试，确保修好的故障不会悄无声息地再次出现。
- **git blame**：记录每一行代码最后由谁修改，这里用来挑选审阅人。
- **PR（pull request，拉取请求）、CI**：公开出来供评审的改动提议；CI 是在它上面自动运行的检查。
- **预生产环境**：发布前的最后一个测试环境。

## 用智能体搭建

**形态：** `project`。流程可以由 skill 承载，但“没有复现就不改产品代码”这条规则必须每次都成立，诊断要在单独的工作者里进行，而且智能体必须无法合并。这些需要子智能体和权限规则。[套件](variants/claude-code.md)把这套搭建方式写成了文件。

**需要：** 对工单系统的读取权限（`gh` 或工单系统的 MCP 服务器）；一个能把同一个测试运行多次的测试命令；一份 `CLAUDE.md`，写明样本量、尝试次数上限和 staging 命令；如果故障只在 staging 里出现，还需要一个一次性的 staging 环境。缺陷报告和日志里可能含有个人数据：复现只用合成数据，绝不要把生产数据或凭据拷进 fixture。

| 步骤 | 搭建方式 |
|---|---|
| 缺陷工单 → 复现（基线运行）+ 诊断 | skill 读取工单，写出复现并运行以取得基线；与此同时，一个自定义的只读诊断子智能体写出发生了什么、一个可行的修复以及长期的理想方案。 |
| 未复现：🛑 handoff | skill 停下，交出一份缺陷文件：试过什么、诊断结论、为什么没能复现。 |
| 已复现：在隔离的 worktree 中修复 → (修复 ⟲ 在 staging 重跑同一复现) | skill 创建 git worktree，应用修复，用相同次数重跑同一个复现，直到尝试次数上限。部署到 staging 之前由权限规则询问。 |
| 开修复 PR + 回归测试 PR → 按 git blame 选审阅人 | skill 准备两个拉取请求，附上修复前后的数字，并根据 `git blame` 建议审阅人。`git push`、`gh pr create` 以及任何工单评论之前都由权限规则询问。 |
| 🛑 review → 合并 | 见“检查点”。 |

**检查点：** `handoff`：复现始终不失败时，skill 交出缺陷文件后停下；智能体不改任何产品代码，只有人批准后才会在工单上发说明。`review`：拉取请求准备好后 skill 停下。`gh pr merge` 被权限规则禁止，智能体也没有关闭工单的工具，所以合并和关闭工单都留给工程师。

**与来源相比：** 来源出自 2026-08 到 2026-11；来源 2 未注明日期。4 个来源中有 3 个是在工单队列上无人值守地运行这些步骤：Block 由一个编排智能体带 6 个子智能体，Cyclotron 每晚为每个 Sentry issue 分组派出一个云端智能体，Sentry 用的是自家的 autofix。上面的搭建方式是交互式版本，一个会话处理一张工单，与套件写法一致。如果团队希望按计划清理积压，可以把同一个 skill 以 `service` 的形态运行（云端定时任务或 Agent SDK），把接手项和完成的拉取请求发到队列；Duolingo 的来源称其智能体是在 Claude Agent SDK 上构建的。“近期实践”中提醒审阅人的例行任务用的是 Claude routine，也就是本目录所说的云端定时任务（研究预览）。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 系统从工单系统接收已上报的生产问题 [[1]](#sources)（或未解决的 Sentry issue 分组，合并时采取保守策略 [[2]](#sources)）。
2. 智能体先复现：把失败的会话变成可回放的测试或评测用例，使用合成数据，并运行 10 次作为基线（只失败过一次的运行 20 次）。随时间变化的状态用 fixture 固定 [[1]](#sources)。与此同时，诊断智能体写出发生了什么、一个可行的修复方案以及长期的理想方案 [[1]](#sources)。
3. 🛑 **接手**：如果故障始终无法复现，智能体就停下来，把工单标为无法复现并搁置，交给人处理。它绝不修复无法观察到的行为 [[1]](#sources)。
4. 智能体在隔离的 git worktree 中修复，然后部署到一次性的 staging 环境，用相同的样本量重跑同一个复现。只有相对基线明显改善才接受，并将循环次数限制在有限轮内 [[1]](#sources)。在运行中的应用里做端到端 UI 验证，做法与此相同 [[2]](#sources)。
5. 智能体开两个 PR：修复，以及把复现作为永久的回归测试。它按 git blame 选审阅人，并把结果（包括失败的尝试）写回工单 [[1]](#sources)。
6. 🛑 **审阅**：工程师评审变更并决定哪些上线。合并和关闭工单仍由人来操作 [[1]](#sources)。智能体的 PR 先通过 CI 和机器人评审，再到预生产环境交由人做最终评审 [[2]](#sources)。

**产出：** 一个已合并的修复，加上由真实故障构建的回归测试；工单更新为处理结果，或搁置交给人。
**失败模式 → 防护：** 不稳定或非确定性的缺陷在通过一次运行后看似已修复 → 重复采样，并对比修复前后相同的样本量 [[1]](#sources)。对报告中的确切措辞过拟合 → 增加一个措辞不同的参考性第二用例 [[1]](#sources)。无限循环 → 设置上限，不可逆的操作由人掌握 [[1]](#sources)。修复忽略仓库规范 → 编码前增加一个功能调研步骤 [[3]](#sources)。
**与相近工作流的区别：** AWF-0003 委派式 PR 从带标签的 issue 出发，以现有测试为关卡。本工作流从原始缺陷报告出发，增加了“先复现，否则搁置”的关卡和对同一复现的修复前后对比，并交付一个新的回归测试。AWF-0004 先分诊再修复通过运维手册处理线上事故，而不是修改代码。

**近期实践（2026）：**
- 审阅人步骤：一个无人值守的例行任务按计划运行，取出最近四小时内无人处理的修复 PR，找到与根因代码接触最多的工程师，确认 PR 仍处于打开状态，然后提醒他合并或关闭、给出一句反馈，并说明这个修复是否值得用智能体来做。它从不重复发帖，也避免在周末发提醒（Sentry）。[[4]](#sources)

## 公开实例

覆盖度（截至 2026-11-06）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [New workflows for empty categories](../../../../../research/2026-11-new-workflows.md)。更多实例补充于 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [Block, Autohealing Moneybot](https://engineering.block.xyz/blog/autohealing-moneybot) (2026-08-28)。6 个子智能体负责复现、诊断、修复，并在 staging 中验证，然后提交修复 PR 和评测 PR 交由人评审。"more than 40 verified fixes"。*第一手：是；可信度：高。*
- [Cyclotron, Closed-Loop Engineering System](https://cyclotron.com/post/how-i-built-a-closed-loop-engineering-system-that-saved-840-hours-in-30-days/) (2026)。Sentry issue → Cursor 智能体复现、修复、端到端验证 → PR → 在预生产环境由人评审。共开出 472 个智能体 PR，合并 410 个（"86.9% merge rate"）。*第一手：厂商（作者在公司自己的产品上运行）；可信度：中。*
- [Duolingo, AI bug-fixing agent](https://blog.duolingo.com/ai-bug-fixing-agent/) (2026-11-04)。摇一摇上报的 Jira 工单 → 上下文、复现步骤、修复、自我评审、CI 修复、供验证的 beta 构建。*第一手：是；可信度：中。*
- [Sentry, How we built an automated debugging workflow at Sentry](https://blog.sentry.io/automated-debugging-workflow-sentry/) (2026-08-06)。Seer autofix 提交 PR；每小时运行的例行任务根据提交历史选出审阅人，并提醒其合并或关闭。"About a 21% increase in the action rate on PRs"。*第一手：厂商；可信度：中。*
