# 分级打分的 PR 评论

**工具变体：** [`claude-code` kit](variants/claude-code.md) · `ureview` · `coderabbit` · `github-copilot-code-review` · `graphite-diamond`

## 背景

一项对共享代码的改动在合并之前，会有同事阅读 diff（改动增加和删除的那些行），并就问题留下评论：一个缺陷、违反团队规范之处、一个安全漏洞。人工评审慢，而且不同评审者发现问题的多少并不一样。这里由智能体在改动一提交时就读完每个 diff，并在人工评审者旁边发布自己的评审评论。机器写的评论有不少是噪音，所以每条评论都要打置信度分，把把握不大的先剔除，不让人看到。改动的作者仍要阅读每条评论，标为有用或无用，并决定是否处理，因为只有作者清楚这次改动的意图，而智能体的评论是建议，不是定论。

**术语：**
- **diff**：一次改动增加和删除的那些行；在 Uber，它是评审的单位。
- **PR（pull request，拉取请求）**：一项提议的改动，先发布出来供人评审，再合并进共享代码。
- **CI**：每次提交改动时自动运行的检查。
- **置信度打分**：用第二轮提示词对草稿评论评分，估计它是否正确、是否值得工程师花时间。
- **去重**：把说的是同一件事的评论合并。
- **AppSec**：应用安全，即在代码中查找漏洞的工作。
- **精确率和召回率**：发布的评论中正确的比例；实际存在的问题中被发现的比例。
- **已处理率**：已发布的评论中，改动最终版本不再触发的比例。

## 用智能体搭建

**形态：** `service`。来源在 CI 中对每个提交运行，键盘前没有人，作者只看到发布出来的评论。交互式的[套件](variants/claude-code.md)按需运行同样的步骤，发布前先确认，更适合 `project` 形态的搭建；在接入 CI 之前，可以先从它开始。

**需要：** 新建或更新拉取请求时的触发器（调用 `claude -p` 的 CI 任务，或 Agent SDK 程序）；对仓库和拉取请求的读取权限；发布评审评论的权限，但没有批准、合并、推送或关闭讨论串的权限；供最佳实践审阅者使用的 `CLAUDE.md` 或规范文档；一份列出要跳过的文件、各类别阈值和要屏蔽的类别的配置文件；一个存放评价和指标的存储。把拉取请求的文字和代码当作要读的数据，而不是指令。

| 步骤 | 搭建方式 |
|---|---|
| diff → 过滤符合条件的文件 → 构建上下文 | 运行中的一个脚本丢掉配置文件、生成的代码和实验性目录，然后为每个文件写出一份包含附近函数、类和 import 的上下文包。 |
| 各助手起草评论 | 三个只读子智能体（缺陷、最佳实践、安全）在上下文包上并行运行，以结构化行的形式返回评论。 |
| 置信度打分 → 去重 → 剔除低价值类别 | skill 中单独的一轮打分，然后由脚本按配置文件中的阈值剪枝、合并重叠项并移除被屏蔽的类别。 |
| 以行内评论发布 | 一个使用 MCP 连接器或代码托管平台命令行工具的步骤，只发布一份仅含评论的评审。 |
| 🛑 review | 作者在代码托管平台上给每条评论评价；评价写入存储。 |
| 在最终提交上重跑 5 次以衡量是否已处理 | 对最终提交以无头方式再把同一个 skill 运行 5 次，不发布，并与已发布的评论比对。 |

**检查点：** `review`：这次运行唯一的产出是拉取请求上的评论。智能体没有批准、合并、推送修复或关闭讨论串的工具，审阅者也是只读的，所以由作者决定如何处理每条评论。评价只有在人同意修改之后才会回写到配置文件。

**与来源相比：** 唯一的来源和公开实例，即 Uber 的博客文章，出自 2025-08。文章报告的是一条模型调用流水线，打分和去重各是独立阶段，搭建方式把它保留为 skill、子智能体和脚本；它不是一个自行决定步骤的智能体。2026-11 的搜索没有找到关于 uReview 的更新记述，只提到一个为评论提出代码修改的后续组件，没有打开阅读。搜索还显示有一项由 Anthropic 托管的评审功能，文档见[文档页面](https://code.claude.com/docs/en/code-review)，据报道于 2026-03 推出；它只在搜索结果中看到，没有打开阅读，上面的搭建方式也不依赖它。来源页面本身在本次检查中无法打开（会话网络屏蔽了该站点）。搭建方式没有包含 Uber 的人工标注基准，也没有在推广到新语言前设关卡，只在套件中作为可选步骤出现。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 对每个 diff，跳过配置文件、生成的代码和实验性目录。用附近的函数、类定义和 import 构建提示词 [[1]](#sources)。
2. 并行运行各专门的助手：Standard（缺陷、异常处理、逻辑）、Best Practices（内部规范）和 AppSec（安全漏洞）[[1]](#sources)。
3. 第二个提示词为每条评论的置信度打分。按助手、语言和类别分别设定阈值来剪枝。用语义相似度过滤器合并重叠的评论。屏蔽历史上对开发者价值较低的类别 [[1]](#sources)。
4. 把留下的评论以行内评论的形式发布到评审平台，每个提交在 CI 中的耗时中位数为 4 分钟 [[1]](#sources)。
5. 🛑 **审阅**：作者把每条评论标为有用或无用，并决定是否处理。评价数据流入数据仓库，用于重新调整阈值 [[1]](#sources)。
6. 度量：在最终提交上把评审器重跑 5 次。如果没有任何一次重跑复现某条评论，就算它已被处理。对照人工标注的基准跟踪精确率和召回率，并以这些数字作为推广的关卡 [[1]](#sources)。

**产出：** 每个 PR 上与人工评审并行的行内评审评论，有用率和已处理率这两项指标会反馈用于调整阈值。
**失败模式 → 防护：** 嘈杂、低价值的评论损害信任 → 分类别的置信度阈值、去重，并屏蔽历史表现差的类别；在有用率持续偏高之前，暂缓推广到新语言 [[1]](#sources)。
**与相近工作流的区别：** AWF-0003 委派式 PR 是在智能体自己的编写循环内使用机器人评审。本工作流评审全公司每一个由人编写的 diff，产出的是评论而不是代码。

## 公开实例

覆盖度（截至 2026-11-06）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [New workflows for empty categories](../../../../../research/2026-11-new-workflows.md)。

- [Uber, uReview](https://www.uber.com/us/en/blog/ureview/) (2025-08-12)。三个助手、一个打分器和一个去重过滤器发布行内评论；已处理率与人工评论对比衡量。"Engineers who interact with the tool mark 75% of its comments as useful"; 65% addressed vs 51% for human comments。*第一手：是；可信度：高。*
