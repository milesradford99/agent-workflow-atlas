# 按风险自动批准 PR

**工具变体：** `custom-harness` · `aws-bedrock` · `claude`

## 背景

多数公司要求，对共享代码的改动在合并之前，要由作者之外的人批准；改动以拉取请求（PR）的形式提出。评审者都很忙，哪怕只改一行文档，也可能要排队等待。这里先由一套固定规则判断某个 PR 是否属于可以不经人批准的类型，比如看它改动了哪些目录、有多大。只有通过之后，智能体才会阅读它，并给出批准或让开的结论。规则或智能体拿不准的，一律像以前一样交给人工评审者。即使是获批的 PR，人也仍在环节里：作者负责合并、观察变更上线，必要时回滚，因为作者仍要承担责任，而一次错误的批准可能触及真实用户。

**术语：**
- **PR（pull request，拉取请求）**：一项提议的改动，先发布出来供人评审，再合并进共享代码。
- **路径策略**：一份文件，列明哪些目录和文件类型可以自动批准，哪些必须由人处理。
- **CODEOWNERS**：一份文件，写明每部分代码由哪些人负责。
- **Terraform**：描述公司云基础设施的代码；改动它可能改变线上系统。
- **迁移**：对数据库结构的改动。
- **功能开关（feature flag）**：不需要重新发版，就能在运行中的产品里打开或关闭某项功能的开关。
- **仿冒包名（typosquatting）**：用模仿热门软件包的名字发布软件包，诱骗人安装。
- **堆叠 PR**：几个前后依赖、层层叠加的 PR。
- **锚定评论**：PR 上用来放结论及其推理的那一条评论。
- **回测**：把改过的提示词放到结果已知的过往 PR 上重跑，看结论是否有变化。

## 用智能体搭建

**形态：** `service`。PR 被打开就启动一次运行，键盘前没有人，人只看到被跳过的 PR 和带标签的批准。

**需要：** PR 事件的触发器（调用 `claude -p` 的 CI 任务，或 Agent SDK 程序）；每个仓库一份路径策略文件；通过 MCP 服务器或脚本提供的一小组只读工具（某个提交处的文件、依赖检查、工单文字、日志、功能开关状态）；一个可以发布批准和评论、但没有合并权限的机器人账号；一个存放结论和审计日志的存储；一批已标注的过往 PR 用于回测。不要给智能体 shell，也不要让它检出代码。

| 步骤 | 搭建方式 |
|---|---|
| PR 打开 → 确定性资格检查 | 触发器中的一个脚本检查路径策略、大小上限、基础分支和标签，任何一项不通过就跳过该 PR，不调用智能体。 |
| 智能体：读取文件 + 检查依赖、开关、日志、工单 | 以无头方式运行的一个 skill，只有读取工具和一个提交结论的工具；PR 文字被当作数据。变体中，内置子智能体各自从一个角度评审。 |
| 提交 approve 或 skip | 结论工具要求固定格式（approve 或 skip，附理由）。没有结论或预算耗尽，都算 skip。 |
| approve：机器人批准，任何不可批准的文件都会阻止 | 智能体之外的一个脚本，对每个改动的文件按路径策略重新检查，通过后才由机器人账号发布批准。 |
| 🛑 action (作者合并，观察发布) | 锚定评论和标签告诉作者该 PR 已获批准；由作者合并。 |
| skip：🛑 review (人工评审者) | PR 保持未批准状态，进入正常的评审队列。 |
| 错误批准：修正提示词 + 在过往 PR 上回测 | 在接受提示词改动之前，skill 先在已标注的过往 PR（包括那次错误批准）上重跑一遍。 |

**检查点：** `action`：智能体没有合并工具，批准由脚本在路径策略检查通过之后才发布，所以无论智能体怎么判断，策略之外的文件都不可能被批准；由作者合并并负责上线。`review`：被跳过的 PR 就是不予批准，所以通常的人工评审者会接手。因为批准正是让改动触达用户的关键，路径策略检查和发布批准要放在智能体的工具之外，而不是写在 skill 的文字里。

**与来源相比：** 来源出自 2026-04 到 2026-10。来源描述的是一套带有基于 API 的工具和批准机器人的自建框架；上面的搭建方式是同样的安排，用无头运行、skill、子智能体和脚本来实现。这次检查时两个来源都能打开，并支持各自被引用的步骤。Clipboard 的文章（2026-10-12）描述了按仓库设置的策略文件、以 `submit_review` 工具调用给出的批准或跳过结论、没有 shell 也没有检出、最后的确定性检查、锚定评论，以及对已标注的过往 PR 做的评测；它运行的是自己围绕模型 API 写的循环。Intercom 的文章（2026-04-21）描述了独立的子智能体、拒绝大型 PR、合并后作者仍负责、可以对任何改动要求人工评审，以及对 AI 批准的 PR 打标签、可查询的记录。Intercom 用独立子智能体的变体作为可选项保留，不是默认做法。本搭建方式没有设定阈值或大小上限，它们属于各仓库的路径策略。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 先过确定性门槛。每个仓库一份策略文件，把路径通配符映射到标记为可批准或不可批准的类别（CI、CODEOWNERS、Terraform、认证和迁移必须由人处理）。其他设置涵盖草稿、标签、堆叠 PR 以及改动行数上限 [[1]](#sources)。
2. 智能体用一组固定的、基于 API 的工具进行评审，没有 shell，也不检出代码：读取该提交处的文件、检查依赖（漏洞、仿冒包名、存续时间）、工单上下文、日志/指标、跨仓库搜索以及在线功能开关状态。PR 内容被当作数据，而不是指令 [[1]](#sources)。
3. 结论是一次有 schema 的 `submit_review` 工具调用（approve 或 skip，附理由）。没有结论或工具预算耗尽，都视为 skip。最后一道确定性检查会在任何文件不可批准时拒绝批准 [[1]](#sources)。
4. 变体：独立的子智能体各自从一个角度评审（问题陈述、意图与 diff、安全、逻辑、最佳实践），过大的 PR 会被拒绝，让作者拆分 [[2]](#sources)。
5. 🛑 **操作**：获批后由作者合并并继续负责。他们观察变更上线，必要时回滚。任何工程师都可以对任何变更请求人工评审 [[2]](#sources)。
6. 🛑 **审阅**：被跳过的 PR 交给人工评审者 [[1]](#sources)。
7. 每个结论连同其推理、读取过的文件和每次工具调用，发布在一条锚定评论中。AI 批准的 PR 带有标签，被记录且可供审计查询 [[1]](#sources)[[2]](#sources)。
8. 基于已标注的过往 PR 的评测为每次提示词改动把关。一次错误批准会成为一个回测用例 [[1]](#sources)。

**产出：** 每个 PR 都有一个批准（或转交人工的跳过）决定，附可审计的推理评论。低风险 PR 无需人工评审即可合并。
**失败模式 → 防护：** 机器人跳过了需要的工具，批准了引发 bug 的 PR → 修正提示词，并在包括那次错误批准在内的过往 PR 上回测 [1]。作者钻空子 → 客观的确定性门槛。在量大时走过场 → 智能体拒绝过大的 PR [2]。
**与相近工作流的区别：** AWF-0070 分级 PR 评论（Graded PR comments）和 AWF-0133 评论转编辑建议（Comment-to-edit suggestions）都是添加评论，每个 PR 仍由人批准。这里智能体的输出就是批准决定本身，低风险 PR 不需要人工评审者参与。自主程度和检查点安排都发生了变化。

## 公开实例

覆盖度（截至 2026-11-13）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [Intercom, AI is approving our pull requests](https://www.intercom.com/blog/ai-is-approving-our-pull-requests-heres-how-we-made-it-safe) (2026-04-21)。先试点再推广的子智能体评审，无需人工评审者即可批准 PR。"In the first four weeks of broader rollout, 497 PRs went fully autonomous"。*第一手：是；可信度：高。*
