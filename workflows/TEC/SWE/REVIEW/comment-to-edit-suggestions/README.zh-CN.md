# 评论转修改建议

**工具变体：** `google-critique-ml-edits`

## 背景

在代码评审中，一位开发者（作者）提出对共享代码的改动，另一位同事（评审者）阅读后留下评论，比如“改个名字”或“处理空列表的情况”。作者随后要把每条评论落实成修改，这类修改往往很小、很机械，却仍要在两个人之间来回一趟。这里评论仍由评审者撰写；智能体起草能解决该评论的修改，并展示给作者。作者必须逐条查看并决定是否应用，因为改动由作者负责，而一条看似合理的修改仍可能有错，或与其他改动冲突。

**术语：**
- **diff**：一次改动增加和删除的那些行。
- **评审工具 / IDE**：评审者对改动留评论的网页，以及作者写代码用的编辑器。
- **精确率**：展示出来的建议中正确的比例。
- **三方合并**：以原文件为共同基础，把建议的修改与作者对同几行所做的较新修改合在一起。
- **展示过滤规则**：决定哪些起草的修改展示给作者、哪些扣下的规则。

## 用智能体搭建

**形态：** `skill`。一位作者一次处理一项改动的评论，并留在对话里，所以一个 skill 就够了。

**需要：** 被评审分支的检出副本；评审者的评论文本，可来自代码托管平台的命令行工具或 MCP 服务器，也可以直接粘贴；项目的测试命令。智能体不需要推送或在评审中回复的权限。

| 步骤 | 搭建方式 |
|---|---|
| 评审者写评论 | 由人在代码托管平台上写；skill 读取这项改动上的评论。 |
| 模型起草建议修改 | skill 一次取一条评论，读取被评论的行及其上下文，以 diff 的形式提出修改。 |
| 置信度 + 启发式过滤 | skill 的指令：丢弃属于提问、要求讨论设计或意思不清的评论，并说明原因；其余的标为可处理。 |
| 在评审工具 / IDE 中展示 → 🛑 action | skill 在对话中展示每个 diff 并停下。文件修改由设为“询问”的权限规则覆盖。 |
| 有用度评分 → 汇总反馈 → 新的展示过滤规则 | 由人指出哪些修改没有帮助；skill 把对应模式追加到身边的过滤规则文件中，由人批准。 |

**检查点：** `action`：skill 展示 diff 后停下，文件修改受询问规则约束，所以在作者同意之前不会往工作区写入任何内容。智能体没有推送或关闭评论的工具，这些由作者在代码托管平台上完成。

**与来源相比：** 唯一的来源是 Google 的一篇研究博客，出自 2023-05，距本次检查已超过 12 个月。该系统用基于过往评论和修改微调的模型，并依据记录下来的反馈调整过滤规则；上面的搭建方式用的是通用智能体加书面过滤规则，没有复现微调和使用记录。Meta 的 MetaMateCR 是针对同一任务的生产系统，见 2025-07 的 arXiv 论文（[MetaMateCR paper](https://arxiv.org/html/2507.13499v1)）；它只在搜索结果中看到，没有打开阅读。来源页面本身在本次检查中无法打开（会话网络屏蔽了该站点）。没有打开其他记述。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 评审者在一次代码改动上留下自然语言评论。[[1]](#sources)
2. 系统根据代码改动和评论构建模型输入。一个基于过往评论及作者针对评论所做修改而微调的模型，起草建议修改。[[1]](#sources)
3. 只有在模型有把握且展示启发式规则通过时，才显示建议。目标精确率是 50%。[[1]](#sources)
4. 🛑 **操作**：作者在评审工具或 IDE 中预览修改，并决定是否应用。冲突通过三方合并视图处理。[[1]](#sources)
5. 作者给建议打分（'Was this helpful?'）。预览和应用事件会被汇总，反复出现的失败模式会变成新的展示过滤规则。[[1]](#sources)

**产出：** 评审评论通过作者应用的修改得到解决，缩短了从评审到提交的时间。
**失败模式 → 防护：** 低精确率的建议侵蚀信任 → 置信度阈值加启发式规则。与本地修改冲突 → 三方合并。反复出现的糟糕模式 → 从“没有帮助”的反馈中挖掘成过滤规则。
**与相近工作流的区别：** AWF-0070 分级的 PR 评论：AWF-0070 由 AI 撰写评审评论，供作者打分。本工作流中，评论由人类评审者撰写，AI 起草解决该评论的代码改动，作者必须逐个应用修改（辅助，而非抽检）。
