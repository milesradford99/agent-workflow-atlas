# 先合并规格再由代理开发

**与相近工作流的区别：** AWF-0001 计划把关式开发（Plan-gated build）中，由一位开发者批准智能体的计划，并由人审阅每个 PR。这里是团队以 PR 的形式审阅并合并规格，事实核查和唱反调的智能体在签发前运行，大多数代码 PR 在 Slack 上一键批准后即合并，无人阅读 diff。检查点和审阅对象都变了。
**工具变体：** `claude-code-skills` · `github-spec-kit` · `kiro`

## 步骤

1. 套用经验法则：如果一项变更包含别人可能不同意的决策，就要先有计划。依赖升级、原因明确的 bug 修复，以及已商定计划内的小改动，不走这个工作流 [[1]](#sources)。
2. `/grill-me`：智能体把计划当作决策树逐一走查。它尽可能多地提问，为每个问题给出推荐答案，并自己查证事实。🛑 **计划**：人来回答，最好结对或集体进行，在自己掌握背景的地方推翻推荐答案。每一轮问答都会记录 [[1]](#sources)。
3. `/to-spec` 把对话整理成 SPEC.md。这是实现智能体依据的唯一来源，其中包含测试门槛（定义“完成”的验收场景）[[1]](#sources)。
4. `/ground-truth` 提取所有关于已有事物（API、配置值、开关、截止日期）的论断，并对照真实代码的克隆或一手来源并行核实每一条。不一致之处会被修正并标注出处 [[1]](#sources)。
5. `/contrarian` 查找是否已有东西覆盖了这个问题，并给出 BUILD、SIMPLIFY 或 KILL 的裁决。只要不是 BUILD，计划就回到追问环节 [[1]](#sources)。
6. `/to-website` 把规格渲染成带图表的 HTML 页面，并附有指向调研、事实核查和裁决的一键链接。🛑 **签发**：计划目录是一个 pull request，由团队讨论并合并。审阅通常持续一两天 [[1]](#sources)。
7. 智能体依据规格实现，并在本地环境（agentlab）中测试、自审自己的改动，然后才开 PR [[1]](#sources)。
8. 代码 PR 以简短摘要的形式发到 Slack。🛑 **操作**：团队里任何人都可以一键批准，大多数变更无人阅读 diff 即合并。🛑 **审阅**：当计划表明变更涉及公开 API 或与安全相关的内容时，由人阅读 PR [[1]](#sources)。

**产出：** git 中一份经确认、带版本的计划目录（规格、事实核查、唱反调裁决、审阅页面），以及依据其测试门槛合并的、由智能体实现的代码 PR。
**失败模式 → 防护：** 错误前提在追问和规格中被保留下来 → 唱反调步骤是在人工审阅者发现一例之后加入的。幻觉出的配置键 → ground-truth 发现 8 条论断中有 7 条成立，并标出了第 8 条。计划在实测中破产 → 计划只是基线：会被重写、替换或放弃。
