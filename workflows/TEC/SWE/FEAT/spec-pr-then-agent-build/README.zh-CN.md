# 先合并规格再由代理开发

**工具变体：** `claude-code-skills` · `github-spec-kit` · `kiro`

## 背景

当团队的大部分代码都由编码智能体来写，改动就多到没人能逐行读完。这个工作流把团队的注意力从写好的代码移到计划上。凡是涉及别人可能不同意的决策，在动手之前，智能体先追问提出需求的人，把计划写成一份规格，对照真实代码核查其中每一条事实性论断，还要专门论证一下是不是根本不必做。然后团队讨论并批准这份规格，智能体依据它来实现，规格里定义的验收测试就是“完成”的含义。做什么、不做什么，这些决定留在人手里，因为智能体缺少产品背景和对客户的了解。凡是出错会影响外部用户或打开安全漏洞的地方，人仍然要亲自读代码。

**术语：**
- **规格（SPEC.md）**：实现智能体所依据的书面计划，其中写明怎样才算完成。
- **追问（grilling）**：智能体就计划尽可能多地提问、每个问题附一个推荐答案，由人来回答或推翻的访谈。
- **结对或集体规划**：两个人或整个小组一起回答这些问题。
- **事实核查（ground truth）**：把规格中关于已有事物（API、配置值、开关、截止日期）的每条论断，对照代码或一手来源进行核实。
- **唱反调裁决**：查找是否已有东西解决了这个问题，并给出 BUILD、SIMPLIFY 或 KILL 的步骤。
- **验收场景（测试门槛）**：规格指定的测试；全部通过就表示工作完成。
- **PR（pull request，拉取请求）**：一份提议的改动，在合并之前公开出来供评审；这里规格和代码都以 PR 的形式提交。
- **diff**：一次改动新增和删除的那些代码行。
- **公开 API**：其他团队或客户调用的接口；改动它可能让他们的代码出错。
- **幻觉**：模型信心十足却不真实的论断，例如一个并不存在的配置键。

## 用智能体搭建

**形态：** `project`。规划步骤由几个相互传递文件的 skill 组成，事实核查需要并行的工作者，唱反调的一方必须是没见过追问过程的审阅者；此外，“哪些代码改动必须有人读 diff”这条规则也必须每次都成立。

**需要：** 一个规划用的仓库或文件夹，每份计划一个目录；对计划涉及的代码克隆的读取权限；一份 `CLAUDE.md`，列出哪些路径属于公开 API 或与安全相关；验收场景的测试命令；如果要把摘要发到 Slack，还需要 Slack 连接器；`gh` 命令行工具。

| 步骤 | 搭建方式 |
|---|---|
| 涉及决策的变更 → 智能体追问（问题 + 推荐答案）→ 🛑 plan (人回答或推翻) | 一个追问 skill：把计划当作决策树逐一走查，每次问一个问题并附推荐答案，自己查证事实，并把每个问题和答案记录到计划目录中。 |
| SPEC.md | 一个规格 skill 把记录整理成带验收场景的 `SPEC.md`。 |
| 每个论断：对照真实代码核对 | 事实核查 skill 列出每条关于已有事物的论断，交给内置子智能体，各自对照克隆的代码或一手来源核实。 |
| 唱反调裁决 → SIMPLIFY 或 KILL：回到追问 \| BUILD：生成审阅页面 | 一个自定义的只读子智能体，只拿到规格和代码，从不接触追问过程，返回 BUILD、SIMPLIFY 或 KILL 并说明理由。裁决为 BUILD 时，由一个 skill 把规格及其依据渲染成一个 HTML 页面。 |
| 🛑 sign-off (团队合并规格 PR) | 智能体把计划目录作为 PR 提交。禁止合并。 |
| 智能体 (实现 ⟲ 测试 + 对照验收场景自审)→ 代码 PR | 实现本身，按 [AWF-0001 Plan-gated build](../plan-gated-build/) 的方式进行，以验收场景作为要通过的测试，再由一个审阅子智能体对照规格检查 diff。 |
| Slack 摘要 → 常规：🛑 action (一键批准) \| 公开 API 或安全相关：🛑 review (阅读 diff) | skill 通过 Slack 连接器发出简短摘要。`gh pr create` 上的 `PreToolUse` 钩子把改动的文件与所列路径对照，并加上一个要求审阅 diff 的标签。 |

**检查点：** `plan`：追问 skill 每问一个问题就等回答，在人回答或推翻所有问题之前不写规格。`sign-off`：规格以 PR 的形式交给团队，智能体没有合并权限，所以只有团队合并之后才开始实现。`action`：常规的代码 PR 由人在代码托管平台上批准；智能体不能合并自己的成果。`review`：钩子发现涉及公开 API 或安全相关路径时，标签会提示审阅人阅读 diff；应在代码托管平台的分支规则里要求合并前必须完成这项审阅。

**与来源相比：** 来源 1 及其公开实例出自 2026-10。来源称整个工作流以 skill 的形式放在仓库里，一条命令就能按顺序跑完各个规划步骤，团队也已将其开源；上面的搭建方式沿用了同样的 skill 划分。有两样来源自建的东西没有包括在内：Slack 里的一键批准，以及 agentlab，也就是智能体在开 PR 之前试运行改动的本地环境。在来源中，大多数代码改动无人阅读 diff 就合并了；本搭建方式在每个代码 PR 上都保留了人的批准，因为批准智能体成果的不应是智能体自己。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 团队套用经验法则：如果一项变更包含别人可能不同意的决策，就要先有计划。依赖升级、原因明确的 bug 修复，以及已商定计划内的小改动，不走这个工作流 [[1]](#sources)。
2. 在 `/grill-me` 中，智能体把计划当作决策树逐一走查。它尽可能多地提问，为每个问题给出推荐答案，并自己查证事实。🛑 **计划**：人来回答，最好结对或集体进行，在自己掌握背景的地方推翻推荐答案。每一轮问答都会记录 [[1]](#sources)。
3. 在 `/to-spec` 中，智能体把对话整理成 SPEC.md。这是实现智能体依据的唯一来源，其中包含测试门槛（定义“完成”的验收场景）[[1]](#sources)。
4. 在 `/ground-truth` 中，智能体提取所有关于已有事物（API、配置值、开关、截止日期）的论断，并对照真实代码的克隆或一手来源并行核实每一条。不一致之处会被修正并标注出处 [[1]](#sources)。
5. 在 `/contrarian` 中，智能体查找是否已有东西覆盖了这个问题，并给出 BUILD、SIMPLIFY 或 KILL 的裁决。只要不是 BUILD，计划就回到追问环节 [[1]](#sources)。
6. 在 `/to-website` 中，智能体把规格渲染成带图表的 HTML 页面，并附有指向调研、事实核查和裁决的一键链接。🛑 **签发**：计划目录是一个 pull request，由团队讨论并合并。审阅通常持续一两天 [[1]](#sources)。
7. 智能体依据规格实现，并在本地环境（agentlab）中测试、自审自己的改动，然后才开 PR [[1]](#sources)。
8. 系统把代码 PR 以简短摘要的形式发到 Slack。🛑 **操作**：团队里任何人都可以一键批准，大多数变更无人阅读 diff 即合并。🛑 **审阅**：当计划表明变更涉及公开 API 或与安全相关的内容时，由人阅读 PR [[1]](#sources)。

**产出：** git 中一份经确认、带版本的计划目录（规格、事实核查、唱反调裁决、审阅页面），以及依据其测试门槛合并的、由智能体实现的代码 PR。
**失败模式 → 防护：** 错误前提在追问和规格中被保留下来 → 唱反调步骤是在人工审阅者发现一例之后加入的。幻觉出的配置键 → ground-truth 发现 8 条论断中有 7 条成立，并标出了第 8 条。计划在实测中破产 → 计划只是基线：会被重写、替换或放弃。
**与相近工作流的区别：** AWF-0001 计划把关式开发（Plan-gated build）中，由一位开发者批准智能体的计划，并由人审阅每个 PR。这里是团队以 PR 的形式审阅并合并规格，事实核查和唱反调的智能体在签发前运行，大多数代码 PR 在 Slack 上一键批准后即合并，无人阅读 diff。检查点和审阅对象都变了。
