# 先审计划再开发

## 背景

按一份书面需求做出一个功能或修复，是软件工作最日常的单位。开发者读需求、找到相关代码、修改、证明改动有效，再请同事评审。编码智能体可以完成阅读、编写和测试，但放任不管时，它可能解决的是一个与需求略有出入的问题，或者没有证据就报告成功。这个工作流把人放在三个位置上，这三处要么纠错成本最低，要么漏掉的代价最高：动手写代码之前的计划；成果离开开发者机器的那一刻；以及完成后的改动。先于代码写好的测试给了智能体一个“通过或不通过”的检查，让它能在这几个点之间自行纠正。

**术语：**
- **议题（issue）**：一份书面的改动请求，存放在 GitHub Issues 之类的工单系统里。
- **验收标准**：改动要满足哪些条件才算完成。
- **失败测试**：在写代码之前写的测试，功能实现之前一直失败；它通过了，就说明这条标准达到了。
- **diff**：一次改动新增和删除的那些代码行。
- **PR（pull request，拉取请求）**：一份提议的改动，在合并进共享代码之前公开出来供评审。
- **CI**：每个 PR 上自动运行的检查。
- **上下文文件**：`CLAUDE.md` 或 `AGENTS.md`，智能体每次会话开始时读取的项目说明文件。

## 用智能体搭建

**形态：** `project`。流程可以由 skill 承载，但有两条规则必须每次都成立（测试写完后保持冻结；未经批准不得推送），而且评审者不能见过实现过程。这些需要钩子或权限规则，再加一个子智能体。[套件](variants/claude-code.md)把这套搭建方式写成了文件。

**需要：** 一个测试命令可用的仓库；一份 `CLAUDE.md`，写明构建、测试和 lint 命令，以及智能体不得触碰的路径；`gh` 命令行工具，或你所用工单系统的 MCP 服务器。

| 步骤 | 搭建方式 |
|---|---|
| 读取议题和代码 | skill 读取议题；内置的只读子智能体梳理受影响的模块。 |
| 制定计划 → 🛑 plan | 计划模式；或者由 skill 写出 `plans/<issue>.md` 后停下。 |
| 编写失败测试 | skill 按验收标准写测试，并运行以确认它们确实失败。 |
| (写代码 ⟲ 测试) | 在主对话中进行，以测试命令作为要通过的检查。用 `PreToolUse` 钩子拦住对已冻结测试文件的修改。如果这个循环必须强制执行，用 `Stop` 钩子重新跑测试。 |
| 全新上下文评审 | 一个自定义的只读子智能体，拿到计划文件和 diff；或者用内置的 `/code-review`，它在一个没见过这段对话的子智能体里评审。 |
| 🛑 action → 创建 PR | 权限规则设为在 `git push` 和 `gh pr create` 之前询问。 |
| 🛑 review | 由人在代码托管平台上评审 PR 和 CI。 |
| 更新上下文文件 | skill 提出要加进 `CLAUDE.md` 的内容；由人决定采纳或舍弃。 |

**检查点：** `plan`：计划模式下无法编辑文件；不用计划模式时，skill 写完计划文件就停下，并由钩子拦住对源码的修改，直到计划被标记为已批准。`action`：对推送和创建 PR 设置询问规则。交互式会话现在默认以自动模式启动，常规命令不再逐条询问，所以只有把这条规则写下来，这个停顿才存在。`review`：PR 以草稿形式创建，智能体没有合并权限。

**与来源相比：** 公开实例出自 2025 年，是用手写的提示词文件来驱动这些步骤的。计划模式、子智能体、钩子和全新上下文的评审命令现在都已内置，所以计划关卡和评审不再需要自定义提示词。“任务之间清空上下文”这条防护出自来源 2 的早期版本；现在的页面把激进的上下文管理列为可以停止遵循的建议，理由是 1M token 的上下文窗口和自动压缩，同时仍建议在不相关的任务之间使用 `/clear`。计划文件还是要保留：评审者要对照它检查 diff。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 智能体读取上下文文件、议题（`gh issue view` 或工单系统的 MCP）以及相关代码。只读的辅助智能体并行展开，梳理受影响的模块。
2. 在计划模式（只读）下，智能体写出计划：要改的文件、方案、测试策略、待确认的问题 [[2]](#sources)。🛑 **计划**：这是杠杆最高的纠偏点。
3. 智能体编写体现验收标准的失败测试，并确认它们确实失败。
4. 智能体分小步实现，每一步后运行针对性测试和类型检查。它根据失败输出循环修复，迭代次数设有上限，超过后转交给人。
5. 一个全新上下文的评审智能体对照规格检查 diff：边界情况、死代码、安全问题。
6. 对于 UI 改动，智能体启动开发服务器、截图，并与设计稿对比。
7. 🛑 **操作**：由人批准提交、推送和创建 PR，除非这些操作已被预先授权。
8. 🛑 **审阅**：由人评审 PR 和 CI 结果。
9. 智能体把反复出现的纠正意见写回上下文文件。

**产出：** 一个带测试、经过评审的 PR，以及更新后的上下文文件。
**失败模式 → 防护：** 智能体为了让测试通过而改测试 → 测试写完后禁止修改测试。范围蔓延 → 标记计划清单之外被改动的任何文件。上下文饱和 → 任务之间清空上下文，并把计划持久化到文件 [[2]](#sources)。
**相近形态：** 每次编辑都要求批准的版本（`assist`，辅助）按替换测试属于另一个物种。

覆盖度（截至 2026-11-06）：**充分**：有详细的第一手实例，与流程的大部分环节一致。来自 [Where are the real runs?](../../../../../research/2026-11-real-runs.md)；每个数字都已对照原页面复核。

- [HumanLayer, *Advanced Context Engineering for Coding Agents*](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md) (无署名和日期；图片标注 Aug 2025)。在 300k 行代码的 Rust 代码库上按研究 → 计划 → 实现推进；由人审阅研究和计划。"shipping 35k LOC to BAML"；"spent 7 hours"。*第一手：是；可信度：高。*
- [Harper Reed, *My LLM codegen workflow atm*](https://harper.blog/2025/02/16/my-llm-codegen-workflow-atm/) (2025-02-16)。规格 → 提示词计划（TDD 变体）→ 逐步实现，每步后都测试。"This entire process will take maybe 15 minutes."（指规划阶段）。*第一手：是；可信度：中。*
