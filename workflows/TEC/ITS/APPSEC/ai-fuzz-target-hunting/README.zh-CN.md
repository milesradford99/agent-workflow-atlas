# AI 模糊测试目标挖掘

**工具变体：** `oss-fuzz-gen` · `clusterfuzz`

## 背景

软件安全研究员寻找会让程序以开发者未预料的方式出错的输入。模糊测试器会生成和变异输入，但仍需要先有人编写一个小型驱动程序，按正确的初始条件调用目标函数。驱动自身的错误也会造成崩溃，却不能说明被测程序有问题。本工作流让智能体起草和修复驱动，提交较长的测试任务，并准备崩溃分析。报告之前仍由人确认哪些崩溃是真漏洞，具体修复则由项目维护者决定。

**术语：**
- **模糊测试 / 测试目标 / harness**：使用生成输入的测试、被调用的目标函数，以及把输入连接到函数的驱动程序。
- **编译 / 运行时**：生成可执行代码，以及执行代码的阶段。
- **交叉引用（xref）**：显示某段代码在哪里调用或引用其他符号的关联。
- **堆栈跟踪**：程序出错时记录的函数调用链。
- **分诊（triage）**：判断崩溃属于驱动还是被测项目。
- **CVE**：为公开披露的漏洞分配的标识符。
- **覆盖率（coverage）**：测试执行过程序的哪些部分；覆盖率不等于安全证明。

- **LLM / API**：大语言模型，以及程序调用其他组件的接口。

## 用智能体搭建

**形态：** `service`。较长的模糊测试任务及之后陆续到达的崩溃，需要持久队列，不适合要求人始终留在对话里。

**需要：** 已授权的项目源码和构建说明；隔离的编译与模糊测试环境；任务提交和结果获取脚本；持久的任务及崩溃存储，以及私密审阅队列。未披露漏洞的细节留在获批的报告环境中；不给智能体发布公开议题的工具。

| 步骤 | 搭建方式 |
|---|---|
| 为项目建立索引 → 每个目标函数：起草模糊测试目标 ⟲ 修复编译错误 | Skill 读取源码、类型和测试；`claude -p` (headless) 处理队列里的每个目标，根据编译器输出修改驱动。 |
| 短时运行 ⟲ 修复运行时错误 | Skill 调用隔离运行器，保存崩溃材料，在接受驱动前检查初始条件。 |
| 在模糊测试基础设施上长时间运行 | Skill 旁的脚本把获批驱动提交到已有模糊测试基础设施；任务标识与状态保存在对话之外。 |
| 每个崩溃：分诊驱动 bug 或项目 bug | 后续无界面运行读取崩溃、驱动和项目源码，写出带证据链接的分析。 |
| 🛑 review → 向维护者报告 → 🛑 handoff | 服务创建私密审阅项；由人确认，并通过项目的披露流程发送报告。 |

**检查点：** `review`：队列中包含复现输入、堆栈跟踪、驱动假设和建议分类。智能体不能发送披露或创建公开议题。`handoff`：由人将已确认报告交给维护者，维护者负责修复；服务记录交接，不自行实施修复。

**与来源相比：** 来源出自 2024-11。2026-11 打开原 URL 时只返回标题和导航，没有正文，因此没有重新核实其主张。检索发现 [OSS-Fuzz-Gen 仓库](https://github.com/google/oss-fuzz-gen)，于 2026-11 打开，显示已在 2026-11-10 归档并设为只读。保留 `oss-fuzz-gen` 作为历史变体，不把它当作仍受维护的依赖推荐。本设计由通用编码智能体的 Skill 承担编译和运行循环，模糊测试后端由运维方维护；不假设已归档框架仍是当前服务，也不认为工具进步可以取消人工崩溃审阅。

## 步骤

*以下按来源所述。*

1. 系统自动为每个项目建立索引：函数、类型定义、交叉引用和已有的单元测试。这给提示词提供了项目特有的上下文，减少幻觉。[[1]](#sources)
2. 针对每个目标函数，LLM 起草一个模糊测试目标。编译错误交回给 LLM，直到能编译通过。[[1]](#sources)
3. 系统短时运行该目标。如果它立即崩溃（是设置错误，而不是项目 bug），由 LLM 修复。[[1]](#sources)
4. 系统把修正后的目标在 ClusterFuzz 上长时间运行。[[1]](#sources)
5. 对每个崩溃，LLM 拿到堆栈跟踪、目标源码和项目代码，并附上分析，把它标为 'bug in fuzz driver' 或 'bug in project'。[[1]](#sources)
6. 🛑 **审阅**：报告发出前，仍由人审阅分诊结果。去掉这一步被列为未来目标。[[1]](#sources)
7. 🛑 **接手**：确认的漏洞交给项目维护者修复（OpenSSL 的 CVE 于 9 月 16 日报告，10 月 16 日修复）。[[1]](#sources)

**产出：** 加入项目 OSS-Fuzz 配置的新模糊测试目标，以及发给维护者的已确认漏洞报告。
**失败模式 → 防护：** 目标中出现幻觉的 API → 带索引的项目上下文加编译修复循环。把驱动 bug 误当成真漏洞 → LLM 分诊，并在报告前由人审阅。把覆盖率提升误当成安全 → 即使对已做过模糊测试的代码，也持续生成新目标。

**与相近工作流的区别：** AWF-0067 Sanitizer 缺陷自动修补：AWF-0067 从已知的 sanitizer 发现出发，交付由代码负责人签发的补丁。本工作流则是发现新的 bug：产出是模糊测试 harness 和已分诊的漏洞报告，关卡是分诊审阅以及向外部维护者的接手。
