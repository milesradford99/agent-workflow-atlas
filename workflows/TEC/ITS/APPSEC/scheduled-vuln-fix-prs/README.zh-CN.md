# 定时漏洞修复 PR

**工具变体：** `bitbucket-agentic-pipelines` · `rovo-dev` · `jira-automation` · `claude-code` · `codex`

## 背景

安全扫描器发现存在漏洞的软件依赖之后，开发者需要找到安全版本，修改正确的文件，并检查应用是否仍能构建和运行。几张工单可能指向同一个依赖，而已经合并的修改也未必进入了实际部署的应用。本工作流定时处理常规情况，把相关工单分组，准备经过测试的修改。智能体可以完成这些可重复步骤并核查部署记录。工程师仍决定是否合并和发布，超出已知模式的情况则留给人处理。

**术语：**
- **漏洞 / 扫描器**：安全弱点，以及报告受影响软件包或镜像的工具。
- **补丁窗口**：应当处理某个安全弱点的时间范围。
- **直接 / 传递依赖**：应用明确使用的软件包，以及由其他软件包间接引入的包。
- **升级父依赖 / 基础镜像**：升级引入该依赖的软件包，或更新应用容器底层的操作系统镜像。
- **PR / diff / commit**：提议的仓库修改、被修改的代码行，以及记录下来的版本。
- **CI/CD / 幂等**：自动化构建与交付检查，以及重复执行不会产生重复效果。

## 用智能体搭建

**形态：** `service`。计划任务启动工作，部署事件稍后到达；工程师收到 PR 和例外情况。

**需要：** 带有所需安全版本的漏洞工单；获批的仓库检出副本及构建环境；存放在代码旁的依赖决策树；工单和代码托管平台的 MCP server (connector) 工具；只读部署记录，以及持久的工单与 PR 对应关系。源码、凭据和安全发现留在获批系统中。编码运行可以开 PR，但不能合并或部署。

| 步骤 | 搭建方式 |
|---|---|
| 工作日开始前定时触发 → 调度器：补丁窗口内的漏洞工单 | 现有调度器调用 `claude -p` (headless)。Skill 读取工单，把资格判断和分组决定记入工作存储。 |
| 每个工单：符合条件或分组或人工处理：🛑 handoff | Skill 套用有版本管理的决策树，为每张工单生成明确的队列结果。 |
| 每个批次：套用修复模式 → 重新生成文件 → 完整构建 + 测试 | 各个无界面运行使用仓库的 Skill、命令和隔离检出副本；Permission rule or mode 将各次运行限制在所需系统内。 |
| 失败或未知模式：停止 + 报告或通过：开 PR → 🛑 review | Hook 在所需检查通过前阻止创建 PR；失败结果附带证据返回人工队列。 |
| 部署 → 收尾智能体核验已部署的提交 → 工单转入扫描器验证 | 后续 Skill 通过 MCP server (connector) 工具读取合并与部署状态，然后更新工单；持久标识让重跑可以审计。 |

**检查点：** `handoff`：未知模式、不完整的部署证据和检查失败均保持打开，附明确原因和日志。`review`：工程师在 PR 中查看依赖修改、重新生成的文件及测试结果；仓库权限不允许智能体合并或部署。没有匹配的已部署 commit 记录，收尾智能体不能标记部署完成。

**与来源相比：** 来源出自 2026-08，已于 2026-11 打开。检索发现 [Atlassian 重新设计的 MCP 集成公告](https://www.atlassian.com/blog/bitbucket/connect-the-redesigned-atlassian-mcp-server-to-your-agentic-pipelines)，出自 2026-10，已于 2026-11 打开。公告为 Claude 和 Codex 引入新版连接器；Rovo Dev CLI 仍使用旧连接器，并计划转向 Rovo CLI。迁移完成前，把 `rovo-dev` 视为来源使用的现有名称，不当作已经下线。上述搭建保留来源中的调度、编码和收尾职责，以带持久状态的无界面 Skills 来表达；工具访问需要按所选提供方的连接器版本检查。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 一条定时自动化规则在工作日开始前启动调度器 [[1]](#sources)。
2. 调度器搜索补丁窗口内的漏洞工单。它判断是否符合条件，把共享同一依赖变更的工单归为一组，并为每个批次并行启动编码智能体。🛑 **接手**：需要判断的条目留给人工处理，每张工单都有明确的结果 [[1]](#sources)。
3. 编码智能体在仓库自己的构建环境中运行，只拥有所需的权限范围。它遵循存放在仓库中的决策树：升级直接依赖、升级传递依赖的父依赖、标记平台托管的包，或走基础镜像路径。它会重新生成生成文件，并运行完整的构建和测试套件 [[1]](#sources)。
4. 如果检查失败，或修复超出了已编码的模式，运行会停止并说明原因。否则它创建分支并开 PR。提示词、skill 和流水线定义都在仓库中有版本管理 [[1]](#sources)。
5. 🛑 **审阅**：工程师审阅 diff 并决定是否合并。现有的分支保护和必需的评审仍然把关 [[1]](#sources)。
6. 部署之后，收尾智能体检查对应的 PR 已合并且已部署的构建包含该提交，然后把工单转入扫描器验证。如果证据不完整，工单保持打开。重复运行是幂等的 [[1]](#sources)。

**产出：** 每天早上都有经测试、可直接评审的漏洞修复 PR，工单只有在确认修复已部署后才会关闭。
**失败模式 → 防护：** 笼统的指令 → 笼统的修复，所以依赖模式、文件位置、构建命令和例外情况按代码库分别存放。重复运行造成重复工作 → 工单、标签、分支和部署状态让重复运行无害。模型输出成为发布门槛 → 由确定性检查和人工评审来决定。

**与相近工作流的区别：** AWF-0067 Sanitizer 缺陷自动补丁（Sanitizer-bug autopatch）从 sanitizer 崩溃出发，对比多个模型给出的修复，并经过安全工程师筛选加代码负责人签发。这里的输入是一队带有已知安全版本的扫描器工单。调度器把它们分批，常规的依赖和镜像修复只走一次 PR 评审，由收尾智能体核验部署。输入、产出物和检查点安排都不同。
