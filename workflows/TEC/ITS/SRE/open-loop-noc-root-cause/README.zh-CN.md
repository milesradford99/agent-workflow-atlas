# 网络故障根因分析（NOC）

**工具变体：** `docomo-agentic-ai` · `langgraph-mcp`

## 背景

电信运营商从网络运营中心（NOC）运行网络，工程师在那里盯着成千上万个网元（路由器、基站、核心网节点）发出的告警。出现故障时，工程师要找出根因，也就是一批告警背后真正的故障，并把原因和修复办法写进故障工单。靠人工，这意味着要查很多系统，一个故障就要花几个小时，而且大多数告警只是噪声。在这里，智能体收集数据、给可能的根因排序、提出建议措施，并作为标注写进工单，不改动网络。NOC 工程师来采纳或修改这份标注，因为对运行中的网络做错误操作可能让客户断网；难办的情形交给二线（Tier-2），即处理一线人员解决不了的问题的更资深运维人员。

**术语：**
- **NOC（网络运营中心）**：监控网络并处理故障的团队和场所。
- **告警（alarm）**：网元自动发出的出了问题的警告。**告警噪声**指大量无需处理的告警。
- **网元（network element）**：网络中的设备或节点，如基站或核心网功能。
- **根因（root cause）**：能解释一组症状的底层故障。
- **故障工单（trouble ticket）**：记录一次故障及其诊断、所采取措施的单据。
- **一线 / 二线（Tier-1 / Tier-2）**：一线运维人员，以及他们把难办情形升级去的更资深的二线。
- **开环（open-loop）**：智能体只提建议、不动手，由人决定。
- **MVP（最小可行产品）**：用来检验想法的第一个可用版本。

## 用智能体搭建

**形态：** `service`。告警全天候到来，没有人去启动每次分析，所以由故障事件触发无界面运行，工程师看到的只有带标注的工单。

**需要：** 从告警或工单系统到一个小型接收器的触发，由它为每个故障情形启动 `claude -p` 或 Agent SDK 程序；对网元数据、资产清单和历史工单的只读 MCP 服务器或 API；把标注写入工单的权限，但没有任何改动网络配置的工具；经批准的模型环境，因为 Atsky 的记述排除了公共模型（出于网络数据保密），推理在运营商自己的环境内进行；二线接收升级的队列或工单字段。

| 步骤 | 搭建方式 |
|---|---|
| 网络告警 / 故障情形 → 收集网元数据 | 故障事件启动运行。skill 列出每类告警要读哪些网元数据和历史工单，通过只读连接器读取。 |
| 根因分析 (检索、标注) | skill 固定的前几步：先检索数据，再标注排序后的根因。内置子智能体可以并行分析不同的网络领域并返回摘要。 |
| 建议措施 → 整理成工单 | skill 的最后几步：给出一条建议措施，再套用固定的工单标注模板。需要强制固定顺序时，用 Agent SDK 程序按顺序调用这四步。 |
| 🛑 review | 见“检查点”。 |
| 复杂：🛑 handoff | 见“检查点”。 |

**检查点：** `review`：运行把标注作为提议写进工单，标明“智能体建议”，没有关闭工单或触碰网络的工具；由 NOC 工程师在工单系统里采纳或修改。`handoff`：证据给不出排序后的根因时，运行说明没能确定什么、为什么，并把工单连同已收集的数据放进二线队列。

**与来源相比：** 来源的日期从 2026（DOCOMO 的幻灯片，出自 MWC 2026）到 2026-10 更新的案例研究（Atsky，这里列为未注明日期）。两者都在 2026-11 打开过，仍然支持引用它们的步骤。Atsky 把流程做成了固定四步的 LangGraph 确定性图，跑在自己托管的模型上，目的是输出可复现、可审计，并保护数据机密；上面的搭建方式用 skill 复现这个顺序，需要强制顺序时用 Agent SDK 程序，并且不指定框架。DOCOMO 的幻灯片展示了一个多智能体系统，没有搭建细节。2026-11 的搜索找到了同一做法较新的厂商记述：[Amdocs](https://www.amdocs.com/insights/case-study/8-hours-7-seconds-root-cause-analysis-reimagined-agentic-ai)（2026-05-27）描述了一家北美运营商已投产的智能体根因分析流程。Ericsson 的另一篇记述（2026-06）打不开，所以没有引用。`variants` 中的工具：`docomo-agentic-ai` 是 DOCOMO 自己的系统，没有找到更新的记述；`langgraph-mcp` 是 Atsky 用的框架组合，LangChain 的[更新日志](https://docs.langchain.com/oss/python/releases/changelog.md)现在说其 `MultiServerMCPClient`（来自 `langchain-mcp-adapters`）已被 `MCPAdapter` 取代，所以该 slug 里的适配器名称已被取代。

## 步骤

*以下按来源所述。*

1. 告警到达；智能体确认告警并从网元收集数据 [[1]](#sources)。
2. 多智能体根因分析；Atsky 采用固定的四步流程：检索 → 标注 → 建议 → 格式化 [[1]](#sources)[[2]](#sources)。
3. 提出建议措施并发布分析报告 [[1]](#sources)[[2]](#sources)。
4. 🛑 **接手**：升级给二线运维人员（DOCOMO）[[1]](#sources)。🛑 **审阅**：'the agent recommends, the NOC decides'（Atsky）[[2]](#sources)。

**产出：** 带标注的故障工单，含排序后的根因和一条建议措施。
**失败模式 → 防护：** 告警噪声 → 抑制。答案不可复现 → 用确定性流程，而不是开放的智能体循环。
**与相近工作流的区别：** 与 AWF-0004 同属一类，但这里智能体从不执行任何 runbook 步骤（没有操作检查点）。产出是给人工运维人员看的工单标注。
