# 代理运营的作战室

**工具变体：** `incident-io` · `datadog` · `slack` · `linear`

## 背景

线上服务出了足以影响客户的故障时，公司会宣告一次事故（incident），负责运行服务的人（站点可靠性工程师 SRE，以及受影响服务的负责人）聚到一个共用的聊天频道，也就是作战室。有人要查清什么变了，决定怎么修，让所有人了解进展，事后还要写一份复盘（post-mortem）：记录发生了什么、为什么、要改什么。靠人工，最初二十来分钟都花在日志、部署历史和监控面板里那些重复的查询上，复盘和后续任务也常常被跳过或忘掉。在这里，智能体负责查询、发布叙述式状态更新、起草复盘并提出后续事项。确认原因、选定修复、审阅复盘、给每个后续事项指定负责人和优先级，仍然要由人来做，因为对线上服务的改动，智能体无法承担责任。

**术语：**
- **事故（incident）**：服务计划外的中断或变慢。P1 最严重（全面中断，对客户影响很大），P2 为高，P3 为中。
- **作战室（war room）**：为一次事故专门开设的聊天频道。
- **遥测（telemetry）**：运行中的系统发出的数据：日志（事件记录）、链路追踪（一次请求穿过各服务的路径）和指标（随时间变化的计数和读数）。APM（应用性能监控）是收集链路追踪和指标的工具。
- **变更事件**：代码部署和配置变更的记录。
- **复盘（post-mortem）**：对一次事故的书面回顾。**复盘负责人（PostMortem Owner）**是响应期间指定、负责审阅复盘的角色。
- **复盘会（debrief）**：P1 和重要的 P2 事故之后，对着复盘逐项过一遍的会议。
- **后续事项（follow-up）**：复盘产生、用来防止重演的任务。
- **SLO（服务水平目标）**：对服务应有可靠程度的目标。**CUJ（关键用户旅程）**：用户依赖的一条产品使用路径。
- **PR（pull request，拉取请求）**：一份提议的代码改动，公开出来供评审。

## 用智能体搭建

**形态：** `service`。事故一经宣告就开始工作，现场没有人在键盘前，响应人员看到的是频道消息、一份草稿和工单，所以它作为无界面任务运行。

**需要：** 事故宣告时启动运行的办法：事故工具向一个小型接收器发 webhook，由它启动 `claude -p` 或 Agent SDK 程序；通过监控工具的 MCP 服务器或 API 对日志、链路追踪、指标和变更事件的只读访问；在作战室频道发消息、创建草稿文档和工单的权限，但没有任何能改动生产环境的工具；存放事故时间线（作战室消息和状态更新）的地方。

| 步骤 | 搭建方式 |
|---|---|
| 宣告事故 → 作战室频道 + 邀请服务负责人 | 由事故工具自己完成。它的宣告事件启动这次无界面运行。 |
| 调查智能体: 日志、链路追踪、指标、变更事件 → 工作假设 | 一个 skill，列出针对受影响服务要跑的查询（近期部署、错误率、链路追踪、数据库指标）。内置子智能体可以各取一个数据源并返回摘要。运行把假设发到频道里。 |
| 🛑 handoff | 见“检查点”。 |
| (叙述式状态更新 ⟲ 每个生命周期阶段) | 事故工具里每次状态变化都会启动一次简短的运行，读取时间线，发布已知什么、变了什么、正在做什么。 |
| Documenting: 根据时间线 + 频道 + 遥测起草复盘 | 一个带复盘模板的 skill；运行读取时间线、频道消息和之前的查询，写出一份草稿文档。 |
| 🛑 review | 见“检查点”。 |
| P1/P2: 带预填议程的复盘会 | skill 根据草稿写出议程；由人安排会议。 |
| 智能体提出后续事项 | 同一个 skill 列出具体的后续事项，每项对应草稿里的一个原因。 |
| 🛑 sign-off → 同步到跟踪器 | 见“检查点”。 |

**检查点：** `handoff`：发出假设后，运行停下来，说明查到了什么、没能确定什么；由响应人员决定修复。智能体只有只读凭据，没有部署、回滚或重启任何东西的工具，所以 P1 和 P2 的修复仍归人。`review`：复盘以草稿形式保存，只有复盘负责人能发布。`sign-off`：智能体只把后续事项作为提议创建，不指定负责人；跟踪器连接器要等人填好负责人和优先级之后才能建工单。

**与来源相比：** 唯一的来源和公开实例都出自 2026-04。它在 2026-11 打开过，仍然支持引用它的步骤。它描述的是一家公司在事故管理产品、监控产品和工单工具之上搭起的系统，没有说明其智能体如何实现，所以上面的搭建方式是设计，不是复现。2026-11 的搜索找到了同一做法的厂商说法，都是自述：incident.io 描述了事故解决后由 AI 根据捕获的时间线起草复盘（[AI SRE explained](https://incident.io/blog/what-is-ai-sre-complete-guide-2026)，2026-02，2026-08 更新），Datadog 在 2026-03 发布了新的 Bits Investigation 智能体，带有分诊和修复能力（[Meet the new Bits Investigation](https://www.datadoghq.com/blog/bits-ai-sre-deeper-reasoning)）。厂商的修复功能不在本条目范围内，本条目把修复留给人。`variants` 里的工具仍以原名存在。本搭建方式不用事故工具内置的调查和起草功能（厂商现在已在出售），而是用通用智能体处理它们的数据。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 事故由人宣告，或由告警触发。事故工具会开设专门的 Slack 作战室，并根据受影响的服务邀请相关人员 [[1]](#sources)。
2. 调查智能体立即启动。它查询生产日志、APM 链路追踪、基础设施和 APM 指标，以及按组件和 PR 过滤的变更事件，并在第一个人加入之前把它们关联成一个工作假设 [[1]](#sources)。
3. 🛑 **接手**：响应人员的职责是确认假设并决定怎么做。P1 和 P2 的判断由人来做 [[1]](#sources)。
4. 在 Triage → Investigating → Fixing → Monitoring → Closed 的各阶段中，智能体发布叙述式状态更新（已知什么、变了什么、正在做什么），让后加入的人能跟上 [[1]](#sources)。
5. 到 Documenting 阶段，智能体根据状态时间线、作战室消息、它查询过的遥测数据，以及根因和解决步骤，起草结构化的复盘。🛑 **审阅**：由复盘负责人（响应期间指定的角色）审阅，而不是撰写 [[1]](#sources)。
6. 每个 P1 和重要的 P2 都会与参与者安排一次复盘会，议程根据草稿预先填好 [[1]](#sources)。
7. 智能体提出具体的后续事项（例如部署前验证、新增监控、SLO 或关键用户旅程的缺口）。🛑 **签发**：每个后续事项都会分配负责人和优先级，然后成为带有负责人、优先级和回链的一等对象，同步到 Linear 并转给所属团队 [[1]](#sources)。

**产出：** 一份经审阅的复盘、一次复盘会，以及团队跟踪器中有负责人的后续工单。事故期间还会产出状态更新和早期假设。
**失败模式 → 防护：** 后续事项被遗忘在 wiki 里 → 同步到团队已在使用的跟踪器。值班名单过时 → 用 Terraform 管理由团队负责的升级路径。越权 → P1/P2 不做自主修复。自主的 P3 分诊目前只是计划。
**与相近工作流的区别：** AWF-0004 先分诊再修复（Triage then remediate）由智能体在操作关卡之后执行运行手册步骤并更新运行手册。这里智能体从不对生产环境动手。它的产出是作战室上下文、状态更新、复盘草稿和被跟踪的后续事项，检查点是接手、复盘负责人审阅和复盘会。AWF-0127 是一个 NOC 工单标注流程。
