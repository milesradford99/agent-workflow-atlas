# 团队智能体事件分诊

**工具变体：** `azure-openai` · `gpt-embeddings`

## 背景

在大型云公司里，成百上千个服务相互依赖，所以记在某个服务名下的事件，可能其实来自另一个服务。每个服务团队都有一个待处理事件的队列，值班的指定工程师（责任人）要判断事件是否归本团队，不归的话该谁来接，再转出去。靠人工，这既慢又容易出错，每一次转错都会多一次重新分派，拉长缓解时间，也就是客户停止受影响之前的时间。在这里，每个团队配一个智能体，根据历史事件和团队的排障指南先做接收或拒绝的判断，并给出理由。每个被接收的事件仍由团队里的一个人审阅并接手，缓解故障也仍由这位工程师负责。

**术语：**
- **事件（incident）**：服务出现的、需要响应的计划外问题。
- **队列（queue）**：等待某个团队处理的事件列表。
- **责任人（DRI，designated responsible individual）**：被指定去调查新到事件的工程师。
- **TSG（troubleshooting guide，排障指南）**：工程师写的文档，说明如何诊断和修复某类常见问题。
- **TTM（time to mitigate，缓解时间）**：从事件被记录到其对客户的影响得到缓解的时间。
- **嵌入（embedding）**：用一串数字表示一段文字的含义，从而能找到相似的文字。**语义提炼（semantic distillation）**是来源对“抽出事件中与分诊相关部分”的叫法。
- **值班工程师（on-call engineer）**：当班负责响应某团队事件的工程师。

## 用智能体搭建

**形态：** `service`。新事件进入队列就开始工作，现场没有人在键盘前，而且智能体可以不经批准把被拒绝的事件转出去，所以它作为对队列起作用的无界面任务运行。

**需要：** 事件进入某团队队列时由事件系统发出的触发，启动 `claude -p` 或 Agent SDK 程序；作为运行可读文件的团队 TSG；通过 MCP 服务器或搜索工具对团队事件历史的读取权限，能返回相似的历史事件；一个连接器，能给事件加备注、把它分给团队的值班工程师、转给另一个团队或留在队列里，并且没有任何改动生产环境的工具；一份说明 TSG 指明了哪些团队的团队清单。

| 步骤 | 搭建方式 |
|---|---|
| 事件进入团队队列 | 事件系统的事件为每个事件启动一次无界面运行。 |
| 提炼事件语义 | skill 要求智能体从事件中抽出症状、受影响的组件和错误文本。 |
| 检索相似历史事件和团队 TSG | 智能体在事件历史中搜索相似案例，并读取放在 skill 旁边作为参考文件的 TSG。 |
| 决定本团队接收或拒绝 | skill 要求做出接收或拒绝的决定，理由要引用用到的事件和 TSG 段落。证据定不下来时，决定就是把事件留在队列里。 |
| 接收：给出理由 → 🛑 handoff | 见“检查点”。 |
| 拒绝：退回上一个团队 / 转给 TSG 指明的团队 / 留在队列等工程师处理 | 连接器的改派操作只允许退回上一个团队，或转给 TSG 指明的团队。其他情况一律留在队列里。 |

**检查点：** `handoff`：对被接收的事件，运行把理由写进事件并分给值班工程师，由其审阅并接手；智能体没有缓解故障的工具。被拒绝的事件像来源所述那样改派，不需要人逐条批准，所以这里漏掉检查会让事件被送到别的团队：连接器只允许上述两种改派目标，每次改派及其理由都有记录，`PreToolUse` 钩子会拦住改派到没有任何 TSG 或历史记录指明的团队。

**与来源相比：** 唯一的来源和公开实例都出自 2025-03（数字截至 2025-01）。该来源在 2026-11 打开过，仍然支持引用它的步骤。它描述的是按团队配置的智能体，用 GPT embeddings、“语义提炼”以及基于事件历史和 TSG 的训练，模型细节没有说明；现在的智能体可以通过 skill 读取 TSG、通过连接器搜索历史事件，所以搭建方式用这些来代替手工搭建的嵌入流水线。全局分诊层（步骤 6）在来源中还在建设，上面的搭建方式没有包含。2026-11 的搜索没有找到 Microsoft 该系统更新的记述。找到的是同一做法的一般性记述：Rootly 的厂商指南（2026-10 更新）认为，通过服务目录把事件对应到负责团队可以减少转错（[AI SRE lifecycle](https://rootly.com/ai-sre-guide/lifecycle)）。`variants` 中的工具（`azure-openai`、`gpt-embeddings`）没有确认被改名或下线；没有打开过 Microsoft 关于它们的退役页面。

## 步骤

*以下按来源所述。*

1. 每个服务团队配一个智能体，代表团队的工程师。它把团队的历史事件和排障指南（TSG）作为领域知识 [[1]](#sources)。
2. 事件进入团队队列后，智能体用 GPT embeddings 和“语义提炼”（semantic distillation）抽出事件中与分诊相关的信息 [[1]](#sources)。
3. 智能体把事件与历史事件和团队的 TSG 对比，然后做二选一的决定：为本团队接收该事件，或拒绝，并给出理由 [[1]](#sources)。
4. 被接收的事件：智能体附上理由。🛑 **接手**：团队中的一位工程师（指定的责任人）审阅该事件并接手 [[1]](#sources)。
5. 被拒绝的事件：智能体把事件退回上一个团队，转给其 TSG 指明的团队，或留在队列里由工程师处理。每次改派无需人逐一批准 [[1]](#sources)。
6. 建设中：全局分诊层（Global Triage），由多智能体编排器挑选候选团队，并与各团队的智能体协商，找出合适的负责方 [[1]](#sources)。团队逐个接入，每个团队带来自己的 TSG 和事件历史 [[1]](#sources)。

**产出：** 对每个新事件给出接收或改派的决定及理由，让事件更快到达负责团队的值班工程师手中，再由该工程师缓解。
**失败模式 → 防护：** 智能体误拒并退回事件，造成多余的重新分派，拉长缓解时间 → 智能体可以把事件留在队列里交给工程师，并为每个决定给出理由。TSG 过时或缺失会削弱决定质量 → 智能体基于各团队的 TSG 和历史事件训练，团队逐个接入。
**与相近工作流的区别：** 最接近的是 AWF-0004 先分诊后修复（Triage then remediate）：该工作流调查信号，并在 🛑 action 之后执行运行手册（runbook）操作。本工作流只产出归属决定（接收或改派），不执行任何修复操作，并且智能体改派时无需逐条审批。它也不同于 AWF-0127（在 NOC 工单中标注根因）和 AWF-0185（作战室协调与复盘）：这两者都不决定事件归哪个团队。
