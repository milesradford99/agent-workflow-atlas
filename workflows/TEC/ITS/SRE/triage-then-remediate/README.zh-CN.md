# 先分诊后处置

## 背景

监控系统发现服务出了故障时，会向值班工程师发出告警，值班工程师是随时待命响应的人。工程师要通过读指标、日志、链路追踪和最近的部署找出是系统哪一部分出了问题，按团队的运行手册（针对某类已知故障的书面处理流程）操作，执行回滚之类的修复，事后还要写复盘（postmortem），回顾发生了什么。靠人工，这在夜里又慢又累，运行手册也会过时。在这里，智能体并行完成阅读，给可能的原因排序并附上证据链接，再起草复盘。每条会改动运行中系统的命令，仍由值班工程师批准，因为错误的回滚或重启可能让故障更糟；复盘则由事件负责人审阅。

**术语：**
- **告警（alert）**：监控系统自动发出的、说明某个被测量的值出了问题的消息。
- **值班工程师（on-call engineer）**：随时待命响应告警的工程师。**事件负责人**是为某次事件及其复盘负责的人。
- **运行手册（runbook）**：针对某类已知故障的诊断和修复的书面流程。
- **指标、日志、链路追踪（metrics, logs, traces）**：运行中的服务发出的随时间变化的数字、事件记录和请求路径。**部署（deploy）**指发布新代码。
- **回滚（rollback）**：把服务退回到之前的版本。
- **SLO（服务水平目标）**：对服务应有可靠程度的目标，这里用来检查恢复是否有效。
- **复盘（postmortem）**：对一次事件的书面回顾：原因、时间线，以及要改什么。

## 用智能体搭建

**形态：** `service`。告警一来就开始工作，现场没有人在键盘前，只在批准命令和审阅复盘时才需要工程师。

**需要：** 从告警系统到一个小型接收器的 webhook，由它为每条告警启动 `claude -p` 或 Agent SDK 程序；按服务打好标签的运行手册文件；通过 MCP 服务器对指标、日志、链路追踪、部署历史和代码仓库的只读访问；一份智能体可以提议的运行手册命令的短清单（回滚、扩容、重启），只有值班工程师批准才能执行；一个事件频道，以及对运行手册提交 PR 的地方。

| 步骤 | 搭建方式 |
|---|---|
| 告警 → 路由到运行手册 | 接收器传入告警的服务标签；skill 选出带该标签的运行手册文件。 |
| 每个信号：调查 (指标、日志、链路追踪、部署) | 内置子智能体每个信号一个，并行执行只读查询，各自返回带链接的摘要。 |
| 假设排序 | skill 把各摘要合并成带证据链接的假设排序，发到事件频道。 |
| 🛑 action → 执行运行手册步骤 | 见“检查点”。 |
| 检查 SLO | 批准的步骤执行后，智能体读取 SLO 指标，报告是否已恢复。 |
| 起草复盘 | skill 根据频道内容、查询和执行过的命令写出草稿。 |
| 🛑 review | 见“检查点”。 |
| 更新运行手册 | 智能体提交修改运行手册的 PR，由人合并。 |

**检查点：** `action`：智能体只有只读凭据，没有在生产环境上执行命令的工具。提议的运行手册命令通过 `canUseTool`，或通过会推迟调用、等人回答的 `PreToolUse` 钩子交给值班工程师，权限规则会拒绝清单之外的所有命令，所以来源所说的白名单是在提示词之外强制执行的。`review`：复盘以草稿保存，智能体没有发布工具；由事件负责人修改并发布。运行手册的 PR 不由智能体合并。

**与来源相比：** 来源的日期从 2024-06 到 2026-04。三篇在 2026-11 都打开过，仍然支持引用它们的内容：Meta 的可疑代码变更检索器和排序器、一位工程师基于运行手册搭建并为运行手册更新提交 PR 的智能体，以及一个只读的调查智能体。没有来源报道过本条目步骤部分整体上的流程，也没有来源报道过工程师批准运行手册命令：Chatwoot 的智能体是只读的，把经批准的操作列为未来的工作，所以操作关卡和 SLO 检查来自本条目的设计，而不是某次实例。Meta 的排序器是微调过的模型；本搭建方式用通用智能体处理同类数据。2026-11 的搜索找到了关于批准关卡的较新记述：Anthropic 的 cookbook 示例（2026-04-10），一个读日志和运行手册、提交修复 PR、合并前等待批准的值班智能体（[cookbook](https://platform.claude.com/cookbook/managed-agents-sre-incident-responder)），以及 Rootly 的一篇观点文章（2026-09-15），主张在修复环节继续保留人在回路中（[Rootly](https://rootly.com/blog/could-2027-be-the-year-you-turn-off-human-in-the-loop)）。本条目没有在 `variants` 中列出工具。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 告警触发智能体，智能体按服务标签路由到对应的运行手册。
2. 并行进行只读调查：错误激增、时间窗口内的部署、典型链路追踪，以及可疑的 diff。
3. 把带证据链接的假设排序发到事件频道。
4. 🛑 **操作**：值班工程师批准某条具体的运行手册命令（回滚、扩容、重启）。
5. 对照 SLO 验证是否恢复。
6. 起草复盘。🛑 **审阅**：事件负责人修改，尤其是根因和后续行动项。
7. 更新运行手册。

**防护：** 写操作工具限制在运行手册命令的白名单内，由代码强制执行。
