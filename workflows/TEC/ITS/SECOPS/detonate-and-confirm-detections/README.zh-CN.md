# 攻击模拟验证检测规则

**工具变体：** `claude-code` · `codex` · `ttpforge` · `splunk`

## 背景

检测工程师需要知道，一条安全规则究竟能不能发现它本来要捕捉的行为。规则看起来正确，仍可能遇到计算机没有发送相关事件、事件迟到，或者查询检查了错误字段的问题。本工作流先编写可控的模拟，在隔离实验室中运行，再沿着检测系统追踪其产生的记录。智能体可以起草、测试并诊断模拟。每个模拟在日常回放前仍需人工审阅，检测缺口如何修复也由人决定，因为表面成功的测试未必真正执行了目标行为。

**术语：**
- **检测规则**：把记录的活动转换为告警的查询或条件。
- **TTP**：战术、技术与过程；这里指可重复执行的攻击行为模拟。
- **YAML / schema**：一种结构化文本文件，以及定义其合法字段的规则。
- **SSH**：经过身份认证的远程命令连接。
- **SIEM**：收集安全事件并运行检测查询的系统。
- **遥测 / 入库（telemetry / ingestion）**：记录的活动，以及这些记录到达中央系统的过程。
- **SPL**：Splunk 的查询语言。
- **黄金镜像 / 转发器**：标准的机器安装镜像，以及把日志发送出去的组件。
- **Devcontainer / 出站规则**：隔离的开发环境，以及对外部连接的限制。

## 用智能体搭建

**形态：** `service`。编写模拟时采用交互式 `project`，完整流程还包括无人值守的定时目录回放。

**需要：** 检测规则及字段文档；得到明确授权的隔离实验室；模拟运行器、校验器及清理脚本；只读访问检测结果的权限；已审阅目录与看板存储。远程执行凭据只限实验室，生产凭据不进入智能体环境。

| 步骤 | 搭建方式 |
|---|---|
| 检测规则 → 编写 TTP 攻击模拟 YAML → 钩子校验 schema | Skill 起草模拟及检查。Hook 在编辑后运行 schema 校验器；PreToolUse Hook 在校验通过之前阻止实验室执行。 |
| 经 SSH 部署到实验室主机并运行 ⟲ 逐步检查 | Skill 调用仅限实验室的脚本并读取检查结果；Permission rule or mode 拒绝访问生产主机及范围外的配置修改。 |
| 验证智能体轮询 SIEM → 超时：调试智能体对失败分类 | 只读 Subagent 通过 MCP server (connector) 查询；Skill 限定轮询次数，并把失败交给只做诊断的 Subagent。 |
| 🛑 review → 加入已审阅目录 | Skill 展示行为、检查、清理及检测证据。智能体不能把未审阅文件加入目录。 |
| 定时运行 → 健康度看板 → 🛑 review | 现有调度器启动 `claude -p` (headless)，调用获批模拟并记录结果；由人决定修复。 |

**检查点：** `review`：编写运行在交付模拟及证据包后停下；由人使用不提供给智能体的凭据，把获批文件加入目录。定时运行只执行已审阅目录。看板分别展示执行失败、缺少遥测和规则未命中；智能体没有修改生产检测或日志流水线的工具。

**与来源相比：** 来源出自 2026-06，已于 2026-11 打开。针对更新实例及所列工具的检索，截至 2026-11 未找到更新实例。来源已经使用 Skills、Hooks 和验证智能体，因此保留这些组件，不另换一套编排。定时回放与交互式编写仍然分开。写入后 Hook 只能在编辑完成后报告 YAML 无效；本设计增加的执行前防护会阻止无效内容进入实验室。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 检测工程师给智能体一条自定义检测规则。一个 Claude Code 插件（skill、钩子、参考资料）让它编写带检查和清理的 TTPForge 攻击模拟 YAML。[[1]](#sources)
2. PostToolUse 钩子在每次写入时运行 `ttpforge validate`，YAML 有效之前阻止继续推进。[[1]](#sources)
3. 智能体把 TTP 复制到一台由生产黄金镜像构建的隔离实验室主机，并通过 SSH 运行。某一步检查失败时，它重写并重新运行。[[1]](#sources)
4. 后台验证智能体每 2 分钟轮询一次 Splunk，超时为 10 分钟。成功需要同时满足：有原始遥测数据，且检测的 SPL 命中。[[1]](#sources)
5. 超时后，只做诊断的调试智能体对失败分类：主机静默、缺少事件类别、入库延迟，或规则谓词拒绝了该事件。[[1]](#sources)
6. 🛑 **审阅**：TTP 进入已审阅目录之前，由人对照检查清单逐个手工审查。[[1]](#sources)
7. 定时的 GitHub Actions 任务回放该目录，并向流水线健康度看板供数。🛑 **审阅**：由人决定检测规则或流水线要改什么。[[1]](#sources)

**产出：** 一份与检测规则对应、经审阅且可重复运行的攻击模拟目录，一个定时更新的健康度看板，以及一份待修复的检测和流水线缺陷清单。
**失败模式 → 防护：** 智能体在无人值守的运行中越出范围（它修改了实验室转发器的配置） → devcontainer 加出站规则，有风险的工作用交互式会话。薄弱的检查让 TTP 在未证明该技术的情况下就“通过” → skill 中的拒绝捷径规则加人工 TTP 审查。把入库延迟当成漏检 → 有限次轮询加调试分类器。

**与相近工作流的区别：** AWF-0005 告警富化与裁决：AWF-0005 对线上告警下判断（自动关闭或转交），并每周抽检审计。本工作流通过在实验室中引爆攻击来测试检测规则本身。它的产出是经验证的模拟目录和缺陷清单，每个产物在定时运行之前都经过人工审阅。
