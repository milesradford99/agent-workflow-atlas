# 紫队式检测规则构建

**工具变体：** `claude-opus` · `claude-mythos` · `sigma` · `proxmox` · `ansible`

## 背景

检测工程师把攻击报告转化为能在自身机构中识别类似活动的规则。仅仅复制一次攻击的表面细节并不够：换一个文件名或执行路径就可能绕过规则，正常业务也可能触发它。本工作流让负责防守的一方起草规则，让对抗测试的一方寻找缺口，再用实验室记录与实际运行记录验证结果。智能体可以协调这些角色并整理证据。规则是否适合进入生产环境，仍由分析师判断，并由其承担运行后果。

**术语：**
- **蓝队 / 红队 / 紫队**：防守者、经过授权的对抗测试者，以及双方协作的测试循环。
- **PoC**：概念验证，用于演示某个攻击或漏洞。
- **狩猎查询 / 遥测**：查找可疑活动的查询，以及被查询的活动记录。
- **引爆（detonate）**：在授权实验室中执行攻击模拟。
- **误报（false positive）**：被错误识别为可疑的正常活动。
- **Sigma / Python 分析逻辑**：可移植的检测规则格式，以及用程序实现的检测逻辑。
- **安全技术栈**：一台机器上部署的监控与防护系统集合。

## 用智能体搭建

**形态：** `project`。防守和对抗角色需要分开的上下文，还需要长期的实验室知识及强制执行边界，单个对话里的操作流程不足以承担这些要求。

**需要：** 威胁报告或代码仓库；授权的实验室部署及清理脚本；检测格式与字段文档；通过获批 MCP server (connector) 只读访问的运行遥测；检测代码仓库。敏感的客户遥测数据必须留在批准的环境中。执行凭据仅限实验室，不给智能体生产合并或部署工具。

| 步骤 | 搭建方式 |
|---|---|
| 威胁文章或 PoC 仓库 → 蓝队智能体：候选检测 + 狩猎查询 | Skill 加载证据；防守 Subagent 起草候选检测及预期信号。 |
| 红队智能体：攻击计划 → 自动部署实验室 → 每个变体：引爆 | 对抗 Subagent 提出变体。Permission rule or mode 与 PreToolUse Hook 要求在部署或执行之前，先批准实验室目标和执行计划。 |
| 对照实验室 + 运行遥测验证 ⟲ 优化逻辑 | 只读 MCP server (connector) 查询把事件与规则命中交给防守方；Skill 在迭代之间保留每个变体及结果。 |
| Sigma 或 Python 分析逻辑 + 证据包 | Skill 把规则、测试记录、排除项及剩余缺口写入可审阅文件。 |
| 🛑 review → 合入检测仓库 | Skill 交出规则与证据后结束；分析师执行最终的仓库修改。 |

**检查点：** `review`：分析师收到规则、已测试的变体、运行数据中的命中、排除项及未解决缺口。仓库权限不允许智能体合并或部署。此外，实验室执行还需通过 Permission rule or mode 明确批准计划；执行工具排除生产主机。这道额外的执行防护沿用了来源中逐次批准实验室引爆的实例。

**与来源相比：** 来源未标发布日期，页面修改日期为 2026-08，已于 2026-11 打开。针对更新实例及所列工具的检索，截至 2026-11 未找到更新实例。来源中的专门 Skills 以及分开的防守和测试角色，可以直接映射为带有 Subagents 的 project；实验室与运行遥测无法仅靠对话取代。来源的编排表还记载了每次实验室引爆前由用户批准，这道防护未出现在本条目的流程形状中，因此在上述搭建方案中明确保留。

## 步骤

*以下按来源所述。*

1. 智能体摄入一个威胁来源：文章、博客、事件报告、分析师描述或 PoC 仓库 [[1]](#sources)。
2. 蓝队智能体：提出一个或多个候选检测，每个都附有用白话写的逻辑描述和一条狩猎查询 [[1]](#sources)。
3. 红队智能体：编写攻击计划，涵盖要引爆的基础设施、软件和 PoC。如果没有公开的 PoC，它会尝试自行创建 [[1]](#sources)。
4. 实验室根据计划自动部署（例如 Proxmox 靶场加 Ansible），并配备与生产环境相同的安全栈。可能会创建多个环境变体 [[1]](#sources)。
5. 红队智能体用该技术的多个变体执行攻击。蓝队智能体对照实验室模拟和真实运营数据验证检测逻辑，反复进行，直到该活动能被可靠检出且误报降到最低 [[1]](#sources)。
6. 蓝队智能体把结果转换为 Sigma（简单情形）或 Python 分析规则（复杂情形），附带过滤条件、调优逻辑和文档，并与支撑证据和验证结果一起打包 [[1]](#sources)。
7. 🛑 **审阅**：分析师在检测规则合并进仓库之前验证、批准或修改它们 [[1]](#sources)。

**产出：** 带验证证据、可用于生产的检测规则，经分析师批准后合并到检测仓库。
**失败模式 → 防护：** 检测只能抓到原样的 PoC → 每条规则测试 5 个以上的技术变体，包括进程内规避，以找到持久的行为指标。误报泛滥 → 在评审前用真实运营遥测验证。AI 自作主张 → 运营决策由分析师掌握。

**与相近工作流的区别：** AWF-0128 引爆并确认检测（Detonate-and-confirm detections）从已有规则出发，用攻击模拟和定期健康检查来验证它。这里的输入是威胁情报，产出是由蓝队/红队智能体循环构建的新检测逻辑，最后只有一次分析师批准。AWF-0005 是对告警分诊，不创建规则。
