# 先自修复再转人工

**工具变体：** `microsoft-foundry` · `microsoft-agent-framework` · `azure-serial-console` · `azure-ai-evaluation`

## 背景

IT 支持工程师帮助员工重新访问用于开发和测试的计算机。连接失败的原因可能在机器、网络或远程访问服务中，尝试修复之前通常要先做多项检查。本工作流让智能体收集诊断信息，只执行已知的修复，再验证结果。超出已知场景的情况仍交给人，因为修改错误设置可能中断工作，或者削弱访问控制。

**术语：**
- **VM**：虚拟机，在共享硬件上以软件形式运行的计算机。
- **RDP / 串口控制台**：远程桌面连接，以及正常访问失败时用于诊断机器的独立文本通道。
- **RAG / API**：先检索相关文档再回答，以及读写其他系统的程序接口。
- **NIC / OS / evals**：网络接口、操作系统，以及可重复的智能体行为测试。

## 用智能体搭建

**形态：** `service`。从支持请求启动，完成诊断和获准的修复，再把例外交给人。

**需要：** 获批的机器健康与实验室管理 MCP server (connector) 工具；当前用户指南；只读诊断工具；权限受限的修复脚本；测试机器与预期结果。员工信息及凭据留在批准的系统中；不提供通用的特权 shell。

| 步骤 | 搭建方式 |
|---|---|
| 用户报告无法访问 → 程序化检查 | 支持前端通过 `claude -p` (headless) 调用 Skill；脚本完成初始检查。 |
| 只读诊断编排器 → 专项诊断 | Skill 选择下一项检查；只读 Subagents 通过限定范围的 MCP server (connector) 工具收集资源健康和控制台证据。 |
| 已知的安全修复 → 验证修复 → 关闭 | Hook 检查目标与获批修复标识后，才运行限定动作的修复脚本。Skill 再检查访问是否恢复并记录结果。 |
| 有风险或未知：🛑 handoff | 服务把诊断包返回给用户或支持队列，不尝试清单以外的修复。 |
| 发布前：弄坏测试虚拟机 + 评测 | 修改流程发布前，Skill 旁的脚本在测试机器上运行受支持的故障场景。 |

**检查点：** `handoff`：有风险、未知或未通过验证的情况，交付检查项、观察结果与尝试过的修复，供支持工程师接手。修复工具只接受针对所选机器的获批操作；Hook 阻止执行许可清单之外的动作。

**与来源相比：** 来源出自 2026-08，已于 2026-11 打开。检索发现 [Microsoft 的 Foundry 更新](https://devblogs.microsoft.com/foundry/whats-new-in-microsoft-foundry-july-august-2026/)，发布于 2026-09，已于 2026-11 打开，宣布托管智能体正式可用。这是可选的托管方式，并不提供 Microsoft 内部 Managed Cloud Labs 工具的访问权限。通用无界面智能体可以协调检查，但运维方仍需提供经过认证的控制台工具、受限的修复动作，以及覆盖各类受支持机器配置的测试。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 系统把“如何做”类问题转给基于用户指南的 RAG 信息智能体。系统把连接问题转给故障排查智能体 [[1]](#sources)。
2. 用户选择虚拟机并报告 RDP 问题。智能体会实时显示它检测到什么、做了什么的摘要 [[1]](#sources)。
3. 先运行程序化检查。然后由只读诊断编排器决定要收集什么：Azure 资源健康、Managed Cloud Labs API，或转给通过串口控制台操作的专门的 Windows RDP 智能体。当早期信号显示原因明确时，它会提前停止 [[1]](#sources)。
4. 当问题是它可以安全处理的类型时，自动修复编排器会重启虚拟机、重置密码或网络接口，或发送串口控制台命令。然后它先验证修复，再结束这一循环 [[1]](#sources)。
5. 🛑 **接手**：当修复带有风险或超出已知场景时，智能体把完整的诊断上下文交给用户，由用户转交人工支持工程师 [[1]](#sources)。
6. 在发布前以及每次变更时，团队用几十种方式故意弄坏测试虚拟机，并运行评测，检查修复是否安全、一致 [[1]](#sources)。

**产出：** 一台已修复并验证的虚拟机，工单被避免或关闭。否则是交给支持工程师的诊断包。
**失败模式 → 防护：** 修复在不同操作系统版本上表现不同 → 对每个受支持的 Windows 版本做大量测试，并用故意弄坏的测试虚拟机加评测。不安全的修复 → 只执行已知的安全修复动作，有风险的情况转交人工。“如何做”类问题的知识陈旧 → 用户指南是唯一的事实来源。

**与相近工作流的区别：** AWF-0068 Slack IT 请求智能体（Slack IT request agent）只有在应用审批人对每个请求操作之后才开通权限。这里智能体端到端地诊断并修复基础设施，没有逐项审批，人只负责接手。自主程度是抽检而不是分段，产出物是修复后的系统，而不是授予的权限。
