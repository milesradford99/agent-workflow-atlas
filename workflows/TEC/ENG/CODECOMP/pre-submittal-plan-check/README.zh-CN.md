# 报建前图纸预检

**工具变体：** `inspectmind` · `archiboost` · `ichi` · `bluebeam`

## 背景

设计公司画完一套图，送交市政府报建。市政府对照建筑规范检查，然后发回一份整改意见，列出哪里不合规；每一轮都要花几周，而"报建干净"本身也是客户买单的理由。所以公司在提交前自己做一遍质量检查：资深建筑师或专职审图人通读整套图——建筑、结构、市政、机电——既看规范合规，也常看专业之间的协调错误，比如结构图上的洞口和建筑图上的墙不在同一个位置。这种通读很慢，而且看到第四十张图时，人就开始看不见了。本工作流把机器检查放在前面：每张图都对照规范、并跨专业读一遍，审图人拿到的是一份按专业和严重程度排序的清单，而不是一叠空白图纸。然后由审图人判断哪些是真问题，因为回来的标记里很大一部分并不是——厂商自己的说法是约每四条一条为真——只有确认的问题才交给绘图员。之后市政府在审查中发现了什么，才是真正要紧的结果，而那些被判定为噪声的标记会被记录下来，用于调整检查项。

**术语：**
- **报建图纸集（permit set）**：为取得建筑许可提交给市政府的完整图纸与规格说明。
- **图纸审查（plan check）**：市政府对该套图纸的审查，以整改意见或批准作为答复。
- **专业（discipline）**：整套图中属于某一专业的部分——建筑、结构、市政、暖通、电气、给排水。
- **协调错误（coordination error）**：两个专业图纸之间的冲突，例如梁的位置正好压在风管走向上。
- **pre-IFC 评审**：公司在图纸发布用于施工之前做的内部检查。
- **误报（false positive）**：审图人判断并不构成真问题的标记。
- **QA/QC**：质量保证与质量控制，即公司自己的检查流程。
- **甄别（triage）**：在任何人动手修改之前，把清单分成真问题和噪声。

## 用智能体搭建

**形态：** `skill`。一位审图人在对话里处理一套图，修改之前有一道甄别关卡；按专业的分头阅读是这个 skill 内部的并行检查。

**需要：** PDF 格式的完整图纸集，放在项目目录里，带图纸索引；一个按专业拆分图纸、并把每张图渲染到可读尺寸的脚本——检查的质量取决于它能看到多少文字和几何；公司自己的检查清单，即它本来手工审的那些规范项与协调项，作为 skill 旁边的参考文件；过往项目的市政府整改意见，用作基准；记录非问题的甄别日志。智能体不需要接触公司的 CAD 文件：修改留给绘图员。

| 步骤 | 搭建方式 |
|---|---|
| 完整报建图纸集（PDF） | 审图人把 skill 指向一个目录；脚本建立图纸索引、按专业拆分，并把每张图渲染到可读尺寸。 |
| AI 检查规范 + 跨专业协调 | 每个专业一个 Subagent，只给它本专业的清单和本专业的图纸；第二遍读取图纸索引，找单个专业看不见的冲突。 |
| 按专业 + 严重程度排序的问题清单 | Skill 把各专业的返回合并成一份清单，合并同一问题在多张图上的重复项，并按清单自带的严重程度用词排序。 |
| 🛑 review（公司甄别真问题与非问题） | Skill 停下，给出清单，每条附图纸局部截图和它来自哪个清单项；审图人标记为真问题或噪声，只有真问题继续往下走。 |
| 绘图员修复 | 在智能体之外：绘图员修改图纸。 |
| 提交市政府 → 🛑 handoff（市政府图纸审查） | 市政府的审查发生在公司的工具之外；Skill 最后的产出是报建记录和已甄别的清单，没有任何智能体产出会送到市政府。 |
| 将非问题记录为工具反馈 | 每个"噪声"标记都记在产生它的清单项名下，这样每个清单项的误报率可见，清单在项目之间迭代。 |

**检查点：** `review`：清单只被呈现，不被执行；审图人的标记决定什么能到绘图员手上，而 skill 没有修改图纸的工具。`handoff`：市政府的审查不是本搭建方式能做、也不该抢先做的事——输出止于公司自己的记录，市政府随后发来的整改意见，才是这次检查值不值得做的独立度量。

**与来源相比：** 来源是两份未注明日期的厂商案例研究，本月已打开。两份都把公司自己的甄别写成关卡，也都没有公开可测的误报率：所谓"约四分之一"是厂商转述其中一家公司的说法。此后有这些变化：这一类工具从"多一双眼睛"扩展到把检查前移到设计工具内部——2026 年一份对六款分区与规范产品的比较，把[设计环境内的模型化检查、带条文引用的规范检索助手、以及报建前审查描述为不同的层](https://engtechnica.com/six-zoning-and-code-compliance-tools-bring-checks-earlier-into-architectural-design)，并都重申结论仅供参考。由此本搭建方式有两点取舍：真正沉淀下来的是检查清单，而不是厂商；覆盖越广，甄别日志越重要，因为清单变长而误报率稳定在四分之一时，审图人付出的时间会比省下的更多。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 设计公司上传它计划提交的完整图纸集（建筑、市政、结构、规格说明） [[1]](#sources)[[2]](#sources)。
2. AI 依据规范和标准并跨专业进行检查，返回按专业和严重程度排序的问题清单 [[2]](#sources)。
3. 🛑 **审阅**：公司把每条标记甄别为真问题或非问题。在一家公司，约四分之一是真问题。公司保留自己的 QA/QC 流程 [[1]](#sources)。
4. 绘图员在提交之前修复已确认的问题 [[2]](#sources)。
5. 🛑 **接手**：市政府自行做图纸审查。公司记录非问题，并发给工具厂商以改进检查 [[1]](#sources)[[2]](#sources)。

**产出：** 提交的是已清理的报建图纸集，留给市政府发现的问题更少，并附一份已甄别的问题日志。
**失败模式 → 防护：** 误报率高（在 Charlan Brock 约每 4 条标记中有 1 条是真问题）→ 修复前先由公司甄别。浅层工具漏掉已知违规 → 以公司自己的 pre-IFC 评审清单做基准。过度依赖 → 保留内部 QA/QC；AI 只是“多一双眼睛” [[1]](#sources)。
**与相近工作流的区别：** 最接近的是 AWF-0058（带引证的预筛查检查），它运行在监管方一侧：申请人修复被标记的检查项，市政府审查员批准每一项判定。这里是设计公司在提交前对自己的整套图纸运行检查，并自行甄别误报。市政府的审查是之后的接手，而不是检查点，因此使用者、产出和检查点的负责人都不同。

## 公开实例

覆盖度（截至 2026-11-06）：**薄弱**：只有匿名、与厂商相关或由记者转述的说法。收集与复核见 [Second collection pass](../../../../../research/2026-11-second-pass.md)。

- [InspectMind, Charlan Brock Architects case study](https://www.inspectmind.ai/case-studies/charlan-brock-architects) (undated)。750 多张图纸的多户住宅报建图纸集；AI 发现了公司自己的 pre-IFC 评审漏掉的问题；公司甄别了误报。"at least 97 others that had escaped their pre-IFC review"；"roughly a quarter of flagged issues being legitimate"。*第一手：厂商；可信度：中。*
- [InspectMind, Owens Design church project](https://www.inspectmind.ai/case-studies/owens-design-church) (undated)。公司在提交市政府之前修复了 AI 标记的问题；市政府的意见很轻微。"The AI plan checker flagged ~300 issues"。*第一手：厂商；可信度：中。*
