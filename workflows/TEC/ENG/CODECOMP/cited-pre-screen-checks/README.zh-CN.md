# 带条文引用的预审检查

**工具变体：** `civcheck` · `archistar` · `codecomply-ai` · `blitz-ai`

## 背景

在房子可以开工之前，图纸必须通过图纸审查：市政审查员对着建筑规范读整套图，写出申请人必须答复的整改意见。审查员大部分时间花在有确定答案的问题上——每一项要求的图纸是否都在、楼梯净宽是否达到规范下限、烟感布置是否覆盖每间卧室——只有一部分花在判断上。本工作流在审查员前面加了一道预审：申请人上传图纸集，软件按一份固定的检查清单跑一遍，每条结果都是"通过"或"不通过"，并挂上其背后的规范要求。申请人先改能改的再提交；审查员照常审查，然后对每项检查要么认可工具的判定，要么标为错判。最终签发只发生在审查员签字那一刻：预审只是参考，规范解释权在市政，漏掉一处缺陷就是安全隐患，所以任何结果都不能以"决定"的形式送到申请人手上。检查清单刻意窄：只收那些能写成明确逻辑的要求；它会根据一路上记录下来的分歧反复校准。

**术语：**
- **图纸审查（plan review）**：市政对报建图纸的审查，结果是批准或一份整改意见。
- **图纸集（plan set）**：为报建提交的成套图纸与文件：场地、建筑、结构、暖通、电气、给排水。
- **审查员（plans examiner）**：审核图纸集、并有权批准它的市政官员。
- **预审（pre-screen）**：在正式审查之前跑的检查，不能替代正式审查。
- **整改意见、重新报审（corrections, resubmittal）**：申请人必须修掉的问题清单，以及改好后送回的新版图纸。
- **完整性检查（completeness check）**：只看某项文件或图纸是否存在，不看其内容是否合规。
- **条文引用（citation）**：某条结论所依据的规范条款，含版本年份。
- **误放行（false pass）**：工具判为通过、审查员后来退回的条目，也是这里代价最大的错误。

## 用智能体搭建

**形态：** `service`。申请源源不断，检查在没人值守的情况下跑；审查员在自己的审查界面里逐项看到结果，之后再做答复。

**需要：** 现行规范文本（含版本年份与地方修订）以及一份规则库，其中每项检查写成一条要求、它的阈值、条文引用，以及需要从图纸上提取什么；一个图纸集转换器，返回文本、图纸索引和尺寸，均带页码与坐标；申请队列，以及按"申请 + 图纸版本"存放每次运行结果的地方；审查员在许可系统里的界面。智能体不能有盖章、批准或签发许可的工具，也不能写申请人的图纸集。

| 步骤 | 搭建方式 |
|---|---|
| 上传图纸集 | 许可门户或一个监视目录，每上传一套就启动一次运行；同一套图的新版本算新的一次运行，旧结果不会显示在新图纸上。 |
| 提取为结构化数据 | 转换脚本返回文本、图纸索引与量取尺寸，均带页码和坐标；定位不到的内容记为缺失，不做猜测。 |
| 每个预设检查：通过/不通过 + 条文引用 | 按检查分组，每组一个 Subagent，只给它该条规则和已提取的数据，并要求只回答这一项；返回通过、不通过或无法判定，附条文引用与读数的页码。 |
| 申请人整改 | 在智能体之外：申请人修改图纸并重新提交。 |
| 提交 | 重新提交触发对新图纸的一次全新运行；上一次结果留作对比。 |
| 审查员查看 AI 判定 → 🛑 review（逐项批准 / 需整改） | 结果以"每项检查一行"的形式进入审查员队列，附条文引用和图纸局部截图；批准或退回某一行是审查员在许可系统里的权限，本次运行对该系统只有读权限。 |
| 结构化反馈 → 重新校准检查项 | 判定被标错时，按检查项 id 与规则版本写一条记录；规则库只能通过一次受审阅的提交来修改，新规则上线前能看到该检查项的误放行率。 |

**检查点：** `review`：运行本身不会对外给出任何决定。它的产出只是审查员队列里每项检查一行，而"批准"或"需整改"这两个动作只存在于许可系统中，本次运行在那里是只读的，所以规范解释与签字都留在市政手上。凡是漏判会有危险的检查，规则要写成"无法判定"而不是"通过"，并且这条约束写在检查项的代码里，不写在提示词里。

**与来源相比：** 来源出自 2026-06：市政府的试点报告（价值验证期为 2025 年 3 月至 10 月）以及市政府自己的总结页面。两者本月均已打开，报告是通过 PDF 文本读取器打开的。此后有这些变化：试点变成了强制要求。檀香山从 2026-09-01 起对符合条件的住宅项目强制使用同一类预审，跳过它的申请会在预审环节被退回，并称每个许可平均节省 40.5 天、[图纸审查轮次从 3.4 轮降到 1.4 轮](https://www.honolulu.gov/dpp?p=43765)。多伦多启动了试点，[每条结论都附上其背后要求的条文引用](https://www.claritisoftware.com/blog/city-of-toronto-launches-ai-pre-check-with-clariti-to-speed-up-housing-approvals)，两市都把工具描述为指引：不批准、不拒绝、也不拖延许可。这与本条目描述的检查点一致，同时把重心挪到了审查员逐项退回这件事上：一旦申请人必须使用预审，误放行率就是真正要看的数字，而上面的校准循环就是守住它的办法。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 只配置那些能转化为明确逻辑的检查项。西雅图用了 34 项完整性检查和 67 项合规性检查，范围限定在《西雅图住宅规范》下较简单的住宅类“中间住宅”（middle housing）[[1]](#sources)。
2. 申请人上传图纸集。工具把图纸内容提取为结构化数据，运行所有预设检查，返回与规范要求挂钩的通过/不通过结论 [[1]](#sources)[[2]](#sources)。
3. 申请人在提交之前先整改被标记的问题。申请仍然要走市政府的正常审查流程 [[2]](#sources)。
4. 🛑 **审阅**：在图纸审查阶段，市政审查员先做正常审查，然后看到工具对每项检查给出的通过/不通过判定。他们点击“批准”或“需整改”，并在工具出错时提交结构化反馈 [[1]](#sources)。
5. 供应商根据审查员的反馈重新校准检查项。试点期间准确率不断提高 [[1]](#sources)[[2]](#sources)。

**产出：** 给申请人的逐项检查结果报告，附规范条文引用，之后是正常的市政许可审查。审查员保有最终决定权。
**失败模式 → 防护：** 漏掉整改项，即工具放行了审查员退回的条目 → 对每项检查设置审查员关卡，并跟踪误放行率。规范无法转化为逻辑而出现覆盖缺口，申请人把它当作“又一道门槛” → 先把范围限制在简单的建筑类型和完整性检查 [[1]](#sources)[[2]](#sources)。
**与相近工作流的区别：** 暂无相近者。AWF-0024 按手册审阅合同（playbook contract review）是对照手册检查文档，但其交付物是带修订标记的合同，而不是许可审查结果。

## 公开实例

覆盖度（截至 2026-11-06）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [New workflows for empty categories](../../../../../research/2026-11-new-workflows.md)。

- [City of Seattle, CivCheck AI Pre-Screening Pilot Report](https://seattle.gov/documents/Departments/Performance/Publications/2026CivCheckEvaluationReport.pdf) (2026)。审查员对 57 份住宅申请中的 1,262 项检查的 AI 通过/不通过判定进行了评判。"Overall Accuracy: 91.7%"。*第一手：是；可信度：高。*
- [Seattle Innovation & Performance, CivCheck pilot insights](https://innovation-hub.seattle.gov/2026/06/17/ai-construction-permitting-seattle-civcheck-study/) (2026-06-17)。市政府对试点的总结：准确率，以及覆盖范围与准确率同样重要。"application completeness checks were 87% accurate and design compliance checks were 92% accurate"。*第一手：是；可信度：高。*
