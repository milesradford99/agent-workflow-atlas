# 规范书生成报审清单

**工具变体：** `custom-rag-gpt-4o-mini` · `pype-autospecs`

## 背景

一个项目的规范书是几百页到上千页的册子，逐章规定建筑的每个部分应该是什么。里面埋着"必须报审"的要求：密封胶要交产品数据表，面砖要交样板，混凝土配合比要交检测报告，防火门要交证书。开工之初，得有人把整本读完，把每一条这样的义务写进一份清单——报审台账——因为这份台账会变成进度的依赖表：某样材料在报审获批之前不能采购、不能安装；而没人写下来的要求，往往在材料已经误期之后才被发现。手工编这份台账要一位有经验的项目工程师好几天，而且这类阅读最容易漏掉段落中间的某个从句。在这里，智能体读规范书，按章节切分，提取每条要求及其附带条件，起草清单和发给分包商的移交函。项目工程师随后核实条目、删除重复、补上遗漏再发出：这份清单是约束各工种节点的合同性文件，所以由人签发。

**术语：**
- **规范书（spec book）**：规定本工程每个部分技术要求的项目手册。
- **CSI 章节编号（CSI section numbering）**：规范章节的标准编号方式，按分部与章节编排，例如保温对应 07 21 00。
- **报审清单 / 台账（submittal register / log）**：每一项须报审批准的事项清单，含所属章节、类型和截止日期。
- **移交函（transmittal）**：随文件发出、并记录已发出的封面函件。
- **动作类报审（action submittal）**：需要先批准才能继续施工的报审，与仅作告知的相对。
- **条件说明（conditional note）**：只在某种情况下才适用的要求，例如"若基层为混凝土"。
- **长周期材料（long-lead item）**：到货周期长到必须提早获批报审的材料。
- **项目工程师（project engineer）**：承包商一方负责现场报审流程的工程师。

## 用智能体搭建

**形态：** `skill`。项目工程师在开工时对一个项目的规范书跑一次，在对话里核实草稿；提取工作在这个 skill 内按章节展开。

**需要：** PDF 格式的规范书，文本版而非扫描版；项目的分部清单和符合团队平台格式的清单模板；移交函模板；类似项目的过往清单用作基准；平台里的章节列表，让清单能与之对齐。智能体不需要平台写权限：发出由人完成。

| 步骤 | 搭建方式 |
|---|---|
| 规范书 PDF | skill 旁边的脚本逐页提取文本，遇到扫描页如实拒绝，而不是半猜半读，扫描图纸因此被排除在外。 |
| 识别 CSI 章节编号 | 同一脚本套用针对标准章节格式调校的数字模式，并列出找到的章节及其页码，供工程师对照规范书自己的目录。 |
| 分块 + 嵌入 + 建索引 | 每个项目一个本地索引，分块相互重叠，跨页断开的条款不会被切成两半。 |
| 每个章节：提取报审要求 + 条件说明 | 每个分部一个 Subagent，只给它该分部的文本块，返回"章节编号、要求、条件、来源页"组成的行；原文没有要求时就返回空。 |
| 起草清单（Excel）+ 移交函（Word） | 脚本用这些行生成两个文件，所以表格和函件不会互相矛盾。 |
| 🛑 review（项目工程师核实条目、删除重复、补全遗漏） | Skill 交出草稿，同时列出"一条都没找到"的章节——遗漏最可能就藏在那里；工程师直接在清单上修改，这些修改留作下个项目的参考。 |
| 向分包商发出清单 + 移交函 | 在智能体之外：由工程师通过项目平台发出。 |

**检查点：** `review`：在有人过一遍之前，清单只是草稿；本搭建方式把"空章节"和"已填章节"一起列出，让这次核实可行——真正要命的失败是漏掉，而一张满是行的表格本身看不出漏了什么。智能体没有平台访问权，所以从它那里发不出任何东西。

**与来源相比：** 来源出自 2026-01，另有一份未注明日期的厂商案例研究。同行评议的现场测试本轮没有重新打开；改为核对了厂商的产品现状。此后有这些变化：`variants` 里点名的那款工具变了。Pype AutoSpecs 现在是 Autodesk 的产品，只在 Forma for Construction Operations 套餐内授权；Pype 的两款老产品（eBinder 与 SmartPlans）已于 2024 年 3 月停止销售；现行产品增加了[跨规范版本的差异比对，以及基于相似项目推荐的遗漏项](https://testedintelligence.com/pype-review)。这对本条目有直接影响：清单一旦编成，来一份补充文件就过时了；上面的搭建方式应当在修订版规范上重跑，并与已发出的清单做差异比对，而不是靠手工维护。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 把项目规范书 PDF（800 到 1,500 页）上传到工具中；文本按页提取 [[1]](#sources)。
2. 用针对 CSI SectionFormat 编号调校过的正则表达式识别并切分规范章节（例如 "07 21 00"、"072100"），无需任何手工标记 [[1]](#sources)。
3. 把每个章节切成相互重叠的块，嵌入后存入向量索引；扫描图像和图纸不在其内 [[1]](#sources)。
4. 针对每个章节（或用户查询，例如 "List all submittals under 07 21 00"），检索相关块，让模型返回结构化的行：章节编号、报审要求、条件说明 [[1]](#sources)。
5. 把这些行导出为可直接用于移交的 Excel 清单和 Word 移交函 [[1]](#sources)。商业工具把同一步骤做成一次性的台账草稿 [[2]](#sources)。
6. 🛑 **审阅**：项目工程师在台账投入使用前，核实提取的条目，并纠正误分类和重复的行；作者报告有些条目 "required expert review" [[1]](#sources)。在 Mortenson，起草环节节省下来的时间被用于 "more thorough reviews" [[2]](#sources)。
7. 向分包商发出经核实的清单和移交函；清单随后驱动报审审查周期（见 AWF-0151）。

**产出：** 一份经核实的报审清单（Excel）加移交函，在项目开始时发出，用于跟踪每一项所需的报审。
**失败模式 → 防护：** 语义漂移会让相邻段落中相似的措辞产生重复条目；过长的条款超出上下文窗口，丢掉次要条件 → 更小的分块、自适应提示词，以及项目工程师的逐行审阅 [1]。
**与相近工作流的区别：** AWF-0151 首轮报审审查（First-pass submittal review）把分包商已经提交的报审资料对照规范书检查，最终由建筑师处置。本工作流是在任何报审资料到达之前，生成所需报审资料的清单；产出物是这份台账，唯一的检查点是项目工程师的核实，没有设计师签发。

## 公开实例

覆盖度（截至 2026-11-13）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [Kalasapudi et al., Frontiers in Built Environment](https://www.frontiersin.org/journals/built-environment/articles/10.3389/fbuil.2025.1713342/full) (2026-01-02)。与一家土木承包商合作的同行评审现场测试；在 10 份 800–1,500 页的规范书上做基准测试；保留对条目的人工审阅。"Average end-to-end processing time was approximately 6–8 min per document"; "total computational costs under USD 0.10 per file"。*第一手：研究；可信度：高。*
- [Pype, Mortenson case study](https://www.casestudies.com/company/pype/case-study/mortenson-scales-accuracy-quality-of-submittal-log-review-with-pype) (n.d.)。大型总承包商自动起草报审台账，然后再审阅；发现了更多报审项。"reduced the time spent creating a draft log by 99%, from 34 hours down to under 5 minutes"。*第一手：厂商；可信度：中。*
