# 规则集结论审阅

**与相近工作流的区别：** 最接近的是 AWF-0151（报审初审，first-pass submittal review）：那是承包商一方给出建议，由项目经理/项目工程师整体修改，再发给分包商或建筑师。本工作流是审核一方（业主/顾问工程师），依据工程师确认过的项目规则集开展工作（有 🛑 plan，0151 没有）。工程师对约 25 条规则结论逐条确认或改写，并记录理由，交付物是按模板生成的合同回复。AWF-0190 是依据规格建立报审登记册，而不是审核某一次报审。
**工具变体：** `qwen3-next-80b-on-prem` · `react-multi-agent`

## 步骤

1. 载入合同的通用规格（GS）和专用规格（PS）。冲突智能体（Conflict Agent）对两者比较，并按合同规定的优先顺序，提出每处不一致的解决办法 [[1]](#sources)。
2. 🛑 **计划**：工程师审阅提出的调和方案，并确认调和后的规格。系统随后把它转成可执行的审批检查清单（Approval Checklist），即项目自己的规则集 [[1]](#sources)。
3. 每份收到的材料报审（产品目录、数据表、第三方检测证书、合规声明；60–100 页）先经过版面感知解析器。表格整体保留为单个分块，每个分块都保存页码和边界框 [[1]](#sources)。
4. 对检查清单中的每条规则，验证智能体（Verification Agent）先做针对性检索，再分三步推理：提取论断、与阈值比较、得出结论。它返回 JSON 格式的结论（通过、不通过或存疑），附置信度分数和证据位置，界面会在原始 PDF 上高亮显示 [[1]](#sources)。
5. 严重程度排序技能按对安装、安全和法定义务的影响，把每个不合规项标为 Critical、Major 或 Minor [[1]](#sources)。
6. 🛑 **审阅**：工程师确认或改写每条结论。改写需要填写自由文本理由，并连同用户身份、时间戳和原因一起记入日志 [[1]](#sources)。
7. 🛑 **签发**：工程师最终批准后，综合智能体（Synthesis Agent）把确认过的结论和评语填入固定的、经法律审定的模板。文件通过项目管理平台回到承包商手中 [[1]](#sources)。
8. 记录下来的改写被收集起来，作为改进系统的反馈 [[1]](#sources)。

**产出：** 一份逐条规则的合规报告，含结论、严重程度和证据链接，另有发给承包商的正式合同回复，通过部门的项目管理平台发出。
**失败模式 → 防护：** 通用规格与专用规格的冲突调和错误 → 在任何检查之前由工程师确认调和后的规格。表格与单位被拆开，或把 IP54 与 IP65 混淆 → 版面感知分块和领域适配的 embedding 模型。工程师不看就接受结论 → 每条结论都有高亮的证据，每次改写都要写明理由。论文中的精确率/召回率数字是基于假设比例的估计；只有 12% 的改写率是实测的。

## 公开实例

覆盖度（截至 2026-11-13）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [Fourth collection pass](../../../../../research/2026-11-fourth-pass.md)。

- [EMSD HKSAR, From Retrieval to Verification (industrial pilot)](https://openaccess-api.cms-conferences.org/articles/download/979-8-950676-12-3_12) (2026-08-25)。在 10 个在建的 RMAA 机电项目上试点：63 份材料报审，1,575 条规则级结论由工程师审阅。"a 70.9% reduction in average review time, from 52.5 minutes under the existing digital workflow to 15.3 minutes"; "human overwrites required in only 12% of verdicts"。*第一手：是；可信度：高。*
