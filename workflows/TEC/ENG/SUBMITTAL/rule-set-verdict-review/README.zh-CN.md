# 规则集结论审阅

**工具变体：** `qwen3-next-80b-on-prem` · `react-multi-agent`

## 背景

政府部门或大型业主建造、改造楼宇时，承包商打算用的材料必须在到货之前获批：产品目录、数据表、第三方检测证书、合规声明，一份六七十页到上百页。审阅人是业主一方的工程师，依据的是合同里的两本规格书——通用规格，以及修改它的专用规格——外加一份清单，规定每种材料必须证明什么：防火等级、防护等级、温度范围、法定证书。判断不大，但后果不小：批错一次，未认证的部件就进了医院或车站；而回给承包商的那份回复，本身就是合同文件。审一份就是：在长长的规格书里找到每个阈值，在 PDF 深处找到对应的声称，再逐项比较；手工做，每份要小一小时，一个项目有几百份。在这里，机器承担检索、提取和比较，每条规则给出一个结论、一个置信度，以及它在 PDF 上读到的确切位置。工程师逐条确认或改写，改写必须写理由，最后由他给出批准，把结论变成合同回复。这两个动作留在工程师手上，因为约束双方的是合同，不是软件。

**术语：**
- **通用规格 / 专用规格（General Specification / Particular Specification）**：合同的标准规格书，以及针对本项目修改它的专用规格书；两者冲突时按合同规定的优先顺序处理。
- **材料报审（material submission）**：承包商为取得产品批准而提交的材料：目录、数据表、检测证书、声明。
- **审批检查清单（approval checklist）**：项目自己的规则集——每种材料必须满足的要求，一项一行，带阈值。
- **结论（verdict）**：针对一条规则的判定：通过、不通过，或存疑（现有证据不足以判定）。
- **防护等级（IP rating）**：说明外壳防尘防水能力的两码等级；IP54 与 IP65 不能互换。
- **严重程度（severity）**：按不合规对安全、安装和法定义务的影响，分为 critical、major、minor。
- **改写（override / overwrite）**：工程师替换机器的结论，必须附书面理由。
- **合同回复（contractual reply）**：回给承包商的正式文件，措辞是固定的、经过法律审定的。

## 用智能体搭建

**形态：** `service`。材料按承包商自己的节奏到达，检查在没人按开始的情况下跑；工程师处理一个结论队列，最终批准释放出合同回复。

**需要：** 两本规格书的文本形式，以及写下来的合同优先顺序；审批检查清单，作为带版本的文件，一行一条规则，含阈值、单位和来源条款；PDF 格式的材料报审，配一个解析器：表格整体保留，每个提取块记录页码和边界框；经过审定的回复模板，冻结不改；一个结论队列和一份改写日志。智能体不能有发给承包商的工具，不能修改模板，也不能写已批准的清单。

| 步骤 | 搭建方式 |
|---|---|
| 通用规格 + 专用规格 → 冲突智能体调和 | 一个 Subagent 读两本规格书，返回一张冲突表，含两边的条款原文和它套用的优先顺序规则；它只提方案，不做合并。 |
| 🛑 plan（工程师确认调和后的规格） | 运行停在冲突表；检查清单只能由工程师确认过的版本生成，`PreToolUse` 钩子拒绝从未确认的草稿生成清单。 |
| 审批检查清单（项目规则集） | Skill 写出规则文件：一行一条要求，含阈值、单位、来源条款，以及它对应的回复模板。 |
| 每份材料报审：版面感知解析 + 建立索引 | 解析脚本把表格作为整体保留，每个分块都存页码和边界框，这样一个数字永远不会脱离它所在那行的单位被报出来。 |
| 每条规则：检索证据 → 提取 → 比较 → 结论 | 每条规则一个 Subagent，只返回 JSON：结论、置信度、证据原文及其页码与位置框；无法判定的返回"存疑"，而不是猜一个。 |
| 严重程度排序（critical / major / minor） | 脚本套用规则文件里的严重程度定义，所以排序是工程师的政策，不是模型的印象。 |
| 🛑 review（工程师逐条确认或改写结论，改写须写明理由） | 结论带着高亮的证据进入工程师队列；改写控件只在那里存在，且强制填写理由，理由与工程师身份和时间戳一起存档。 |
| 用经过审定的模板生成合同回复 → 🛑 sign-off | Skill 只用确认过的结论和评语填充映射好的模板；释放它的动作是工程师的批准，而发送工具属于项目管理平台，不属于本次运行。 |
| 发送给承包商 → 改写日志用于改进 | 投递由工程师完成；改写累积成对规则文件的差异，作为建议提交审阅，而不是自动生效。 |

**检查点：** `plan`：工程师确认调和后的规格之前不开始任何检查，钩子负责落实，因为后面每条结论都继承这次调和。`review`：结论不经人就不能离开队列；改写必须写理由，理由与作者一起存档，所以"没看就接受"事后看得见。`sign-off`：回复只用冻结的模板和确认过的结论装配，释放靠工程师批准，而本次运行没有任何通往承包商的通道——一次错误批准要经过两个人才能变成合同文件。

**与来源相比：** 来源出自 2026-08：一份经过同行评议的工业试点，本月通过 PDF 读取器打开，也是本条目的公开实例。它实测的是改写率，精确率与召回率仍是基于假设比例的估计，条目标注了这一点。此后有这些变化：同样的形态正在别处被产品化。2026-10，一家中国建筑央企上线了一个平台，用多智能体对危大工程施工方案做初审，覆盖 26 类工程，[每条意见都附规范条文或规则出处、全过程留痕，复核人确认、驳回或补充后才生成标准报告](https://www.stdaily.com/web/gdxw/2026-10/09/content_592939.html)——同样是一步"确认或改写"，只是从另一个行业长出来。上面的搭建方式与论文有一处有意的不同：它把规则集保存成工程师确认过的带版本文件，所以一次改写是对某条规则的差异，这才让改写日志能用于改进，而不只是留痕。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 载入合同的通用规格（GS）和专用规格（PS）。冲突智能体（Conflict Agent）对两者比较，并按合同规定的优先顺序，提出每处不一致的解决办法 [[1]](#sources)。
2. 🛑 **计划**：工程师审阅提出的调和方案，并确认调和后的规格。系统随后把它转成可执行的审批检查清单（Approval Checklist），即项目自己的规则集 [[1]](#sources)。
3. 每份收到的材料报审（产品目录、数据表、第三方检测证书、合规声明；60–100 页）先经过版面感知解析器。表格整体保留为单个分块，每个分块都保存页码和边界框 [[1]](#sources)。
4. 对检查清单中的每条规则，验证智能体（Verification Agent）先做针对性检索，再分三步推理：提取论断、与阈值比较、得出结论。它返回 JSON 格式的结论（通过、不通过或存疑），附置信度分数和证据位置，界面会在原始 PDF 上高亮显示 [[1]](#sources)。
5. 严重程度排序技能按对安装、安全和法定义务的影响，把每个不合规项标为 Critical、Major 或 Minor [[1]](#sources)。
6. 🛑 **审阅**：工程师确认或改写每条结论。改写需要填写自由文本理由，并连同用户身份、时间戳和原因一起记入日志 [[1]](#sources)。
7. 🛑 **签发**：工程师最终批准后，综合智能体（Synthesis Agent）把确认过的结论和评语填入固定的、经法律审定的模板。文件通过项目管理平台回到承包商手中 [[1]](#sources)。
8. 记录下来的改写被收集起来，作为改进系统的反馈 [[1]](#sources)。

**产出：** 一份逐条规则的合规报告，含结论、严重程度和证据链接，另有发给承包商的正式合同回复，通过部门的项目管理平台发出。
**失败模式 → 防护：** 通用规格与专用规格的冲突调和错误 → 在任何检查之前由工程师确认调和后的规格。表格与单位被拆开，或把 IP54 与 IP65 混淆 → 版面感知分块和领域适配的 embedding 模型。工程师不看就接受结论 → 每条结论都有高亮的证据，每次改写都要写明理由。论文中的精确率/召回率数字是基于假设比例的估计；只有 12% 的改写率是实测的。
**与相近工作流的区别：** 最接近的是 AWF-0151（报审初审，first-pass submittal review）：那是承包商一方给出建议，由项目经理/项目工程师整体修改，再发给分包商或建筑师。本工作流是审核一方（业主/顾问工程师），依据工程师确认过的项目规则集开展工作（有 🛑 plan，0151 没有）。工程师对约 25 条规则结论逐条确认或改写，并记录理由，交付物是按模板生成的合同回复。AWF-0190 是依据规格建立报审登记册，而不是审核某一次报审。

## 公开实例

覆盖度（截至 2026-11-13）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [Fourth collection pass](../../../../../research/2026-11-fourth-pass.md)。

- [EMSD HKSAR, From Retrieval to Verification (industrial pilot)](https://openaccess-api.cms-conferences.org/articles/download/979-8-950676-12-3_12) (2026-08-25)。在 10 个在建的 RMAA 机电项目上试点：63 份材料报审，1,575 条规则级结论由工程师审阅。"a 70.9% reduction in average review time, from 52.5 minutes under the existing digital workflow to 15.3 minutes"; "human overwrites required in only 12% of verdicts"。*第一手：是；可信度：高。*
