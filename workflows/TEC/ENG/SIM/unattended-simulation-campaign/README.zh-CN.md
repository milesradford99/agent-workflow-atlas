# 无人值守仿真批量计算

**工具变体：** `move-platform`

## 背景

设计车辆悬架时，团队想知道它在成千上万种组合下的表现：每个硬点朝各个方向挪一点，每个衬套变软或变硬。与其逐个造出来测试，不如做仿真：多体模型能预测车轮怎么动、零件承受多大载荷。跑一次仿真只回答一个问题；真正关心的问题需要试验设计——在设计空间上有计划地扫一遍——以及代理模型，也就是拟合在仿真结果上的快速近似，让某种配置几秒钟就能查出来，而不是跑一小时。瓶颈不在求解器，而在中间那个人：搭运行、盯着跑、诊断失败的那些、再手工处理输出。在这里，智能体在一个已验证的模型上通宵跑完整个批量计算：规划运行、分批执行、捕捉失败——包括求解器报告成功但结果错误这种危险情况——在多种样本量下拟合几种代理模型技术，并找出近似最弱的区域。没有两道人工关卡，这一切都不安全。资深工程师在任何一次运行花出去之前定义研究和验收检查，因为在没校准的模型上做批量计算，会得到成千上万个自信的错误答案；代理模型也要在有人据此做设计之前，由工程师验证。

**术语：**
- **多体仿真（multibody simulation）**：预测由连杆、衬套、弹簧等连接起来的刚体在载荷下的运动。
- **K&C**（kinematics and compliance，运动学与柔度）：车轮运动与所施加力之间实测或仿真的关系，用来核对悬架模型与实车是否一致。
- **硬点（hardpoint）**：悬架连杆的连接点，由设计师可调的坐标给出。
- **衬套刚度（bushing stiffness）**：橡胶或高分子接头在载荷下的变形量，对预测结果影响很大。
- **试验设计（design of experiments）**：为高效覆盖参数空间而挑选的一组运行计划。
- **代理模型（surrogate model）**：拟合在已完成运行上的、对仿真器的快速统计近似。
- **平衡点（equilibrium）**：求解器收敛到的稳定状态；收敛到错误的那一个，看上去同样像成功。
- **样本量（sample count）**：拟合代理模型所用的仿真次数，决定其精度。
- **HPC**（high-performance computing，高性能计算）：并行跑大量仿真的机器集群。

## 用智能体搭建

**形态：** `service`。批量计算在夜里分批跑，现场没人；工程师看到的是一份待批准的研究计划，结束时是一个待验证的代理模型，失败项从队列里处理。

**需要：** 能在无人值守下运行的求解器，部署在工程师的工作站或 HPC 队列上，许可证允许多次批量使用；已校准的模型以及用于校准的实测数据；对话之外的状态存储——一张数据库表或一个运行记录目录——保存运行队列、每次运行的输入、状态和结果路径；智能体可用于提交作业的计算账号；以文件形式给出的研究定义与验收检查；脚本化的绘图与拟合库。智能体不能发布代理模型应用，也不能写进设计记录。

| 步骤 | 搭建方式 |
|---|---|
| 🛑 plan（工程师定义研究、设计空间、检查项） | 智能体起草研究文件——参数、范围、输出、验收检查——并投到工程师的队列；在批准版本进入状态存储之前不提交任何运行，`PreToolUse` 钩子负责拦住提交。 |
| 对照实测数据校准模型（运行 ⟲ 对比曲线）→ 验证报告 | 脚本运行模型并与实测曲线叠加；Skill 提出修正、重跑，并把验证报告写在模型旁边。 |
| 规划运行 | Skill 把批准的试验设计对应的运行清单写入队列，每个输入都记录下来，使每个结果都能追溯到产生它的设置。 |
| 每个批次：求解 ⟲ 合理性检查，诊断 + 重新求解 | 一个 Agent SDK 程序从队列取出一个批次并提交；检查脚本对每个结果做物理合理性与收敛判定；未通过的结果带着诊断进入修复队列，程序修正设置后重新提交，直到该批次干净。 |
| 后处理完整结果集 | 脚本把运行归并成一个结果集——每种配置的曲线与载荷峰值——并记录哪些运行被剔除、原因是什么。 |
| 在多种样本量下拟合代理模型技术 → 误差研究 + 最差情形叠加图 | 对结果子集做脚本化拟合；Skill 比较各技术、写出误差研究，并把最差预测叠加到仿真曲线上。 |
| 🛑 review（工程师验证代理模型） | Skill 汇总一份验证包——误差研究、最差情形叠加图、被剔除的运行、未解的疑点——放进评审队列；工程师签字之前代理模型不得投入使用，智能体也没有发布它的工具。 |
| 以交互式应用 + 过程日志共享 | 应用由脚本基于拟合好的代理模型生成；发布给同事由人完成，Skill 的决策日志与研究报告一起提交，下一次批量计算从这里起步。 |

**检查点：** `plan`：没有批准的研究文件就无法开始运行，而且拦住提交的是钩子而不是一句叮嘱——批量计算的算力代价高且不可撤回。`review`：验证包进入评审队列，智能体没有发布或签发的工具，所以没人核对过的代理模型到不了设计人员手上；被剔除的运行也列在包里，悄悄出错的运行无法从记录里消失。

**与来源相比：** 来源出自 2026-07：一份厂商文字，也是本条目的公开实例。该页面本月已打开。此后厂商又发表了[同一方法的第二份记录](https://www.movedot.ai/blog/closing-the-loop-between-simulation-driver-in-the-loop-and-real-measurements)（2026-05-29），把它扩展到驾驶模拟器在环和实测；并在 2026-09 宣布[与 HBK、VI-grade 合作](https://www.vi-grade.com/en/about/news/hbk-vi-grade-and-movedot-partner-to-bring-ai-agents-to-simulation-and-physical-testing-3424)，把智能体接进这两家的仿真与测试工具。对本搭建方式的意义：连接件的工作正在转向商业工具链，上面的脚本仍是团队自己要写的那部分，而研究定义和验证包必须留在工程师手上。没有改变的是：识别“收敛到错误平衡”的检查属于闸门逻辑而不是模型判断；厂商自己的数字也把工程师工时节省标注为估算而非实测。

## 步骤

*以下按来源所述。*

1. 🛑 **计划**：资深工程师定义研究（参数、范围、输出）；该页面把“定义研究”计入工程师的实际动手时间 [[1]](#sources)。
2. 先校准模型：智能体运行五连杆悬架模型，把曲线与实测的 K&C 数据对比，发现衬套刚度解释了大部分差距，并应用一致的缩放修正；它会写出一份验证报告 [[1]](#sources)。
3. 在设计空间上规划批量计算（38 个参数：30 个硬点坐标在 +/-15 mm 内、7 个衬套刚度、弹簧刚度），并在夜间分批运行，在本地或 HPC 上均可，保持每个结果都可追溯到其输入 [[1]](#sources)。
4. 检查每个结果的物理合理性，既能发现未收敛的运行，也能发现求解器报告成功但收敛到错误平衡的运行；找出哪些参数组合会让求解器出问题，并重新求解 [[1]](#sources)。
5. 后处理为一个结果集（运动学和柔度曲线，每种配置的硬点载荷峰值）[[1]](#sources)。
6. 调研候选的代理模型技术，在不同样本量下逐一拟合并量化误差；把 6 个最差的预测叠加在仿真曲线上 [[1]](#sources)。
7. 🛑 **审阅**：工程师在代理模型投入使用之前对其做验证（“验证”计入动手时间）[[1]](#sources)。
8. 把代理模型打包成供同事使用的交互式应用，并保留智能体对决策和失败的记录，供下一次研究使用 [[1]](#sources)。

**产出：** 一个结果数据库、一个附误差研究的经验证代理模型、一个交互式应用，以及下一次研究可以起步的、有文档记录的流程。
**失败模式 → 防护：** 悄悄出错的运行（求解器在错误的平衡点报告成功）污染数据集 → 逐次运行的合理性检查 [1]。未经验证的基础模型会产生数千个错误答案 → 先对照实测校准 [1]。代理模型在某些区域较弱 → 审阅最差情形叠加图 [1]。
**与相近工作流的区别：** AWF-0057 工程师把关的 CFD 运行（Engineer-checked CFD run）搭建并求解单个算例，对该算例做物理方案检查和物理审阅。这里的产出是包含数千次运行的试验设计批量计算，加上代理模型和应用；没有人检查单次运行，只检查研究定义和最终的代理模型。
