# 差异验证的 dbt 迁移

**工具变体：** `datafold-migration-agent` · `claude-code-skills` · `dbt-mesh` · `snowflake`

## 背景

企业把多年积累的业务逻辑以 SQL 脚本和存储过程的形式放在数据仓库里。它们能跑，但很少有人真正读得懂，也很难修改和测试。团队把它们迁移到 dbt，这个工具把每项转换保存为一个小的、纳入版本控制、带测试的模型。风险在于，重写后的模型可能悄悄算出不同的数字，所以真正的工作是证明新表在生产数据上和旧表一致。智能体翻译代码，把每个结果与生产数据比对，并解释每一处差异。每张表仍须由它的负责人批准，因为只有负责人能判断差异是旧逻辑的错还是新逻辑的错，而最后的切换会改变所有报表显示的内容。

**术语：**
- **数据仓库**：企业存放报表用数据的中央数据库。
- **存储过程（stored procedure）**：保存并运行在数据库内部的长程序，常常有几千行 SQL。
- **dbt 模型**：一项转换，写成版本控制项目里的一个 SQL 文件并带测试；dbt 是运行这些模型的工具。
- **血缘（lineage）**：哪些表由哪些表生成的关系图。
- **语义层**：业务指标的统一定义，例如什么算收入。
- **维度表和事实表**：报表所依赖的描述性表（客户、产品）和事件或度量表（销售）。
- **data diff**：逐行比较两张表，显示哪些行或值不同。
- **一致性（parity）**：新输出与旧输出相符；双向 MINUS 检查会分别列出只在一边出现的行。
- **增量水位线（incremental watermark）**：让模型只处理比上次运行更新的行的过滤条件；它可能悄悄丢掉时间戳为空或迟到的行。
- **dbt Mesh**：dbt 把大项目拆成多个相互依赖的项目的方式。
- **数据负责人**：对某张表的数字负责的人。
- **切换（cutover）**：把报表从旧表指向新表。

## 用智能体搭建

**形态：** `project`。翻译本身可以由 skill 承载，但有三件事必须对每个模型都成立：没有 data diff 就不能把表标为已批准；绝不写入生产环境；在所有批准都记录在案之前不得切换。这需要钩子或权限规则，而且工作要扇出到几百个模型，需要自定义的工作者。来源 3 中的单人变体是把各阶段做成 Claude Code skill，处理了 45 条管道。

**需要：** 以文件形式提供的遗留代码、血缘元数据、导出的 wiki 页面和会议转写；仓库里的一个 dbt 项目（或每个负责人一个）；一个能读生产环境、只能写开发 schema 的数据仓库角色；一个运行 data diff 并把有差异的行写入文件的脚本或工具；每张表的数据负责人名单；新模型的需求。

| 步骤 | 搭建方式 |
|---|---|
| 梳理血缘 + 遗留代码 + 文档 | 只读子智能体阅读代码、血缘元数据和导出的文档，把血缘图和没有文档记录的假设清单写入文件。 |
| 切分大型存储过程 | skill 的一条指令：在逻辑边界处拆分过大的存储过程，并记录哪个片段对应哪个模型。 |
| 每个模型：翻译成 dbt | 自定义子智能体，每个模型一个，在分支上写出 dbt 模型和测试。可以用动态工作流脚本扇出到大量模型。 |
| (与生产数据做 data diff ⟲ 智能体解释或修复差异) | 脚本对生产数据运行双向 MINUS diff。子智能体必须依据遗留代码、新代码和需求写出每处差异的解释，或者修复模型后重跑。仍无法解释的差异回到循环中。 |
| 🛑 review | 见“检查点”。 |
| 批量处理外观类修改 | skill 维护一份重命名等修改的清单，等数据验证完毕后一次性应用。 |
| 🛑 sign-off | 见“检查点”。 |

**检查点：** `review`：每张表都由 skill 停下，呈现行级 diff 和解释，而不只是文字总结；数据负责人的批准记录在一个批准记录文件里。审阅阶段开始后，`PreToolUse` 钩子会拦住任何涉及没有批准记录的模型的推送。`sign-off`：智能体的数据仓库角色对生产环境只读，也没有部署或切换的工具，所以只有每个维度表和事实表都有批准记录之后，才由人切换报表层背后的表。

**与来源相比：** 来源的日期从 2025-07 到 2026-10。三者都在 2026-11 打开过，各自支持其所引用的步骤。主要的记述（来源 1）是厂商博客对一次客户演讲的总结，讲的是 Datafold 的迁移智能体这一产品。本搭建方式用通用智能体、脚本和钩子替代了它的各个部分，不含该产品自带的切片和可视化 diff 功能。通用智能体在来源 1 那样的规模上表现如何，没有报道；来源 3 只报告了单人处理 45 条管道的情况。来源 1 说切换不在其所述阶段的范围内，这里切换仍然是人来做的事。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 智能体梳理完整的血缘、遗留代码库和语义层，并从 wiki 和会议录音中提取没有文档记录的背景信息 [[1]](#sources)。
2. 智能体在逻辑边界处拆分过大的存储过程。一个 300K 字符的存储过程被拆成了约 400 个模型 [[2]](#sources)。它把遗留代码翻译成职责清晰的模块化 dbt 项目，跨项目的部分使用 dbt Mesh [[1]](#sources)。
3. 智能体用自动化的 data diff 把每个翻译后的模型与生产数据比对。对任何预期内的差异，它都必须结合遗留代码、新代码和需求来说明理由。无法解释的差异回到循环中，直到解决 [[1]](#sources)。单人变体在每次推送前运行双向 MINUS 一致性检查，以及 schema/CI 检查 [[3]](#sources)。
4. 🛑 **审阅**：数据负责人看过可视化的行级 diff 后，逐表审批。仅有文字说明是不够的 [[1]](#sources)。
5. 团队把列重命名这类外观修改批量处理，等数据验证完成后再做，因为每次修改都要消耗智能体调用 [[1]](#sources)。
6. 🛑 **签发**：只有每个维度表和事实表都经过评审并获批之后，才切换报表层背后的表 [[1]](#sources)。

**产出：** 一个纳入版本控制、与遗留输出验证一致的 dbt 项目，可在现有报表之后直接切换。
**失败模式 → 防护：** 负责人认为任何不一致都意味着“数据有问题”→ 展示行级 diff [[1]](#sources)。增量水位线悄悄丢掉 NULL 或迟到的行 → 双向一致性 diff，并检查两侧行数是否不对称 [[3]](#sources)。审阅人因过度检查成为瓶颈 → 让 diff 证据承担更多评审工作 [[1]](#sources)。
**与相近工作流的区别：** AWF-0002 扇出式代码迁移（fan-out codemod）：同样是并行改代码，但它的关卡是测试和 PR 评审。本工作流的关卡是生产数据行级一致，加上数据负责人逐表审批。
