# 主动修复数据管道

**工具变体：** `snowpark-container-services` · `dbt-cloud` · `dbt-mcp` · `notion-kb` · `bigquery` · `claude-code-headless`

## 背景

公司的报表由数据管道生成：一串按计划运行、把原始记录变成干净表格的步骤，常常用 dbt 这个工具，它根据 SQL 文件构建表并对其测试。某一步失败时，工程师得收集日志、代码和历史记录，找出原因再修复，而多数时间花在为一处小改动收集上下文上。在这里，智能体在故障发生时主动接手，也按计划扫描管道里的劣质代码。它在数据的副本上试验修复并开 PR；如果故障出在传入的数据上、改代码治不了，就写一份报告。合并或采取行动仍由工程师来做，因为智能体可能误判故障出在代码还是数据上，而一个掩盖了糟糕数据的补丁比一次失败更糟。

**术语：**
- **数据管道（data pipeline）**：一串搬运和转换数据的自动化步骤。
- **dbt**：根据 SQL 文件构建表并对其运行测试的工具。
- **webhook**：某个系统在事情发生时（这里是一次运行失败）自动发往某个网址的消息。
- **代码异味（code smell）**：代码中并不算错、但容易引发麻烦或浪费的写法。
- **已知修复知识库**：团队书面记录的以往故障及各自的补救办法。
- **CODE / SOURCE**：两类故障：可以在项目代码里修复的，以及由上游传来的糟糕数据造成的。
- **开发沙箱**：数据仓库数据的开发副本，可以在其中测试修复而不触碰生产环境。
- **DAG 血缘**：哪些表依赖哪些表的关系图。
- **PR（pull request，拉取请求）**：一份提议的改动，在合并之前公开出来供评审。

## 用智能体搭建

**形态：** `service`。智能体由故障 webhook 或定时器启动，现场没有人，工程师只会看到 PR 或报告。

**需要：** 启动运行的办法：一个接收故障 webhook、并启动 `claude -p` 或 Agent SDK 程序的小型接收器，以及扫描用的计划（这些系统能从云端访问时用云端定时任务，否则用自己的调度器）；一组脚本，用来克隆仓库、下载运行产物、把失败的测试压缩成简短摘要、把知识库渲染成 Markdown 文件，并把生产数据克隆到沙箱；对生产环境只读的数据仓库角色；推送分支和开 PR 的权限，没有合并权限；团队通知用的频道。

| 步骤 | 搭建方式 |
|---|---|
| 管道故障告警 \| 定时代码异味扫描 | 故障 webhook 通过接收器启动一次无界面运行；扫描是另一个带自己提示词的定时运行。 |
| 拉取日志 + 代码 + 已知修复知识库 | 智能体启动之前由普通脚本完成，这样智能体一开始就拿到失败文件、Markdown 格式的知识库和现成的沙箱。 |
| 对故障分类 | skill 先搜索知识库，匹配到文档化的修复就严格照做；否则调查日志、血缘和数据，再把故障标为 CODE 或 SOURCE。 |
| 代码问题: (在开发沙箱中应用修复 ⟲ 运行受影响的测试) | 智能体在沙箱中修改并运行受影响的模型和测试，直到通过。生产角色是只读的，`PreToolUse` 钩子可以拦住指向生产目标的命令。 |
| 带完整上下文开 PR | 由脚本或连接器开 PR，附上诊断和测试结果，并通知频道。 |
| 源数据问题: 根因报告 + 给源数据负责人的说明草稿 | skill 把诊断查询、根因和一段给数据负责人看的通俗说明写入报告文件。对 SOURCE 类故障，它不修改代码。 |
| 🛑 review | 见“检查点”。 |
| 新的故障模式写入知识库 | 由人添加条目。智能体对知识库没有写入权限，所以下一次运行遵循的是人批准过的内容。 |

**检查点：** `review`：这次运行唯一的产出是给值班工程师的草稿 PR 或报告；智能体没有合并的工具，生产环境按角色只读，所以即使 CODE 或 SOURCE 判断错了，也到不了生产环境。由工程师合并 PR，或根据报告采取行动。

**与来源相比：** 来源的日期从 2026-03 到 2026-10。2026-03 的来源（Hiflylabs）在 2026-11 打开过，仍然支持引用它的那些步骤：由脚本收集上下文、先搜索知识库、把故障分成 CODE 和 SOURCE、生产环境只读、输出是 PR 而不是自动合并的提交。2026-10 的来源（Snowflake）这次核对时无法打开（该站点拒绝了自动读取），所以引用它的内容没有重读。本搭建方式沿用 Hiflylabs 的记述（它说是在无界面模式下运行编码智能体产品），不复现 Snowflake 自己的平台。两个来源都不到 12 个月，所以不需要再搜索更新的记录。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 来自调度器的 webhook 在每次受监控的管道故障时触发智能体，定时器也会触发它（例如每 12 小时），扫描管道中的代码异味和性能问题；无需工程师来召唤智能体 [[1]](#sources)[[2]](#sources)。
2. 由确定性脚本而不是智能体收集上下文：克隆仓库、下载运行产物、只把失败的测试提取成紧凑的摘要、把团队的已知故障知识库渲染成 markdown，并把生产数据克隆到开发沙箱 [[2]](#sources)。
3. 智能体先搜索知识库，匹配到文档化的修复时就严格照做；否则从头调查日志、DAG 血缘和数据，在上游修复，而不是逐个给下游测试打补丁 [[2]](#sources)。
4. 智能体对每个故障分类：CODE（可在项目内修复）或 SOURCE（上游数据有问题）。SOURCE 问题只出报告：智能体用诊断查询记录根因，为源数据负责人起草一段通俗英文说明，绝不在代码里加变通办法 [[2]](#sources)。
5. 对 CODE 修复，智能体应用改动并在沙箱中运行受影响的模型/测试直到通过；生产保持只读，由数据仓库角色强制执行 [[2]](#sources)。Snowflake 的智能体在 "before anything touches production" 之前测试修复 [[1]](#sources)。
6. 智能体带完整上下文开 PR 并通知团队频道；Snowflake 报告从检测到 PR 平均不到 16 分钟 [[1]](#sources)。
7. 🛑 **审阅**：工程师审阅并合并 PR（或根据源数据报告采取行动）；"The agent proposes the repair. A person still decides what ships." [[1]](#sources)。输出是 PR 而 "not an auto-merged commit"，因为 CODE/SOURCE 分类并不完美 [[2]](#sources)。
8. 出现新的故障模式时，由人在知识库中添加一条记录；下一次运行就会遵循它 [[2]](#sources)。

**产出：** 每天早上有一个经测试的修复 PR（或带起草的干系人说明的源数据根因报告）等着值班工程师；以及已合并的 PR 和知识库条目。
**失败模式 → 防护：** 智能体用一个取巧的过滤条件掩盖糟糕的源数据 → 按规则 SOURCE 问题只出报告 [2]。智能体逐个给失败的测试打补丁 → 提示词要求在上游修复 [2]。智能体把 CODE 与 SOURCE 分错类 → 人工审阅 PR，不自动合并 [2]。智能体触碰生产环境 → 只读角色、沙箱中的 dbt 运行 [2]。
**与相近工作流的区别：** AWF-0124 被召唤的 dbt 调试员（Summoned dbt debugger）只有在工程师 @ 它时才启动（🛑 action），并且只有在工程师决定修复后才起草修复（第二个 🛑 action）。这里智能体在每次故障时主动运行，并按计划运行以做改进工作，直接产出经沙箱测试的 PR，唯一的检查点是合并审阅：检查点安排不同，首个产出物也不同（是 PR，而不是诊断线程）。

## 公开实例

覆盖度（截至 2026-11-13）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [Snowflake, How Snowflake Built an Agent to Fix Broken Data Pipelines](https://www.snowflake.com/en/blog/ai-agent-fixes-data-pipeline-failures/) (2026-10-19)。在内部团队的管道上已在生产环境运行 5 个月；每个受监控的故障都被调查；PR 由人合并。"Under 16 minutes from incident detection to PR creation."; "100s of PRs merged."; "500+ pipelines improved."。*第一手：是；可信度：高。*
- [Hiflylabs, Agentic System for DataOps](https://hiflylabs.com/blog/2026/3/5/ai-agent-for-data-pipeline-ops) (2026-03-05)。咨询公司为客户的 dbt Cloud 作业搭建的生产系统；先查知识库的修复、CODE/SOURCE 分流、PR 审阅。"Total elapsed time: maybe an hour. The fix itself took two minutes." (人工基线)。*第一手：是；可信度：中。*
