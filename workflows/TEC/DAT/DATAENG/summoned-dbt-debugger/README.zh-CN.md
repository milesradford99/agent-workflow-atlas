# 按需召唤的 dbt 排障助手

**工具变体：** `claude-agent-sdk` · `dbt` · `snowflake` · `slack` · `jira` · `kestra`

## 背景

公司的报表每晚由数据管道生成：一串把原始记录变成干净表格的步骤。dbt 是后面这些步骤常用的工具，每一步之后都会运行测试。某一步失败时，值班工程师得弄清原因，通常要一层一层地检查数据，从最终的报表表一路回溯到原始来源。这些大多是常规的取证工作，而且许多失败其实是数据仓库的瞬时错误，根本不用修。智能体负责追溯并说明发现了什么。每次排查由工程师发起，是否值得修复也由工程师决定并合并，因为一次不必要的修复要占用评审，一次错误的修复则可能改变大家依赖的数字。

**术语：**
- **数据管道（data pipeline）**：一串搬运和转换数据的自动化步骤。
- **dbt**：用 SQL 文件构建表并对其运行测试的工具；失败意味着某次构建或某个测试出了问题。
- **数据仓库**：表所在的中央数据库。
- **层（source、base、staging、intermediate、mart）**：一张表所经过的各个阶段，从原始输入（source）到报表读取的最终表（mart）。
- **行数查询**：统计一张表行数的查询，用来找出数字开始对不上的第一层。
- **故障特征（failure signature）**：错误信息中可识别的模式，指向某个已知原因。
- **schema 路径**：定位一张表的完整名称，例如数据库、schema 和表名。
- **PR（pull request，拉取请求）**：一份提议的改动，在合并之前公开出来供评审。
- **值班工程师（on-call engineer）**：本周负责应对生产故障的工程师。

## 用智能体搭建

**形态：** `skill`。每次排查针对一个故障，由人发起并决定下一步，所以一个带查找表和查询模板的 skill 就是够用的最小形态。来源是以 Slack 机器人的形式运行的；Slack 连接器可以把结果发到串里，但这些步骤并不需要它。如果希望在 Slack 里 @ 一下就在无人值守的情况下启动，那就属于 `service` 搭建。

**需要：** 对数据仓库的只读访问，角色不能写入；失败作业的日志；一份参考文件，列出已知故障特征以及各自的修复或分类；按层级顺序预先写好的行数查询模板；各模型 schema 路径的简短注册表；仅第二阶段需要：推送分支、开 PR 和创建工单的权限。

| 步骤 | 搭建方式 |
|---|---|
| Slack 中的 dbt 故障告警 → 🛑 action (工程师 @ 智能体) | 工程师用失败作业的名称或日志启动 skill。skill 绝不自行启动。 |
| 对照已知故障特征分类 | skill 在做任何其他推理之前，先用参考文件里的查找表匹配这条错误。 |
| (对某一层执行模板化行数查询 ⟲ 上移一层) | 脚本里存放查询模板；智能体填入模型名和日期，在只读角色下运行，找到行数不一致的第一层，阅读该模型的 SQL，再上移一层重复。查询失败时，用注册表里正确的 schema 路径重试。 |
| 根因发在 Slack 串中 | skill 写出诊断，标明是常规修复还是需要判断的情况，返回给工程师，或者通过连接器发到串里。 |
| 🛑 action (工程师决定是否修复) | 见“检查点”。 |
| 智能体起草修复 PR + Jira 工单 | 另一个修复 skill，由工程师按名字运行，修改分支、开草稿 PR 并创建工单。 |
| 🛑 review | 见“检查点”。 |

**检查点：** `action`：第一个是工程师启动 skill。第二个是决定是否修复：诊断 skill 只拿到读取类工具，并以提问结束；`git push`、创建 PR 和创建工单的权限规则都设为“询问”，所以即使漏掉了这次停顿，也还会遇到一次确认提示。`review`：PR 是草稿，智能体没有合并它的工具；由工程师阅读、批准并合并。

**与来源相比：** 唯一的来源和公开实例的日期是 2026-05。这次核对时无法打开它的页面（该站点拒绝了自动读取），所以本条目是依据它自己的文本转换的，这里也没有重复它的数字。来源有意选择了手动触发；本搭建方式保留这一选择。查询模板和故障特征表之所以需要，理由与来源给出的相同：否则智能体会编造列名和 schema 路径。来源不到 12 个月，所以不需要再搜索更新的记录。

## 步骤

*以下按来源所述。*

1. dbt 生产故障发布到数据通知频道。🛑 **操作**：值班工程师通过 @ 智能体来启动排查。团队有意选择了手动触发 [[1]](#sources)。
2. 智能体把错误与 11 种已知故障特征的查找表进行匹配来分类。它不从第一性原理出发做诊断 [[1]](#sources)。
3. 智能体按固定的层级顺序向上游追溯：mart、intermediate、staging、base、source。它运行预先写好的行数查询，只需填入模型名和日期。它找到行数开始出现差异的第一层，阅读该层的 SQL，再上移一层重复。编造的列名会让查询失败，智能体随后用修正后的 schema 路径重试 [[1]](#sources)。
4. 智能体几分钟内在同一个 Slack 串中回帖诊断结果，标明是常规修复还是需要判断的情况 [[1]](#sources)。
5. 🛑 **操作**：由工程师决定是否继续。只有此时，修复 skill 才会起草修复、开 PR 并创建 Jira 工单。🛑 **审阅**：工程师阅读、批准并合并 [[1]](#sources)。
6. 随着新模式出现，团队持续更新故障分类和数据仓库上下文注册表 [[1]](#sources)。

**产出：** 告警串中的根因诊断；工程师提出要求时，再加上修复 PR 和 Jira 工单。
**失败模式 → 防护：** 数据仓库的瞬时错误若由修复流程自行处理，会产生不必要的工单和 PR → 每项修复都由人决定（83% 的诊断无需任何操作）。编造的 schema 路径（起初约 25% 的查询失败） → 模板化查询加上下文注册表，把失败率降到约 13% [[1]](#sources)。上游 API 漂移等边缘情况 → 仍交给人处理。
**与相近工作流的区别：** 最接近的是 AWF-0063（经 diff 验证的 dbt 迁移），它把遗留代码翻译成 dbt，并在切换前用行级 diff 加以证明。本工作流诊断的是已在生产中运行的流水线的故障。每次运行由人发起，每项修复由人决定。
