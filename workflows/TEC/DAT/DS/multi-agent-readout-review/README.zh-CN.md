# 多智能体实验报告评审

**工具变体：** `claude-code-skills` · `statsig` · `snowflake` · `notion` · `metabase` · `mercari-cursor-ab-report`

## 背景

公司要给所有用户改动产品之前，常常先让一部分用户用上改动，再与没用上的用户对比；这就是 A/B 实验，记录其结果的文档叫实验报告（readout）。之后由一位没参与该项目的数据科学家以独立评审者的身份审阅报告，就像工程师互相评审代码，评审之后才做上线决定。一次完整的评审，要对照实验平台核对各项结论，到数据库里数清到底有哪些用户被曝光，重新计算收入数字，并确认代码确实按定向规则运行，往往要花 30 分钟到一小时。这里由智能体执行机械性的检查，并把结果发布到报告上。独立评审者仍要阅读报告和这些结果，上线决定也由人来做，因为需要判断的地方和业务风险都归他们。

**术语：**
- **实验报告（experiment readout）**：记录实验设置和结果的文字报告。
- **曝光（exposure）**：真正看到了被测改动的用户；曝光数要与预期数核对。
- **样本比例失配（sample-ratio mismatch）**：各组的实际比例与计划的分流比例不同，说明用户分配环节可能出了问题。
- **置信区间（confidence interval）**：真实效应大概率落入的范围；若区间包含零，就不能证明该效应真实存在。
- **统计功效 / 样本量**：纳入的用户是否足够多，能检测出所声称大小的效应。
- **护栏指标（guardrail metric）**：即使主指标改善，也不能变差的度量，例如投诉。
- **蚕食效应（cannibalization）**：一个指标的提升以牺牲另一个指标为代价。
- **2 组缩放（2-cell scaling）**：50/50 分流时只有一半用户用上了改动，所以实测的增量要翻倍，才能推算全量上线的影响。
- **DAU**：日活跃用户数；各公司定义不同，所以智能体需要公司自己的定义。
- **上线决定（ship decision）**：决定把改动发布给所有用户。
- **monorepo**：把许多项目放在同一个代码仓库里。

## 用智能体搭建

**形态：** `skill`。数据科学家一次评审一份报告并留在对话里，三份检查清单可以作为 skill 内置的子智能体并行运行。来源也是把它做成带子智能体的 skill。如果希望每份新报告都在无人启动的情况下被评审，那就属于 `service` 搭建。

**需要：** 一个连接到存放实验报告的文档工具的连接器（MCP server），能读取报告并发布评论；到实验平台和数据仓库的只读连接器；放在智能体可搜索位置的产品代码；把预期与实际曝光画成图表的方式；一份公司指标定义文件；每个评审角色各一份检查清单文件。给智能体的是汇总计数，而不是用户级记录。

| 步骤 | 搭建方式 |
|---|---|
| Notion 中的实验报告 | 数据科学家带着报告链接启动 skill；skill 通过文档工具的连接器读取它。 |
| 预过滤：拉取 Statsig 配置 + 结果、Snowflake 曝光计数、Metabase 图表、代码 | skill 通过各系统的连接器读取，写出一份简短的上下文材料包，只含各清单所需的字段，而不是完整的指标数据。 |
| 工程师智能体判定平台、实验类型、版本 | 一个子智能体搜索代码和定向规则，返回平台、是否为新手引导实验，以及版本要求。skill 据此选择曝光查询。 |
| 每个评审者 (统计学家、数据工程师、业务分析师)：通过/不通过检查 | 三个子智能体并行运行，各自带自己的检查清单文件、指标定义和材料包，各返回一份通过/不通过清单。 |
| 综合 | skill 把三份清单合并成一组评论。 |
| 发布结构化 Notion 评论 | skill 通过文档工具的连接器发布评论。 |
| 🛑 review | 见“检查点”。 |
| 🛑 sign-off | 见“检查点”。 |

**检查点：** `review`：评论发布后 skill 就结束，并告诉启动它的数据科学家，这份报告现在需要项目之外的独立评审者；skill 不参与那次评审。`sign-off`：上线决定由 skill 之外的人做出。实验平台的连接器是只读的，权限规则也拒绝那里的任何写入工具，所以智能体无法启动、停止或上线实验。

**与来源相比：** 唯一的来源和公开实例的日期是 2026-03-27。这次核对时它能打开，并支持每一步：skill 和子智能体、三位评审者的检查、预过滤，以及任何上线决定之前的独立人工评审。作者把该系统描述为带 MCP 连接的 Claude skill，所以本搭建方式与它一致，改动很小。页面说评审器现在对每份报告都会运行，但没有说一次运行如何启动，所以这里的触发方式是设计上的选择。页面没有报告准确率之类的数字，本搭建方式也不作任何性能声明。来源不到 12 个月，所以无需再搜索更新的记录。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 编排器是数据 monorepo 中的一个 Claude skill，它从 Notion 取得实验报告。然后从 Statsig 收集配置、分流和指标结果，从 Snowflake 收集曝光计数和趋势，从 Metabase 收集曝光对账图表 [[1]](#sources)。
2. 工程师子智能体搜索后端、前端和移动端代码，弄清实际被曝光的是谁：哪个平台、是否经过新手引导、所需的应用版本。这决定使用哪种 SQL 模式。公司特有的指标定义在这里附上 [[1]](#sources)。
3. 三位评审者并行运行。统计学家：样本比例失配、实验时长、样本量，以及每个声称的效应是否都有不含零的置信区间。数据工程师：空指标，以及预期与实际的曝光曲线。业务分析师：声称的变化量、护栏指标、蚕食效应、按 2 组缩放重新计算的收入，以及权衡取舍 [[1]](#sources)。
4. 编排器综合各项发现，作为结构化评论发布到该实验的 Notion 文档上 [[1]](#sources)。
5. 🛑 **审阅**：项目之外的一位独立数据科学家审阅实验报告和 AI 的评论。🛑 **签发**：只有经过这次同行评审，才做上线决定 [[1]](#sources)。

**产出：** 每份实验报告上的通过/不通过评审意见，交给人工同行评审者，用于上线决定。
**失败模式 → 防护：** 评审泛泛而谈、没有帮助 → 数十轮提示词迭代。公司内部术语（例如内部所说的 'DAU' 是什么意思）造成误报 → 一行定义就消除了一整类误报。倾倒完整的指标数据让智能体困惑 → 增加预过滤阶段 [[1]](#sources)。
**与相近工作流的区别：** 最接近的是 AWF-0064（基于代码库的分析），由智能体撰写分析备忘录，供分析师核实。本工作流中，智能体用三份并行的专业检查清单批评他人的实验报告，评论先于必需的人工同行评审和上线决定发布。产出和检查点布局都不同。
