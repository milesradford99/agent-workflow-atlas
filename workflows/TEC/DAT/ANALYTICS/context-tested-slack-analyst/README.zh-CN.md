# 经上下文测试的 Slack 分析师

**工具变体：** `slack` · `dbt` · `looker` · `snowflake` · `snowflake-cortex-analyst` · `bigquery`

## 背景

公司里的人总在要数字：今天有多少用户用了某个功能，某位客户在用哪个版本。这些“顺口一问”通常落到数据团队头上，分析师要写一段 SQL（向数据库提问的语言），核对后再把结果贴回去，一次次打断手头的深度工作。这里由智能体直接在提问的 Slack 对话里回答，并附上它跑的查询。没有人逐条批准答案，所以数据团队的工作变成：抽看公开线程，并保证关于公司数据表的文字说明准确、经过测试。这个角色不能去掉，因为来自错误或已停用表的答案读起来同样笃定，而大家会拿这些数字做决定。

**术语：**
- **SQL**：向数据库要数字的语言；查询语句就是答案背后的证据。
- **数据仓库（data warehouse）**：存放公司各张数据表的中央数据库。
- **dbt**：用 SQL 文件构建数据表、并记录每张表和每一列含义的工具。
- **BI 工具**：基于仓库数据表制作看板和图表的软件。
- **语义视图（semantic view）**：由数据科学家认可、专门用来回答问题的一组命名表和指标。
- **上下文层（context layer）**：智能体在查询前读取的文字说明，包括表、列和业务规则。
- **领域负责人（domain owner）**：负责某一领域（如销售或产品）数据的人。
- **端到端测试**：向智能体问一个固定问题，检查最终答案和它所走步骤的测试。
- **@ 提及（@mention）**：在 Slack 里按名字点名用户或机器人；**线程**是挂在一条消息下的一串回复。

## 用智能体搭建

**形态：** `service`。提问的人很多，都经由 Slack 进来，没有人在键盘前运行智能体，数据团队只看到答案的一个抽样。

**需要：** 对数据仓库的只读访问，角色不能写入；表元数据和领域负责人写的文档，存成智能体可读的文件（从 dbt 和 BI 工具导出）；一个 Slack 连接，把 @ 提及和公开频道的问题送给程序，并在线程里回帖；记录每个答案、查询和工具调用的日志；每个领域一份高优先级问题清单，写明预期的答案和表，用于测试。除非数据团队批准用于此用途，否则把含客户个人数据的表排除在可读范围之外。

| 步骤 | 搭建方式 |
|---|---|
| Slack 线程中的问题 | 用 Agent SDK 写的程序，由每个 Slack 事件启动，把问题和线程里之前的消息交给智能体。 |
| 获取已索引的 dbt/BI/数据仓库元数据 + 领域文档 | 一个 skill 把智能体指向元数据和文档文件，并列出哪类问题该用哪些表。 |
| (查询 ⟲ 检查列值，回溯) | 智能体通过数据仓库的 MCP server（连接器）运行查询，查看列值，结果看起来不对时换一张表或换个过滤条件。权限规则只放行读取类工具。 |
| 在线程中给出答案，附 SQL + 数据预览 | skill 要求每个答案都附带 SQL 和一小段预览；程序把它发到线程里。 |
| 🛑 sample | 见“检查点”。 |
| (更新上下文 ⟲ 对答案、工具调用、表做端到端测试) | 数据团队修改 skill 和参考文件。测试脚本在清单上的问题上重新运行智能体，把答案以及日志里记录的工具和表与预期对照，直到全部通过。 |

**检查点：** `sample`：答案不经批准就发出，所以停顿是抽检。程序把固定比例的答案连同 SQL 复制到数据团队阅读的审阅频道，团队通过修改智能体读取的文件来补上缺口。智能体在数据仓库上没有写入类工具，权限规则也拒绝其他任何工具，所以错误的答案不会改动数据。

**与来源相比：** 来源的日期从 2025 年到 2026-02。来源 1 没有日期；它的页面头部（唯一加载出来的部分）显示 2025-09-18。来源 3（2026-02-06）这次核对时能打开，它证实了答案附带 SQL、只读访问，以及以审阅代替手工作答；它用的是一份每次出错后就增补规则的提示词，而不是测试套件。来源 2（2026-01-29）拒绝了自动读取，来源 1 的正文也没有加载出来，所以步骤 1、4、6 和 Whatnot 的引文只能依据条目自身的文本。这些来源是在各自的技术栈上搭的机器人（来源 3 提到了云函数、一个 Gemini 模型和一个 Slack 应用）；本搭建方式改用通用智能体，并不需要这些。上下文层测试来自来源 1，这里只是作为设计提出，并非已证明有效。无需再搜索更新的记录：最新的来源不到 12 个月。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 数据团队汇总并索引来自 dbt、BI 工具和数据仓库的元数据；各领域负责人为自己的领域撰写文档，存成智能体可读取的文件 [[1]](#sources)。Whatnot 则把智能体限制在数据科学家认可的语义视图上，"accepting that we’d miss around 30% of questions" [[2]](#sources)。
2. 用户在 Slack 中 @ 智能体（或在公开频道提问）。它探索表、检查列值、分支和回溯，并在线程内回答 [[1]](#sources)。
3. 每个答案都附有证据：线程内的 CSV 预览 [[1]](#sources) 或底层 SQL [[3]](#sources)，方便提问者核对。
4. 没有逐问题审批：Ramp 起初对每个领域内的问题都要 @ 领域负责人，后来放弃了，因为这样 "didn’t scale" [[1]](#sources)。
5. 🛑 **抽检**：数据专家在公开频道审阅问题和答案，并通过更新智能体的访问权限或上下文来补上缺口 [[2]](#sources)；Sourcegraph 审阅答案 "the way we review PRs: glance at the SQL, confirm the logic, and move on" [[3]](#sources)。
6. 数据团队评估上下文层，而不是每个答案：与领域专家一起列出每个领域的高优先级概念，并编写端到端测试，对最终答案和中间步骤（预期的工具调用、表引用、查询形态）做断言；更新上下文，重新运行，确认 [[1]](#sources)。

**产出：** 发布在 Slack 线程中、附 SQL/数据预览的答案；由数据团队维护的、经过测试且有版本管理的上下文层。
**失败模式 → 防护：** 因表错误或已弃用而给出自信的错误答案 → 限制在认可的数据集上 [2]，展示 SQL [3]，上下文层测试 [1]。逐问题的人工审阅会重新造成瓶颈 → 把审阅改为抽检线程加测试 [1]。
**与相近工作流的区别：** AWF-0006 受治理的查询（Governed query）在发布前对每条查询都有 🛑 review 和 🛑 sign-off。这里答案发出时没有逐条审批；人们审计公开线程，团队测试上下文层，所以自主程度是抽检，产出物是聊天中的回答，而不是经签发后发布的图表。AWF-0123 是定时评论，不是由问题驱动的。

## 公开实例

覆盖度（截至 2026-11-13）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [Ramp, Building Ramp Research](https://engineering.ramp.com/post/meet-ramp-research) (n.d.)。内部的 Slack 分析师；放弃逐问题人工审阅，改用上下文层测试。"In the last 4 weeks, Ramp Research answered 1,476 questions in #ramp-research-beta, compared to 66 answered in #help-data."。*第一手：是；可信度：高。*
- [Whatnot, Lessons learned from scaling data scientists with AI](https://www.whatnot.com/engineering/lessons-learned-from-scaling-data-scientists-with-ai) (2026-01-29)。基于认可的语义视图的 Slack 机器人；数据专家监控公开问答并补上缺口。"over ten thousand data questions answered by AI systems"。*第一手：是；可信度：高。*
- [Sourcegraph, Building DataBot](https://sourcegraph.com/blog/building-databot-our-always-on-data-assistant) (2026-02-06)。答案附带 SQL；数据团队做审计而不是亲自回答。"Each question may only take 5-10 minutes" (DataBot 之前的基线)。*第一手：是；可信度：中。*
