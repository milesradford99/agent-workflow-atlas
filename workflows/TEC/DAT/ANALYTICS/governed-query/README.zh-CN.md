# 受治理的数据查询

## 背景

“上季度收入怎么变化？”这样的业务问题，要用 SQL（向数据库要数字的语言）写查询，从公司的数据库里得出答案。风险不在查询本身，而在含义：“收入”可能有官方口径，而 join 写得草率的查询会悄悄把数字放大。通常由分析师写查询，拿一份大家都信得过的看板来核对，再把结果呈现出来，既费功夫又要有经验。这里由智能体依据官方口径起草查询、做检查并画出图表。分析师仍要复核逻辑，高管看到结果之前也必须有人签发，因为高管会据此行动，公司要为自己对外报告的数字负责。

**术语：**
- **SQL**：向数据库要数字的语言。
- **受治理的指标（governed metric）**：像收入、活跃用户这样、有唯一官方书面口径且人人必须沿用的度量。
- **语义层（semantic layer）**：把受治理的指标只定义一次、让查询直接复用而不必重写的地方。
- **schema**：数据库里有哪些表和列，以及里面存什么。
- **join 扇出（join fan-out）**：一行匹配到多行的 join，会让行数成倍增加、合计被放大。
- **权威看板（canonical dashboard）**：其总数已被公认为正确的现有看板，用来核对新查询。
- **黄金查询集（golden queries）**：经过验证、留待复用的查询。
- **高管（exec）**：收到结果的高级管理者。

## 用智能体搭建

**形态：** `skill`。由一位分析师一次提一个问题，并留在对话里复核答案，所以一个带参考文件的 skill 就是够用的最小形态。

**需要：** 对数据仓库的只读访问；一份受治理指标的定义文件，或到语义层的连接；每个指标在权威看板上的总数（给出数字或查询）；存放黄金查询的文件夹；把结果画成图表的方式。不要给智能体任何向高管发布的工具。

| 步骤 | 搭建方式 |
|---|---|
| 问题 | 分析师在对话中提出问题。 |
| 加载指标定义 + schema | skill 把问题中的术语映射到指标文件，术语有歧义时询问分析师。它通过只读的数据仓库 MCP server（连接器）读取 schema 和样例行。 |
| (SQL ⟲ 合理性检查) | 智能体起草 SQL，优先使用语义层，然后运行 skill 里列出的检查：合理性边界、每次 join 前后的行数，以及与权威看板总数是否吻合。检查不通过就修改并重复。 |
| 图表 + 摘要 | 智能体把结果画成图表并附上 SQL。 |
| 🛑 review | 见“检查点”。 |
| 🛑 sign-off | 见“检查点”。 |
| 发布 | 签发人在自己的工具里发布。 |
| 存入黄金查询集 | 签发之后，skill 把验证过的查询存入黄金查询文件夹。 |

**检查点：** `review`：skill 带着 SQL、检查结果和图表停下，等待分析师决定。`sign-off`：智能体没有任何发布或发送的工具，所以发给高管是签发人在对话之外执行的操作。只有分析师确认已签发之后，skill 才会把查询存入黄金查询文件夹。

## 步骤

*以下按来源所述。*

1. 智能体把业务术语映射到受治理的指标定义。术语有歧义时，它先提问，不去猜。
2. 智能体查看 schema 和样例行。
3. 智能体起草 SQL，优先使用语义层。
4. 智能体验证：合理性边界、join 扇出（行数是否暴增）、与权威看板总数对账。
5. 智能体把结果绘制成图表，并附上 SQL。
6. 🛑 **审阅**：分析师复核逻辑。
7. 🛑 **签发**：结果发给高管之前必须签发。
8. 智能体把验证过的查询存入黄金查询集，供复用。
