# 定时指标解读

**工具变体：** `grab-spartan-rca` · `slack` · `internal-context-registry`

## 背景

公司会持续跟踪一批数字：订单、收入这类指标，以及 OKR（目标与关键结果，即团队为一个周期设定的目标）。每周或每月，分析团队里总得有人写一段文字解读，说明什么变了、为什么变，供管理者阅读。人工做这件事，要先判断哪些变动是真的、而不是正常波动，再下钻看是哪个国家或哪类客户带来了变化，还要去查业务上同期做了什么（调价、促销）。这里由智能体按计划完成这些，并立刻发布解读，同时通知负责该指标的分析师。分析师事后审阅并纠正，因为只有了解业务的人才能确认因果解释，而管理者会据此行动。

**术语：**
- **指标 / OKR**：被跟踪的度量，或某个周期的目标。
- **标准差（standard deviation）**：衡量一个数字平时波动幅度的量；变动远超它，就不太可能只是偶然。
- **同比（year on year）**：把一个周期与一年前的同一周期相比。
- **指标树（metric tree）**：把一个总指标拆成各部分，例如按国家、客户细分或漏斗阶段。
- **漏斗阶段（funnel stage）**：客户路径上的一步，例如浏览、下单、付款。
- **运营指标**：来自日常运营的度量，例如配送时长、司机供给，可能解释某次变动。
- **季节性因素**：与日历相关的规律性上升或下降，例如节假日。
- **经认证的指标（certified metric）**：其定义和细分粒度（grain）已获数据团队批准的指标。
- **上下文文档（context documents）**：说明指标和数据表含义的文字材料，供智能体读取。
- **黄金数据集 / 评测（golden dataset / eval）**：一组核对过的答案，以及用它来检验智能体的测试。
- **根因分析（root-cause analysis）**：查明变化是由什么引起的。
- **分析负责人（analytics owner）**：负责某个指标或报告的分析师。

## 用智能体搭建

**形态：** `service`。运行按计划启动，没有人在场，负责人只看到已发布的解读，并在其中被通知。

**需要：** 对数据仓库的只读访问；每个被跟踪指标的指标树说明文件；经认证的指标定义和上下文文档（文件）；内部变更日志（费用调整、激励、上线的实验）；指标和 OKR 清单，注明各自的负责人；只能向解读频道发帖、别无他权的权限；对话之外的存储，记录已发布的内容和负责人的修改。

| 步骤 | 搭建方式 |
|---|---|
| 计划触发 | 云端定时任务，或你自己的调度器启动 `claude -p` 或 Agent SDK 程序。 |
| 逐个指标/OKR：检验变动是否显著 | 脚本把每个指标与其 6 个月标准差和去年同期数字比较；只有显著变动的指标才继续。每个指标交给一个子智能体，指标很多时用动态工作流（dynamic workflow）。 |
| 沿指标树下钻 | skill 里存放指标树；智能体通过只读的数据仓库 MCP server（连接器）查询每个切面。 |
| 关联运营指标 + 扫描内部变更日志 + 去年同期 | skill 要求智能体读取运营指标、变更日志和去年同期数字，只写这些记录能支持的原因。 |
| 发布解读，通知分析负责人 | 智能体通过只限解读频道的聊天连接器发帖，并 @ 该指标对应的负责人。 |
| 🛑 review | 见“检查点”。 |
| 修改同步回上下文 | 每次运行开始时，从存储中读取负责人的修改，写入 skill 会加载的上下文文档。 |

**检查点：** `review`：来源是先发布、后由负责人审阅，本搭建方式保持这个顺序。通知就是请负责人审阅的方式：每份报告都会附上，运行日志会列出尚无修改或回复的报告。智能体只对解读频道和存储有写入权限，对数据仓库没有写入权限。如果解读会到达公司之外的读者，就拿掉发帖工具，改为让运行保存草稿，由负责人自己发布。

**与来源相比：** 唯一的来源（同时也是唯一的公开实例）的日期是 2026-08-01。这次核对时它能打开，其中“无人值守的循环”一节支持步骤 1 至 4，以及步骤 5 中通知负责人并同步修改的部分。文章把“把反复出现的失败写进上下文文档、黄金数据集、评测和关卡”表述为适用于其全部智能体的原则，而不是专门针对这类解读。它描述的是 Grab 自己的根因分析平台能力；本搭建方式使用通用智能体加上述 skill 和脚本，并不复制那个平台。最新的来源不到 12 个月，所以无需再搜索更新的记录。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 按既定计划，根因分析智能体检查每个被跟踪的指标或 OKR。它对照 6 个月的标准差和同比数据，判断变动是否显著 [[1]](#sources)。
2. 智能体沿指标树下钻，找出是哪个国家、细分或漏斗阶段带来了这一变动。关联随之变化的运营指标 [[1]](#sources)。
3. 智能体扫描内部上下文，了解各团队在一线做了哪些改动（费用和激励调整、商家曝光、同期上线的实验）。与去年同期对比，区分季节性因素和真实因素 [[1]](#sources)。
4. 智能体让叙述以经认证的指标和上下文文档为依据，自动发布解读，并在每份报告上通知分析负责人 [[1]](#sources)。
5. 🛑 **审阅**：被通知的负责人审阅并编辑已发布的报告。修改会同步回去，让纠正进入系统。反复出现的失败会写入上下文文档、黄金数据集和评测 [[1]](#sources)。

**产出：** 周期性发布的指标和 OKR 解读，附根因，由一位明确的分析师负责。
**失败模式 → 防护：** 指标定义不清会产生自信的错误输出 → 在合适的粒度上认证指标，并配上上下文文档。把季节性下降误读成真实下滑 → 做同比对比。没人盯着运行 → 通知负责人、同步修改，以及升级关卡 [[1]](#sources)。
**与相近工作流的区别：** 最接近的是 AWF-0006（受管控的查询），由人提问，答案经审阅和签发后才发布。这里由计划触发运行，智能体先不经批准就发布，负责人事后审阅并纠正。自主程度是抽检，产出是周期性的叙述，而不是一次性的答案。
