# 通宵实验迭代

**工具变体：** `autoresearch` · `git` · `weights-and-biases`

## 背景

机器学习团队改进模型的办法，是对训练代码或设置做改动，重新训练，再在模型没见过的测试上看结果。每次尝试都要准备、占用数小时算力并做分析，所以研究员手里总有一长串永远排不上的想法。这里由智能体通宵逐条处理这份清单，做成一个棘轮：改动一处，训练，测量，只有分数提高才保留改动，否则撤销。风险在于智能体改进的是衡量标准而不是模型，所以测试代码和数据划分都被锁定。运行规则由人事先写好，第二天早上由人审计全部记录。只有人才能决定候选模型是否投入生产，因为离线分数并不能证明模型适合真实使用。

**术语：**
- **训练 / 评估**：让模型在数据上学习，再用它没见过的数据来测量。
- **留出指标（held-out metric）**：在不参与训练的数据上算出的分数；循环就是要把这个数字提上去。
- **训练/测试划分**：把数据分成模型学习用的部分和测量用的部分。
- **超参数（hyperparameters）**：训练前选定的设置，例如学习率，区别于模型自己学到的东西。
- **损失函数（loss function）**：模型训练时要最小化的公式。
- **挂钟时间预算（wall-clock budget）**：一次训练最多可以花多少真实时间的硬性上限。
- **钻指标的空子（gaming the metric）**：不改进模型而把分数刷高，例如改动分数的计算方式。
- **过拟合（overfitting）**：在用来挑选改动的测试上表现好，换了新数据就不行。
- **git commit / revert**：记录代码的一个版本，以及撤销改动以回到上一版本。
- **协议（program.md）**：由人写明指标、优先级、限制和命令的文件。
- **晋级（promotion）**：把候选模型转入生产使用。

## 用智能体搭建

**形态：** `project`。由一位科学家启动运行后就离开，所以它不止于一次对话；而且有一条规则必须每次都成立：智能体不得改动评估代码和数据划分，这只有钩子或权限规则才能保证。如果想让你自己的调度器每晚在无人在场时启动运行，那就成了 `service`。

**需要：** 放在 git 代码库专用实验分支上的训练代码；与之分开、放在锁定路径里的评估框架和数据划分；运行可使用的算力；由科学家写好的协议文件；存放实验日志的地方（例如实验追踪工具）；只允许运行协议列出的训练和评估命令、以及在该分支上做 git 提交的权限。

| 步骤 | 搭建方式 |
|---|---|
| 🛑 plan (人编写协议：指标、优先级、约束) | 科学家写协议文件，`CLAUDE.md` 要求智能体先读它，没有它就什么也不做。见“检查点”。 |
| 冻结评估框架和数据划分 | `PreToolUse` 钩子拦下对评估、指标和划分路径的任何修改；权限规则只允许修改训练代码和模型配置。 |
| (修改代码 → 提交 → 训练 → 评估 → 保留或回退) ⟲ 直到人叫停 | 一个 skill 存放这个循环：智能体修改允许的文件，做一次 git 提交，在协议规定的预算内运行训练命令，读取指标，分数提高就保留这次提交，否则回退，并把结果追加到结构化日志中。它还维护 `experiments.md`，记录假设、结果和长期计划，每轮重新读取。由科学家叫停运行。 |
| 智能体撰写结果报告 | skill 的收尾步骤：尝试了什么、什么失败了以及原因，还有最优配置是如何形成的。 |
| 🛑 review (科学家审计日志) | 见“检查点”。 |
| 🛑 sign-off (晋级) | 见“检查点”。 |

**检查点：** `plan`：协议文件缺失时，skill 立即停下，权限规则只放行协议列出的命令。`review`：智能体在实验分支上工作，没有合并它的工具；科学家第二天早上审计完整的日志和 git 历史。`sign-off`：智能体没有登记、发布或部署模型的工具，所以晋级是由人在自己的系统里做出的决定。

**与来源相比：** 来源的日期从 2026-04-15 到 2026-07-22。来源 3（2026-06-24）这次核对时能打开。它证实了改动经 git 版本管理、运行在 Weights & Biases 中追踪、可编辑范围限定在训练代码和模型配置、验证和指标代码保持固定，以及一份通用的操作手册（playbook）；它还认为固定步数的预算比时间限制更好，因为基础设施的波动让基于时间的比较噪声很大，而步骤 3 依据来源 1 和 2 写的是挂钟时间预算，所以本搭建方式把预算类型留给协议决定。来源 3 描述的是一次黑客松上对三项任务所做的概念验证，而不是通宵的生产运行。它在来源列表中的条目仍写着“仅有搜索摘要，未打开”，这次没有改动。来源 1（Rocket）和来源 2（Faire）拒绝了自动读取（HTTP 403），所以步骤 1 至 7 以及公开实例中的数字只能依据条目自身的文本。最新的来源不到 12 个月，所以无需再搜索更新的记录。

## 步骤

*以下按来源所述。*

1. 🛑 **计划**：由人编写协议（program.md）：主要指标、尝试方向的优先顺序（先特征后超参数，先简化后复杂化）、约束和命令 [[1]](#sources)[[2]](#sources)。
2. 团队把评估代码和训练/测试划分设为只读，让智能体无法钻指标的空子 [[1]](#sources)[[3]](#sources)。Faire 在发现损失函数的改动让指标无法比较之后，增加了明确的防护规则 [[2]](#sources)。
3. 智能体循环：修改代码 → git commit → 在严格的挂钟时间预算内训练 → 评估 → 有提升就保留，否则回退。它把每次结果追加到结构化日志中 [[1]](#sources)[[2]](#sources)。
4. 智能体维护一份持久的 experiments.md，记录假设、结果和长期计划，这样长时间运行也不会忘记已放弃的想法。科学家可以随时查看并重新引导方向，无需停止运行 [[2]](#sources)。
5. 运行停止后，智能体撰写报告，说明尝试了什么、什么失败了以及原因，还有最优配置是如何形成的 [[1]](#sources)。
6. 🛑 **审阅**：科学家在第二天早上审计完整的结果日志和 git 历史 [[1]](#sources)。
7. 🛑 **签发**：问题的界定和指标的选择由人负责，上线哪个模型也由人决定 [[2]](#sources)。

**产出：** 一个更好的候选模型，附带 git 记录、实验日志和书面报告，交由人做晋级决定。
**失败模式 → 防护：** 钻指标的空子 → 评估框架只读 [[1]](#sources)[[3]](#sources)。迭代 20-30 轮后丢失上下文 → 持久的实验记忆 [[2]](#sources)。智能体过早断定搜索已穷尽 → 持续提供新想法，并由人引导 [[2]](#sources)。对离线指标过拟合 → 晋级前由人审阅候选模型 [[1]](#sources)[[2]](#sources)。
**与相近工作流的区别：** AWF-0023 事件驱动的模型更新是根据新闻事件更新投资模型。本工作流是针对冻结的留出指标做 ML 训练的棘轮式迭代。AWF-0004 先分诊再修复属于运维，不是训练。
