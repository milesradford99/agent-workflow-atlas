# 智能体生成补货计划

**与相近工作流的区别：** ORG/LOG 下现有条目都不涉及计划编制。其他类别中最接近的是 AWF-0123（定时指标解读，Scheduled metric commentary），它发布对指标变动的解读。本工作流产出可执行的补货计划，由计划员采纳，并增加了带操作检查点的修正循环。AWF-0064（基于仓库的分析，Repo-grounded analysis）产出分析备忘录而非计划，也没有执行监控环节。
**工具变体：** `jd-scpa`

## 背景

一个零售品类的补货计划，是一周一次与数据争论：每个 SKU 该进多少，取决于去年的销量、今年的促销日历、仓库里已经有多少，以及供应商实际能交多少。计划员把一周的大部分时间花在拼证据上——拉销售与库存、对账、做出会议会要的那个对比——少部分时间花在决定上。语言模型擅长拼装、不擅长决定，所以本工作流把两者分开：计划员用自然语言提问，智能体把问题变成结构化参数、按意图分流、编排子任务，返回一份带证据的计划。然后有意思的那一半才开始。计划一旦在跑，实际销量每天都会偏离预测，而有用的那个问题是"为什么"——客流下降、促销没跑起来、竞品动作——因为答案决定了正确的响应是改计划，还是什么都不做。修正智能体诊断偏差并提出更新建议，由人决定要不要采纳。整个设计靠一条性质成立：每一步都是可审计的原子操作，所以一份错计划可以追到取数、参数抽取、聚合或工具中的某一环。

**术语：**
- **补货计划（replenishment plan）**：未来一段时间里，哪些 SKU 进多少。
- **计划槽位（planning slot）**：从自由文本请求中抽出的结构化参数——品类、周期、SKU 集合、约束。
- **意图分类（intent classification）**：把请求分流到计划、诊断、监控或推荐。
- **text-to-SQL**：把问题变成数据库查询，是最容易出现无声错误的一步。
- **原子操作（atomic operation）**：可重跑、可核查的单个数据步骤（过滤、转换、分组、排序）。
- **偏差（deviation）**：实际销量或库存与计划的差距，是修正循环的触发点。
- **计划修正（plan correction）**：对在跑计划提出的变更建议，由人接受或拒绝。
- **库存满足率（stock fulfilment rate）**：用现货满足需求的比例，是这里的成效指标。

## 用智能体搭建

**形态：** `service`。计划循环按时间表运行——每周出计划、每天对照执行、偏差一出现就诊断——没有人去启动监控。计划员与业务人员在两道关口出现：采纳计划、决定修正；中间的活由智能体持续做。这是围绕一份在跑计划的服务，不是某个计划员跑一次的 skill，也不是项目持有的语料。

**需要：** 供应链系统的读权限，以及有文档的表结构，因为没有文档的结构上跑 text-to-SQL 只会产出自信的胡话；把经验证的库存与预测工具暴露为可调用函数，而不是让模型重新实现，因为那些算法承载着领域假设；计划槽位定义，好让含糊的请求在任何查询之前变成一组可核查的参数；每个原子操作的审计痕迹，这样一份坏计划能被归因；在开始执行之前就商定的基线；以及偏差的上报清单——哪些原因归计划员修，哪些其实是促销或供应问题。智能体不能提交采购订单，也不能判定某个偏差不需要处理。

| 步骤 | 搭建方式 |
|---|---|
| 计划员请求（自然语言） | 用计划员自己的说法提出，包括那些点了周期和品类、却没点约束的请求。 |
| 查询增强为计划槽位 | 请求被解析成槽位——品类、SKU 集合、时间跨度、服务目标——并在拉任何数据之前回显确认，因为歧义正是在这里变成错计划。 |
| 意图分类（计划 \| 诊断 \| 监控 \| 推荐） | 一个路由器决定跑哪条流水线；分错类的请求会产出一份对错误问题的漂亮回答，所以路由被当作关键环节而不是文书工作。 |
| 任务编排 → 每个子任务：text-to-SQL 取数 → 原子操作或经验证的工具 | 请求被拆成子任务，各自取自己的数并调用原子操作或已批准的预测与库存工具，每拿到一个中间结果就更新剩余任务清单。 |
| 有依据的计划报告 | 报告给出计划及其背后的证据——销售历史、库存位置、在途——好让计划员去否定一个数字，而不是否定一个结论。 |
| 🛑 review（计划员采纳计划） | 计划员与分析师读报告并决定；系统的定位是辅助决策，而搭建没有任何执行计划的通路。 |
| 每日执行对照计划 | 实际销量与库存每天对照计划值，这是唯一能在周期结束前发现计划失效的办法。 |
| 出现偏差：计划修正智能体诊断原因并建议更新 | 每个偏差对照候选原因诊断——客流、促销表现、市场变化——并给出一条带理由的修正建议。 |
| 🛑 action（业务人员决定） | 业务人员接受或拒绝修正；调拨与加急补货是他们的决定，搭建两者都下不了。 |

**检查点：** `review`：计划员采纳计划，而交付物被设计成让"采纳"成为对证据的判断而不是对文笔的判断。`action`：在有人动手之前，修正只是建议，这把在跑的计划留在商业问责之下，而不是留在模型之下。

**与来源相比：** 来源出自 2025-09 到 2026-01，本轮都没有重新打开。此后有变化的是围绕它的项目而不是那项研究本身：同一家公司此后发布了范围更广的供应链模型体系，把决策、流程与物理执行连在一起，称其工业板块已部署 70 多个智能体、覆盖从采购到履约，并称把跨系统重复工作交给智能体后，仓储运营效率提升 13.8%。这些都不改变本条目的数字，反而让该向这些数字提的问题更清楚。一篇对那次发布的行业评述指出："1,000 多个场景"数的是智能体被打开的地方，而不是被证明胜过它所替代之物的地方；一个削平均值却让尾部变胖的智能体，会让投诉上升而不是下降。对本工作流来说这就是正确的检验：计划由偏差与满足率来评判，而不是由多少计划员问过它来评判；而一条变胖的尾巴会最先出现在修正循环里。条目自己的数字——每周数据处理时间减少约 40%、准确率偏差在 5% 以内的计划占比提高 22%、超过 70,000 个 SKU 上库存满足率改善 2% 到 3%——仍是那项研究在某个大促峰值前后测得的，不宜外推到常态年份。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 计划员用自然语言说明计划需求。查询增强把它变成结构化的计划参数（槽位）[[1]](#sources)[[2]](#sources)。
2. 意图分类把请求分流到计划、诊断、监控或推荐。任务编排把它拆成可执行的子任务 [[2]](#sources)。
3. 每个子任务通过 text-to-SQL 与槽位匹配从供应链系统取数，然后运行可审计的原子数据操作或经验证的分析工具（如库存决策算法）。每得到一个中间观察结果就更新剩余任务清单 [[2]](#sources)。
4. 智能体返回一份有依据的计划报告（销售、库存、入库计划）[[1]](#sources)。
5. 🛑 **审阅**：计划员与分析师收到报告并就计划作出决定。论文把系统定位为辅助业务人员，而不是取代他们的决定 [[1]](#sources)。
6. 计划实施之后，计划修正智能体把每日实际销量与指标同计划值比较，检出异常偏差，识别原因（客流下降、促销不力、市场变化），并生成计划更新建议 [[1]](#sources)。
7. 🛑 **操作**：业务人员决定是否采纳建议的修正（例如调拨或加急补货）[[1]](#sources)。

**产出：** 面向京东品类团队的每周销售/库存补货计划与周期中修正建议。在被评估的部署中，这些覆盖粮油、母婴与小家电三个品类超过 70,000 个 SKU [2]。
**失败模式 → 防护：** 含糊的请求产出错误的计划 → 在执行之前做查询增强与意图路由。错误难以追溯 → 原子、可审计的数据操作能显示故障来自数据、槽位抽取、聚合还是工具。计划在周期中途失效（618 备货期与销售高峰期的差异）→ 持续偏差监控与修正智能体。
