# 分层智能体安全审核

**与相近工作流的区别：** AWF-0040 全量内控测试（Full-population control testing）是对每项控制都留证据的财务审计。本工作流是基于现场文档的运营安全审核，由一名人工对智能体的过程做一次审查。
**未归类原因：** taxonomy.yaml 中目前没有涵盖此类的类别。在有三个类似的工作流足以支撑新类别 `EHS`（TAXONOMY.md 规则 2）之前，先归在这里。
**工具变体：** `claude-vertex`

## 背景

对一个在运营的现场做安全审核，意味着读这个现场说自己在做什么——程序、许可、检查记录、培训台账，有时是跨数种语言的 400 页——再对照一套来自监管机构、保险方和客户的标准去核。这是"读"的活，而"读"正是模型擅长的，只是体量击败了多数审核员用的方法：扫一遍你以为会出现的那几节，细看那几节，其余相信它。把工作分成几层才让这个体量可处理。文档智能体阅读并创建任务，任务智能体把每条审核标准拆成它隐含的那些问题，报告智能体对标准汇总发现。然后由一个人审查**过程**，而不是重读现场的文书——这跟完整重审相比是一次不同而且更弱的检查，而这正是对这套工作流所买到的东西的诚实描述：用一次人工审查换取对整个语料的覆盖，而不是由一个人对样本深读。它不能变成的是一张合规证书：一项发现是给审核员的问题，而安全文档里漏掉的发现才是真正要紧的失败。

**术语：**
- **审核标准（audit criteria）**：现场被衡量的那些要求，来自监管机构、保险方或客户。
- **文档智能体（document agent）**：读取现场文档的一个子集并抽取出相关内容的步骤。
- **任务智能体（task agent）**：把一条审核标准变成要向文档提出的具体问题的步骤。
- **报告智能体（report agent）**：把发现组织成审核报告结构的步骤。
- **发现（finding）**：说明某条标准已满足、部分满足或"无证据"的陈述。
- **假阴性（false negative）**：审核漏掉的真实缺口，在安全工作中最要命的失败。
- **多语言语料（multilingual corpus）**：用不止一种语言写成的文档，在有外来务工人员的现场很常见。
- **人在回路（human in the loop）**：由人审查过程，区别于由人重做审核。

## 用智能体搭建

**形态：** `project`。每次审核有自己的语料、标准集与报告，而这套装置——层的定义、标准拆解方式、报告模板——在一个现场或一个客户的多次审核之间留存。这是一个带仓库和工作流的 project，不是跑一次的 skill，也不是服务，因为审核是被委托的而不是持续发生的。

**需要：** 现场的文档作为带清单的语料，因为一次悄悄漏掉某份文档的审核比没有审核更糟；写出来并做版本管理的标准集，因为拆成问题的这一步才真正决定了审核范围；经过检查而不是假定的语言处理，因为被翻译的程序文件可能丢掉承载义务的那个情态动词；层的定义以及每层可以得出什么结论的规则，好让文档智能体不能宣布合规；每条发现对所依据页码与条款的引用，没有它，人工审查的对象就变成了文笔而不是证据；以及一位有权驳回报告的审阅人。智能体不能自行出具合规结论，也不能把找不到证据的标准关掉——"无证据"就是发现，不是通过。

| 步骤 | 搭建方式 |
|---|---|
| 现场安全文档（最多 400 页，多语言） | 带清单的导入，并对每份文档做语言检查，使语料是已知的，承载义务的句子是可读的。 |
| 文档智能体分析 + 创建任务 | 对文档子集并行阅读，各自返回带位置的摘录，以及一份"没能解决什么"的清单，后者成为下一层的工作。 |
| 任务智能体拆解审核标准 | 每条标准被拆成它隐含的问题，报告回答的正是这些问题——范围在这里定下，所以它做版本管理。 |
| 报告智能体汇总合规发现 | 按标准汇总为已满足、部分满足或"无证据"，每条都带引用；没有证据的标准保持"无证据"，而不是被填上。 |
| 🛑 review（人在回路中审查过程） | 审阅人检查拆解、引用与判断处，这是过程审查而不是重审——搭建没有任何自行出具报告的路径。 |

**检查点：** `review`：一名人工审查过程，而来源对此只做了很简短的描述，这正是本条目最大的弱点——这道检查在构造上就弱于完整重审，所以搭建必须尽量把它做强：给每条发现附上证据，并让"无证据"成为一个真实的结果。

**与来源相比：** 两份来源都是未标日期的厂商客户故事，本轮都没有重新打开；截至 2026-11 没有找到更新的记述。这对本条目意味着什么，值得直说：两个被引用的数字——每次审核从 14 天到 1 小时，以及每年约 1,500 次审核——都是厂商给的，没有公布准确率、没有假阴性率、也没有说明人工审查究竟在查什么。条目的证据等级因此仍为 B，安全论证只能由设计本身承担，而不是由数字承担。来源唯一确立的是规模，而规模就是理由：一年做约 1,500 次审核的机构，不可能每次深读 400 页，所以现实的选择是在"深读抽样"与"浅覆盖全量"之间，而本工作流选的是覆盖全量，再在上面加一次人工过程审查。这样读下来，缺的那个数字恰恰最重要，也正是应当向厂商提的那个问题：在审核漏掉的发现里，完整重审能抓回多少。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 文档处理智能体分析审核文档并创建任务 [[1]](#sources)。
2. 任务拆解智能体把复杂的审核任务简化 [[1]](#sources)。
3. 报告生成智能体把结果汇总成最终审核报告 [[1]](#sources)。
4. 🛑 **审阅**：智能体承担一半的工作量；"另一半——即由人在回路中审查过程——仍然保留在人手上" [[2]](#sources)。

**产出：** 安全管理项目审核报告（AES 每年约做 1,500 次）。
**失败模式 → 防护：** 长且多语言的文档中漏掉发现 → 分层智能体加人工审查。检查点只有很简短的描述。
