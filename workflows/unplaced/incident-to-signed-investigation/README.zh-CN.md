# 从事故上报到签字调查

**与相近工作流的区别：** 最接近的是 AWF-0152（分层安全审计智能体）：它对照标准审计现场的安全文档并产出审计报告（多智能体，只审阅一次）。本工作流处理的是单起事故，从上报到签字的调查，逐条接受整改措施，并由合格人员签发；交付物和检查点都不同。
**工具变体：** `safety-space` · `custom-gpt`

## 背景

一个刚受了伤、或者险些受伤的工人，在手机上写几行字，这几行字就变成监管机构几个月后会读的记录。这几行字的质地决定了下游的一切：这起事故能不能与其他事故放在一起看趋势，正确的整改措施有没有被派到人，向安全监管机构的上报有没有在期限内提交，以及调查能不能确立一个根本原因而不是讲一个故事。失败大多不在分析上，而在文书上——描述写成互不兼容的自由文本，措施派给了没有人，报告是一周后凭记忆拼出来的。模型可以卸掉这部分文书负担：在上报时就把描述重排进公司模板，从同类事故中提出整改措施，标出这段描述是否命中强制上报的任一条标准，并在调查员做完取陈述、附照片、定原因这些人的工作之后起草调查报告。是否上报的决定刻意留给人，因为错误上报与漏报都很严重，而只有一件是可逆的。

**术语：**
- **事故 / 未遂事件（incident / near miss）**：造成伤害、或本可能造成伤害的事件。
- **整改措施（corrective action）**：派给具体责任人以消除原因的一项改变。
- **须上报事故（notifiable incident）**：必须在法定期限内报给安全监管机构的事件。
- **合格人员（competent person）**：法律上有资格签署调查结论的角色。
- **根本原因（root cause）**：底层的条件，区别于直接行为。
- **自由文本描述（free-text description）**：上报人自己的话，必须保留而不是被替换。
- **趋势分析（trend analysis）**：跨时间与场地比较事故以找出模式。
- **EHS 系统**：环境、健康与安全的记录系统。

## 用智能体搭建

**形态：** `service`。上报从手机持续到来，每一条触发一条固定流水线，产出进入主管与调查员的队列。没有人逐起启动，量由现场发生的事决定，人出现在措施关口与签名处——一条带关口的队列，而不是某个人的工具。

**需要：** 按原样提交的上报，并在任何改写之外保留上报人自己的原话，因为原始措辞是证据；公司模板与须上报事故的标准清单，做版本管理，因为那些标准是法律；过去事故的措施库，好让建议有据可依、落在组织真正做过的事上；一条让每条建议要么到达具体责任人、要么被明确丢弃的路径；调查员自己的材料——陈述、照片、测量——作为附件而不是粘进正文的文本；以及给合格人员的签署路径。智能体不能判断是否须上报，不能自行把措施派给某人，也不能写出调查员尚未得出的根本原因。

| 步骤 | 搭建方式 |
|---|---|
| 工人上报事故 / 未遂事件（语音 \| 文字） | 手机入口，语音或文字，原始录音或文本与转写并排保存，因为上报人的措辞可能对调查有意义。 |
| 按公司模板起草描述 | 按模板字段重写，同时保留原文并列，于是标准化帮助了趋势分析而没有毁掉证据。 |
| 建议整改措施 + 标出是否符合须上报标准 | 建议取自同类既往事故；当描述命中某条上报标准时打标——标给人工核对，从不是决定，因为错误上报与漏报都很严重。 |
| 🛑 action（主管逐条接受 / 修改 / 忽略措施） | 每条建议被单独接受、修改或忽略，在有人这么做之前不派任何活；记录显示哪些建议被丢弃。 |
| 调查员记录陈述、照片和根本原因 | 这是人的阶段，刻意放在模型之外：访谈、照片与因果判断作为案卷附件，而不是被它概括。 |
| 起草调查报告 | 报告从案卷组装——描述、人员、时间线、促成因素、措施——每一节都可追溯到来处的记录。 |
| 🛑 sign-off（合格人员） | 合格人员审阅、修改并签署；搭建没有任何通往已签字报告的路径，这让法律角色留在持有它的人手里。 |
| 跟踪措施 + 趋势 | 措施被跟踪到关闭，事故跨场地比较；趋势视图才是让整条流水线成立的那个产出。 |

**检查点：** `action`：主管逐条决定，安全的责任实际就在这里——模型可以建议，但把工作派给具体的人是管理行为。`sign-off`：由合格人员签署，而条目对"这个角色在实践中如何行使"证据很薄，所以搭建把签名设为绝对关口，而不是一个审阅步骤。

**与来源相比：** 来源出自 2026-08-17 与 2026-10-23，足够新，截至 2026-11 没有找到更新的记述；两份本轮都没有重新打开。条目漏掉、而监管时钟使之紧迫的，是时间。按 29 CFR 1904.39，与工作相关的死亡必须在得知后 8 小时内报给美国监管机构，住院、截肢或失去眼球必须在 24 小时内报；未在这些窗口内上报被作为独立违规处理，而应记录的案件必须在 7 天内登入台账。这改变了设计要求的形态：标出上报标准的那一步必须在报告窗口内到达一个人，这意味着起草与标记两步不能隔夜排队还能有用。实际做法是一条双速流水线——到达即标记、之后再起草——加上一份写明非工作时段由谁接收标记的轮值表。条目"只标记、不决定"的选择仍然正确；它需要的是一个挂在标记上的期限。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 工人在手机应用上以语音或文字上报事故或未遂事件 [[2]](#sources)。在 Sundt，安全经理的现场描述会先由一个定制 GPT 重排进标准事故模板，再进入报告 [[1]](#sources)。
2. AI 阅读描述、建议整改措施，并把命中须上报标准描述标出来供人核对；它不判断是否须上报 [[2]](#sources)。
3. 🛑 **操作**：主管或安全经理逐条接受、修改或忽略建议的措施；在人发话之前不派任何活 [[2]](#sources)。
4. 由人取陈述、附照片并记录根本原因；AI 在这一阶段什么都不做 [[2]](#sources)。
5. AI 从记录起草调查报告（描述、人员、时间线、促成因素、根本原因、措施）[[2]](#sources)。
6. 🛑 **签发**：合格人员审阅、修改并签发报告 [[2]](#sources)。在 Sundt，集团 HS&E 经理正式上报并跟踪它 [[1]](#sources)。

**产出：** 一份签字的调查报告与已派发的整改措施进入 EHS 系统，供趋势分析使用。
**失败模式 → 防护：** 自由文本描述不一致会伤害趋势分析 → 用标准模板重排 [1]。在监管上报上过度依赖 AI → AI 只做标记；上报决定留在人手里 [2]。
