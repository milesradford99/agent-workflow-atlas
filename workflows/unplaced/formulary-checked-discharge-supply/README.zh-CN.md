# 对照处方集的出院用药供应

**与相近工作流的区别：** 现有唯一的药房条目 AWF-0215 药师核验的处方录入，是一个分段的 RPA 机器人，把处方录入药房管理系统，配发前有两次先后的药师核验（QV1/QV2）。替换测试不通过：本工作流的交付物是在护理过渡时，对照另一机构的处方集逐行给出供应/不供应决定（而不是录入完成的处方记录）；这里只有一次药师审阅，而不是两阶段核验链；自主程度是辅助（没有"跳过并记录"的自主档）；并且在系统变更后设有自己的重新验证关卡。
**工具变体：** `pair-govtech-assistant` · `pairchat-epic-assistants`

## 背景

当患者从医院转入过渡护理机构——社区医院、养老院——出院带药必须按那家机构实际备了什么，逐条决定。发出一盒对方本来就有的药，是浪费，有时被直接丢弃；扣下对方没有的药，患者到了那边就没有药吃。接收机构的处方集是一份出院药房并不拥有的文件，它会悄悄变化，而要用它去核对的医嘱清单是从配药系统里导出的非结构化文本。药师靠记忆加一张打印清单来做，这在排班轮转之前都还行，直到周末值班的药师从没往那家养老院送过病人。一个装着处方集和供药规则的助手把这个问题变成一次查表，而它的理由不是快，而是让各自熟悉不同机构的一部分员工之间保持一致。它不能做的是把决定定下来：这里的假阴性意味着患者带着缺药转院，所以每一行在打包之前都要过药师。

**术语：**
- **过渡护理机构（step-down facility）**：患者转往的照护强度较低的场所，如社区医院或养老院。
- **处方集（formulary）**：一家机构常备并供应的药品清单。
- **出院带药（discharge supply）**：随患者转运一起发出的药品。
- **医嘱行（order line）**：处方上的一种药，含药品、剂量与剂型。
- **假阴性（false negative）**：本应供应却被标为"不供应"，是这里最需要避免的错误。
- **过量供应（oversupply）**：把接收机构本来就常备的药发过去，属于浪费而非伤害。
- **重新验证（re-validation）**：配药系统变更后，在新的样本上重跑评测。
- **决策支持（decision support）**：给建议、由人决定的工具，区别于自行执行的自动化。

## 用智能体搭建

**形态：** `skill`。一位药师、一张出院处方、一份必须逐条验证的按行建议——助手只配置一次处方集，之后由当班的人逐个患者使用。没有按患者累积、可由服务持有的东西，工作形态是一次带粘贴的对话，而不是一条队列。

**需要：** 接收机构的处方集及其供药规则，作为持续维护的参考文件，因为助手的答案只跟这份文件一样新；医嘱清单，以配药系统实际输出的非结构化形式提供，因为要求"先导出干净数据"等于这套流程永远跑不起来；逐行输出，写明药品、剂量与理由，好让药师对着医嘱核这一行，而不是重新推一遍；一条规则——不确定时归为"供应并标注"而不是"不供应"，因为两种错误的代价并不对称；以及绑在系统变更上的重新验证计划，因为最容易坏的是输入格式。智能体不能最终确定供应决定，也不能指望它自己发现处方集已经过期。

| 步骤 | 搭建方式 |
|---|---|
| 为转入过渡护理机构的患者开具出院处方 | 案件从目的机构开始，因为处方集是按接收机构查的，目的地错了每一行都会错。 |
| 把非结构化的医嘱清单粘贴进企业 AI 助手 | 粘贴进经批准的企业助手，不用脚本，因为跑这套流程的是药师而不是程序员。 |
| 智能体解析每条医嘱（药品、剂量、剂型） | 解析结果按行回显以供确认，于是药名被读错在对处方集匹配之前就能看见。 |
| 每条医嘱：对照接收机构的处方集匹配 | 处方集是助手读取的参考文件，机构名明确写出；文件里找不到的匹配就报"未找到"，而不是推断。 |
| 每行给出供应 | 不供应建议 | 每行给出建议及其依据，不确定时的默认是供应，因为多一盒的代价低于缺一种药。 |
| 🛑 review（药师在配发前验证每一行） | 打包前每一行都由药师核对；搭建没有任何绕过这次核对产出供药清单的通路，而以假阴性为中心的错误分类决定了复核人要找什么。 |
| 只打包并送出不在处方集内的药品 | 打包清单由已验证的决定推出，浪费的减少来自这里，而不只来自模型的准确率。 |
| 配药系统变更后，对处方样本定期重新验证 | 配药系统任何变更之后都重跑一个固定样本，因为弄坏输入的是这次迁移，而不是模型。 |
| 🛑 sign-off（质量团队确认准确率后才可继续使用） | 质量团队在重新验证样本上接受实测准确率之后，助手才继续使用；搭建不能自己宣布已验证。 |

**检查点：** `review`：药师逐行验证，这是"一条建议"与"患者带着缺药转院"之间唯一的屏障——条目的错误分类围绕假阴性构建，原因就在这里。`sign-off`：系统变更后，质量团队在新的样本上重新接受这个助手，这把"去年它好用"变成了一句关于当前流水线的、带日期的断言。

**与来源相比：** 来源出自 2025-12-31（两项医院内评估），本轮没有重新打开。此后有这些变化：这套平台模式在新加坡公立医疗里扩散得比评估文献更快，而这个扩散本身更值得记。本工作流所依赖的企业助手，现在被政府科技机构描述为有数万名公务员在用；在另一个公立医院集群里，一个没有编程背景的护理团队在它上面搭了自己的病房工具——此前先用低代码机器人撞上数据保护规定的墙，又用学生做的原型撞上"自己维护不了"的墙——之后药学部还主动要求把自己的数据加进去。这跟本条目从一家药房记录到的教训是同一个，只是从另一个方向来：助手之所以被采用，是因为拥有这个问题的人自己能配置它；而杀死这类工具的不是模型质量，是维护。它也把那条告诫变得更锋利：共享平台上的自建助手意味着没人复核过的代码与配置，这正是政府自己的 CTO 开始谈"要给 AI 生成的代码分类"而不只是给数据分类的原因——对一个临床工具来说，系统变更后的重新验证关卡是这条纪律的最低版本。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 医院药房收到一张出院处方，患者将转入一家过渡护理机构（社区医院或养老院），该机构有一部分药品来自它自己的处方集。医嘱数据是从配药系统复制出来的，属于非结构化文本，因此用不了电子表格宏 [[1]](#sources)。
2. 没有编程基础药学人员，在 Pair（获准处理 Restricted/Sensitive Normal 数据的政府 AI 平台）上配置了一个助手，把接收机构的处方集和供药规则放进去 [[1]](#sources)。
3. 粘贴进去的医嘱清单被解析，每一行药品都对照该机构的处方集核查；助手实时给出每行的供应／不供应建议 [[1]](#sources)。
4. 🛑 **审阅**：在供应决定定稿之前，药师逐条验证建议。论文明确说系统必须保持为带强制人工监督的决策支持，因为假阴性意味着需要的药没有发出 [[1]](#sources)。
5. 只为转运配发被建议的药品，减少在接收机构一端的过量供应与浪费 [[1]](#sources)。
6. 🛑 **签发**：医院在 2025 年 6 月从 iPharm 迁到国家统一综合药房系统之后，先在一份 100 张处方的新样本上重跑技术评测，才继续依赖该助手；准确率保持在 99.4%，假阴性从三例降到零 [[1]](#sources)。
7. 同一家医院的同类部署说明这个模式可以推广：在同一平台上搭建的两个 LLM 助手（EPIC Notes Analyser 与 Medication Change Identification）也处在出院处方流程中，遵循同样的强制验证规则，并通过 63 名不同用户的持续反馈进行监控 [[2]](#sources)。

**产出：** 为转院患者的出院处方给出经逐行验证的供应决定，用于打包转运用药；准确率与时间动作指标进入药房的质量复核。
**失败模式 → 防护：** 假阴性会漏掉需要的药 → 逐行强制药师验证，并采用以假阴性为中心的错误分类。配药系统改变输出格式时产生漂移 → 系统迁移后在一份新的 100 张处方样本上做完整重评。员工高估节省（92.3% 自认为每张处方省下 3 分钟以上，实测约 48 秒）→ 采用时间动作测量而不是自述。周末轮班员工不熟悉各机构规则 → 让助手承载处方集，而不是依赖排班表。

## 公开实例

覆盖度（截至 2026-11-13）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [Fourth collection pass](../../../research/2026-11-fourth-pass.md)。

- [Tan, Yew & Phua, Evaluation of an AI-Assisted Decision Support for Medication Supply in Stepdown Care Transitions](https://www.rescp.org/journal/view.html?uid=311&vmd=Full&year=) (2025-12-31)。前瞻性医院内评估，每条建议都由药师验证。"The AI assistant achieved 99.5% overall accuracy in the former system and 99.4% in the new system"；"a 68.5% reduction in processing time per medication (median 5.4 to 1.7 seconds)"。*第一手：是；可信度：高。*
- [Tan W.Q. et al., Integration of AI Powered Co-Pilot Tools for Discharge Prescription Processing Efficiency](https://www.rescp.org/journal/view.html?uid=218&vmd=Full&year=) (2025-12-31)。同一家医院、同样的强制验证规则，用在出院处方流程中。"an average of 17% reduction in processing time"；"analysis of 1,219 utilisations"。*第一手：是；可信度：高。*
