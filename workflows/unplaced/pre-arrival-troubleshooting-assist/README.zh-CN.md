# 到场前排障辅助

**与相近工作流的区别：** AWF-0214（调度员可改派的工单分配，dispatcher-overridden job assignment）决定由哪位技术员接单，调度员抽查任务看板。本工作流从派单之后开始：为诊断做计划，并指导一位技术员完成维修，每一步由技术员决定（辅助），并可交接给人工支持台。交付物、用户和检查点都不同。AWF-0108（住户报修分诊，resident maintenance triage）把住户的报修请求分诊成工单，不指导维修。
**工具变体：** `amazon-bedrock-claude` · `fluid-topics-rag`

## 背景

一台电梯坏了，技术员开车过去，而"一次修好"与"跑三趟"的差别通常在到达之前就定了：有没有带对零件、那个故障码有没有被读懂、这台设备过去十二个月的维保记录有没有人看过。有二十年经验的技术员把这些装在自己熟悉的机型里，不熟悉的就没有。一个助手若能在车开动之前读完服务历史、解码故障码、给出诊断建议，这次上门的样子就变了；在现场，它还能回答后续问题——哪个参数、哪个部件、手册哪一页——依据是经批准的手册与以往核实过的支持台案例，附带引用，有时直接给出图纸。它不能做的是编。这次部署把规则说得很直白：它不能产出不安全可用的指令，所以检索被限定在经批准的手册与已核实的案例，最终判断留给技术员——只有他站在机器前面。

**术语：**
- **报修工单（callout）**：针对具体设备派出的一次上门。
- **故障码（failure code）**：设备报出的错误代码，能缩小范围但不指出故障。
- **联网设备（connected equipment）**：持续回传遥测的设备，把近期信号加进服务历史。
- **有据（grounding）**：把回答限定在经批准的来源，使答案可核查。
- **模型评判（LLM-as-judge）**：用模型检查另一个模型的输出，这里用作展示前的相关性与依据闸门。
- **升级（escalation）**：把未解决的案例交给技术支持台。
- **知识库（knowledge base）**：已解决案例的核实记录，是会复利的资产。
- **语音转文字（speech-to-text）**：用说的而不是打字提问，因为现场双手占着。

## 用智能体搭建

**形态：** `skill`。一位技术员、一次派单、在现场提问并得到来自经批准来源的回答，每一步由技术员决定。没有按技术员累积的东西，交付物是这次维修的方案加带引用的步骤——它所依据并回馈的知识库属于组织，不属于这次运行。

**需要：** 这台具体设备的维保历史与故障码，因为对一台具体机器给出泛泛答案比没有更糟；手册与经批准文档作为唯一的检索语料，因为安全主张就建立在这个限定上；已核实的支持台案例，实务知识住在那里；展示前的依据检查，使一条看起来合理的步骤在来源不支持时不被显示；简短的回答，因为站在梯子上的技术员不会读一整页；以及通往技术支持台的交接路径，并捕获支持台做了什么，因为这让下一次上门更容易。智能体不能给出经批准文档之外的指令，也不能关闭工单：故障是否修好由技术员判断。

| 步骤 | 搭建方式 |
|---|---|
| 派出报修工单 → 确认设备 | 运行从派单开始，先确认设备身份，因为这一步错了，后面每一次检索都对着错误的机器。 |
| 12 个月维保摘要 + 近期故障码 + 联网设备数据 | 从服务记录与遥测组装的摘要，这才把一个故障码变成一个可能原因，而不是一次查表。 |
| 到场前给出建议排障步骤 | 一份简短的上门前方案，带上最可能需要的零件，让第一次上门有机会成为唯一一次。 |
| 现场：（技术员提问 → 检索手册、往期支持台案例 → 带引用的步骤） | 只从经批准文档与已核实案例作答，每个答案带引用、常常带图纸，并在技术员看到之前做相关性与依据检查。 |
| 🛑 action（技术员判断并完成修复） | 由技术员判断并动手；助手没有执行能力也没有授权，这也正是它不进入安全论证的原因。 |
| 未解决：🛑 handoff（技术支持台）→ 入档 → 知识库不断扩充 | 升级给有经验的工程师，其解决方案被写成已核实案例——这条回路使助手在这批设备上随时间变得更好。 |

**检查点：** `action`：技术员的判断就是决定点，工具被设计成给这个判断提供信息而不是代替它，这也是为什么它关于安全的主张窄到可以辩护。`handoff`：未解决的工作交给人工支持台，其结论成为新的已核实案例，于是升级不是死胡同，而是训练信号。

**与来源相比：** 来源出自 2024 年（一份会议转录）到 2026-08-19，另有一篇未标日期的本地报道；本轮都没有重新打开，截至 2026-11 也没有找到关于这次部署更新的记述。此后有变化的是这项能力的来源。现场服务管理厂商开始把同样的东西装进平台内部：其中一家在 2026-06 宣布，其对话层将在当年夏天覆盖到现场技术员，在工单中回答关于设备手册、诊断与零件的问题。这没有改变本条目的设计，却改变了搭建的决策——2026 年选择这条工作流的团队，更可能是在配置随派工系统一起到来的功能，而不是自己拼一套检索栈，于是决定成败的问题也跟着移动：语料是否限定在经批准文档、回答是否短到能在梯子上用、支持台的解决方案是否被写回成已核实案例。这里的证据仍是单一公司、由厂商发布，不过数字是铺开式部署才会产出的那种，而不是试点数字：约 15,000 名技术员、60 个国家在用，受访技术员中 80% 表示满意。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 技术员被派出处理一次报修。在现场服务管理工具中，Technician Assistant 先确认技术员正在处理的是正确的设备 [[1]](#sources)[[3]](#sources)。
2. 它汇总该设备过去 12 个月的维保记录与近期故障数据，包括联网设备（24/7 Connect）信号，并把含义不清的故障码解码为可能的根本原因与修法 [[1]](#sources)[[3]](#sources)。
3. 在技术员到达之前，它生成建议的排障步骤，好让技术员带上正确的零件 [[1]](#sources)[[2]](#sources)。
4. 在现场，技术员提出后续问题（部件更换、参数设置、访问权限）。助手检索经批准的手册、支持文档与已核实的往期支持台案例，返回简短、带引用的步骤，有时附带手册中的图片。展示之前用 LLM 评判／护栏检查相关性与依据 [[1]](#sources)[[3]](#sources)。
5. 🛑 **操作**：由技术员决定做什么并动手。KONE 表示该工具支持决策，"同时始终把最终判断留给他们" [[1]](#sources)。
6. 🛑 **接手**：如果问题仍未解决，技术员升级到技术支持台（有经验的现场服务工程师）。支持台解决的案例被记录并加入知识库，该知识库"每天都在增长" [[1]](#sources)[[3]](#sources)。

**产出：** 一次报修的排障方案与带引用的现场指导。未解决的案例转到技术支持台，每一个解决的支持台案例都成为下一次上门的新知识。
**失败模式 → 防护：** 不安全的指令 → 只检索经批准文档与已核实案例（"我们不能让 AI 生成不安全可用的指令"）。现场用不上的长回答 → 依技术员反馈缩短输出。双手占着 → 已提出语音转文字需求并在路线图上。跨市场术语差异 → 技术员参与修订译法。
