# 调度员可覆盖的派工

**与相近工作流的区别：** 没有特别接近的。按检查点风格最接近的是 AWF-0150（邮件转订单）这类抽检式路由工作流，但这里的交付物是技术员排班表，人是通过覆盖实时调度板来审核，而不是处理未解决的条目。
**工具变体：** `servicetitan-dispatch-pro` · `domo-roborouter`

## 背景

一家现场服务企业的命脉在派工板上：工单通过预约链接或电话进来，得有人决定哪位技术员去。这个决定是一次带软约束的小型优化——谁有空、谁有这件设备的资质、谁离得近、谁快、谁能把回访卖出去——而且一整天反复做，这正是调度员昂贵、也正是他们的判断会随着离职一起走出门的原因。一个按这些维度给技术员打分并派工的智能体，大部分时候是对的；真正有意思的设计是它不对的时候怎么办。调度员继续盯板，把自己不同意的改掉，而关键在于，原因要被记下来，因为覆盖率是"算法有没有学会这门生意"的唯一诚实度量。在一家承包商那里，它起初约 40%，经过数月调整技能与设置后落在 10% 附近。安装与回访保持人工，这个边界是对的：带销售与排序维度的复杂工作，正是模型最没有依据的地方。

**术语：**
- **派工板（dispatch board）**：办公室据以工作的工单与技术员排班表。
- **覆盖（override）**：调度员改掉智能体作出的派工。
- **覆盖率（override rate）**：覆盖占全部派工的比例，是本工作流被评判的指标。
- **技能矩阵（skills matrix）**：哪位技术员持证、受过哪类工作的训练。
- **近因加权分数（recency-weighted score）**：把近期工单看得比旧工单更重的绩效分。
- **产能规划（capacity planning）**：在派工上游决定接多少活。
- **回访（follow-up）**：安装或维修之后的再次上门，常保持人工。
- **潜在收入（revenue potential）**：一单的预期价值（含增购），作为打分输入。

## 用智能体搭建

**形态：** `service`。工单通过预约与电话持续进来，落地即派，调度员按例外监督而不是逐单批准。没有人启动一次运行；队列就是这一天。这是服务——不是调度员调一次的 skill，也不是按客户持有东西的 project。

**需要：** 预约与工单数据，连同真正起约束的那些条件——按地区分的执照、设备认证、保修条款；一份被维护的技能矩阵，因为分数只等于它；反映这门生意地理的行驶时间，而不是全国平均；按工单的历史收入，如果收入要作为打分输入的话，因为输入会塑造行为；一套覆盖原因分类，因为只有比率没有原因什么都教不了；以及有权不问就覆盖的调度员。智能体不能派遣一单在法律上要求技术员不具备的资质的工作，也不能把覆盖当作噪音：每一次覆盖要么是分数的一个 bug，要么是生意变了。

| 步骤 | 搭建方式 |
|---|---|
| 预约工单（在线预约 \| 电话） | 两条入口汇入一块板，在线那条从产能规划取数，于是预约链接不会给出这一天服务不了的时段。 |
| 为技术员打分（空闲时间、技能 / 资质、位置、绩效、潜在收入） | 只对合格技术员打分——先按执照与认证筛，再排序，于是不合格的派工是"不可能"而不只是"不太可能"。 |
| 派到调度板 | 工单落地即自动派板，这才让调度员的注意力腾给例外。 |
| 🛑 sample（调度员盯看调度板并覆盖；安装和回访保持人工） | 调度员盯板并覆盖；复杂工作保持人工，覆盖是在板上的一次动作，而不是去改设置的一张工单。 |
| 记录覆盖原因 | 原因在覆盖的那一刻按简短分类记下，因为事后重建的原因只是合理化解释。 |
| 调整设置 / 技能 | 技能与设置的调整来自覆盖日志，而一簇覆盖变成一份缺陷报告也是在同一个地方。 |
| 技术员获得路线 | 技术员拿到派工以及需要知道的信息；如果有覆盖，他看到的就是覆盖后的结果。 |

**检查点：** `sample`：调度员的监督就是那道检查——抽查实时调度板而不是事后复查产出——而覆盖率随时间的变化，是衡量智能体是否在这门生意的活上挣到了自主权。

**与来源相比：** 来源出自 2026-06-01 与 2026-06-22，本轮都没有重新打开。此后有这些变化：其中一家厂商开始公布本工作流所依赖那个产品包的汇总数据，而这些数据属于需要细读的那一类。2026-06-24 发布的口径把用该产品包的客户与同行比较——电话预约率高出 500 多个基点、成交率高出 1,000 多个——但没有说明队列规模、没有基线区间，除了"未使用 Max 的相似企业"之外没有对照组，而且当时该产品包还在限量发布。那是厂商的比较，不是本条目用覆盖率所主张的那种受控测量。更实质的变化是范围：同一份发布描述了会按可用产能调节需求获取的智能体，与接电话预约的语音智能体、在工单中回答设备问题的现场副驾并列。派一单只是这一组决定中的一个；决定接多少需求是另一个，而且在这块板的上游。加入产能调节的搭建，继承的是一个商业决定而不是排班决定，应当说明这一点，而不是把它当成又一个打分输入。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 客户通过在线链接预约，链接显示来自产能规划的可约时段；或者由办公室代接电话预约 [[1]](#sources)。
2. 派工智能体按技能、位置与潜在收入把每单派给技术员 [[1]](#sources)。T3 自研的 RoboRouter 按空闲时间、技能（含地区特定执照）与近因加权绩效分实时排序技术员 [[2]](#sources)。
3. 🛑 **抽检**：调度员盯看调度板，改掉自己不同意的派工；在 Esser，覆盖率从早期约占 40% 降到约 10% [[1]](#sources)。T3 把安装与回访保持人工，让调度员专注例外 [[2]](#sources)。
4. 覆盖原因被记录用于改进算法；团队调整技术员技能与设置 [[1]](#sources)[[2]](#sources)。

**产出：** 现场服务管理系统中已填好的派工板 / 技术员排班。
**失败模式 → 防护：** 早期把活派给不合适的技术员 → 调度员覆盖并调整技能/设置（从 40% 到约 10%）[1]。调度员嫌弃工具慢 → T3 把运行时间从 15-20 分钟降到五分钟以内 [2]。调度员离职带走经验知识 → 把决策逻辑固化下来 [2]。

## 公开实例

覆盖度（截至 2026-11-13）：**偏弱**：只有匿名、与厂商相关或经记者转述的说法。收集与复核见 [Third collection pass](../../../research/2026-11-third-pass.md)。

- [ServiceTitan, Esser Air](https://www.servicetitan.com/blog/success-story-esser-air-ai-dispatch-automation) (2026-06-22)。办公室经理讲述随时间推移越来越少覆盖派工智能体的指派。"the team changed the software's assignments about 40% of the time" … "Today that number is around 10%."。*第一手：厂商；可信度：中。*
- [Domo, T3 Services Group RoboRouter](https://www.domo.com/blog/human-loop-ai-roborouter-dispatch) (2026-06-01)。CIO 自研的派工系统，覆盖七个地点；例外留给人。"they reduced runtime from 15–20 minutes down to under five minutes"。*第一手：厂商；可信度：中。*
