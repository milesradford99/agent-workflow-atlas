# 术语把关的游戏本地化

**工具变体：** `rag-llm` · `rule-qa`

## 背景

一款游戏同时发行十种语言，而每个补丁都会新增文本：菜单标签、技能描述、剧情对白、公告、社媒帖子。每种语言都要有对应的文案，而这些文本不能互换——技能描述里对某个机制的叫法，必须和两个版本前的教程一致；角色的名字必须是社群里已经在用的那个。用通用模型翻，丢的正是这一点：它写出看起来通顺的句子，却把机制重新命名，并偏离既有术语表。本工作流把术语表放在模型之前。术语从历史译文和新文本里挖出来，由语言专家确认，然后每条文本都在术语表和最相近的已批准译文面前翻译。规则层抓机械性问题——某条文本留在了错误语言、格式标签坏了、术语与术语表不符——并在人看到之前退回。语言专家批准术语表是最要紧的关卡，因为下游每条文本都继承它；而最后的本地化质检专家，是玩家拿到构建之前最后一次由人通读。

**术语：**
- **文本条（string）**：一条面向玩家的文字，带一个 id。
- **术语库（glossary）**：本版本获批准的术语对——源语词到目标语词。
- **术语挖掘（term mining）**：从历史译文与新源文中抽取候选术语对。
- **翻译记忆（translation memory, TM）**：以往已批准译文的存储，带上下文。
- **RAG 翻译**：先检索相关术语条目与相似历史译文，再把它们作为上下文来翻译。
- **重排序（rerank）**：在使用之前把检索到的候选按相关度排序。
- **LQA**（本地化质检）：在上下文中检查译文的准确性、术语与适配。
- **文本类型（text type）**：一条文本所属的类别——系统、技能、剧情、公告、社媒——各有自己的语气规则。

## 用智能体搭建

**形态：** `service`。一个版本的文本以几千条为一批到达，逐语言跑完而没有人启动；人出现两次——跑之前的术语表，和跑之后的交付检查。

**需要：** 按文本类型打标的源文本；以往版本的译文作为翻译记忆；现行术语表与本版本拟新增的条目；一个规则检查器，其规则来自游戏自己的格式（标签、占位符、字数上限）；各语言及其地区约定；接收交付批次的构建流水线。智能体不能上线：交付是人的动作，而术语表对本次运行只读，因此一次翻译会话无法悄悄改掉机制的名字。

| 步骤 | 搭建方式 |
|---|---|
| 新版本文本，按类型 | 每个版本建一个作业，文本按类型分组，因为语气规则不同，评审人也应当一次只看一类。 |
| 从历史译文 + 新文本中挖掘术语 | Skill 从翻译记忆中抽取候选术语对，并标出只出现在新源文里的术语；每条候选都带上证据——它在哪里被用过——让评审人几秒钟就能判断。 |
| 🛑 review（语言专家确认术语对） | 每个语言对一个评审队列；只有获批的术语对进入本版本术语表，而本次运行读取该文件，不修改它。 |
| 每个语言：RAG 翻译 | 对每条文本做混合检索：术语精确匹配（名称与道具名），加上按语义、说话人、风格、情绪重排序的记忆命中；译文在这份上下文中产生，别处不做发明。 |
| 规则后检查 ⟲ 修正 | 检查器测试语言混杂、标签与占位符完整性、长度上限、术语合规；不合格的带着触发规则退回，连续两次不合格的直接进 LQA 队列，而不是无限循环。 |
| 🛑 review（LQA 专家交付前检查） | 专家在上下文中读——尽可能在构建里读——对照术语表与源文；交付是他的动作，本次运行没有通往构建的路径。 |
| 上线 | 已核验的批次进入游戏构建。 |

**检查点：** `review`：两道关卡、两个负责人。术语表这道更重要，因为一个错术语被批准一次就会扩散到几千条文本，所以本次运行把术语表当作只读，由专家去改。交付这道是 LQA 专家在运行中的构建里做，因为表格看不出的问题——截断、文字重叠、单独看对但放进句子里就错的术语——在那里才现形。

**与来源相比：** 来源出自 2025-10：一份大型游戏公司的第一手工程记录，也是本条目的公开实例；它已超过十二个月，本轮没有重新打开。此后有这些变化：这套做法已被写成生产方式，而附在它上面的数字并不夸张。2026 年一份讲同一套流水线的记录描述了[三级质控——机器过滤负责术语、长度、敏感词与占位符；语言学家过一遍语义与文化；游戏内 LQA 把文本装回界面里走一遍](https://blog.csdn.net/weixin_42628846/article/details/165582175)——并给出：纯机翻可用率约 70%，加上术语引擎约 85%，其余交给专家。这与本条目的规则层和两道关卡一致，也给出了现实预期：术语表和检查买下前 85%，最后一段仍归人。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 每个游戏版本的源文本按文本类型拆分（系统界面、技能描述、剧情对话、公告、SNS），每种类型有各自的风格规则 [[1]](#sources)。
2. 术语挖掘：用少样本 LLM 从过往译文中抽取术语对（例如「風ノ剣士」→「风之剑士」），并在只有源文的新文本中发现候选术语 [[1]](#sources)。
3. 🛑 **审阅**：候选术语对交给语言专家，只有获批的才进入该版本的术语库（glossary）[[1]](#sources)。
4. RAG 翻译：混合术语检索（IP 名和角色名精确匹配），外加按语义、说话人、风格和情绪相似度重排序的翻译记忆片段 [[1]](#sources)。
5. 规则后检查在生产中运行：混合语言检测、HTML 标签和格式完整性、术语表合规。不合格的条目退回返工 [[1]](#sources)。
6. 🛑 **审阅**：交付前由专业的 LQA（本地化质检）专家检查 [[1]](#sources)。

**产出：** 每个版本最多 10 种语言的本地化文本，上线到游戏构建中。
**失败模式 → 防护：** 增译或漏译、违反术语表、输出语言混杂、标签损坏 → 规则层（覆盖 70%+ 的格式和术语问题）加 LQA 专家。术语表在版本之间过时 → 每个版本都做经专家批准的术语挖掘。
**与相近工作流的区别：** AWF-0076 术语表支撑的机翻后编辑连载中，由人工校对（译后编辑者）逐章对每个网文章节做后编辑，并根据读者评论更新术语表。本工作流中，语言专家预先批准术语表，自动规则检查负责捕获问题，最后由 LQA 专家检查，文本按类型分流并覆盖多种语言。检查点的位置和产出（游戏文本，而非章节）都不同。
