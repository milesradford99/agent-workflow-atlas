# AI 先读的剧本初筛

**工具变体：** `scriptsense` · `greenlight-coverage` · `screenplayiq`

## 背景

影视公司、经纪公司和各类比赛收到的剧本，远多于任何人读得过来的量。通常的第一道筛选是审读人（story analyst，剧本分析员）：他读一部剧本，写出审读报告（coverage），内容是梗概、角色分析和一个推荐意见。大多数剧本，尤其是无名作者的，根本没有人读。在这里，智能体为每部投稿剧本写审读报告，并归入可以检索的地方，高管因此能看到全部稿件，挑出值得精读的剧本。入选的剧本仍由人通读并写意见，剧本推进之前也必须有人力挺，因为开发或购买一部剧本，是把资金和一位作者的前途押在某个人的判断上；而在已报道的测试里，智能体对较弱的剧本过于宽容。

**术语：**
- **审读报告（coverage）**：审读人对一部剧本写的简短报告：梗概、角色说明、对标作品，有时还有结论。
- **剧本分析员、审读人**：撰写审读报告的人。
- **logline（一句话梗概）**：用一句话概括剧本的故事。
- **对标作品（comps）**：与该剧本相似的现有影片或剧集，用来确定它在市场中的位置。
- **片单（slate）**：公司正在考虑或开发的剧本集合。
- **内容需求（content mandate）**：买方目前在找什么，例如某个子类型或某种场景设定。
- **力挺者、附议者**：在剧本推进前为它说话的人，以及表示同意的另一个人。
- **放弃 / 考虑 / 推荐**：审读人给剧本的三种结论：淘汰、继续考虑、向前推。

## 用智能体搭建

**形态：** `skill`。审读人或高管把一批剧本交给智能体，并留在对话中从结果里挑选，所以一个保存审读报告模板的 skill 就够了；稿件量很大时可以用子智能体并行，每个处理一部剧本。

**需要：** 文本或 PDF 形式的剧本；一个 skill，里面有审读报告模板（分场摘要、角色、对标作品，以及可选的选角设想）和不给结论的规则；一个可检索的索引，例如数据库文件，或带目录表的一个审读报告文件夹，由 skill 更新；一套经贵机构批准、可处理未发表剧本的使用环境，因为作者期待自己的作品不被用于训练。不要接入邮件或合同工具。

| 步骤 | 搭建方式 |
|---|---|
| 收取投稿 | 由人把剧本放进一个文件夹；skill 列出它将处理的内容。 |
| 每个剧本：智能体拆解(分场摘要、角色、对标作品、选角建议) | skill 分阶段读每部剧本（先场次，再角色，再主题），写出一个审读报告文件。稿堆很大时，由子智能体各处理一部。 |
| 审读报告(部分工具附评分/结论) | 即这个审读报告文件。skill 不给评分或结论，沿用那款不下结论的工具的做法；每个说法都引用剧本自己的文字。 |
| 索引到可检索片单数据库 | skill 把每部剧本的子类型、场景设定、主题、角色类型和故事线加入索引。 |
| 🛑 review | 见检查点。 |
| 人工通读全本并写意见 | 由人完成。智能体不写意见。 |
| 🛑 sign-off | 见检查点。 |

**检查点：** `review`：skill 在结尾展示片单和审读报告后停下；高管或审读人挑出要精读的剧本，对其余剧本 skill 不再做任何事。`sign-off`：智能体没有推进剧本、联系作者或记录决定的工具；由一位人类力挺者和另一位附议者自己做出并记录这个决定。

**与来源相比：** 有日期的来源是 2025-10 的 Variety；Anthropic 客户案例和 INTERDEPENDENT 规则页面未注明日期。有日期的最新来源已超过 12 个月，所以在 2026-11 做了搜索：ScriptSense 的厂商 Jumpcut 已被 Cinelytic 收购，2025-03-12 宣布（[SiliconANGLE](https://siliconangle.com/2025/03/12/cinelytic-acquires-jumpcut-media-expand-ai-powered-entertainment-analytics-platform/)），搜索结果称它现在属于 The Cinelytic Group；没有找到 2026 年对其流程的报道。客户案例提到的是较早的模型 Claude 3 Opus。Anthropic 的页面和与厂商相关的工具介绍的是产品，没有展示其提示词；INTERDEPENDENT 规则页面在 2026-11 无法打开，所以那一步依据的是条目原文。本搭建方式是用通用智能体照着已报道的步骤做的设计，来源并没有报道有通用智能体这样做过。它没有评分和结论，因为 Variety 的测试发现这些工具偏向作者，同时它让意见保持由人撰写。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 团队上传剧本，可以是积压未读的稿堆，也可以是比赛或投稿池 [[1]](#sources)[[2]](#sources)。
2. 工具运行多步骤的智能体拆解，把每部剧本分成情节、角色和主题等部分，并生成审读报告：分场摘要、角色分析、相似作品。有的工具还加上选角建议；有的加上 1–10 分评分和放弃/考虑/推荐的结论 [[1]](#sources)[[2]](#sources)。
3. 工具为上传的材料建立索引，团队可以按子类型、场景设定、主题、角色类型或故事线，对照内容需求在数千部剧本中检索 [[1]](#sources)。
4. 🛑 **审阅**：高管、经纪人或审读人阅读报告，决定把精读的重点放在哪里。ScriptSense 有意不给出推荐（“我们不会替你做决定”）[[2]](#sources)。
5. 由人通读全本并写意见。在编剧工会（Editors Guild）的测试中，AI 的意见“几乎全面失败”，所以意见仍由人来写 [[2]](#sources)。
6. 🛑 **签发**：在 INTERDEPENDENT，先由内部 AI 读过的剧本，“必须有一位人类力挺，再有另一人附议”，才能继续推进 [[3]](#sources)。

**产出：** 审读报告和可检索的片单。入围剧本进入人工精读和开发决策。
**失败模式 → 防护：** AI 的审读报告倾向于讨好，常会“推荐”较弱的剧本 → 不要相信结论，由人阅读入围名单 [2]。面对复杂剧本时，它会把动作安到错误的角色头上，还会编造情节点 → 引用梗概前先对照剧本核实 [2]。意见需要 AI 缺乏的分析能力 → 意见保持由人撰写 [2]。
**与相近工作流的区别：** 最接近的是 AWF-0013（按节拍写分场剧本）和 AWF-0014（钩子节奏短剧剧本）。两者都是写剧本。本工作流是读别人的剧本，输出的审读报告用于支持人工的立项或精读决定。交付物和检查点（初筛而非草稿审阅）都不同。
