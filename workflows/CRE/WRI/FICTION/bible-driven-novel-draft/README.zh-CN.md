# 设定集驱动的长篇小说

**工具变体：** `claude-code`

## 背景

小说作者借助 AI 模型起草长篇时，最大的难题是让几百页内容前后一致。写作者的办法是一份故事设定集，记下每个人物、地点、日期和世界规则，再加一份细到单个场景的大纲。手工把每个新场景对照设定集核一遍很慢；而模型自己起草时，会忘掉前面的事实，文风滑向千篇一律，还会改写作者已经定下的决定。在这里，智能体通过访谈帮作者建立设定集，提出大纲，每次只凭一小组文件起草一个场景，并另外运行只读的连贯性和文风检查。设定集、文风和大纲仍由作者批准，哪些检查批注算数也由作者挑选，因为书里的取舍属于作者，书也以作者的名义出版；平台的披露规则还取决于文字有多少出自作者本人。

**术语：**
- **故事设定集（story bible）**：一本书的参考文件：人物、地点、时间线和世界的规则。
- **文风文件**：一段体现作者风格的示范场景，加上从中提炼的规则（视角、时态、禁用词句），用来约束每一次起草。
- **锁定的正典**：作者已批准的设定或文风条目；除非作者自己改，下游任何内容都不得改动它。
- **节拍（beat）**：情节中的一个转折；节拍归入章节，章节再分成场景。
- **场景卡**：一个场景的简短计划：视角人物、目标、冲突、结果，以及揭示了什么。
- **视角（POV）**：讲述一个场景时所依托的人物。
- **连贯性**：全书必须保持一致的事实；**信息泄露**指人物在不可能得知某事之前就已知道。
- **AI 痕迹、lint**：模型文字中常见的套话和平板节奏；lint 脚本机械地统计它们。
- **提交（commit）**：在 git 中保存文件的一个版本；git 是存放稿件的版本管理工具。
- **KDP**：Amazon Kindle Direct Publishing，亚马逊的自助出版平台。在那里，**AI 生成**的文字（由模型写出，即使之后经过修改）必须披露；**AI 辅助**的文字（作者在 AI 帮助下自己写的）则不必。
- **GameLit**：以游戏化世界为背景的一类小说。

## 用智能体搭建

**形态：** `project`。一位作者在对话中写一本书，但这本书要跨越很多次会话，需要长期存在的项目知识（设定集和文风文件）、一条“锁定的正典绝不修改”的规则，以及没见过正在写的草稿的检查者。[套件](variants/claude-code.md)把这套搭建方式写成了文件。

**需要：** 一个 git 仓库，分别存放设定集、文风文件、大纲，每章一个文件；作者本人的文字样本，而不是 AI 写的文字；放在 skill 旁边的文字 lint 脚本；一份 `CLAUDE.md`，写明目录结构以及起草时允许加载的文件。稿件是作者的财产：不要接入任何会把章节上传到作者未选定之处的网络工具或 MCP 服务器。

| 步骤 | 搭建方式 |
|---|---|
| 创作前提 + 文风样本 → 通过访谈建立故事设定集 | skill 一次问一个问题，把回答写到 `bible/` 下；它用五种文风各写一个场景，作者亲手修改后选中的那段放进 `voice.md`。 |
| 🛑 plan | skill 展示设定集和文风文件后停下。获批的条目标记为 `LOCKED`。 |
| 节拍 → 章节 → 场景卡 | skill 写出节拍、每章一份简报、按模板每个场景一张卡，并附一张线索落点图。 |
| 🛑 plan | skill 展示大纲，停下等作者签批。 |
| 每个场景按顺序：加载场景卡、设定集、摘要、前文最后约 2k 词 → 起草 | 在主对话中进行，只加载 `CLAUDE.md` 列出的起草用文件，绝不加载整部稿件。 |
| 连贯性检查 → 文风检查 | 先跑 lint 脚本，再由两个自定义的只读子智能体（连贯性、文风）写出批注文件；它们没有修改正文的工具。 |
| 🛑 review | skill 把所有批注编号列出后停下；作者挑选适用的几条，智能体只依据这一选择修订一次。 |
| 更新设定集和摘要 | 作者说“接受”后，skill 提交，补写摘要和时间线，并提出人物文件的修改，交作者批准。 |

**检查点：** `plan`：skill 停两次，一次在设定集和文风之后，一次在大纲之后。一个 `PreToolUse` 钩子拦住对 `voice.md` 和标记为 `LOCKED` 的设定文件的修改，使已批准的正典不会在起草途中被智能体改写；作者亲手解锁文件。`review`：检查结束后 skill 带着编号批注停下，检查者不能修改正文，再用一条在 `git commit` 前询问的权限规则，让场景在作者接受之前进不了稿件。智能体没有发布工具；由作者自己上传 KDP 并记录披露情况。

**与来源相比：** 来源和公开实例的时间从 2023-09（KDP 披露政策）到 2026-09；Sudowrite 和 NovelCrafter 的两个页面未注明日期。McNestrie 在 Claude Code 里用一个设定集仓库、自定义命令和评审智能体完成这些步骤 [[12]](#sources) [[13]](#sources)；他的文章和模板仓库在 2026-11 无法打开，所以这些细节依据的是条目原文。Garrett 讲的是把 AI 当作一支制作团队、用锁定的正典来管控，但没有提到由哪个智能体运转流程；Saoulidis 在一个 AI 代码编辑器里逐章起草，每一章都由他自己掌舵。本搭建方式保留按场景加载，因为来源给出的理由仍然成立：防止起草者模仿自己先前的输出；不过 McNestrie 报告说，篇幅长了这一做法仍然吃力 [[12]](#sources)。它没有纳入其他模型家族的可选评审者和 Ollama 的上下文设置，那是某一位作者自己的配置。`LOCKED` 钩子是本搭建方式新加的；套件只在 `CLAUDE.md` 里写明了这条规则。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 智能体通过访谈作者来填充设定集：主题、受到的影响、世界观、人物、时间线，再加一个 `parked.md` 存放暂时没有位置的想法。在 Claude Code 仓库里，这是一个把 Markdown 写入 `bible/` 的 `/foundations` 命令 [[12]](#sources) [[13]](#sources)。写续集时，按每章一个文件加载第 1 部，让模型据此起草包含人物、地点和事件的设定集 [[15]](#sources)。
2. 作者和智能体锁定文风：起草用的模型用五种文风各写一个场景，作者挑出最接近的一个并手工修改，修改后的场景放入 `voice.md`，标记为 LOCKED，并从修改中提炼出约 10 条规则。对话单独开一个会话 [[12]](#sources)。
3. 🛑 **计划**：作者批准设定集和文风。智能体提出建议，由作者提升为正式内容；一旦某项获批，就成为锁定的正典，下游所有内容都必须遵守，除非作者更改 [[12]](#sources) [[14]](#sources)。
4. 智能体和作者把故事拆成节拍、章节和场景卡：每章一份作者写的简报 [[13]](#sources)，或者一份场景清单，其中每个场景的视角人物各占一个 Markdown 文件 [[15]](#sources)。悬疑结构（哪条线索落在哪里）要预先规划 [[14]](#sources)。
5. 🛑 **计划**：作者签批大纲。把它当作导航系统而不是操作手册，当写出的场景胜过计划时就更新大纲 [[14]](#sources)。Saoulidis 在第 10 章发现并修正了场景清单中的一个关键情节点，并在第 20 章又做了一次完整检查 [[15]](#sources)。
6. 智能体用狭窄的上下文按顺序起草每个场景：文风文件、主题、简报，以及仅前一章，绝不放入整部稿件，这样起草者就无法对自己先前的输出做模式匹配 [[12]](#sources)。
7. 智能体在全新的上下文中运行检查，只写批注、不做修改：先用 lint 脚本检查机械的 AI 痕迹（破折号、套话、句长变化过于平淡），再依次是文笔评审者、查找信息泄露的只读连贯性智能体、主题守护者和痕迹猎手。可选地加入其他模型家族的评审者（通过 Ollama 的本地模型，或另一家 API），弥补起草者所属模型家族共有的盲点 [[12]](#sources)。
8. 🛑 **审阅**：作者挑选哪些批注算数，起草者只依据这一选择一次性修订。然后作者接受并提交，或者回退并重写简报 [[12]](#sources) [[13]](#sources)。Garrett 分 8 批修订，每批 4 章 [[14]](#sources)。
9. 接受之后，智能体更新 `timeline.md`，并提出人物文件的修改，交作者批准 [[12]](#sources) [[13]](#sources)。最后由作者把整本书当作一个整体来审计：文风漂移、人物离开后仍带着的物品、出现在使用它的推理之后的线索、以及把这本书称作书的旁白 [[14]](#sources)。

**产出：** 在 git 中经作者接受的稿件（每章一个文件），旁边是设定集、时间线和评审批注。接下来是编译（Scrivener 一次导出 EPUB [[15]](#sources)）和上传 KDP，并记录 AI 生成与 AI 辅助的披露情况 [[11]](#sources)。
**失败模式 → 防护：** 智能体互相采纳对方的反馈，直到文字变得平滑的“共识糊”（"consensus mush"）→ 评审者从不修改，由作者选择采纳哪些批注 [[12]](#sources)。循环优化模型打分的“质量”指标，会训练起草者去讨好评委 → 只对底线（lint、连贯性、口头禅额度）做循环，上限由作者设定 [[12]](#sources)。起草者自己解释自己的主题 → 由主题守护者和评审者标出 [[12]](#sources)。AI 改写已定的决定 → 锁定的正典 [[14]](#sources)。偏离大纲，以及全书级 AI 编辑悄悄改掉关键桥段 → 对照场景清单定期做是否在轨的检查，稿件搁置一段时间后再手工编辑 [[15]](#sources)。Ollama 默认的 4k 上下文会悄悄截断章节，静默失败的 curl 会掩盖评审调用的失败 → 显式设置上下文并暴露错误 [[12]](#sources)。长篇会超出任何上下文窗口 → 按场景加载加设定集；McNestrie 指出，过了第 17 章这个问题仍未解决 [[12]](#sources)。
**来源中的角色：**

| 角色 | 职责 | 变体 |
|---|---|---|
| 设定集管理者 | 人物、地点、时间线、规则 | Sudowrite Story Bible，从随想 → 梗概 → 大纲 → 场景的引导式流程 [[10]](#sources)；NovelCrafter Codex，链接进稿件的 wiki 条目，可自带模型 [[10]](#sources)；Markdown 资料库 + Claude Code |
| 大纲师 | 节拍 → 场景卡（目标、冲突、结果、视角、揭示的信息） | 同上 |
| 起草者 | 场景正文 | 长上下文 LLM |
| 连贯性检查者 | 全新上下文；标出矛盾（眼睛颜色、行程时间、提前知晓的信息） | 独立的智能体 |
| 文字编辑 | 风格表：禁用的陈词滥调、视角、时态 | 评审智能体 |

**作者在哪里拍板：** 🛑 作者掌握设定集和大纲（两处都是**计划**），创作上的大部分控制权在这里行使。作者还会改写每一章（**审阅**）。
**标签说明：** Amazon KDP 要求披露 AI *生成*的文字、图片和翻译，即使之后经过大幅修改也一样。纯粹 AI *辅助*的作品则无需披露 [[11]](#sources)。请在每个示例中记录属于哪一种。

## 公开实例

覆盖度（截至 2026-11-06）：**充分**：有详细的第一手实例，与流程的大部分环节一致。来自 [Where are the real runs?](../../../../../research/2026-11-real-runs.md)；每个数字都已对照原页面复核。

- [Jon McNestrie, *Writing a novel with Claude Code*](https://medium.com/@JonMcNestrie/writing-a-novel-with-claude-code-a-ci-pipeline-for-prose-6f8f30c71bb1) (2026-07-07)。带锁定文风文件的设定集仓库；评审者写批注，由人挑选哪些适用。"about ten rules extracted from your own edits"；"five in the core team"。*第一手：是；可信度：高。*
- [Matt Garrett, *How I Used AI To Write KDP GameLit Novel*](https://mattgarrett.com/how-i-used-ai-to-write-kdp-gamelit-novel/) (2026-09-10)。故事、世界观和连贯性三份设定集；获批的条目锁定为正典；分批修订；全书连贯性审计。"102,737 words, 32 chapters"；"eight revision batches"。*第一手：是；可信度：高。*
- [George Saoulidis, *How to Write a Sequel Using AI*](https://georgesaoulidis.com/how-to-write-a-sequel-using-ai/) (2025-09-21)。以第 1 部为上下文 → 设定集 → 场景清单 → 逐章写作 → 修改。"Asked for 40 scenes list"；"more than 100k words"。*第一手：是；可信度：中。*
