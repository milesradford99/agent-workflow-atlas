# 设定集驱动的长篇小说

**工具变体：** `claude-code`

| 角色 | 职责 | 变体 |
|---|---|---|
| 设定集管理者 | 人物、地点、时间线、规则 | Sudowrite Story Bible，从随想 → 梗概 → 大纲 → 场景的引导式流程 [[10]](#sources)；NovelCrafter Codex，链接进稿件的 wiki 条目，可自带模型 [[10]](#sources)；Markdown 资料库 + Claude Code |
| 大纲师 | 节拍 → 场景卡（目标、冲突、结果、视角、揭示的信息） | 同上 |
| 起草者 | 场景正文 | 长上下文 LLM |
| 连贯性检查者 | 全新上下文；标出矛盾（眼睛颜色、行程时间、提前知晓的信息） | 独立的智能体 |
| 文字编辑 | 风格表：禁用的陈词滥调、视角、时态 | 评审智能体 |

**检查点：** 🛑 作者掌握设定集和大纲（两处都是**计划**），创作上的大部分控制权在这里行使。作者还会改写每一章（**审阅**）。
**标签说明：** Amazon KDP 要求披露 AI *生成*的文字、图片和翻译，即使之后经过大幅修改也一样。纯粹 AI *辅助*的作品则无需披露 [[11]](#sources)。请在每个示例中记录属于哪一种。

## 步骤

1. 通过访谈作者来填充设定集：主题、受到的影响、世界观、人物、时间线，再加一个 `parked.md` 存放暂时没有位置的想法。在 Claude Code 仓库里，这是一个把 Markdown 写入 `bible/` 的 `/foundations` 命令 [[12]](#sources) [[13]](#sources)。写续集时，按每章一个文件加载第 1 部，让模型据此起草包含人物、地点和事件的设定集 [[15]](#sources)。
2. 锁定文风：起草用的模型用五种文风各写一个场景，作者挑出最接近的一个并手工修改，修改后的场景放入 `voice.md`，标记为 LOCKED，并从修改中提炼出约 10 条规则。对话单独开一个会话 [[12]](#sources)。
3. 🛑 **计划**：作者批准设定集和文风。智能体提出建议，由作者提升为正式内容；一旦某项获批，就成为锁定的正典，下游所有内容都必须遵守，除非作者更改 [[12]](#sources) [[14]](#sources)。
4. 把故事拆成节拍、章节和场景卡：每章一份作者写的简报 [[13]](#sources)，或者一份场景清单，其中每个场景的视角人物各占一个 Markdown 文件 [[15]](#sources)。悬疑结构（哪条线索落在哪里）要预先规划 [[14]](#sources)。
5. 🛑 **计划**：作者签批大纲。把它当作导航系统而不是操作手册，当写出的场景胜过计划时就更新大纲 [[14]](#sources)。Saoulidis 在第 10 章发现并修正了场景清单中的一个关键情节点，并在第 20 章又做了一次完整检查 [[15]](#sources)。
6. 用狭窄的上下文按顺序起草每个场景：文风文件、主题、简报，以及仅前一章，绝不放入整部稿件，这样起草者就无法对自己先前的输出做模式匹配 [[12]](#sources)。
7. 在全新的上下文中运行检查，只写批注、不做修改：先用 lint 脚本检查机械的 AI 痕迹（破折号、套话、句长变化过于平淡），再依次是文笔评审者、查找信息泄露的只读连贯性智能体、主题守护者和痕迹猎手。可选地加入其他模型家族的评审者（通过 Ollama 的本地模型，或另一家 API），弥补起草者所属模型家族共有的盲点 [[12]](#sources)。
8. 🛑 **审阅**：作者挑选哪些批注算数，起草者只依据这一选择一次性修订。然后作者接受并提交，或者回退并重写简报 [[12]](#sources) [[13]](#sources)。Garrett 分 8 批修订，每批 4 章 [[14]](#sources)。
9. 接受之后，更新 `timeline.md`，并提出人物文件的修改，交作者批准 [[12]](#sources) [[13]](#sources)。最后把整本书当作一个整体来审计：文风漂移、人物离开后仍带着的物品、出现在使用它的推理之后的线索、以及把这本书称作书的旁白 [[14]](#sources)。

**产出：** 在 git 中经作者接受的稿件（每章一个文件），旁边是设定集、时间线和评审批注。接下来是编译（Scrivener 一次导出 EPUB [[15]](#sources)）和上传 KDP，并记录 AI 生成与 AI 辅助的披露情况 [[11]](#sources)。
**失败模式 → 防护：** 智能体互相采纳对方的反馈，直到文字变得平滑的“共识糊”（"consensus mush"）→ 评审者从不修改，由作者选择采纳哪些批注 [[12]](#sources)。循环优化模型打分的“质量”指标，会训练起草者去讨好评委 → 只对底线（lint、连贯性、口头禅额度）做循环，上限由作者设定 [[12]](#sources)。起草者自己解释自己的主题 → 由主题守护者和评审者标出 [[12]](#sources)。AI 改写已定的决定 → 锁定的正典 [[14]](#sources)。偏离大纲，以及全书级 AI 编辑悄悄改掉关键桥段 → 对照场景清单定期做是否在轨的检查，稿件搁置一段时间后再手工编辑 [[15]](#sources)。Ollama 默认的 4k 上下文会悄悄截断章节，静默失败的 curl 会掩盖评审调用的失败 → 显式设置上下文并暴露错误 [[12]](#sources)。长篇会超出任何上下文窗口 → 按场景加载加设定集；McNestrie 指出，过了第 17 章这个问题仍未解决 [[12]](#sources)。

## 公开实例

覆盖度（截至 2026-11-06）：**充分**：有详细的第一手实例，与流程的大部分环节一致。来自 [Where are the real runs?](../../../../../research/2026-11-real-runs.md)；每个数字都已对照原页面复核。

- [Jon McNestrie, *Writing a novel with Claude Code*](https://medium.com/@JonMcNestrie/writing-a-novel-with-claude-code-a-ci-pipeline-for-prose-6f8f30c71bb1) (2026-07-07)。带锁定文风文件的设定集仓库；评审者写批注，由人挑选哪些适用。"about ten rules extracted from your own edits"；"five in the core team"。*第一手：是；可信度：高。*
- [Matt Garrett, *How I Used AI To Write KDP GameLit Novel*](https://mattgarrett.com/how-i-used-ai-to-write-kdp-gamelit-novel/) (2026-09-10)。故事、世界观和连贯性三份设定集；获批的条目锁定为正典；分批修订；全书连贯性审计。"102,737 words, 32 chapters"；"eight revision batches"。*第一手：是；可信度：高。*
- [George Saoulidis, *How to Write a Sequel Using AI*](https://georgesaoulidis.com/how-to-write-a-sequel-using-ai/) (2025-09-21)。以第 1 部为上下文 → 设定集 → 场景清单 → 逐章写作 → 修改。"Asked for 40 scenes list"；"more than 100k words"。*第一手：是；可信度：中。*
