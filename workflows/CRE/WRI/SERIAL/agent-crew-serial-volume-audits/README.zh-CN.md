# 代理团队连载与分卷审计

**工具变体：** `claude-code-skill` · `sumeru-skills`

## 背景

网文是在阅读平台上逐章发布的超长连载小说，往往一连几个月按固定节奏更新。通常由一位作者构思情节、写完每一章，并记住成百上千条事实：谁知道了什么，每个角色手里有什么，哪些伏笔已经埋下却还没回收。写到一百多章，错误会不知不觉地混进来：角色的伤凭空消失，资源数量突然跳变，同样的句子和章末收尾开始反复出现。在这里，一个智能体起草每一章，另一个智能体负责审校并更新故事事实的记录，脚本则按固定间隔核对数字。作者仍要抽读成稿，因为横跨几十章的重复和被智能体误解的规则，只有读者才看得出来，也因为发给付费读者、署着作者名字的内容由作者来决定。

**术语：**
- **网文**：为网络阅读平台创作、逐章发布的连载小说。
- **设定集（project bible）**：故事的固定参考：世界观、人物、设定规则、情节规划。
- **状态表**：随章节变化的事实的流水记录，例如每个角色身在何处、手里有什么。
- **伏笔**：早早埋下、之后必须回收的线索；伏笔表列出尚未回收的那些。
- **写作日志**：写作智能体随每章留下的说明，记录它为什么做出这些创作选择，不记录故事事实。
- **卷**：构成一段完整情节的一组章节；这次连载共 6 卷。
- **文风审计**：对整卷扫描重复句式、模板化结尾和固定比喻。
- **番茄（番茄小说）**：中国的网文平台，按计划定时发布章节，每天有字数上限。
- **字**：一个汉字，网文篇幅以它为单位计算。
- **段评**：读者附在章节某一段上的评论。

## 用智能体搭建

**形态：** `project`。作者在一个对话里运行它，但审校者不能见过草稿，每 5 章的脚本检查必须每次都通过，这需要一个自定义子智能体和一个钩子。

**需要：** 一个项目文件夹，以文件形式存放设定集、状态表、活跃与已归档的伏笔表、章节摘要和各章正文；一份写明写作规则（结尾轮换、身体反应备选库、场景化规则）的 `CLAUDE.md`；放在 skill 旁边的一致性脚本和文风检查清单；作者的番茄账号，不交给智能体。

| 步骤 | 搭建方式 |
|---|---|
| 项目设定集 + 状态表 + 伏笔表 | 项目里的文件，规则写在 `CLAUDE.md`。状态表里最近 3 章写细，更早的压缩；只加载活跃伏笔文件。 |
| 每个章节：写作智能体 → 章节 + 写作日志 | 一个 skill，读取设定集、状态、活跃伏笔和最近 3 章，写出章节文件和它的日志。 |
| 审校智能体检查连贯性，并自行更新状态/伏笔/摘要文件 | 一个有独立上下文的自定义子智能体，拿到章节、日志和状态文件，检查连贯性，并修改状态、伏笔和摘要文件。 |
| 每 5 章检查 (一致性脚本 ⟲ 修复) | skill 旁边的脚本。一个 `PreToolUse` 钩子拦住下一章文件的写入，直到脚本最近一次的结果是 PASS。 |
| 每个分卷：文风审计 → 批量修复 | skill 的分卷步骤，使用检查清单文件；可以让检查清单的每一部分各由一个子智能体并行扫描整卷。 |
| 🛑 sample | 见“检查点”。 |
| 按计划发布到番茄 | 由作者在平台上传章节并设置定时发布。 |

**检查点：** `sample`：每卷做完审计和批量修复后，skill 停下，把审计报告和该卷章节交给作者阅读；作者读完、把新规则补进 `CLAUDE.md` 或检查清单之前，不开始下一卷。智能体没有任何能连到番茄的工具，所以不经作者，什么都到不了读者手里。

**与来源相比：** 来源出自 2026-05 到 2026-06；撰写本节时，来源 2 打开后是空页面。来源 1 归在工具 `claude-code-skill` 之下，作者把这套方法打包成一个 Claude Code skill，一次让它做一步；这套搭建方式保留了这个流程，只把两部分从 skill 的文字里挪了出来：审校者改成自定义子智能体，这样它读章节时不带写作者的上下文；每 5 章必须 PASS 的规则改成钩子。分层的状态表和活跃/归档两份伏笔表，是作者针对智能体在长文件里找不到事实而想出的办法；搭建方式保留了它们。来源讲的是一位作者写一部小说的经历，不是经过测量的流程；作者自己的规则修正来自阅读正文，这一环在搭建方式里仍留给作者。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 作者建立项目设定集、状态表和伏笔表（后来拆分为活跃和已归档两部分），作为智能体读取的文件 [[1]](#sources)。
2. 写作智能体读取设定集、状态表、活跃伏笔和最近 3 章，然后写出一章加一份写作日志。日志只记录创作决定，不记录事实 [[1]](#sources)。
3. 审校智能体读取章节、日志和全部状态文件，检查连贯性（人物走样、设定矛盾、时间线倒退），并自行更新状态表、伏笔表和章节摘要，无需人工合并 [[1]](#sources)。
4. 每 5 章运行一次 Python 一致性脚本，检查资源跳变、重复伏笔和章节过长。所有检查必须 PASS，才能继续写作 [[1]](#sources)。
5. 每卷结束时，智能体做一次文风审计，扫描重复句式、模板化结尾和固定比喻，然后批量修复 [[1]](#sources)。
6. 🛑 **抽检**：作者阅读成品，抓出智能体发现不了的系统性规律（例如 180 章里同一个身体反应出现了 13 次）。修正方式是制定规则：5–8 个备选反应组成的池子、6 种结尾轮换，以及改写被误读的规则 [[1]](#sources)。
7. 作者把章节按计划发布到番茄小说，并控制在平台的每日字数上限内 [[1]](#sources)。

**产出：** 按计划发布的长篇连载（180 章），以及打包成技能的可复用规则集。
**失败模式 → 防护：** 模板化结尾和固定措辞在几十章里悄悄堆积 → 用具体的检查清单（“最近 3 个结尾必须不同”）和轮换表 [1]。规则措辞被误读（“食物来源”规则变成了一行库存）→ 把规则改写成场景指令 [1]。状态表膨胀到无法有效检索 → 状态分层（最近 3 章写细，更早的压缩），只读取活跃伏笔 [1]。
**与相近工作流的区别：** 最接近的是 AWF-0012（日更网文连载）。那里每章约 2,000 字，发布前由人逐章审阅，并根据段评调整。本工作流由写作/审校智能体成对运作，自己维护状态文件，每 5 章运行脚本把关，人只在分卷层面抽检。自主程度是抽检，而不是逐章分段把关。AWF-0011 属于辅助级，按场景由人审阅。
