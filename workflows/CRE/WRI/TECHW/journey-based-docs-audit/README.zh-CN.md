# 按用户旅程审计文档

**工具变体：** `markdown-docs-as-code` · `github-prs`

## 背景

一家出售多个软件产品的公司，会为每个产品发布文档，由不同的人在不同时间写成。每一页单看可能都没错，但开发者把一项任务从头做到尾（称为一条旅程，例如拿到证书、打包视频、在手机上播放）时，要跨过好几份文档，会遇到文档之间对不上、前置条件藏在另一个产品的指南里、步骤放错位置等问题。逐页检查发现不了这些。在这个工作流里，智能体把一条旅程涉及的所有文档作为一个整体来读，记录每个问题，在源文件里修复能修的，并按产品线把修复拆成各自一个 pull request（PR，提交给他人评审、通过后才合并的修改）。每条产品线的产品负责人仍须确认每一条事实，因为智能体只能依据文档里已有的内容，而有些答案（推荐的行为、合同约定值、控制台上的标签）只存在于其他团队的脑子里。

**术语：**
- **旅程（集成场景）**：客户的开发者要完成的端到端任务，以客户的视角写成；这里一条旅程就是一个审计单元。
- **产品线**：公司单独销售的产品之一，各有自己的文档和负责人。
- **产品负责人（PO）**：对一条产品线的行为和事实负责的人。
- **问题类型**：错误（页面写得不对）、缺失（缺少需要的内容）、位置不当（内容对，但放错了地方）。
- **Pull request（PR）**：提交给仓库、经他人评审后才合并的修改。
- **Markdown 源文件**：文档所用的纯文本文件，像代码一样保存在仓库里。
- **FairPlay**：苹果的视频版权保护系统；它的证书是示例旅程的第一步。

## 用智能体搭建

**形态：** `skill`。一个人一次审一条旅程并且全程在对话中，所以一个装有流程和问题清单格式的 skill 就够了。

**需要：** 存放各产品线 Markdown 源文件的文档仓库；每条产品线已写好的旅程；问题清单的模板（类型、描述、文件和行号、备注）；每条产品线的产品负责人名单。给智能体某个分支的写权限，不要给生产站点的权限。

| 步骤 | 搭建方式 |
|---|---|
| 挑选端到端集成旅程 | 由人列出要审计的旅程；skill 一次处理一条。 |
| 每个旅程：智能体把该旅程涉及的所有文档作为一个整体阅读 → 记录问题 | skill 把旅程涉及的所有文件读进同一个上下文，并把问题清单写成文件。旅程多时，由内置子智能体各负责一条旅程并返回各自的清单。 |
| 智能体修复能修的问题并逐条记录结果 | skill 在分支上编辑源文件，并在每个问题旁写下检查和修改的内容。答案不在文档里的问题标为受阻，不去猜。 |
| 按产品线拆成每条产品线一个 PR | skill 按产品线把改动的文件分组，每条产品线准备一个分支。由人来打开 PR。 |
| 🛑 review → 🛑 sign-off → 部署 | 见“检查点”。 |
| 无法解决的问题转交产品/平台团队 | skill 列出受阻的问题，以及每个团队必须回答的问题。由人发出。 |

**检查点：** `review`：skill 在准备好各产品分支和问题清单后停下；每位产品负责人在自己的 PR 里逐行审阅改动并确认事实。`sign-off`：智能体没有部署或合并的工具，碰不到生产环境；所有产品负责人确认之后，由团队合并并部署。

**与来源相比：** 最新的来源出自 2026-10，另一个出自 2026-08。来源 1 是审计本身的记述，撰写本节时没能打开（站点拒绝了请求），所以步骤依据的是条目本身的文字。来源 2 讲的是每周对照代码库复查文档，不是按旅程审计。条目没有写明审计用的是哪个智能体工具，所以上面的搭建方式也不指明。来源里的 71 个问题和 9 个受阻问题属于公开实例，不属于这套设计。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 团队使用各产品线已写好的客户视角集成场景。开发者实际走通的一条旅程（例如 FairPlay 证书 → 打包 → iOS 播放）就是一个审计单元 [[1]](#sources)。
2. 智能体把该旅程涉及的每份文档的 Markdown 源文件作为一个整体来读，寻找单个页面看不出的问题，例如文档之间的衔接不一致，或某个前置条件被埋在另一个产品的指南里 [[1]](#sources)。
3. 为每个问题记录类型（错误、缺失或位置不当）、描述以及源文件和行号。这份清单成为基线和工作日志 [[1]](#sources)。
4. 智能体通过编辑源文件修复能修的条目，并在每条旁边的备注列写下检查和修改的内容 [[1]](#sources)。
5. 由人把修复按产品线拆成每条产品线一个 pull request（PR）（三个主要产品），让每位审阅人只看到自己产品的改动 [[1]](#sources)。
6. 🛑 **审阅**：各产品线的产品负责人（PO）逐行审阅自己的 PR，确认每一条事实是否正确 [[1]](#sources)。
7. 🛑 **签发**：所有产品负责人确认后，团队部署到生产环境 [[1]](#sources)。
8. 答案在文档里根本找不到的问题（推荐的 API 行为、合同约定值、控制台标签）会卡在其他团队那里。团队把它们转交给产品、平台或业务相关方 [[1]](#sources)。

**产出：** 已上线的更正后文档，加一份问题清单；未决事项转给必须裁定事实的团队。
**失败模式 → 防护：** 一个混合的大 PR 容易被草草放行 → 按产品线拆分 PR，各配自己的产品负责人 [1]。智能体无法凭空编造文档里没有的事实 → 标记为受阻并转交，不让它猜 [1]。逐页审计会漏掉跨文档的缺口 → 按旅程审计 [1]。
**与相近工作流的区别：** 最接近的是 AWF-0075（代码 PR 文档草稿）和 AWF-0135（发布周期文档技能）。两者都由代码变更或发布触发，为新变更起草文档更新。本工作流则是沿用户旅程，对现有文档整体做一次性或周期性审计。交付物是问题清单加按产品线拆分的修复 PR，由产品负责人审阅，而不是代码作者或文档团队。

## 公开实例

覆盖度（截至 2026-11-13）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [DoveRunner (Daniel Kim), Auditing and Fixing Documentation Content with an AI Agent](https://doverunner.com/blogs/auditing-documentation-with-ai-agents/) (2026-08-03)。按旅程审计六条产品线；发现 71 个问题；每个产品的 PR 由产品负责人审阅；9 个问题卡在其他团队。"Across six product lines, this stage produced 71 content issues"; "Fixed | 59"; "Blocked on another team | 9"。*第一手：是；可信度：高。*
- [Biel.ai (David Garcia), Our AI teammate keeps our docs up to date](https://blog.techdocs.studio/p/our-ai-teammate-keeps-our-docs-up) (2026-10-08)。每周对照代码库复查文档，每次覆盖新的范围；发现以 PR 形式交给写作者审阅。"Nova also reviews the codebase against the documentation once a week"（未给出数量）。*第一手：是；可信度：中。*
