# 代码 PR 文档草稿

**工具变体：** `promptless` · `github-agentic-workflows` · `ona-automations` · `biel-nova` · `claude-code-doc-check-skill`

## 背景

软件团队把产品的代码和文档放在不同的仓库里，而文档有两类读者：用户文档（怎么使用产品）和开发者文档（怎么基于产品开发）。产品每个受支持的版本，往往还各有一个文档分支。开发者通过 pull request（PR，提交给他人评审、通过后才合并的修改）改了代码，就得有人同步更新对应的文档页面。这一步很容易被忘掉，在志愿者项目里，文档甚至落后了整整几个发布版本。智能体在代码 PR 一打开时，就在文档仓库里以草稿 PR 的形式写好文档更新，并随着代码 PR 的变化保持同步。仍然要由两个人批准：写这次代码变更的开发者，因为只有他知道实际做了什么；以及文档团队，因为读者看到的措辞和文风归他们负责。

**术语：**
- **Pull request（PR）**：提交给仓库、经他人评审后才合并的修改。**草稿 PR**是标明尚未准备好评审的 PR。
- **代码仓库 / 文档仓库**：分别存放产品代码和产品文档的仓库。
- **用户文档 / 开发者文档**：分别面向使用产品的人 / 基于产品开发的人。
- **版本分支**：文档的并行副本，每个受支持的产品版本一个。
- **diff**：一次修改增加和删除的那些行。
- **风格指南**：文档团队关于语法、措辞和语气的规则。

## 用智能体搭建

**形态：** `service`。代码 PR 打开或变化时没有人守在键盘前，所以智能体由仓库事件触发运行，人只看到它打开的草稿 PR。

**需要：** 对代码仓库的读权限，以及对文档仓库及其各版本分支的读写权限；作为智能体可读文件的风格指南；仓库托管平台的连接器或令牌，只能打开和更新 PR，不能合并；一份智能体不该写进文档的路径和改动类型清单（测试、依赖升级、内部重构）。

| 步骤 | 搭建方式 |
|---|---|
| 代码 PR 已打开 → 智能体起草对用户文档、开发者文档及各版本分支的更新 | 一个由仓库的 pull request 事件触发的云端定时任务，挂载代码仓库和文档仓库。一个 skill 保存流程：读 diff，在每个版本分支上找出受影响的页面，按风格指南写出更新。 |
| 以草稿形式打开文档 PR → (代码 PR 有改动 ⟲ 智能体更新草稿) | 同一个任务以草稿形式打开文档 PR，并与代码 PR 关联。代码 PR 有新提交时，事件再次触发任务；它找到关联的文档 PR 并更新。 |
| 代码 PR 已合并 → 将文档 PR 标为就绪 | 合并事件触发任务，任务把文档 PR 标为可供评审。 |
| 🛑 review (代码作者：准确性) → 🛑 review (文档团队：文风) → 合并 | 见“检查点”。 |

**检查点：** `review` 出现两次，都在文档 PR 里。智能体的令牌可以打开和编辑 PR，但没有合并的权限，所以 PR 会一直开着，直到有人合并。先请代码作者审阅准确性，再请文档团队审阅文风，两者都在 PR 里答复。

**与来源相比：** 来源出自 2026-02 到 2026-10。各来源用不同的工具做同一件事：由每个代码 PR 触发的文档写作产品（Promptless）、每天定时运行并把过去 24 小时的 diff 合并成一个草稿 PR 的智能体（Ona）、检查主分支上已合并 PR 和近期提交的智能体（Biel.ai 的 Nova），以及由撰写人运行、先分诊已合并 PR 再起草的 Claude Code skill（NetFoundry）。上面的搭建方式沿用第一种，按每个 PR 触发；如果按每次提交运行太嘈杂，团队也可以像 Ona 那样攒成一批。Mautic 起初只是给出建议，由人手动转成 PR，直到草稿符合风格指南之后才切换为自动草稿 PR；这套搭建方式没有这样的试运行期，想要的话，可以先让智能体只给建议。只有 Mautic 报告了两位审阅人的安排；其他来源讲的是撰写人在 PR 里审阅。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 触发：开发者在代码仓库上打开一个 pull request（PR）。智能体（Promptless）起草对用户文档和开发者文档的相应更新，并覆盖两者各自的版本分支 [[1]](#sources)。
2. 代码 PR 尚未合并时，文档 PR 保持为草稿。如果代码 PR 在评审期间有改动，智能体会同步更新文档草稿 [[1]](#sources)。
3. 代码 PR 合并后，智能体自动把文档 PR 标为可供评审 [[1]](#sources)。
4. 🛑 **审阅**：编写该代码变更的开发者检查草稿是否与自己构建的内容一致。有人就发现过草稿描述了一个已不存在的按钮 [[1]](#sources)。
5. 🛑 **审阅**：文档团队（Education Team，教育团队）像对待任何文档贡献一样检查语法、措辞和文风，然后合并 [[1]](#sources)。
6. 推广关卡：项目（Mautic）起初只是在仪表盘上给出建议，由团队手动转成 PR；直到草稿持续符合风格指南之后，才切换为自动生成 PR [[1]](#sources)。

**产出：** 已合并到文档仓库的文档 PR，与代码发布保持同步。
**失败模式 → 防护：** 文档描述了过时的界面或行为 → 合并前由代码作者审阅。文风漂移 → 由文档团队审阅，并且只在经过有人监督的试运行之后才启动自动化。

**近期实践（2026）：**
- 步骤 1（触发）：一些团队把合并后的改动攒成每天一个文档 PR，而不是为每个代码 PR 配一个，因为按每次提交运行太嘈杂（Ona）。另一些团队先由撰写人触发一份分诊报告，只为被标记的 PR 起草文档（NetFoundry doc-check）。[[3]](#sources)

**与相近工作流的区别：** AWF-0003 委派式 PR 是让智能体根据工单修改代码。这里的输入是代码 PR，输出是文档 PR，两位审阅人各把关不同的方面。

## 公开实例

覆盖度（截至 2026-11-06）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [New workflows for empty categories](../../../../../research/2026-11-new-workflows.md)。更多实例补充于 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [Mautic, How we keep docs up to date automatically with AI](https://mautic.org/?p=26025) (2026-09-03)。这个开源项目借助智能体起草的文档 PR，缩小了文档相对发布的滞后。约 4 个月内合并了 129 个 Promptless 文档 PR；从代码合并到文档合并的间隔为 27 天，此前是 98 天。*第一手：是；可信度：高。*
- [Ona (Siddhant Khare), How we automated writing docs with an Ona Automation](https://ona.com/stories/docs-automation) (2026-02-12)。每天早上 8 点，智能体读取代码仓库和文档仓库过去 24 小时的 diff，打开一个文档草稿 PR。"Reviewing a draft takes about 30 seconds. Writing that same page from scratch would have been 30 minutes."。*第一手：是；可信度：中。*
- [Biel.ai (David Garcia), Our AI teammate keeps our docs up to date](https://blog.techdocs.studio/p/our-ai-teammate-keeps-our-docs-up) (2026-10-08)。智能体检查 main 上已合并的 PR/提交，打开后续的文档 PR（附截图）；撰写人在 PR 中审阅。没有数量统计；一个示例 PR 补上了两处缺失的 React 组件章节。*第一手：是；可信度：中。*
- [NetFoundry, Inside NetFoundry docs: Streamline doc freshness with AI](https://blog.openziti.io/streamline-doc-freshness-with-ai) (2026-03)。由撰写人运行的 doc-check 技能，把跨仓库已合并的 PR 分诊为需要处理/已覆盖/已跳过，并按指令起草。"5 PRs analyzed · 2 need doc work · 1 already covered · 2 skipped (internal)"; "a 20-to-1 engineer-to-writer ratio"。*第一手：是；可信度：高。*
