# 发版周期文档技能

**工具变体：** `agent-skills` · `cli-scripts`

## 背景

软件产品按固定节奏发版，这里是大约每两周一次，每次发版都需要配套的文档。技术撰稿人要重新生成 API 参考（自动生成的页面，列出开发者可以调用的每个方法和设置），弄清楚改了什么，写发布说明，重画图表，并更新或新增新功能的页面。这项工作每个周期都要重复，而意外藏在细节里：某个目录搬了家，两个已弃用的 API 被合并成一个，某项改动在最后一刻被回滚。智能体接手其中可重复的部分，并对自己写的说明做检查。撰稿人仍要审阅每一次发版，因为只有人才能讲清某项变更对开发者为何重要，也只有人能决定发版本身出问题时怎么办。

**术语：**
- **API 参考**：根据接口定义生成的文档，列出开发者可以使用的方法、枚举和设置。
- **发布说明**：对一次发版改了什么的简短记述。
- **枚举（enum）**：某个设置允许取值的固定清单。
- **变更列表（changelist）**：构成一次发版的那组文件改动。
- **发布阶段标签**：源码中的标签，说明一项功能进展到哪一步（例如预览或正式发布），决定文档是否展示它。
- **YAML 可见性文件**：决定在哪个发布阶段展示哪些文档内容的配置文件。
- **SKILL 文件**：智能体为某项任务加载的 Markdown 指令文件；这里每个产品一个。
- **小毛病（gremlins）**：撰稿人对发版时打乱常规流程的意外的称呼。

## 用智能体搭建

**形态：** `skill`。一位撰稿人一次处理一个产品的一次发版并且全程在对话中，所以每个产品一个装有流程和检查的 skill 就够了。

**需要：** 每个产品一个 skill（各团队的发版流程不同）；含变更列表、YAML 可见性文件和生成的参考文档的代码仓库；放在 skill 旁边、用来重新生成参考文档的脚本；上一次发版的说明，作为格式范例；能启动子智能体打开构建好的文档并对比截图的方式。发布这一步留给撰稿人。

| 步骤 | 搭建方式 |
|---|---|
| 发版 → skill 询问产品专属输入 | skill 的第一条指令：列出它需要的所有输入（版本号、分支、链接），并等撰稿人提供。 |
| 重新生成 API 参考文档 (15 步脚本) → 检测 API 变更 | skill 运行放在它旁边的脚本，然后对比新旧参考文档，列出新方法、枚举和被改动的描述。 |
| 起草发布说明 | skill 根据检测到的变更，按该产品既定的格式写出说明，附预发布链接。 |
| (对照变更列表的文件改动核查说明 + 对照 YAML 核查发布阶段标签 + 子智能体对比截图 ⟲ 修正) | skill 对自己的草稿做三项检查：说明对照变更列表，标签对照 YAML 文件，以及用内置子智能体把截图与原图对比。skill 修正不通过的地方并重新检查。 |
| 更新图表 + 受影响文档 + 新功能文档 | skill 根据同一份变更清单编辑这些文件。 |
| 🛑 review → 撰稿人评论 → 智能体修改 SKILL 文件 → 发布 | 见“检查点”。 |

**检查点：** `review`：skill 最后给出说明、改动的文件以及它无法检查的事项，然后停下；撰稿人补充每项变更为何重要，并处理 skill 应付不了的情况（迁移的目录、合并的 API、回滚）。撰稿人的评论回到智能体手中，由它修改该产品的 SKILL 文件。skill 没有发布步骤，所以由撰稿人发布。

**与来源相比：** 唯一的来源出自 2026-05。它描述的是撰稿人每个产品用一个智能体 skill，并用子智能体检查截图，与这套搭建方式很接近。撰写本节时，打开的页面里看不到 15 步脚本、20 分钟这个数字，也看不到参考文档是 Java 的；它们仍按条目原先的记录保留在步骤里。来源说，各团队的发版流程不同，所以每个产品需要自己的 skill；换模型或工具时，skill 可能需要修改。智能体在会话之间不带记忆，所以撰稿人教给它的东西必须写进 SKILL 文件，来源里也是这么描述的。截至 2026-11 未发现更新的记述。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 每次发版（约每两周一次），每个产品各有一个 SKILL 文件（共四个产品），让智能体预先向撰稿人询问该产品的发版输入 [[1]](#sources)。
2. 一键脚本运行 15 个步骤，重新生成 Java API 参考文档。它取代了约 20 分钟的手工工作 [[1]](#sources)。
3. 智能体检测 API 变更（新方法、枚举、描述变更），并按既定格式起草发布说明，附预发布链接 [[1]](#sources)。
4. 自我核查：智能体对照变更列表的文件改动检查发布说明，对照 YAML 可见性文件检查发布阶段标签，并启动一个子智能体，把截图与原图对比 [[1]](#sources)。
5. 智能体更新 API 图表、受影响的文档和新功能文档 [[1]](#sources)。
6. 🛑 **审阅**：撰稿人做一轮审阅。他们补充某项变更对开发者为何重要，并处理 skill 应付不了的情况（迁移的目录、合并的弃用 API、最后一刻的回滚、错误的标签、构建问题）[[1]](#sources)。
7. 撰稿人的评论回到智能体手中，由它修改 SKILL 文件本身。大约十几轮迭代后，每次发版的评论数从 15–20 条降到约 3–5 条 [[1]](#sources)。

**产出：** 每次发版重新生成的参考文档、发布说明和更新后的概念文档，外加一个每个周期都在改进的 SKILL 文件。
**失败模式 → 防护：** AI 抓不住某项变更为何重要，发版时的意外（回滚、错误标签）被漏掉 → 强制撰稿人审阅一轮。提示词漂移或更换了模型 → 把评论回写进各产品的 SKILL 文件。
**与相近工作流的区别：** AWF-0075 代码 PR 文档草稿按每个代码 PR 触发，跟随 PR 的改动，有两道审阅（代码作者，然后文档团队）。本工作流由发版周期驱动，涉及四个产品，带自动交叉检查，以及由撰稿人主导、会修改 skill 本身的循环。触发方式、产出（发布说明加重新生成的参考文档）和检查点安排都不同。

## 公开实例

覆盖度（截至 2026-11-06）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [Second collection pass](../../../../../research/2026-11-second-pass.md)。

- [I'd Rather Be Writing, Developing internal skills for recurring documentation processes](https://idratherbewriting.com/blog/internal-skills-release-docs) (2026-05-04)。每个产品一个带自我核查的发布说明 skill；随着 skill 不断完善，撰稿人的审阅评论减少。早期 "15–20" 条评论，经过 "a dozen iterations" 后 "maybe 3–5"。*第一手：是；可信度：高。*
