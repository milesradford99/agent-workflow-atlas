# 自有声音的文章音频

**工具变体：** `azure-speech-custom-voice` · `google-wavenet-speechbert` · `elevenlabs-beyondwords`

## 背景

有些报纸和新闻网站为每篇文章提供语音版，方便订阅用户通勤或做饭时收听。让真人旁白每天为每篇文章录音并不现实，所以音频由文字转语音（TTS）系统朗读文章生成。风险在于生成的声音会读错人名和生僻词，读者会注意到，也会损害对报纸的信任。因此系统使用专为这家媒体制作的声音，并维护一个不断增长的纠错清单。声音做好、测试完之后，流水线在每篇文章发布时自动转换，不需要任何人去启动。先由语音专家抽听一部分输出，找出反复出现的错误；之后由编辑纠正听众反馈的错误读音，因为只有熟悉内容和报纸用名的人才能说清一个词该怎么读。

**术语：**
- **TTS（文字转语音）**：由文字生成语音音频的软件。
- **自有声音（house voice）**：用出版方请来的演员的录音制作的合成声音，是该媒体自己的声音，而不是通用的现成声音。
- **语料**：演员朗读的那批句子，声音就是用它训练出来的。
- **影子运行（shadow run）**：试运行期，每天都生成音频，但不向听众发布。
- **发音/替换词库**：一份词表，记录能让 TTS 读对某个词的写法或读音。
- **小标题**：文章内部的短标题，音频中会略去。
- **片头音（jingle）**：旁白前播放的一小段固定声音。

## 用智能体搭建

**形态：** `platform`。声音来自定制的语音模型，通用智能体替代不了。其余部分，通用智能体可以以 `service` 的形态承担：文章一发布就启动，无人在键盘前，人只看审阅队列。

**需要：** 出版方的内容系统，通过 MCP 连接器或 API 连接，能发出文章已发布的信号；一个支持定制声音的 TTS 服务以及用它做好的自有声音；存放发音词库的位置，以及存放抽检音频和听众反馈的位置；一个编辑队列（工单系统或共享文件夹）。除了 TTS 服务获准接收的内容，智能体不得持有未发布的文章。

| 步骤 | 搭建方式 |
|---|---|
| 打造自有声音 | 与 TTS 厂商和演员一起完成，不经过智能体。 |
| 影子运行 → 🛑 sample | 云端定时任务，或自己的调度器启动 `claude -p`，挑出当天的文章。脚本把每篇发送给 TTS 服务。固定比例放入审听文件夹交给语音专家；不向听众发布任何内容。 |
| 发音/替换词库 | 一个文件或表格，由脚本在合成前套用。智能体根据专家的笔记提出新增条目，由人采纳。 |
| 上线：去掉小标题和括号 → TTS → 片头音 + 标题 + 署名 | 脚本去掉不读的部分，调用 TTS 服务，并加上片头音以及朗读的标题和署名。 |
| 应用内发布 → 听众反馈 | 由内容系统发布音频。错误读音的反馈进入队列；智能体按词归类。 |
| 🛑 review → 扩大到更多文章 | 见“检查点”。 |

**检查点：** `sample`：影子运行期间及之后，每天音频的固定比例会复制到语音专家的队列；专家的纠正进入词库，并决定何时上线。`review`：智能体只为每个被反馈的词提出替换建议，发到编辑的队列。它没有修改线上词库的工具；由编辑在管理界面里应用改动。

**与来源相比：** 来源 1 是厂商的案例，页面标注日期为 2023-06，此后有更新；来源 2 没有日期。截至 2026-11 没有找到这一工作流更新的第一手记录。较新的材料来自厂商一侧：BeyondWords 介绍了编辑可在项目设置或通过 API 设定的发音规则（[BeyondWords blog](https://beyondwords.io/blog/enhancing-ai-generated-audio-articles-with-pronunciation-rules-2/)），南华早报宣布改进了文章的旁白（[SCMP](https://www.scmp.com/announcements/article/3367019/high-quality-natural-audio-listen-scmp-articles-improved-narration)）。来源 1 中厂商的工具 Azure 定制声音仍是受限访问功能：只有获批的客户才能使用（[Microsoft Learn](https://learn.microsoft.com/en-us/azure/ai-services/cognitive-services-limited-access)）。没有获批的出版方需要改用其他 TTS 厂商的定制或克隆声音。两个来源都是厂商或代理机构的说法，不是独立报道。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 报社打造自有声音：演员录制厂商的基础语料，外加取自报社自家文章的 400 个句子，让声音能适应报纸冗长、多引语的文风。《世界报》（Le Monde）使用一男一女两个声音，按篇交替（访谈和社论除外）[[1]](#sources)。
2. 🛑 **抽检**：在为期 2 个月的影子运行中，系统每天自动生成 20 篇文章的音频，但不对外播出。语音专家试听，并按读音纠正用词 [[1]](#sources)。
3. 报社维护一个替换/发音词库，让编辑可以覆盖难词的默认读音。词库随时间不断增长 [[1]](#sources)[[2]](#sources)。
4. 上线时，系统自动转换每篇选定的文章，排除小标题和括号内的内容，配上片头音、标题、导语和作者，发布到订阅用户的应用中 [[1]](#sources)。
5. 🛑 **审阅**：编辑通过管理界面的替换区，纠正被报告的错误发音 [[2]](#sources)。
6. 报社收集听众反馈（上线时的弹窗），关注完播率和收听时长，然后扩大覆盖范围。《世界报》从每天 20 篇扩展到全报，仅排除地图或图表较多的文章 [[1]](#sources)。

**产出：** 在出版方的应用或网站中，随文章发布同步生成的文章音频版本。
**失败模式 → 防护：** 通用声音听起来都一样，让听众疲劳 → 定制自有声音并交替使用 [1]。自家文风打乱了 TTS 的节奏 → 用自家文章的句子训练，而不是改变写作 [1]。错误发音损害信任 → 设影子期并配语音专家试听，加上长期维护的替换词库 [1][2]。
**与相近工作流的区别：** 最接近的是 AWF-0139（导演式 AI 有声书）。那是辅助级的，对一本书逐章导听，由作者签发。本工作流是新闻编辑部的流水线：经过抽检式的影子期后，每篇文章无人值守地朗读，人只负责维护词库和回应反馈。交付物（逐篇的音频流）、自主程度（抽检）和检查点都不同。AWF-0078 是对已录制音频做播客后期制作。

## 公开实例

覆盖度（截至 2026-11-13）：**薄弱**：只有匿名、与厂商相关或经记者转述的说法。收集与复核见 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [Microsoft, Le Monde audio articles](https://www.microsoft.com/en/customers/story/1642942168798077445-lemonde-media-entertainment-azure-en-france) (page dated 2023-06-03, text since updated)。先由语音专家试听做影子运行，再每天为 20 篇文章生成音频，最后覆盖全报。"Over a 2-month period, 20 articles were generated automatically in audio format every day without being broadcasted"; "72% of the article read on average"; "over 100 articles a day"。*第一手：厂商；可信度：中。*
- [Diesdas Digital, Speechbert for ZEIT ONLINE](https://www.diesdas.digital/en/cases/speechbert) (undated)。文章发布后数秒内转成音频；编辑维护发音替换词库。"over 250,000 text-to-speech conversions since launch"。*第一手：厂商；可信度：中。*
