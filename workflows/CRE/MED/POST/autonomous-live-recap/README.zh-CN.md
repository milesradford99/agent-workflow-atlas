# 自动直播战报

**工具变体：** `aws-media-replay-engine` · `amazon-rekognition`

## 背景

一场直播比赛会产出一串观众想在几秒内再看一遍的时刻：进球、扑救、那次冲突。转播方靠人工在素材墙前剪，这既限制了能剪多少条，也限制了多快；而在赛事期间，等剪好，观众已经走开了。这套安排把手拿掉了。一个计算机视觉模型同时盯着几路信号，找那些总在关键时刻之前出现的线索——人声鼎沸、解说音调、切到某个机位——在每个事件前后剪出片段，并重建一份滚动回顾，一场比赛里反复发布很多次。任何片段在出现在应用里之前都不经过人。这既是全部的意义，也是全部的风险：编辑范围必须窄到可以把机器放进去，而这里窄到只做比赛事件——不加评论、不加背景、不讲故事。事后团队查看输出的表现，读观众的点赞和点踩，增补或修正事件类型。想要逐条批准每个片段的人，其实是在选另一种工作流。

**术语：**
- **回顾（recap）**：把到目前为止的比赛剪成一段简短摘要，随事件不断更新。
- **事件（event）**：一个被检测到的时刻——进球、扑救、点球——带进出点。
- **计算机视觉模型（CV model）**：判断画面与声音里正在发生什么的模型，这里是用"事件之前的线索"训练出来的。
- **音频线索（audio cue）**：声音里的信号，例如人声爆发或解说语气，用来在不看每一帧的情况下定位时刻。
- **CMS**：应用所读取的内容管理系统。
- **抽检式自主（sampled autonomy）**：不逐条审批就发布，事后复核其中一部分。
- **事件类型（event type）**：被检测的时刻类别；增加一类就是扩充覆盖面的方式。

## 用智能体搭建

**形态：** `platform`。检测与拼装是专业的视频工作——在直播音频和画面上跑 CV 模型，加上跟上比赛节奏的渲染管线——通用智能体做不了；智能体负责的是围绕它的一圈：事件词表、片段规范、抽样报告和改进闭环。

**需要：** 信号的使用权和允许自动剪辑的授权；带时间信息的直播流；用该运动的专属线索训练过的 CV 模型，以及一批已标注的历史比赛用于衡量它；一个能在比赛进行中产出并重新发布回顾的剪辑与渲染服务；一个接受无人步骤发布请求的 CMS 或应用接口；抽样所读的分析数据——播放、完播、点赞。搭建必须为窄编辑范围之外的一切准备硬性拦截：不带任何针对个人的评论、不带受伤画面、不带赞助敏感时刻，而这条排除要写在事件词表里，不能写在提示词里。

| 步骤 | 搭建方式 |
|---|---|
| 接入直播比赛流 | 平台工作：几路信号被切成短片段送推理，每个片段的时间戳全程保留，使检测到的时刻能映射回播出时间。 |
| CV 检测关键时刻 | 训练好的模型给每个片段打分；一个阈值把分数变成事件，阈值是团队自己的设置，可以在一个糟糕的比赛夜之后调整。 |
| 每个事件：剪辑 + 自动拼装回顾 | 剪辑服务按事件前后预留时间切出片段，用台里的转场拼装回顾，并写成新版本而不是改旧版本，所以剪错的片段可以下架而不必重建。 |
| 直接发布到 CMS/应用 | 没有审批环节的发布调用，受模板约束，模板只接受比赛事件类标签；智能体贡献的是字幕模板与事件标签，两者都带版本。 |
| 🛑 sample（团队查看表现 + 观众点赞/点踩） | 智能体每天对已发布集合做一次巡检：哪些事件类型触发了、哪些片段被看完、点赞在哪里掉了，以及同一时间窗里模型漏掉了哪些时刻——漏掉的部分是任何看板都看不出来的。 |
| 推出改进 | 发现的问题变成对词表或阈值的修改建议，像流水线的其他改动一样被审阅。 |

**检查点：** `sample`：按设计没有逐条关卡，所以控制发生在事后，而且必须系统化——每天固定复核已发布片段加上观众信号，按事件类型报告误报数和漏报数。因为发布是自动的，排除项必须是结构性的：词表不能产出权利或编辑政策禁止的片段类型，发布模板只接受词表定义的标签，所以一个突然对受伤画面起反应的模型也无法把它发布出去。

**与来源相比：** 来源出自 2023-07：一篇关于世界杯部署的行业媒体报道，本月已打开。它已超过十二个月，因此重新检索了这项实践。此后有这些变化：这已经是一类产品，而不是某家转播方的一次自建。2026 年的平台在几十种运动上卖同一套"检测—拼装"链路，其中几家还提供竖屏重构图和滚动回顾；而它们的分歧点正是本条目所做的那个决定——一家主打"AI 找时刻，你来决定发布什么"，另一些则自动发布。如今中等级别的联盟可以直接买，而不必自建，于是问题从"能不能做"变成"什么样的编辑范围才值得无人值守地发布"；本条目给出的答案是只做比赛事件，比现在产品所提供的范围更窄。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 接入多路并发的转播流，并用 Amazon 开源的 Media Replay Engine 剪出片段供推理使用 [[1]](#sources)。
2. 一个基于音频线索和机位训练的计算机视觉模型找出比赛的关键时刻 [[1]](#sources)。
3. 每出现一个新事件，回顾就重建并自动拼装，加上转场和淡出黑场。它直接进入 CMS 和 FOX Sports 应用，把比赛 'upwards of 20 times per match' 重述一遍 [[1]](#sources)。
4. 🛑 **抽检**：没有逐个片段的审批。团队监控表现并推出修复，例如点赞/点踩，以及扑救和点球等新事件类型 [[1]](#sources)。该页面对这个检查点只是简略描述。

**产出：** 每场比赛期间发布到应用的滚动精彩回顾。
**失败模式 → 防护：** 足球没有固定套路，检测会漏检或误报 → 用音频和机位线索训练模型，并根据表现推出修复。每个片段都没有人把关 → 只有在编辑范围很窄时（仅限比赛事件）才安全。
**与相近工作流的区别：** AWF-0077 逐字稿优先的视频剪辑由作者审阅内容剪辑，并在渲染前签发一遍完整观看。本工作流不经逐条审批就发布，人只监控输出流。自主程度（抽检对分段）和产出（一场比赛中多次更新的直播回顾）都不同。
