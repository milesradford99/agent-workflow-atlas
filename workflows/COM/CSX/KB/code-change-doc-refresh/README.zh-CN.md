# 随代码变更更新帮助文档

**与相近工作流的区别：** 最接近的是 AWF-0048 缺口匹配式知识维护：那是从已解决的工单出发，把它们聚类，需要计划 + 编辑 + 产品负责人签字；本工作流从代码变更出发，找出已经变得不实的文章，每份草稿只有一次采纳/拒绝的审阅。输入、交付物（修正过时段落）和检查点都不同。
**工具变体：** `happysupport` · `ferndesk` · `wonderdesk` · `theneo` · `falconer` · `productlane`

## 步骤

1. 监视代码仓库中已合并的 pull request（或变更日志）；过滤掉重构、测试和依赖升级 [[1]](#sources)。
2. 把相关的 PR 归并为一项通俗易懂的产品变更：改了什么、谁会注意到 [[1]](#sources)。
3. 在帮助中心搜索该变更影响的文章；读取 PR 的 diff，如果拿不到 diff 就停下，而不是猜测 [[1]](#sources)[[3]](#sources)。
4. 针对被变更改错的段落起草修改，文章的其余部分不动；如果没有文章涉及该功能，就起草新文章；在支持的情况下重新截图 [[1]](#sources)[[2]](#sources)。
5. 第二个模型对照代码变更检查每处修改，删除或标记它无法佐证的内容 [[1]](#sources)。
6. 🛑 **审阅**：文档负责人审阅被标记的段落，并对每份草稿采纳、修改或驳回；采纳之前不会上线，未发布的行为也保持不公开 [[1]](#sources)[[2]](#sources)[[3]](#sources)。
7. 发布；翻译和帮助中心的聊天机器人会同步到新版本 [[1]](#sources)。

**产出：** 更新或新增的帮助中心文章，每篇都链接到触发它的 PR。
**失败模式 → 防护：** 文档描述了未合并或未发布的行为 → 以合并为触发条件，只在客户可用时才发布 [3]。整篇重写会掩盖错误 → 段落级 diff 加校验模型 [1]。
