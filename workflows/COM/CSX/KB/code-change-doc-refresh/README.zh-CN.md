# 随代码变更更新帮助文档

**工具变体：** `happysupport` · `ferndesk` · `wonderdesk` · `theneo` · `falconer` · `productlane`

## 背景

卖软件的公司都有帮助中心：一批面向客户公开的支持文章，说明产品怎么用。开发者随时在改产品，每一次改动都可能让某篇文章里的一句话、一个菜单名或一张截图变得不实。出现这种情况时不会有任何东西报错，错误会一直留着，直到有客户来投诉。在这里，智能体在代码变更合并时启动，判断客户会注意到什么，找出已经对不上的文章，只为现在已经不对的段落起草修改。第二个模型对照代码变更检查每处修改。哪些内容上线，仍由帮助中心的负责人决定，因为发布的文章是对客户的一项声明，而一项变更可能在向客户发布之前就已经合并。

**术语：**
- **帮助中心**：对外公开的一组支持文章，常常也用作支持聊天机器人的知识来源。
- **PR（pull request）**：提议的代码变更，经审阅后合并进主代码。
- **diff**：一次变更新增和删除的行。
- **段落级修改**：只改错了的句子，文章其余部分不动。
- **文档负责人**：负责帮助中心内容的人。
- **变更日志（changelog）**：按日期列出每次发布改了什么的清单。

## 用智能体搭建

**形态：** `service`。一次 pull request 合并就启动运行，现场没有人；文档负责人只看到一份等待决定的草稿清单。

**需要：** 对代码仓库的读取权限，包括 pull request 的 diff；对帮助中心文章的读取权限，可以是 Markdown 仓库，也可以通过帮助中心工具的连接器；一个不是公开站点的草稿落点（草稿分支、草稿状态或审阅队列）；一份说明哪些变更对用户可见的规则，放在参考文件里，由文档负责人维护。智能体不需要发布权限。如果帮助中心是机器翻译的，也不要给它翻译工具的权限。

| 步骤 | 搭建方式 |
|---|---|
| 已合并的 PR 或发版 | 由 GitHub 事件启动的云端定时任务，或合并后由 CI 任务运行 `claude -p`。 |
| 剔除用户无感的变更 → 归并为产品变更 | skill 读取 diff，按参考文件剔除重构、测试和依赖升级，再为每项产品变更写一段通俗的描述。 |
| 找出受影响的帮助文章 | skill 在文章中搜索被改动的功能、设置或标签。读不到 diff 时就停下并报告，而不是猜测。 |
| 起草段落级修改 + 为缺口补写新文章 | skill 针对错了的段落写出修改，没有文章涉及该功能时起草新文章草稿。每份草稿都链接到对应的 PR。 |
| 第二个模型对照 diff 检查修改 | 一个没看过起草过程的子智能体拿到 diff 和修改，删除或标记 diff 无法佐证的修改。 |
| 🛑 review (文档负责人逐条采纳或拒绝草稿) | 见检查点。 |
| 发布 + 重新翻译 | 由文档负责人在帮助中心工具里完成，翻译也由该工具触发。 |

**检查点：** `review`：草稿进入审阅队列，每处修改一条，附上对应的 PR 和支持它的那部分 diff。智能体没有发布或修改线上文章的工具，所以文档负责人采纳之前不会上线；负责人还要判断这项变更是否已经到了客户手上。

**与来源相比：** 来源 4 出自 2026-06，其余未注明日期，也没有公开实例。四个来源描述的都是厂商产品（HappySupport、Ferndesk、Helpin、Productlane），其中一个是厂商文档里的配置方案，所以没有一个报告了某个团队自己的结果。本搭建用通用部件沿用它们共同的设计：合并时触发、段落级草稿、由人采纳或驳回。它无法从线上产品重新截图，而厂商把这一点列为功能。来源 4 提到可以通过厂商的连接器让 Claude Code 或 Codex 对着代码仓库来写帮助中心；这与让现有文章保持最新是两件不同的事。因为最新的来源不足 12 个月，没有再查找更新的叙述。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 智能体监视代码仓库中已合并的 pull request（或变更日志）；过滤掉重构、测试和依赖升级 [[1]](#sources)。
2. 智能体把相关的 PR 归并为一项通俗易懂的产品变更：改了什么、谁会注意到 [[1]](#sources)。
3. 智能体在帮助中心搜索该变更影响的文章；读取 PR 的 diff，如果拿不到 diff 就停下，而不是猜测 [[1]](#sources)[[3]](#sources)。
4. 智能体针对被变更改错的段落起草修改，文章的其余部分不动；如果没有文章涉及该功能，就起草新文章；在支持的情况下重新截图 [[1]](#sources)[[2]](#sources)。
5. 第二个模型对照代码变更检查每处修改，删除或标记它无法佐证的内容 [[1]](#sources)。
6. 🛑 **审阅**：文档负责人审阅被标记的段落，并对每份草稿采纳、修改或驳回；采纳之前不会上线，未发布的行为也保持不公开 [[1]](#sources)[[2]](#sources)[[3]](#sources)。
7. 文档负责人发布；翻译和帮助中心的聊天机器人会同步到新版本 [[1]](#sources)。

**产出：** 更新或新增的帮助中心文章，每篇都链接到触发它的 PR。
**失败模式 → 防护：** 文档描述了未合并或未发布的行为 → 以合并为触发条件，只在客户可用时才发布 [3]。整篇重写会掩盖错误 → 段落级 diff 加校验模型 [1]。
**与相近工作流的区别：** 最接近的是 AWF-0048 缺口匹配式知识维护：那是从已解决的工单出发，把它们聚类，需要计划 + 编辑 + 产品负责人签字；本工作流从代码变更出发，找出已经变得不实的文章，每份草稿只有一次采纳/拒绝的审阅。输入、交付物（修正过时段落）和检查点都不同。
