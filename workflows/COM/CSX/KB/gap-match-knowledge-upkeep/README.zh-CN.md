# 缺口匹配知识库维护

**工具变体：** `microsoft-ai-for-knowledge-management` · `supabase-gemini-webflow`

## 背景

客服团队回答客户的问题，并把每个问题作为工单关闭。知识库（KB）是一批文章，让客户和客服聊天机器人不必提交工单就能找到这些答案。文章会过时，也会缺失，而团队往往要等到有人抱怨或客服上报才知道。工单里其实已经有证据：同一个问题反复出现，或者客服给出的解决办法没有出现在任何一篇文章里。在这里，智能体读取已解决的工单，把反复出现的问题归成组，拿每一组与现有文章对照，再提议新建文章、更新文章或不做改动，然后起草。哪些候选项继续推进由人批准，草稿的准确性由人检查，发布之前还要有人签发，因为一篇错误的文章会让许多客户走错方向，而且文章是以公司的名义发出的。

**术语：**
- **已解决工单**：客服已经关闭的客户请求，附有客服记录的问题所在和解决办法。
- **KB（知识库）**：帮助文章的集合。
- **聚类（cluster）**：围绕同一个根本问题的一组工单。
- **SME（领域专家）**：足够了解产品、能判断文章对不对的人。
- **风格指南和模板**：文章措辞和版式的规则，以及每篇文章遵循的固定提纲。
- **CMS（内容管理系统）**：存放和发布文章的工具。
- **完整度评分**：判断收集到的材料是否足以不靠猜测写出文章的评分。

## 用智能体搭建

**形态：** `service`。按计划运行，读取新工单，现场没有人；人在之后回应三个请求：批准计划、审阅草稿、签发。

**需要：** 对已解决工单和知识库文章的读取权限；一个状态存储，列出每个候选项、其决定和所处阶段，避免之后的运行重复处理；作为参考文件的风格指南和文章模板；候选清单和草稿的落点，例如工单队列或 CMS 里的草稿状态；三位批准人的名字（批准计划的人、编辑或领域专家、产品负责人）。工单文本在到达智能体之前先去掉客户的个人信息，并且不给它发布权限。

| 步骤 | 搭建方式 |
|---|---|
| 导入已解决工单 → 结构化 + 聚类 | 云端定时任务，或由自己的调度器运行 `claude -p`，通过 MCP 连接器拉取新的已解决工单。skill 把每张工单整理成字段（报告的问题、实际问题、修复步骤），并把相似的工单归成组。 |
| 与现有知识库匹配 → 新建 \| 更新 \| 跳过 | skill 在知识库中搜索每个聚类，评估现有文章对该解决办法的覆盖程度，并按条目报告的阈值分流（低于 40% 新建，40% 到 80% 更新，高于 80% 跳过）。 |
| 🛑 plan | 见检查点。 |
| 收集来源 + 完整度评分 | 对每个获批的候选项，skill 收集工单、现有文章和产品说明，再把该候选项标为完整、部分，或需要与产品经理通话。 |
| 起草（风格指南 + 模板） | skill 按模板和风格指南起草。一个没看过起草过程的子智能体，对照收集到的来源检查草稿里的每一个步骤。 |
| 🛑 review (编辑/专家) | 见检查点。 |
| 🛑 sign-off (产品负责人) | 见检查点。 |
| 逐篇发布 | 由产品负责人或编辑在 CMS 里发布单篇文章。 |

**检查点：** `plan`：运行在贴出候选清单及各聚类的分流结果后结束；只有人批准的候选项，才会在下一次运行中写成文章。`review`：草稿进入编辑或领域专家的队列，他们的修改写入状态存储，供下次运行使用。`sign-off`：智能体没有发布或修改线上文章的工具；产品负责人批准，发布由人在 CMS 里完成。

**与来源相比：** 来源 1 出自 2026-07，来源 2 出自 2026-04。上次打开时，来源 2 的链接指向了一个无关的网站，所以依赖它的步骤 4、5 和 7，在 2026-11 无法对照该来源核实。来源 1 描述了导入、聚类、对照和通知专家，没有描述计划关口或签发。微软的系统是内部平台；本搭建用通用部件取代它。40% 和 80% 的阈值来自该系统，需要对照你自己的文章来校准。来源报告的是预计节省的工时；本条目不对这套搭建方式作任何此类声称。

## 步骤

*以下按来源所述。*

1. 系统导入已解决的工单。AI 富化环节把杂乱的备注整理成结构化字段，例如报告的问题与实际问题、修复步骤 [[1]](#sources)。
2. 系统对工单聚类，让反复出现的问题浮现出来，把一次性的个案排除在外 [[1]](#sources)。
3. 系统把每个聚类的解决方案与现有文章对照评分并分流：匹配度低于 40%，新建文章；40% 到 80%，更新现有文章；高于 80%，不做改动 [[1]](#sources)。
4. 🛑 **计划**：由人批准哪些候选项继续推进。在一次运行中，AI 分流的准确率约为 90%，其余由这道关口拦下 [[2]](#sources)。
5. 智能体为每篇文章收集 5–6 个来源，起草前先给完整度评分（完整 / 部分 / 需要与产品经理通话）。然后它对照风格指南、组件库和模板起草 [[2]](#sources)。
6. 🛑 **审阅**：编辑或领域专家检查准确性并补充细节。专家的反馈同时用于调优模型 [[1]](#sources)[[2]](#sources)。
7. 🛑 **签发**：产品经理批准。这在实践中是最慢的一步，需要 3–5 天 [[2]](#sources)。只发布单篇，绝不整站发布，并把链接回贴到工单 [[2]](#sources)。

**产出：** 新建和更新后的帮助中心文章，位于 CMS 中，每篇都能追溯到来源工单。对现有文章的更新会通知其负责人。
**失败模式 → 防护：** 工单上下文单薄时起草，会编出不存在的步骤 → 先给来源的完整度评分，把薄弱的候选项交给人工通话 [[2]](#sources)。一次性的修复弄乱知识库 → 起草前要求先形成聚类 [[1]](#sources)。整站发布会泄漏预发布内容 → 逐篇发布 [[2]](#sources)。
**与相近工作流的区别：** AWF-0018 聚类—简报—起草（Cluster-brief-draft）把搜索关键词聚类成用于获客的 SEO 文章。本工作流由已解决工单驱动，把每个聚类分流为新建、更新或跳过，并以专家验证为关口。
