# 续约窗口风险简报

**工具变体：** `statisfy` · `revllama-pulse` · `kortix-postgres-hubspot-slides`

## 背景

按年订阅销售的软件公司，必须在每份合同到期前拿下客户的续约。负责某个客户的客户成功经理（CSM）本应提前看出问题：主要联系人不再回复，支持工单越来越严重，使用产品的人变少，发票迟迟未付。这些信号分散在不同的系统里，只靠数字算出的分数，可能直到客户退订的那天都还显示它很健康。在这里，智能体每周运行一次，只读这些系统、不改动任何东西，为每个看起来有风险的客户写一份附有证据的简报，外加一份挽留计划草稿。哪些标记是真的、对客户说什么，仍由人来定，因为只有 CSM 了解这段客户关系，而且每一条消息都以公司的名义发出。

**术语：**
- **CSM（客户成功经理）**：负责留住现有客户、促成续约的人。
- **续约窗口**：合同到期前，必须把续约谈下来的那段时间。
- **挽留计划（save plan）**：为留住有风险的客户而提议的行动：联系谁、提供什么方案或补救。
- **QBR（季度业务回顾）**：公司向客户说明产品这个季度交付了什么、下一步怎么做的会议。
- **健康度评分**：通常根据使用量和账单数字得出的评分，用来估计客户续约的可能性。
- **关键联系人（champion）**：客户内部推动采用该产品的人。
- **席位变化趋势**：活跃的授权用户数量的走势。
- **CRM**：记录客户、联系人和合同的系统。

## 用智能体搭建

**形态：** `service`。扫描按每周的计划启动，现场没有人；CSM 只看到它留下的简报和草稿。

**需要：** 对 CRM、通话录音、产品使用、支持和账单的只读连接，所有这些系统都不给写入工具；一个能找出窗口期内续约的列表或查询；简报和草稿的落点，例如共享文件夹或 CSM 的工作区；一个状态存储，记录哪些客户被标记、CSM 如何评价每个标记，以及团队对“有风险”的定义，这个定义放在参考文件里，由客户成功副总裁签字确认。智能体不需要邮件或任何能触达客户的工具。

| 步骤 | 搭建方式 |
|---|---|
| 每周列出窗口期内的续约 | 云端定时任务，或由自己的调度器每周运行 `claude -p`；脚本列出续约日期落在窗口内的客户。 |
| 每个客户：汇总使用量 + 工单 + 通话 + 账单信号 | 只读的 MCP 连接器。每个客户交给一个子智能体并行处理，它返回找到的信号及其出处。 |
| 带证据标记 | skill 按参考文件中团队的风险规则打标记，并保留每个标记的证据。 |
| 简报 + 挽留计划草稿 / QBR 草稿 | skill 为每个被标记的客户写一份简报和挽留计划草稿，为到了回顾节点的客户写演示稿草稿和简报文档，放入共享文件夹。 |
| 🛑 review (CSM 核实标记) | 见检查点。 |
| 🛑 action (CSM 批准外联) | 见检查点。 |
| 跟踪计划行动 | 每次运行把每份计划及其状态追加到状态存储，下次运行时读回。 |

**检查点：** `review`：简报进入 CSM 的队列；CSM 把每个标记评为有用与否、早已知晓与否之前，客户不会有任何后续动作；这些评价写入状态存储，用来调整规则。`action`：智能体没有任何能触达客户的工具，对源系统也没有写权限，所以获批的外联由 CSM 从自己的邮箱发出。

**与来源相比：** 来源和公开实例出自 2026-05 至 2026-07；来源 1 的日期是 2026-07-24，来源 2 和 3 列为未注明日期（来源 3 的页面显示 2026-05-20）。Revllama 和 Statisfy 的叙述描述的是内部实现未公开的厂商产品，Kortix 的页面描述的是在自家平台上运行、只出草稿的智能体；本搭建用通用部件遵循同样的只读、仅草稿限制。云端定时任务截至 2026-11 仍是研究预览。来源 2 还报告了把规则放到过往流失客户上回放验证；上面的搭建方式不包含这一步，团队可以把它作为单独的分析加上。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 定时任务列出即将进入续约窗口的每个客户。在一个部署中，CSM 会在三个月前收到提前提醒 [[1]](#sources)。智能体以只读方式连接数据源：CRM、通话录音、产品使用、支持、账单 [[2]](#sources)[[3]](#sources)。
2. 对每个客户，智能体汇总 CSM 本来就信任的信号，例如关键联系人沉默、工单严重度构成、席位变化趋势和发票争议，并附上证据抛出事件 [[2]](#sources)。
3. 对被标记的客户，智能体起草附有证据链的挽留计划。对到了回顾节点的客户，整理 QBR 演示稿草稿和简报文档。它绝不回写源系统 [[2]](#sources)[[3]](#sources)。
4. 🛑 **审阅**：团队对每个高优先级事件评价是否有用、是否早已知晓。这也用来调整“有风险”的定义，该定义由客户成功（CS）副总裁签字确认 [[2]](#sources)。
5. 🛑 **操作**：CSM 先批准挽留计划，任何内容才会触达客户；QBR 草稿也由 CSM 修改后再演示 [[2]](#sources)[[3]](#sources)。

**产出：** 一份带证据、按优先级排序的续约风险清单，外加位于 CSM 工作区的挽留计划草稿和 QBR 演示稿。获批的外联发送给客户。
**失败模式 → 防护：** 静态健康分让客户在流失时仍显示为绿色 → 跨系统汇总非结构化信号，并用过往的流失案例回放验证 [[2]](#sources)。智能体越权 → 对源系统保持只读，对产出保持仅草稿 [[3]](#sources)。告警太多 → 让团队评价事件是否有用并调整规则 [[2]](#sources)。
**与相近工作流的区别：** 暂无相近者。AWF-0006 受管控的查询（Governed query）按需回答分析问题；本工作流是对全部客户的定期扫描，最后以 CSM 批准的客户外联收尾。

## 公开实例

覆盖度（截至 2026-11-06）：**薄弱**：只有匿名、与厂商相关或由记者转述的说法。收集与复核见 [New workflows for empty categories](../../../../../research/2026-11-new-workflows.md)。

- [Statisfy, Simpplr customer story](https://www.statisfy.com/customers/simpplr) (2026-07-24)。Simpplr 的 CS 团队持续运行续约分析；CSM 在续约前三个月收到预警。"Renewal and risk workflows account for 85% of the agentic workflows the team has run to date."。*第一手：厂商；可信度：中。*
- [Revllama, enterprise SaaS renewals](https://www.revllama.com/case-studies/enterprise-saas-renewals) (undated)。对 500 个续约做了 30 天审计；CS 团队评价每个事件；挽留计划由 CSM 批准。"In 30 days Pulse raised 41 high-priority events across the 500 accounts. The team rated 29 useful"。*第一手：厂商；可信度：低。*
