# 确认输入后的 QBR 演示稿

**工具变体：** `rippling-ai` · `google-slides` · `salesforce` · `gong`

## 背景

季度业务回顾（QBR）是软件公司与客户开的一次会议，向客户说明过去一个季度里产品的使用情况、产生的价值，以及下一步怎么做。负责这位客户的客户经理要为此准备一份幻灯片。准备工作包括：从销售系统里调出订阅数据，阅读最近的通话记录，查看产品实际用了多少，再把同一份演示稿换上新数字重做一遍。这很费时，而且数字来自好几个系统，彼此可能对不上。在这里，智能体负责收集数据，在有成文规则覆盖的地方为每个产品提出状态，填好演示稿模板，并对照团队已确认的决定检查成稿。规则覆盖不了的情况仍由人来判断（某个功能用得少，可能是问题，也可能无关紧要），演示稿也由人向客户汇报，因为客户会拿稿子里的每一项说法来要求公司兑现。

**术语：**
- **TAM（技术客户经理）**：负责客户对产品的技术使用，并向客户汇报 QBR 的人。
- **使用率**：客户买下的功能里，实际在用的比例。
- **账户快照**：把一个客户的归属、续约日期、健康信号、订阅、支持工单和近期活动合并成的一份记录。
- **CRM**：记录客户、联系人和合同的系统，这里是 Salesforce。Gong 是录制并转写销售和支持通话的工具。
- **ROI（投资回报）**：客户从产品获得的价值，与其为此付出的成本相比。
- **评分标准（rubric）**：一组对演示稿逐项打分的问题，例如每项说法能否对照客户自己的记录核实。

## 用智能体搭建

**形态：** `skill`。一位客户经理一次准备一个客户的演示稿，并在对话中回答智能体的提问，所以一个包含步骤、规则和模板指令的 skill 就够了。

**需要：** 对 CRM、通话录音或转写、产品采用度数据和支持历史的读取权限，通过连接器或导出的文件提供；放在 skill 旁边参考文件里的使用率规则和产品对照表；一份 Google Slides 模板，以及能写入它的连接器或脚本；保存已确认输入的 Drive 文件夹或文件；如果有的话，再加一份评分标准作为第二个参考文件。智能体不需要任何把演示稿发给别人的途径。

| 步骤 | 搭建方式 |
|---|---|
| 账户快照（CRM、通话、采用度、续约、支持） | 由脚本或连接器为该账户写出一份快照文件。skill 只读这份文件，不逐个去查各系统。 |
| 每个产品：评估使用率 | skill 按参考文件中的规则评估。产品很多时，可以让子智能体各负责一个产品。 |
| 规则覆盖：提出状态 \| 需判断：🛑 review | skill 列出每个判断项及其证据，请 TAM 确认或修改；规则覆盖的状态也列出，供快速过目。 |
| 保存已确认的输入 | skill 把产品、状态、原因和确认人写入 Drive 中的文件，下次会话可以从这里接着做。 |
| ROI 计算 | skill 旁边的脚本根据快照和已确认的输入计算。 |
| 填入 Slides 模板 → (修正 ⟲ 对照已确认输入做 QA) | skill 按逐页指令写出演示稿。另一个没有参与写稿的子智能体，对照已确认的输入和评分标准回读，列出占位符、数字不一致和状态错误。明确的错误直接修正并复查，其余交给 TAM。 |
| 🛑 review (TAM 修改并汇报) | 见检查点。 |

**检查点：** `review`：skill 在每个判断项处停下，TAM 答复之前不生成演示稿；回读之后再停一次，把演示稿连同未决事项一并呈上。智能体没有分享或发送演示稿的工具，所以由 TAM 在 Slides 里修改并亲自汇报。

**与来源相比：** 来源和公开实例出自 2026-08 至 2026-10，都是搭建者团队自己的第一手叙述。Rippling 用自家的数据平台和智能体插件搭建，Handshake 则搭了一个对照评分标准打分的智能体；本搭建用快照文件和连接器取代数据平台，并不复现任何一家公司的工具。来源报告了准备时间；本条目不对这套搭建方式作此类声称。像 Handshake 那样写出 54 项评分标准是否值得，由团队自己判断。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 团队在模型接触数据之前先准备好数据：把 Salesforce、Gong 通话、采用度指标、规划文档和支持历史合并为一份账户快照（归属、续约、健康信号、订阅、工单、活动） [[1]](#sources)。
2. AI 评估产品使用率；已批准的规则能覆盖的情况，AI 提出状态，证据不全或依赖上下文的情况，则标记出来 [[1]](#sources)。
3. 🛑 **审阅**：技术客户经理（TAM）确认被标记的评估（例如某功能采用率低是否要紧），机械性的步骤则异步运行 [[1]](#sources)。
4. 工作流把已确认的输入保存为结构化记录（产品、状态、原因、confirmed_by_team）写入 Drive 文档，这样次日可以从 ROI 和演示稿生成继续工作 [[1]](#sources)。
5. 智能体运行不同的技能，分别收集上下文、分析通话、评估使用率和计算 ROI；演示稿构建器按结构化的逐页指令写入固定的 Google Slides 模板 [[1]](#sources)。Handshake 的版本会对照与客户经理共同制定的 54 项评分标准给演示稿打分 [[2]](#sources)。
6. QA 技能对照已确认的输入回读演示稿（占位符、数字不一致、状态错误）；明确的错误直接修正并复查，需判断的修改则交回团队 [[1]](#sources)。
7. 🛑 **审阅**：客户经理审阅完成的演示稿，并向客户汇报 [[1]](#sources)[[2]](#sources)。

**产出：** 每个账户一份原生 Slides 格式的 QBR 演示稿，基于已确认的输入生成，TAM 可直接汇报；已确认的输入保存在 Drive 中。
**失败模式 → 防护：** 数字过时或冲突、跨多天会话丢失决定、内容放错幻灯片 → 单一快照数据集、结构化的保存记录、固定模板加 QA 回读。推荐客户已拥有的模块 → 把已拥有产品的数据送入叙述环节 [2]。
**与相近工作流的区别：** 最接近的是 AWF-0049 续约窗口风险简报（其中提到了 QBR 草稿）。AWF-0049 交付的是内部风险简报和挽留方案，由 CSM 验证风险标记并批准外联；本工作流交付的是面向客户的演示稿，运行中途对各产品的判断项设有检查点，终审前还有自动 QA 循环。AWF-0174 是自主的续约流程（抽检），交付物和自主程度都不同。

## 公开实例

覆盖度（截至 2026-11-13）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [Fourth collection pass](../../../../../research/2026-11-fourth-pass.md)。

- [Rippling, Taking QBRs from hours to minutes](https://www.rippling.com/blog/taking-qbrs-from-hours-to-minutes) (2026-10-30)。Rippling TAM 的 QBR 工作流，判断项由团队确认并带演示稿 QA，在 15 个账户上测试。"Across 15 test accounts, prep time fell from two to three hours per review to under 20 minutes.". *第一手：是；可信度：高。*
- [Handshake, The QBR agent that gave sellers a week back every quarter](https://joinhandshake.com/blog/enterprise/building-agents-that-require-judgment/) (2026-08-25)。Handshake 客户经理的 QBR 智能体，对照 54 项评分标准逐步爬坡优化。"our agent reduced preparation time from 45 minutes per account to around 10". *第一手：是；可信度：高。*
