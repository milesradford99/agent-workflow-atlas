# 有人监督的语音代理

**工具变体：** `sanas` · `cloneops` · `heyrevia` · `livekit`

## 背景

有些服务线至今还跑在电话上：快递迟了、预约要改、账单有争议。语音代理现在可以接这些电话，做自然对话、查信息、执行操作，多数来电者根本不会察觉对面不是人。风险在于那种开头顺利、后来走偏的电话——来电者开始发火、三次要求转人工、或者说到剧本没有覆盖的事——而事后的审计救不了电话那头的当下。所以这套安排是控制室而不是队列：一位主管坐在一块实时通话看板前，每通电话都带着一个"多需要人"的实时评分，主管可以静默收听、私下给智能体耳语提示、接管通话、处理完难点再交还，来电者不必重讲一遍。智能体和人的每个动作都写进 CRM 记录，已结束的通话事后审计，而对例行外呼跟进来说，审计就是它得到的唯一人工投入。主管不是"智能体坏了"的兜底：他们要介入的比例，恰恰是衡量智能体自身升级规则哪里写错的指标。

**术语：**
- **语音代理（voice agent）**：用语音识别、语言模型和语音合成完成口头对话的软件。
- **实时转写（live transcript）**：通话进行中的文字流，主管读它而不必句句都听。
- **耳语提示（whisper）**：给智能体的私下指导，来电者听不到。
- **插话接管（barge-in / take over）**：主管以可听见的方式加入通话并与来电者对话。
- **交还（hand back）**：通话中途把控制权交回智能体，来电者无需重复。
- **热转接（warm transfer）**：带着上下文把电话转给人工，而不是盲转。
- **通话后审计（post-call audit）**：通话结束后复核转写与操作。
- **介入率（intervention rate）**：主管不得不介入通话的频率；它是设计信号，不是考核目标。

## 用智能体搭建

**形态：** `platform`。通话本身是实时音频——识别、轮次交替、打断以及可听见的接管，都需要通用智能体没有的语音模型和电话链路；而推理、规则、通话后审计和 CRM 写入可以是通用智能体的活，本搭建方式写的正是这一部分。

**需要：** 一个具备亚秒级轮次交替、插话和主管控制台的语音平台，控制台要能耳语、接管、交还——`variants` 里列的就是这类产品；一份通话策略文档，供智能体遵循，升级触发条件要逐条写明；看板可以排序的实时评分流；工具调用背后的 CRM、订单或计费系统，且在做任何账户操作之前完成来电者身份验证；一份按通话保存的记录，含转写、每个动作以及是谁做的。搭建里不能允许智能体许下工具兑现不了的承诺，也不能允许主管在不告知来电者的情况下接管通话。

| 步骤 | 搭建方式 |
|---|---|
| 呼入或预约的通话 | 平台电话链路负责接听或外呼；智能体的指令与升级触发按活动加载，所以预约跟进跑的策略比投诉热线窄。 |
| 语音代理对话 + 实时转写 | 平台的语音环路，智能体的每一轮由模型生成，转写随生成实时推到控制台。 |
| 通话评分和告警为通话排序 | 一个打分的任务，把转写信号——情绪、要求转人工、命中关键词、沉默、已用时长——合成为每通电话一个排序值，让主管的注意力落在列表顶部而不是全部。 |
| 🛑 handoff（主管监听、耳语、接管、交还） | 控制台上的控件是平台权限，按主管与线路授权；接管要向来电者宣告并留痕，交还时把人工已确认的状态交给智能体。 |
| 工具操作 + CRM 记录 | CRM 与业务系统的 MCP 连接器，每次写入都带通话 id 以及是人工还是智能体授权的。 |
| 🛑 sample（通话后审计） | 一个由智能体跑的审计，覆盖固定比例的已结束通话加上所有被主管介入过的通话，用同一份标准给转写打分，并把发现写回去用于修改策略。 |

**检查点：** `handoff`：检查点就是主管的控件——智能体不能把通话转给自己，控制台是唯一能发起接管的地方，每次介入都记录是谁、何时做的，所以通话不可能被"悄悄加入"。同时要给每位主管的通话数设上限，因为这套模式的失效方式是注意力不够，而不是工具不够。`sample`：通话后审计是另一道独立的检查，有自己的标准，覆盖固定比例以及全部被介入的通话；它的发现用来改升级触发条件，而不是改那份转写。

**与来源相比：** 来源出自 2025-02 到 2026-10，另有两份未注明日期的厂商页面，本月均已打开。此后有这些变化：实时监督从"一个功能"被写成了"一套运营模式"。2026 年的一份从业指南把[监看席位描述为人员与流程决定——谁坐在这里、什么把注意力拉到某通电话、插话如何接入既有升级路径——并主张高介入率说明智能体自身的升级规则在失效，而不是应该扩大监看团队](https://www.dilr.ai/blog/voice-ai-live-monitoring-supervisor-dashboard-enterprise)。它也写明了上面强制执行的那条：接管应当被宣告并留痕，而不是悄悄进行。`variants` 里的平台仍是各自独立的产品，控件模型不同，采用之前要核对的正是控制台的权限设计。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 语音代理接听呼入电话或发起预约的外呼，并实时转写到主管看板 [[2]](#sources)[[3]](#sources)。
2. 每通电话都有一个持续更新的分数，表示它多需要真人介入；情况更糟的通话排到前面；出现不满情绪、要求转人工、命中关键词或通话时间过长时触发告警 [[2]](#sources)[[4]](#sources)。
3. 🛑 **接手**：一名主管同时关注多路通话（Sanas：最多四路；HeyRevia 演示：10-15 路），可以收听、私下指导 AI、在通话中途接管并交还控制权，来电者无需重新开始 [[1]](#sources)[[5]](#sources)。
4. 代理完成工具操作，并把每一个 AI 和人的操作记入审计记录和 CRM [[1]](#sources)[[3]](#sources)。
5. 🛑 **抽检**：已完成的通话事后审计；对于例行的外呼跟进，审计是唯一的人工投入 [[2]](#sources)。

**产出：** 由代理或实时加入的主管解决的通话，附转写和操作日志。
**失败模式 → 防护：** 主管的注意力有限，告警会被忽略 → 限制每位主管的通话数并调整告警 [1][4]。声音突然变化会让来电者困惑 → 采用「平滑」接管，由 AI 先介绍一位同事 [4]。
**与相近工作流的区别：** 最接近的是 AWF-0021 流程代理：那里敏感案件会转给一个并不在场的人，事后由质检抽样。本工作流中有人实时监看通话，可以在同一通电话里介入再退出；检查点是持续的实时监督，而不是转接队列。
