# 住户报修分诊派单

**工具变体：** `eliseai` · `qed-labs`

## 背景

房东或物业管理公司要为几百套房子维持可居住状态，而故障是按发生的那一刻被报上来的：中午一颗滴水的水龙头，凌晨两点爆掉的水管。得有人接住每一份报告，判断有多严重，把它变成写明工种的工单，再送到技师或外部承包商手上——而且半夜里总有人要决定，住户口中的"紧急"是否值得把值班工程师叫醒。人工做得好，但只在醒着的时候；两类错误的代价都很高：真正的爆水拖到早上会泡坏两户，而每一次误报都消耗值班工程师的一夜和一笔钱。在这里，智能体通过留言或电话接住报告，问出该工种会问的问题，看照片，按房东写好的规则判定紧急程度，开出工单并派发。真正的紧急情况带着足以行动的全部信息交给值班人员，同时告诉住户当下该怎么做。规则——什么算紧急、叫醒谁、可以说什么——仍然属于房东，因为可居住性与安全是法定义务，分诊错了是责任问题，不是服务体验问题。

**术语：**
- **工单（work order）**：一条维修记录：房产、单元、故障、工种、优先级、入户信息。
- **分诊（triage）**：在尝试维修之前，先把报告分出紧急程度和责任归属。
- **降级安抚（de-escalate）**：把看起来像紧急、实际上不是的报告安抚下来，并给出可信的时间预期。
- **值班工程师（duty / on-call engineer）**：非工作时间处理紧急情况的人。
- **可居住性（habitability）**：法律要求房东维持的条件，例如供暖、供水与安全。
- **派发（dispatch）**：把工作交给指定技师或承包商，并授权其上门。
- **一次修复率（first-time fix rate）**：首次上门就完成的工单比例，这正是信息收集完整与否在保护的东西。

## 用智能体搭建

**形态：** `service`。报告全天候到达，没人启动运行；人出现在紧急情况处，以及之后对转写的抽检里。

**需要：** 房东的紧急判定规则，写成可观察的条件——水正在流、室温低于某温度且无供暖、闻到燃气味、完全没有供水、门锁无法锁闭房产——每一类都要有责任人和下一步；单元与租约记录，让智能体能识别房产与入户安排；工单系统与承包商名录，通过 MCP 连接器或平台 API 接入；照片（渠道支持时）；值班表，以及一个要求确认的呼叫通道。智能体不能在没有人工的情况下派出超过设定金额的工单，也不能给出房东未书面批准的维修指导。

| 步骤 | 搭建方式 |
|---|---|
| 住户留言或来电 | 消息渠道的 webhook，或语音平台的通话结束事件，每份报告启动一次运行；语音场景需要 AWF-0175 描述的语音层。 |
| 诊断式分诊（提问、照片、安全风险） | Skill 只问那些会改变紧急程度、入户方式或下一步的问题，按故障类型的固定顺序问，并读取照片；答案以字段记录，不写成散文。 |
| 咨询：回答 | 状态类问题从已开工单回答，不新建工单。 |
| 报修：分类 + 排定优先级的工单 | Skill 写出工单——故障类别、按规则定出的优先级、入户备注、宠物——并注明是哪一条规则定的优先级。 |
| 指派技师 / 派发承包商 | 派发工具按工种与区域从已批准的承包商名录中选择；超过金额阈值时，工具要求一个本次运行无法自行生成的审批编号。 |
| 紧急情况：降级安抚或 🛑 handoff（值班人员） | 真正的紧急情况把决策包呼给值班人员——谁、在哪、什么情况、触发了哪条规则、已告诉住户什么——并等待确认；非紧急的报告得到的是平静的时间预期，而不是一次呼叫。 |
| 跟踪工作 → 收集反馈 | Skill 跟踪工单状态，每次状态变化通知住户；完工后收集反馈，记在该承包商名下。 |

**检查点：** `handoff`：呼叫通道是通向值班工程师的唯一路径，它携带事实，而不是"请回电"。有两件事靠代码而不是靠提示：紧急规则由分类器依据结构化答案套用，所以住户坚持说"很急"也抬不高类别；以及在决策包齐全之前不发呼叫——房产、单元、危险、规则、已给的指导。智能体无法派出超过金额阈值的工单，所以金额较大的紧急活儿仍需人的审批编号。

**与来源相比：** 来源是三份厂商案例，其中一份带 2026 年 4 月至 5 月的数据，三份本月都已打开。它们都没有细说转交环节，所以上面的搭建方式自己规定了决策包和判定规则。此后有这些变化：这个转交环节的设计已经有人公开写出来了。2026 年的一份从业指南给出了[升级配置：点名接收人、一条"合并规则"使同一根立管爆裂引发的十二通电话只产生一次告警，以及两个用来调规则线的指标——误报紧急率与漏报紧急率](https://oncallclerk.com/blog/property-management-maintenance-call-triage)。这正是来源留下的空白，而在搭建里它属于配置加每月复盘，而不是智能体自己的判断。厂商关于"降级了多少紧急情况"的说法仍是厂商说法，本月打开的页面里没有独立测量。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 用结构化的提问和照片对报修请求做分诊，并评估安全风险 [[2]](#sources)。
2. 对状态类咨询直接回答，不生成工单（L1 Property 为 44%） [[2]](#sources)。
3. 创建分类的工单，并对虚假的“紧急情况”降级安抚 [[1]](#sources)。
4. 自动指派或派发承包商，然后跟踪工作的整个生命周期 [[2]](#sources)。
5. 🛑 **接手**：真正的紧急情况和复杂案件转交工作人员 [[1]](#sources)。

**产出：** 已派发并被跟踪的工单，以及向住户的进展通知。
**失败模式 → 防护：** 真正的紧急情况被误分诊 → 安全风险提问和升级路径。来源中对接手环节的设计描述很少。
**与相近工作流的区别：** 与 AWF-0021 同属一个类别，但这里的事务是向技师或承包商做实际派单，而不是账户操作。

- [QED Labs, L1 Property](https://qedlabs.co.uk/case-studies/l1-property) (n.d.)。603 个单元；向 36 家承包商派发 765 项工作。"66% Increase in first-time fix rate"。*第一手：厂商；可信度：低。*
- [EliseAI, Woodward Properties](https://eliseai.com/customer-stories/how-woodward-properties-built-a-24-7-operating-model-with-eliseai) (n.d.; data Apr-May 2026)。约 2,300 套的运营商；紧急情况分诊 + 自动指派；引述了 CEO 和员工的话。"a 50% reduction in after-hours emergency dispatches"。*第一手：厂商；可信度：中。*
