# 人工发送的回复起草

**工具变体：** `salesforce-agentforce-service` · `dynamics-365-copilot-service` · `zendesk-agent-copilot`

## 背景

客户给公司的客服团队写信后，这条消息在服务台里成为一个案件，由客户关怀顾问来回复。回复之前，顾问要阅读往来内容，查客户的历史和订单，找到合适的帮助文章，用品牌的语气写邮件，有时还要做一件附带的小事，比如生成折扣码。每一项都要花时间，还要在几个屏幕之间来回点击。在这里，由智能体负责阅读和准备：总结对话、调取记录、起草回复、执行常规任务。每一条回复仍由顾问阅读、修改并发送，因为回复是以品牌的名义发给客户的，而判断、同理心和例外情况都要由顾问来处理。

**术语：**
- **案件（case）**：一个客户请求，连同它的消息往来，保存在服务台里。
- **顾问（advisor）**：回复案件的客服员工。
- **案件意图（case intent）**：说明客户要什么的标签（退货、配送问题）；处理案件时选定，用于报表。
- **CRM**：保存每位客户已知信息的系统；**ERP** 保存订单和库存。
- **KB（知识库）**：回复必须依据的、经过批准的帮助文章。
- **品牌语气**：每个品牌对客户说话的方式，写成指令。
- **处理时长**：一个案件从打开到关闭所需的时间。

## 用智能体搭建

**形态：** `skill`。一位顾问一次处理一个案件，草稿出现时他就在对话里，所以一个包含步骤和品牌语气指令的 skill 就够了。

**需要：** 通过连接器对案件对话、案件历史、CRM 记录、知识文章和订单数据的读取权限；放在 skill 旁边参考文件里的品牌语气指令和案件意图清单；一个用于常规任务（例如生成促销码）的工具，其限制设在工具里，而不是写在 skill 的文字里。智能体不需要任何向客户发送消息的工具。支付信息和不必要的个人信息，不要放在智能体能读到的范围内。

| 步骤 | 搭建方式 |
|---|---|
| 案件到达 → 总结对话 + 确认意图 | 顾问在该案件上打开 skill。它读取对话，写出简短总结，并说明客户看起来要什么，由顾问来纠正。 |
| 调取案件历史、CRM、KB、订单数据 | 只读的 MCP 连接器。skill 标明草稿里每个事实来自哪条记录。 |
| 以品牌语气起草回复 + 执行常规工具任务 (如优惠码) | skill 依据语气指令和检索到的文章起草。常规任务通过它的连接器执行，结果与草稿并排展示给顾问。 |
| 🛑 review (顾问修改并发送每条回复) | 见检查点。 |
| 结案前核对案件意图 | skill 把选定的意图与对话比较，不一致就指出来。 |
| 使用情况 + 处理时长跟踪 | 用服务台自己的报表。skill 不跟踪自己。 |

**检查点：** `review`：skill 最后展示草稿和它生成的任何代码，然后停下。智能体没有发送邮件或在服务台里回复的工具，所以由顾问修改草稿并在服务台里发送。

**与来源相比：** 来源 1 是 2025-02 的期刊文章，来源 2 是 2026-09 的厂商客户案例。期刊页面在 2026-11 拒绝了页面读取工具，所以来源 1 没有重新打开核对。来源 2 描述的是厂商内置在其服务台里、以其数据平台为依据的助手；本搭建把步骤从该产品里拿出来，通过连接器交给通用智能体运行，没有顾问输入时在服务台里显示建议的面板。来源报告了时间和生产率的变化；本条目不对这套搭建方式作此类声称。下面的失败模式记录了经验最丰富的客服人员采纳建议时质量会有所下降，所以让顾问可以不理会草稿，是设计的一部分。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 每个案件到达时，助手先总结目前的对话，并在开始处理前确认消费者要什么 [[2]](#sources)。
2. 服务台让助手以案件历史、CRM 记录和知识文章为依据，再加上来自 ERP 的订单数据，使草稿反映当前的促销和订单状态 [[2]](#sources)。
3. 助手按品牌自己的语气要求和该品牌的知识起草回复初稿。在所研究的部署中，建议会实时出现，由客服人员决定是否采用 [[1]](#sources)[[2]](#sources)。
4. 助手根据一条提示词执行案件内的常规任务，例如生成促销码，这可替代约 15 个屏幕的手工操作 [[2]](#sources)。
5. 🛑 **审阅**：人工顾问审阅草稿、修改并发送。没有人发送，任何回复都不会到达客户 [[2]](#sources)。
6. 结案前，助手检查所选的案件意图与对话是否一致，使整个团队的意图保持统一 [[2]](#sources)。
7. 团队一次只上线一个品牌和市场，了解哪些意图有效，再逐步扩大 [[2]](#sources)。同时跟踪处理时长、每小时解决数和质量，并按客服人员的资历细分 [[1]](#sources)。

**产出：** 由人工客服发送的回复，以及写入服务台的案件摘要和经核对的意图标签。它们为 KB 缺口和质检工作提供输入。
**失败模式 → 防护：** 经验最丰富的客服人员采纳建议时质量会有所下降 → 按客服人员的技能水平衡量，并允许专家忽略建议 [[1]](#sources)。草稿编造订单号或日期等细节 → 让草稿以实时的 CRM/订单数据为依据，并保留人工发送这一步 [[2]](#sources)。
**与相近工作流的区别：** AWF-0021 流程智能体：在那里智能体直接回复客户并自主行动，辅以抽检式质检。本工作流中每条回复都由人发送（辅助级自主，逐条回复审阅）。产出是由客服人员发送的回复，而不是自主完成的解决。

## 公开实例

覆盖度（截至 2026-11-06）：**薄弱**：只有匿名、与厂商相关或由记者转述的说法。收集与复核见 [Second collection pass](../../../../../research/2026-11-second-pass.md)。

- [Brynjolfsson, Li, Raymond, Generative AI at Work (QJE)](https://academic.oup.com/qje/article/140/2/889/7990658) (2025-02-04)。在一家财富 500 强软件公司，向 5,172 名客服人员分批推出 AI 助手。"increases worker productivity, as measured by issues resolved per hour, by 15% on average"。*第一手：研究（对一家未具名公司的实地研究）；可信度：高。*
- [Salesforce, L'Oréal customer story](https://www.salesforce.com/eu/customer-stories/loreal/agentic-service-advisor-assistance/) (2026-09-11)。顾问审阅并发送 AI 草稿；先在加拿大对一个品牌试点，现已扩展到 25 个品牌。"cutting the time to resolve a case from about 7 minutes to about 2.5 minutes"。*第一手：厂商；可信度：中。*
