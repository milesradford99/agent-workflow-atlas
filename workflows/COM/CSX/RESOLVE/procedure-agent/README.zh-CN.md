# 流程型客服智能体

## 背景

电商或软件公司的客服在聊天窗口里接客户的问题：我的订单到哪了、能不能改地址、卡被重复扣款了、这个怎么退。其中大部分可以照帮助中心回答；一部分需要在系统里做动作——退款、取消、改地址——而且要先证明来的人确实是这个账户的主人。客服负责人把这些答案和规则写成处理流程，现在智能体可以在对话里照着走：咨询按文章回答，交易则先做身份验证、调用系统、再告诉客户结果。有三件事把人也留在环路里。动钱的动作必须有上限，而上限写在提示词里只是建议，所以限额落在工具本身。流程覆盖不到的情况——客户威胁拒付、家中有丧事、提到法律——带着摘要交给真人。还有，一段看起来"已解决"的对话仍可能是错的，所以质检人员给对话打分，并复读被标记的和被抽中的。来源所说的解决率，是衡量整套安排的指标，而每家厂商对它的定义都不一样。

**术语：**
- **知识库（KB）**：智能体据以回答的帮助中心文章。
- **处理流程（procedure）**：带条件和限额的成文流程，例如"包裹延误超过十天且金额在上限之内的，可退款"。
- **分流（route）**：先判断这是哪一类消息，再决定怎么答。
- **身份验证（authenticate）**：在动账户之前证明来者拥有该账户。
- **工具调用（tool call）**：智能体在外部系统里执行的动作，例如发起退款。
- **转人工（handoff）**：把对话交给真人，并附摘要。
- **质检抽检（QA sampling）**：给每段对话打分，并让人复读其中一部分。
- **转接率与解决率（deflection vs resolution）**：客户自己放弃的对话，与问题真正被解决的对话；只有后者算解决。

## 用智能体搭建

**形态：** `service`。客户任何时间都在写，智能体在没人启动的情况下作答；人只出现在例外、转接和抽检处。

**需要：** 知识库和处理流程以文件形式供本次运行加载，一个意图一个流程，条件与限额都写成数字；账户类工具——退款、取消、改地址——通过 MCP 连接器暴露，且上限在工具内部执行；一个身份验证步骤，其结果是账户工具的前置条件；对话之外的状态存储，记住这次案件已确认了什么；转人工队列与抽检复核队列。智能体不能有任何可以越过的上限工具，也不能有聊天之外的触达客户的通道。

| 步骤 | 搭建方式 |
|---|---|
| 加载知识库 + 处理流程 | Skill 的第一条指令：读分流表，只加载本意图对应的流程，这样生效的限额就是为这类案件写下的那一套。 |
| 每条消息：分流 | 调用方程序里的小分类器从固定意图表中选择；表里没有的进转人工，而不是自由发挥。 |
| 咨询：回答 | 在知识库上检索，回复中引用文章；无法落地的提问进入缺口日志，而不是凭常识回答。 |
| 交易：身份验证 | 身份验证工具返回会话令牌，账户工具要求携带它；没有令牌时所有账户调用一律失败。 |
| 🛑 action（限额写在代码里） | 退款与取消工具自己执行上限，超过一律拒绝；智能体可以选择退不退，永远不能决定上限多高。 |
| 调用工具 | 订单、计费与 CRM 系统的 MCP 连接器，各自返回结构化结果，写进回复和日志。 |
| 敏感问题：🛑 handoff | 转接工具把转写、身份状态、已尝试的动作以及为什么停下，打包进对应团队的队列。 |
| 🛑 sample（质检） | 每段对话都打分，固定比例加上全部被标记的进入复核；分数用来改流程，不用来教训智能体。 |
| 知识库缺口聚类 → 新文章 | 定期任务每周把未答上的问题聚类，产出文章草稿交给内容团队采纳。 |

**检查点：** `action`：上限是工具的属性，提示词里的任何写法都抬不高它；身份验证失败也没有通往账户动作的路径。`handoff`：通向真人的唯一通道是转接工具，它结束本次运行并留下决策包，而不是一句"转人工"了事。`sample`：复核比例由项目设定而非智能体决定，而流程的修改依据就是那些打了分的对话。

**与来源相比：** 来源出自 2023 年到 2026-10：两份第一手工程记录、一份厂商案例、一个从业者论坛帖，以及一篇 2026 年的客户故事。2026 年的解决率基准综述和 Aircall 的故事本月已打开；较早的论坛帖没有重新打开。此后有这些变化：那个头条数字怎么算。2026 年的综述给出的平台均值从 52% 到 76%，并明确指出[每个公开数字都是按发布者自己写的定义自报的](https://www.lorikeetcx.ai/articles/resolution-rate-ai-customer-support-benchmarks-2026)：有的厂商把走完流程或转人工也算解决，有的只算没有升级的对话。这让本条目里的"指标提示"更重要而不是更轻：搭建时应当先按意图类型定死"解决"的定义再测量，否则数字动的原因是厂商换了口径，而不是服务变了。作为 2026 年近期实践记下的"升级前固定尝试次数"，在更新的材料里没有变化。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 把口口相传的经验改写成带有明确条件和限额的自然语言流程。Decagon 的 AOP 会把这些流程编译成工作流，退款和身份核验在代码中执行 [[21]](#sources)。Intercom Fin Procedures 和 Sierra journeys 是同类的变体。
2. 按意图对每条消息分流。
3. 任何账户操作之前先做身份验证。
4. 🛑 **操作**：限额由代码强制执行，而不是写在提示词里。
5. 🛑 **接手**：转人工时附上对话摘要。
6. 🛑 **抽检**：质检对每段对话打分；人工复核被标记的和随机抽取的对话。
7. 把每周的知识库缺口聚类转成新文章。

**指标提示：** 各厂商对解决率的定义并不一致。据报道，Fin 官网声称平均解决率为 76%，而独立测试和小企业测试集中在 38–53% [[22]](#sources)。Decagon 客户超过 70% 的数字来自一份分析师文章 [[21]](#sources)。这些都属于厂商材料（证据 B）。

**近期实践（2026）：**
- 转人工：先设定固定的尝试次数上限（TripCity：三次）再升级，并把 AI 写的摘要交给真人坐席（Aircall，2026-10-29）。[[23]](#sources)

## 公开实例

覆盖度（截至 2026-11-06）：**充分**：有详细的第一手实例，与流程的大部分环节一致。来自 [Where are the real runs?](../../../../../research/2026-11-real-runs.md)；每个数字都已对照原页面复核。更多实例见 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [Gupta et al., Nubank, arXiv 2606.08867](https://arxiv.org/abs/2606.08867) (2026-06)。五个生产部署：标准流程、身份验证后才能调用的工具、升级转交、人工标注的评估。"37 percentage-point improvement in AI transactional Net Promoter Score"。*第一手：是；可信度：高。*
- [Jackson Gold, Pinecone](https://www.pinecone.io/blog/support-agent-nexus/) (2026-09-01)。工单分流 → 账户查询 → 调查 → 退款和限额问题的升级简报。"resolves 55.1% of the tickets"；"27 of the 49"。*第一手：是（早期，样本小）；可信度：高。*
- [Decagon, Tremendous case study](https://decagon.ai/case-studies/tremendous) (undated)。双因素所有权核验 → 重发、取消或换货 → 带上下文升级。"92% CSAT… compared with 86% for its BPO team"。*第一手：厂商；可信度：中。*
- [Intercom Community, Fin resolution thread](https://community.intercom.com/questions/3622) (2023–2026)。从业者报告解决率以及他们如何维护知识库。"around 55-60% from the past week, in around 3000 conversations"。*第一手：是（论坛）；可信度：低。*
- [Aircall, How TripCity cut live call volume in half with AI Voice Agent "Miles"](https://aircall.io/customer-stories/tripcity/) (2026-10-29)。语音渠道的流程型智能体，覆盖三条电话线路；三次解决尝试后升级给真人坐席。"87% of calls resolved without escalation to live agents"。*第一手：厂商；可信度：中。*
