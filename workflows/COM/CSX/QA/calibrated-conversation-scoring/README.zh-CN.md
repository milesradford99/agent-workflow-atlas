# 校准式对话质检评分

**工具变体：** `in-house-llm-classifiers` · `instacart-lace` · `amazon-bedrock`

## 背景

客服团队检查工作质量的办法，是让质检专家阅读一部分已关闭的对话，并对照检查表打分。这样一来，团队只能读到很小的一部分，大多数对话，包括由 AI 智能体处理的那些，根本没人看，错误的政策答复、被送错队列的案件这类问题就一直没人发现。在这里，智能体对每段对话按几条是非题打分，保留它的理由，并把失败的案例按根本原因归组。人保留两项工作。质检专家自己给一批抽样对话打分，并与智能体的分数比较；出现分歧时以专家为准，并重新修改标准的措辞。客服运营负责人决定修什么，因为修复涉及路由、知识库或对客服人员的辅导，而且不能仅凭一个分数去处分某个人。

**术语：**
- **二元标准（criterion）**：关于一段对话的一个是非题，例如“是否理解了问题？”
- **分类器（classifier）**：让模型针对一段对话回答一条标准的提示词。
- **理由（rationale）**：模型对其答案写下的理由，和分数存在一起。
- **校准（calibration）**：把模型的分数与专家对同一批对话的分数比较，并调整到两者一致。
- **根因（root cause）**：多段对话失败背后的共同原因，例如知识库里的某一篇文章有误。
- **路由**：决定案件由哪个团队或哪位客服接手的规则。
- **知识库**：客服和客户查找答案所依据的文章。

## 用智能体搭建

**形态：** `service`。评分按计划对每一段新对话运行，现场没有人；人只看到抽检样本和聚类后的发现。

**需要：** 通过连接器或导出文件，读取所有渠道的对话记录，人工处理和 AI 处理的都包括；作为参考文件的标准，措辞要精确；一个状态存储，保存分数、理由和专家对抽样的打分；一个审阅队列或表格，用来放抽检样本和聚类报告。智能体只读取记录并写入分数；它对客服系统没有任何写入功能，记录里的个人信息在评分前按你们的隐私规定脱敏。

| 步骤 | 搭建方式 |
|---|---|
| 拉取对话（人工 + AI 智能体） | 云端定时任务，或由自己的调度器运行 `claude -p` 或 Agent SDK 程序，取回新的对话记录，只保留每段对话中客户一侧的内容。 |
| 每个对话：分项分类器 + 理由 | 每条标准一个子智能体，或在脚本里每条标准一次调用，依据参考文件中该标准的措辞回答是或否，并给出理由。 |
| 合成通过/未通过分数 | 一个脚本：只有每项标准都通过，这段对话才算通过。存储的记录里各项标准保持分开。 |
| (评分 ⟲ 🛑 sample) | 见检查点。 |
| 按根因聚类失败案例 | skill 根据理由把未通过的对话归组，写出附有示例对话的聚类报告。 |
| 🛑 review | 见检查点。 |
| 修复路由/知识/辅导 | 由路由、知识库和辅导的负责人完成。智能体只提出建议，没有修改这些的工具。 |

**检查点：** `sample`：固定比例的已评分对话被复制给质检专家，专家在看不到智能体分数的情况下打分；对比结果写入状态存储，出现分歧就修改参考文件里该标准的措辞，由负责该文件的人动手。标准或模型每次变更后，都要重做这项对比。`review`：聚类报告进入客服运营负责人的队列；智能体没有修改路由、知识库或客服记录的工具，所以修复和辅导由人来做。

**与来源相比：** 来源和公开实例出自 2025-06 至 2026-11。它们来自三家公司自己的叙述（Oura、Instacart，以及一家厂商的测试）和两篇厂商博客。它们用的是各自的分类器和工具；本搭建用通用部件复现其结构（二元标准、理由、专家校准、聚类），除智能体自己使用的模型外不运行别的模型。厂商的叙述报告了一致率和改进幅度；本条目不对这套搭建方式作此类声称。来源中每条标准用不同模型的做法，这里并不要求。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 客服团队定义一小组二元标准，只从客户一侧的对话记录来判断，忽略内部备注：是否理解了问题、是否有不满情绪、是否已解决或已妥善升级、方案给出后的情绪 [[1]](#sources)。二元标准比 1–10 分的量表更可靠 [[2]](#sources)。
2. 模型给每段对话评分，不论来自哪个渠道，也不论由人工还是 AI 智能体处理。只有每项标准都通过，这段对话才算通过 [[1]](#sources)。把模型给出的理由和每个分数存在一起 [[2]](#sources)。
3. 🛑 **抽检**：质检专家按同样的标准给选定的一批对话打分，并与模型的分数比较。出现分歧时以人工为准：调整标准的措辞或重新组织标准，然后重复，直到两者一致。每次更新都要重新做这项检查 [[1]](#sources)[[2]](#sources)。
4. 系统把各项分数合成一个指标，并对未通过的对话做聚类，找出新出现的问题，例如 AI 智能体给出错误的政策指引，或案件被错误路由 [[1]](#sources)。
5. 🛑 **审阅**：客服运营负责人拿到聚类后的发现，修复路由或知识库，或对客服人员做辅导。不要仅凭原始分数处分个人 [[1]](#sources)。

**产出：** 带理由的逐段对话评分、汇总的体验指标，以及一份按重要性排序的根因清单，交给运营、知识库和辅导的负责人。
**失败模式 → 防护：** 评判模型偏离人工判断，或混淆相近的标准，一个标准出问题却让多个标准一起失败 → 定期对照专家评分重新校准，并保留理由以便找出主要问题 [[1]](#sources)[[2]](#sources)。综合分数掩盖了变化的来源 → 在报告中把各项标准分开列出。

**近期实践（2026）：**
- 评分 ⟲ 抽检循环：在修改提示词之前，先追查每一处人与 AI 的分歧原因（检索到错误文档、标准措辞含糊、推理有误）；每次政策或模型变更后重新抽样（Revelir，2026-11-03）。[[4]](#sources)
- Booth 测试的发现：AI 对未兑现的承诺更严格，而人工在上下文存在于工单之外时更严格；要对完整的对话线程评分，因为工单在审计日期之后可能还会变化。

**与相近工作流的区别：** AWF-0028 锚点校准评分器（Anchor-calibrated grader）给学生作业评分，由教师放行。本工作流的输入是每一段客服对话，产出是运营层面的根因修复，把关方式是抽样审计，而不是教师按批审阅。AWF-0021 流程智能体（Procedure agent）负责解决工单；本工作流负责审计工单。

## 公开实例

覆盖度（截至 2026-11-06）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [New workflows for empty categories](../../../../../research/2026-11-new-workflows.md)。更多实例见 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [Oura, How Oura Uses AI to Measure Customer Experience](https://ouraring.com/blog/how-oura-uses-ai-to-measure-customer-experience/) (2026-08-25)。四个分类器给几乎每次会员互动打分；对照质检专家做了校准；发现推动了路由和政策修复。"repeated troubleshooting has dropped from 40 percent to around 20 percent"。*第一手：是；可信度：高。*
- [Instacart, LACE framework](https://company.instacart.com/tech-innovation/turbocharging-customer-support-chatbot-development-with-llm-based-automated-evaluation) (2025-06-11)。覆盖五个维度的二元标准；人工与 LACE 的结果反复比对，直到一致。"five key dimensions"。*第一手：是；可信度：中。*
- [Jen Spencer / Booth, We Scored Every Support Ticket. Here's What the Audit Missed](https://hirebooth.com/blog/we-scored-support-ticket-heres-what-the-audit-missed) (2026-11-12)。在 20 张工单上，用质检分析师自己的评分表，对比 AI 评分与这位受过培训的分析师的审计。"The automated scoring agreed with the human on 96% of individual checks (192 of 200)."。*第一手：厂商；可信度：中。*
