# 模拟对话发布闸门

**工具变体：** `snowglobe` · `intercom-fin-evals` · `claude-code`

## 背景

现在许多公司让 AI 智能体回答客户的支持问题。对这个智能体做的每一次改动（新的指令提示词、它所依据的某篇帮助文章被改了、换了底层模型），都可能在一个方面变好，在另一个方面变差，而过去要知道结果，只能先发布，再观察真实客户的反应。在这里，团队先测试每一次改动。由智能体扮演双方：另一个模型扮演客户，按照某个场景（比如配送延误）说话，客服智能体则使用假的工具来回答，所以不会碰到任何真实的订单或账户。然后由一个评判模型对每段对话标出通过或失败，并拿新版本与当前使用的版本比较。失败案例仍由人来读，因为只有人知道一个错误答案要付出什么代价，发布则由指定的负责人签字。智能体不能批准自己的改动，模拟出来的客户也不是真实的客户。

**术语：**
- **现版本（incumbent）**：目前线上运行的客服智能体版本，任何改动至少要做到不比它差。
- **场景和人设（scenario、persona）**：一种情形（配送延误、超出政策的退款）与一类客户（不耐烦、用另一种语言写）组合起来，构成一段测试对话。
- **模拟器（simulator）**：扮演客户的模型。
- **模拟工具（mocked tools）**：在智能体本该查订单或改账户的地方，返回编造结果的替身。
- **LLM 评判和评分标准（rubric）**：由模型对照负责团队写好的一组是非题，给一段对话打分。
- **回归（regression）**：原来能用、改动之后坏掉的东西。
- **A/B 测试**：把新版本给一部分真实客户，旧版本给其余客户，比较结果。
- **知识库（KB）**：智能体回答问题所依据的帮助文章。

## 用智能体搭建

**形态：** `project`。skill 可以跑这些步骤，但有两件事必须每次都成立：模拟运行绝不能碰到生产系统，评判者不能看到这项改动是怎么做的。这需要钩子或权限规则、给评判者用的自定义子智能体，以及并行跑对话的工作者。

**需要：** 把客服智能体的定义（提示词、知识库、模型设置）作为文件放在代码仓库里，这样候选版本和现版本都能运行；一批去除了个人信息的真实对话，分成用于配置模拟器的一组和用于检验它的一组；由负责团队写的场景和人设；评分标准；客服智能体所调用的每个工具的模拟版本；存放对话记录和评判结果的地方。不要给测试用的智能体任何生产系统的凭据。

| 步骤 | 搭建方式 |
|---|---|
| 候选变更（提示词、知识库、模型）+ 假设 | 工程师把变更及其成功标准写在 skill 首先读取的文件里。 |
| 对照真实对话检验模拟器 | skill 在真实对话的测试集上运行模拟器，检查它对已上线版本的排序是否与生产一致；不一致就停下。 |
| 每个场景 × 人设：模拟客户对话，工具已模拟 | 用动态工作流，或每段对话一个子智能体，让每个场景和人设分别对候选版本和现版本运行。`PreToolUse` 钩子拒绝任何不是模拟工具的调用。 |
| LLM 评判相对现版本通过/失败 | 一个自定义的只读子智能体，只看到对话记录和评分标准，给每段对话打分，并比较候选版本与现版本。 |
| (修订代理 ⟲ ...) | 主对话修改候选版本的文件并重新运行，直到通过率达到退出标准。 |
| 🛑 review (失败的对话记录) | 见检查点。 |
| 🛑 sign-off (发布负责人/客户质检) | 见检查点。 |
| 线上 A/B → 上线 | 线上流量的切分由人在客服平台上完成。 |

**检查点：** `review`：skill 在循环结束后停下，列出失败的对话记录，并对照预期与实际表现；工程师读完之后才进行下一轮。`sign-off`：智能体没有修改线上客服智能体或其流量切分的工具，钩子也拒绝生产工具；发布负责人或客户质检团队在测试环境里试用候选版本，批准后由他们自己完成发布。

**与来源相比：** 来源和公开实例出自 2026-06 至 2026-11，另有两个页面未注明日期。来源 1（DoorDash）在 2026-11 拒绝了页面读取工具，所以其中的数字没有重新打开核对。来源 2 至 5 描述的团队，有的自建了模拟器（Nubank、DoorDash），有的用了厂商的（Snowglobe、Telonic 的测试集）；本搭建假定你用提示词和模拟工具自己写模拟器。来源 3（Delight.ai）描述的是用 Claude Code 构建这类工具，与本设计最接近。Nubank 的盲审人员仍能把大多数模拟对话与真实对话区分开，所以检验模拟器的真正标准是它能否像生产那样给已上线版本排序，这里通过并不能取代线上 A/B 测试。来源报告了发布周期和指标的变化；本条目不对这套搭建方式作此类声称。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 团队说明待测的变更（提示词、知识库、模型）和预先约定的成功标准，例如减少不必要的转人工 [[2]](#sources)。
2. 团队在信任模拟器之前先检验它：把真实对话分成开发集（用于配置模拟器）和测试集，并确认模拟分数对已上线版本的排序与生产环境一致 [[2]](#sources)。DoorDash 比较了 302 条模拟对话和 175 条生产对话，升级率相近 [[1]](#sources)。
3. 模拟器模型根据场景和人设生成多轮对话（配送延误、政策边缘情形、语言切换）；模拟工具输出，不触及任何生产后端或客户记录 [[1]](#sources)[[2]](#sources)[[4]](#sources)。
4. 评判模型用负责团队定义的二元通过/失败评分标准给每条对话打分；它比较候选版本与现版本，团队反复修改直到通过率达到退出标准 [[1]](#sources)[[2]](#sources)。
5. 🛑 **审阅**：工程师阅读失败的对话记录和预期与实际的执行轨迹，找出修复办法 [[3]](#sources)。
6. 🛑 **签发**：客户的质检团队（Delight.ai）或业务负责人（Telonic：前台经理）在测试环境试用后批准发布 [[3]](#sources)[[4]](#sources)。
7. 只有明显胜出者才进入线上 A/B 测试，比较自助解决率和满意度，然后上线 [[2]](#sources)。

**产出：** 针对一次代理变更的放行/不放行决定，并保存模拟对话记录和评判结果，用于回归跟踪。
**失败模式 → 防护：** 模拟客户的行为与真实客户不同 → 先用已上线版本验证模拟器；Nubank 的盲审人员仍能识别出大多数模拟对话，所以排序一致性才是关键检验 [2][5]。评判漂移 → 固定的回归套件加针对具体功能的评分标准 [1]。
**与相近工作流的区别：** 最接近的是 AWF-0047 校准式对话评分：那是事后对线上对话评分并抽样；本工作流在任何客户看到之前就测试变更，以发布签字和 A/B 测试收尾。交付物（发布决定与质检发现）和检查点（上线前签字与持续抽样）都不同。

## 公开实例

覆盖度（截至 2026-11-13）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [DoorDash, one-click simulation and evaluation platform](https://careersatdoordash.com/blog/doordashs-one-click-simulation-and-evaluation-platform-for-support-chatbots/) (2026-06-01)。模拟的订单状态对话与生产升级率吻合；用作上线前闸门。"Simulation: 302 conversations in five minutes, with a 46% escalation rate"。*第一手：是；可信度：高。*
- [Nubank, arXiv 2609.30137](https://arxiv.org/html/2609.30137v1) (2026-09-24)。经模拟筛选的卡片管理代理随后赢得线上 A/B 测试并上线。"Simulation-guided iteration increased transactional net promoter score (tNPS) by 36.69 points in a live A/B test"。*第一手：是；可信度：高。*
- [Anthropic, Delight.ai case study](https://claude.com/customers/delightai-qa) (undated)。为每个客户的代理做人设加场景的回归运行；客户质检团队给出放行。"it used to take us about a week to fix issues, test, and deploy. Now it takes just one or two days max"。*第一手：厂商；可信度：中。*
