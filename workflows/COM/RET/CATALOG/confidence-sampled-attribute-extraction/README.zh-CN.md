# 置信度抽检的属性抽取

**工具变体：** `instacart-parse` · `walmart-qc-llm`

## 背景

一条商品记录是一组有名字的事实：材质、纹样、开合方式、版型、颜色、容量。这些事实由供应商提供，格式千差万别，或者干脆缺失，于是总得有人去读图片和文案，把字段填上。几十万件的目录靠人做不可能，只靠模型又危险，因为错的属性比空的更糟：它会作为事实展示给客户，会驱动筛选和对比，而替人逛店的智能体会把它当真。本工作流从文本和图片里抽取每个属性，并给每个值一个置信度。高于阈值的直接进目录；不确定的长尾交给人工修正，其余部分定期抽样检查，以便在抽取开始漂移的那一刻发现。这个环路里的人是审核员而不是作者：他们看到的是建议值、读到它的证据和一个置信度，而他们的修正成为设定阈值的标注数据。机器只写入暂存区，从不直接写主记录，所以一次糟糕的运行可以回滚，而不必修补。

**术语：**
- **属性（attribute）**：商品的一个具名字段，例如材质或开合方式。
- **抽取（extraction）**：从供应商的文字和图片中读出某个属性的值。
- **置信度（confidence score）**：附在每个建议值上的数字，来源可以是评分提示词，也可以是用人工标签训练的模型。
- **金标准值（gold value）**：由人标注的正确答案，用来衡量抽取质量。
- **LLM 评判（LLM judge）**：用第二次模型调用检查第一次的答案。
- **阈值（threshold）**：高于它就无需复核即可发布的置信度。
- **漂移（drift）**：随着目录里的商品与图片变化，准确率缓慢下滑。
- **暂存区（staging store）**：与主目录分开、存放待定建议的表。

## 用智能体搭建

**形态：** `service`。抽取按批次跑过整批商品，没人逐条启动；人以修正队列和抽样计划的形式与它相遇。

**需要：** 每件商品的供应商文本与图片，以及写明允许值的属性模式（schema）；一张一行一条建议的暂存表，记录值、置信度、模型版本，以及它读自哪张图、哪句话的证据；按置信度排序的修正队列；一套已标注的评估集；主目录，智能体不得写入。模式与模型同样重要：落在允许集之外的值是缺陷，不是同义词。

| 步骤 | 搭建方式 |
|---|---|
| 开发模式：提示词 + 模型配置 ⟲ 🛑 sample（人工标注金标准值）+ LLM 评判 | 每个品类建几百件已标注商品，建一次反复用：任何提示词或模型改动在部署前都先在这套数据上打分，评判模型与人工标签并行作为第二意见，而不是替代品。 |
| 部署 | 部署把模型版本与提示词版本写进它写下的每一行，这样一批坏结果可以按版本定位，而不是靠猜。 |
| 每个商品：抽取属性（文本 + 图像） | 脚本把商品批量送进抽取器；需要看图的属性和需要读文的属性分开抽取，于是两者的不一致会变成标记，而不是被默默择一。 |
| 自我验证置信度评分 | 评分调用与抽取调用分开，且在信任它之前先用标注集校准——模型自报的分数与正确率只有松散关系。 |
| 低置信度：🛑 review（审核员修正） | 修正队列展示每条建议及其证据和模式允许值；审核员的修改写回暂存行，分歧保留为训练数据。 |
| 定期 🛑 sample（质量漂移） | 每个周期抽取固定比例已发布的值对照来源核对，结果按属性和品类分别报告；一旦下滑，该属性的自动通道暂停。 |
| 写入商品目录 | 只有被标为 promoted 的行才移动到主目录，移动带批次 id 留痕。 |

**检查点：** `review`：低置信度路径只有审核员队列这一条，且智能体对主目录没有写权限，所以未经复核的值不可能被误发布。`sample`：抽样计划在智能体之外配置、按它无法更改的日程运行；抽样的结果决定某个属性能否保留自动阈值。凡涉及安全、法律或兼容性宣称的字段，无论分数高低都走 `review`，这条写在晋级策略里而不是写在提示词里。

**与来源相比：** 来源出自 2025-05 与 2025-08：两份来自大型零售商的第一手工程记录；两者都已超过十二个月，本轮没有重新打开。此后有这些变化：暂存表的架构已经成为公开的默认做法。2026 年的一篇从业文章主张[模型输出绝不能直接写主目录；晋级策略要写明白——置信度达标且无冲突则自动，否则复核；法律与安全属性无论置信度高低一律复核；阈值要用自己标注的样本定，而不是采用厂商默认值](https://paragraph.com/@techcirkle/building-a-product-catalogue-enrichment-pipeline-that-doesnt-corrupt-your-data)。它还提醒，自报置信度与正确率只有松散相关——上面的搭建方式用"先校准再用它做闸门"来回应。来源里的"自我验证"一步没有变；新增的要求是：这道验证本身要先被测量，才值得信任。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 在开发模式下，团队在小样本上迭代提示词和模型；人工审核员标注金标准值，并配合一个 LLM 评判 [[1]](#sources)。
2. 在生产中，从文本和图像中抽取每个商品的属性 [[1]](#sources)[[2]](#sources)。
3. 置信度来自第二个“评分提示词”（Instacart），或来自用人工标签训练的独立 QC 模型（Walmart） [[1]](#sources)[[2]](#sources)。
4. 🛑 **审阅**：低置信度的值交给人工审核员修正 [[1]](#sources)。
5. 🛑 **抽检**：定期对新商品抽样评估，以发现质量下滑 [[1]](#sources)。

**产出：** 写入商品目录数据管道的属性值。
**失败模式 → 防护：** 随着商品目录变化而悄然漂移 → 定期抽样。看似合理但错误的值 → 独立的验证器/QC 模型。
**与相近工作流的区别：** 上文的 Zalando 副驾由人批准每一个值。这里人只看低置信度条目和抽样。AWF-0063 以 diff 为证的 dbt 迁移则以生产数据为检验依据，而不是人工金标准标签。
