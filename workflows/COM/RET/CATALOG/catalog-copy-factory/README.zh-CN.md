# 商品文案工厂

**工具变体：** `chatgpt-api` · `claude-api` · `shopify-graphql` · `jd-apcg`

## 背景

网店必须描述它卖的每一件商品，几万件规模的目录意味着每件都要标题、描述、卖点列表，往往还要一份结构化摘要。运营人员按供应商给的数据手写：什么材质、适配什么、多大尺寸。这活既重复，两种失败方向还正好相反。写得太少卖不动；写得太满就是编事实——编出材质、保修、兼容性——而客户一旦信了这条编出来的事实，麻烦就是法律层面的。在这里，批处理按商品记录和品类简报为每件商品起草，逐条对照文字规则检查（长度、必备段落、记录不支持的说法），不合格的先自动重写，然后才让人看。审阅人在队列里筛查并批准上线，效果与旧文案对比衡量。审阅的作用不是润色文字：它是唯一能判断某句话对这件真实商品是否成立的环节，所以被存储和发布的是批准后的文本，而不是生成出来的文本。

**术语：**
- **PIM**（product information management，商品信息管理）：保存每件商品结构化记录的系统——属性、尺寸、材质。
- **SKU**：一件可售单品；一个颜色或尺码的变体算另一个 SKU。
- **品类简报（category brief）**：运营对一个商品族的指示：语气、必须写什么、不许宣称什么。
- **规则检查（rule check）**：检验草稿的程序——长度、必备字段、禁用词、记录中并不存在的数字。
- **无依据宣称（unsupported claim）**：商品记录支撑不了的表述，责任正是从这里开始的。
- **筛查队列（screening queue）**：草稿等待人批准、修改或拒绝的列表。
- **批量发布（bulk publish）**：把批准后的文案一次性写上线上的商品页。
- **CTR / CVR**：点击率与转化率，与旧文案对比衡量。

## 用智能体搭建

**形态：** `service`。工作是成千上万条按批处理的队列，没人逐条启动；人以筛查队列的形式出现，而不是以作者的身份。

**需要：** 结构化形式的商品记录，且简报所依赖的字段确实填了；每个品类的简报和文字规则，作为带版本的文件；规则检查器写成代码，而不是写成对模型的嘱咐；草稿存放区，与线上页面隔开，直到被批准；发布接口，只接受带审批记录的文本；对比新旧文案的分析数据。智能体不能有线上商品页的写权限。

| 步骤 | 搭建方式 |
|---|---|
| 商品数据 + 品类简报 + 文字规则 | 运行只从"记录完整"的 SKU 导出开始；缺了简报所需字段的行被扣下，而不是补出来。 |
| 每个品类一个提示词模板 | 模板是带版本号的文件，所以每句上线的文字都能追溯到产生它的模板与记录。 |
| 每个 SKU：起草 | Skill 一次起草一条，只把记录里的字段当作事实；缺失字段变成占位符，绝不做推断。 |
| 规则检查 ⟲ 重新生成 | 检查脚本跑长度、结构与无依据宣称三类检验；不合格的回炉一次，第二次仍不合格的带着标记进队列，不无限重试。 |
| 🛑 review（筛查队列） | 审阅人看到草稿与记录并排，被标记的行都有标注；批准后写入草稿存放区，修改则记到模板名下供下一轮参考。 |
| 存储已批准文案 + 批量发布 | 发布脚本只搬运已批准的行，按品类一次一个批次，并记录批次。 |
| CTR/CVR 反馈 → 更新模板 | 分析数据定期到达；Skill 比较各版本效果，提出模板或提示词的改动，改动人批准后才生效。 |

**检查点：** `review`：发布是另一个工具，它会拒绝没有审批记录的行，所以任何草稿都无法经由智能体到达商品页；审阅人的界面上，每条说法旁边就是来源字段。宣称检查写在代码里而不是写在提示词里，因为编出来的保修是法律风险，不是文风问题。

**与来源相比：** 来源出自 2022-06 到 2026-03；2026 年那份本月已打开，两篇更早的论文没有重新打开。此后有这些变化：护栏层已经被写成一种通用做法。2026 年的一份从业指南把分工划在[规则化校验在人读到之前先拦掉大部分事实错误，每批抽一部分给人看，并对高风险品类做法律审计](http://theneuralbase.com/ai-for-ecommerce/learn/intermediate/quality-guardrails)，另加两点被本搭建方式采纳：护栏规则要有版本号，这样某一批文案能追溯到生成时生效的规则；涉及健康、安全或保修的宣称，不能只靠规则检查就放行。筛查队列保持原样，更新的材料改变的是"让队列判断什么"。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 从店铺数据库或 PIM 拉取 SKU 及其结构化商品数据。收集专业部门的简报和商品文案规则 [[1]](#sources)[[2]](#sources)。
2. 把简报转成提示词模板。把同样的规则转成供规则检查器使用的独立检查项 [[2]](#sources)。
3. 为每个 SKU 批量生成描述，然后做后处理 [[1]](#sources)[[2]](#sources)。
4. 运行自动检查（规则合规、长度、必备段落、输入数据不支持的宣称）。不合格的先重新生成，再交给人看 [[1]](#sources)[[2]](#sources)[[3]](#sources)。
5. 🛑 **审阅**：对生成的文案做人工筛查。只有获批的文本才会存入待发布库 [[1]](#sources)。在一次 6,000 个 SKU 的运行中，审阅人对其中约 8% 做了实质性修改 [[3]](#sources)。
6. 将获批文案批量发布到商品页 [[3]](#sources)。用新数据重新训练或更新模型和模板；JD 对选定领域每天重新训练 [[1]](#sources)。

**产出：** 存储并发布到商品详情页的已批准商品描述；CTR/CVR 与旧文案对比衡量。
**失败模式 → 防护：** SKU 数据稀疏导致编造规格 → 只对数据完整的 SKU 运行，增加不受支持宣称的检查，并让审阅人核对事实 [[3]](#sources)。文案违反部门的文本规范 → 用同一份简报构建规则检查器 [[2]](#sources)。
**与相近工作流的区别：** AWF-0018 聚类-简报-起草式内容：它逐篇产出 SEO 文章，每篇都有 SERP 简报和 SME 输入。本工作流以目录级的体量产出结构化的逐 SKU 商品文案，经过规则检查和筛查队列。产出和检查点的安排都不同。

## 公开实例

覆盖度（截至 2026-11-06）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [Second collection pass](../../../../../research/2026-11-second-pass.md)。

- [JD.com, Automatic Product Copywriting for E-commerce](https://arxiv.org/html/2112.11915v1) (2022-06-28)。生成 → 人工筛查 → 存储已批准文案；自 2021 年 2 月起上线。"Daily uploads to the descriptions database can reach up to 28,570 generated descriptions, with an average daily acceptance rate of 80%"。*第一手：是；可信度：高。*
- [Troy Morgan, Shopify description pipeline](https://www.tdmorgan.com/blog/building-ai-product-description-pipeline-shopify) (2026-03-28)。一家约有 8,000 个 SKU 的零售商：校验、重新生成、人工审阅队列、批量发布。"The human review step catches about 8% of descriptions that need meaningful edits"。*第一手：匿名（未具名店铺）；可信度：中。*
