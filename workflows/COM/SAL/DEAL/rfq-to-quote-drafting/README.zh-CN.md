# 询价单转报价草稿

**工具变体：** `canals` · `quotery` · `proton-ai` · `azure-openai`

## 背景

阀门、管材、管件之类工业零件的经销商，会收到客户发来的询价单（RFQ）：一份物品和数量的清单，形式可能是邮件、PDF、电子表格，或者一张手写清单的照片。销售或估价员要弄清每一行指的是目录里的哪件产品，查出这位客户适用的价格，再回一份报价。手工做意味着要破解含糊的描述、在成千上万个零件的目录里搜索、核对每位客户各自的价格条款；而一个错误的零件或价格到了客户手里，就成了公司可能必须兑现的报价。智能体读取询价单，把每一行匹配到一个目录条目并给出置信度，从公司的定价系统取价，再起草报价，每一行都注明来源。被智能体标记的行由销售核对，报价也由销售发出，因为报价是对客户的价格承诺，而智能体从不自行定价。

**术语：**
- **询价单（RFQ）**：客户就一份物品和数量清单索取价格的请求。
- **SKU**：公司对某一件目录产品的编码。
- **估价员**：负责给询价定价的人，常见于项目单或大宗订单。
- **价目表档位、合同价、批量折扣**：客户所处的价格档位、该客户合同里约定的价格，以及数量越大单价越低的折扣。
- **ERP**：公司主要的运营与财务系统，保存目录、价格和订单。
- **置信度**：匹配程序对某个匹配正确可能性的估计；低于设定阈值的行会被标记。
- **不符合政策的行**：报价规则不允许不经核对就放行的行，例如没有价格记录的物品。

## 用智能体搭建

**形态：** `service`。询价单到达共享邮箱时没有人在操作，销售只看到已完成的草稿及其中被标记的行。

**需要：** 对共享销售邮箱的读取权限，通过邮件的 MCP 服务器或一个取回新邮件和附件的脚本；对 ERP 中目录和每位客户价格的只读权限，每种查询一个脚本或使用 MCP 服务器；公司的报价模板；草稿的审阅队列，例如邮箱的草稿文件夹或工单队列；一份以往修正的文件（客户用语 → SKU）。不要给智能体发送邮件的工具，也不要给它写入 ERP 的工具。

| 步骤 | 搭建方式 |
|---|---|
| 收到询价单（邮件、PDF、表格、照片） | 由你自己的邮件触发器为每份新询价启动 `claude -p` 或一个 Agent SDK 程序；或者用云端定时任务按计划检查邮箱。智能体读取正文和附件，包括图片。 |
| 提取行项目 | skill 的第一条指令：把每个所需行连同数量和客户原话写进一张表。 |
| 每个行项目：匹配目录 SKU + 置信度 | skill 旁边的脚本先尝试精确的零件编码匹配和修正文件。剩下的行由智能体对照目录搜索结果匹配，每行记下置信度和备选项。 |
| 按客户价目表/ERP 定价 | 定价脚本返回该客户、该物品、该数量的价格。智能体照抄结果，从不自己写价格。 |
| 起草报价，每行标注来源 → 标记低置信度或不符合政策的行 | skill 按报价模板填写，每行写明客户原话、匹配的 SKU 和价格来源，并标出低于阈值或没有价格的行。 |
| 🛑 review (销售确认被标记的行和价格后发送) → 回写 ERP | 见“检查点”。 |
| 销售的修正用于调整匹配 | 之后的一次运行把发出的报价与草稿对比，把每个被改动的匹配加入修正文件，匹配脚本下次会读取它。 |

**检查点：** `review`：运行结束时把草稿放进审阅队列，被标记的行已注明。智能体没有发送工具，也没有写入 ERP 的工具，所以报价只有在销售发出时才会到达客户，已接受的报价也由销售在 ERP 中录入。草稿保存之前，调用它的程序会把其中每个价格与定价脚本的输出对比，只要有一处不同就退回草稿。

**与来源相比：** 来源出自 2024-06 至 2026-09；来源 1 和 3 未注明日期。五个来源都是厂商案例研究或厂商的试点总结，讲的是它们自己的报价产品，所以报告了步骤，却没有说明每一步如何搭建，也都没有描述由通用智能体来执行。上面的搭建方式是针对同样步骤的方案。来源 4 报告说，准确性得到证明后，某些类别（例如库存答复）可以不经审阅；本搭建方式把每份草稿都送进队列。来源 5 没有被任何步骤引用。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 智能体监视共享的销售邮箱，按请求到达时的形式读取（邮件正文、PDF、Excel、手写清单的照片） [[1]](#sources)[[3]](#sources)。
2. 智能体提取每个所需行项目；先按精确编码匹配目录 SKU，再用 AI 匹配，每行给出置信度分数，描述含糊时给出备选项 [[2]](#sources)[[3]](#sources)。
3. ERP 根据客户自己的价目表档位、合同价和批量折扣给每行定价；模型从不自行定价 [[3]](#sources)[[4]](#sources)。
4. 智能体用公司的模板起草报价，每行列出来源描述、匹配的零件和价格来源，并标记低置信度的匹配和未定价的项目 [[2]](#sources)[[3]](#sources)。
5. 🛑 **审阅**：销售或估价员确认被标记的行，补充替代品或库存说明，然后发送；起初每份报价都要审阅 [[2]](#sources)[[3]](#sources)。有些团队在准确性得到证明后，会放开某些类别（例如库存答复）不经审阅，而定价仍由人负责 [[4]](#sources)。
6. 系统把已接受的报价/订单回写 ERP，销售的修正反馈到匹配中 [[1]](#sources)[[4]](#sources)。

**产出：** 客户邮箱和 ERP 中的一份已定价报价，每行来源可追溯。
**失败模式 → 防护：** 错误的 SKU 或价格到了客户手里 → 先做确定性的编码匹配，设置置信度阈值，对被标记的行审阅 [2][3]。ERP 目录混乱 → 从销售过往的报价中学习 [1]。
**与相近工作流的区别：** 最接近的是 AWF-0050 通话转 CRM 的 diff 审批：那是把一次销售通话变成 CRM 字段变更和跟进邮件。本工作流把客户的询价单变成基于目录和价目表的定价报价。交付物和输入都不同；审阅针对的是被标记的报价行，而不是 CRM 的 diff。

## 公开实例

覆盖度（截至 2026-11-13）：**薄弱**：只有匿名、与厂商相关或记者转述的说法。收集与复核见 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [Quotery, Brazos Valve case study](https://quotery.io/blog/case-study-brazos-valve-distributors/) (2026-05-12)。15 人团队；确定性加 AI 的逐行匹配；销售发送前审阅；跟踪了五个月。"Quote time: 8 minutes average. Down from 3 hours."。*第一手：厂商；可信度：中。*
- [Canals, Puget Sound Pipe & Supply](https://www.canals.ai/case-studies/puget-sound-pipe-and-supply-slashes-quote-times) (undated)。经销商销售审阅并确认 AI 的条目匹配；客户谈到了节省的时间。"with an advanced user, the time savings is probably three or four to one"。*第一手：厂商；可信度：中。*
- [EasiraAI, wholesale quote pilot](https://easiraai.com/work/wholesale-quote-from-enquiry) (undated)。在一家约 30 人的经销商做了为期六周的试点；估价员审阅每份草稿。"~10 minutes (incl. estimator review)"。*第一手：厂商；可信度：中。*
