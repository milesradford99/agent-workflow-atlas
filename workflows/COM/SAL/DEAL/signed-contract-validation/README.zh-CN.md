# 已签合同校验

**工具变体：** `salesforce` · `docusign` · `gemini` · `claude`

## 背景

客户以电子方式签下一份销售合同后，在这笔交易被记为赢单之前，必须有人核对：签字的人是否有权代表客户签署，价格和合同的年度金额是否与批准过的报价一致，所有必需的缩写签名和条款是否齐全。很多公司由一个叫交易支持台的小团队逐份手工完成这项检查。到了季末，大多数合同同时涌来，检查就排成了长队，而漏掉的错误会直接进入财务和法务所依赖的记录。在这里，智能体对每份回传的合同执行检查，没有问题的由它自己记录；凡是它有一丝疑问的合同，都转给交易支持台的专员。存疑的情况仍由人处理，因为一份有问题的合同若被记为赢单，会让收入失实，还可能让公司受制于没人批准过的条款。

**术语：**
- **电子签**：通过 DocuSign 之类的服务在线签署文件，所有人签完后服务会回传已签的 PDF。
- **交易支持台（deal desk）**：负责核对和批准交易商务条款的团队。
- **签署人权限**：签字的人是否有权让客户公司承担义务。
- **ACV**：年度合同价值，即合同每年的金额。
- **报价**：经批准的报价单，列明产品和价格，合同应与之一致。
- **缩写签名**：签署人在特定页面或条款上签的姓名缩写，表示已阅读并接受。
- **赢单（Closed Won）**：CRM 中表示交易已签署的阶段；财务和法务以它为准开展工作。
- **中间件**：位于智能体和 CRM 之间、负责写入的独立程序。
- **审计轨迹**：记录检查了什么、写入了什么、由谁操作。

## 用智能体搭建

**形态：** `service`。每次检查在已签合同回传时启动，现场没有人，专员只看到智能体存疑的合同。

**需要：** 电子签服务在合同完成签署时发出的通知，用来启动你自己的程序；通过 MCP 服务器或脚本读取已签 PDF 以及对应的 CRM 商机和报价；一份依据专员手工检查项和升级原因写成的检查清单文件；交易支持台的队列；一个负责写入 CRM 字段和审计记录的独立程序或脚本。不要给智能体本身任何写入 CRM 的工具。

| 步骤 | 搭建方式 |
|---|---|
| DocuSign 回传 | 电子签服务的通知带着合同标识启动一个 Agent SDK 程序或 `claude -p`。 |
| 读取已签 PDF（视觉） | 智能体读取 PDF，签名页和缩写签名页按图像读取。 |
| 核对签署人权限 → 对照报价校验价格 + ACV → 确认缩写签名 + 必备条款 | 一个装有检查清单的 skill，专员做的每项检查各占一行，对照以只读方式取得的 CRM 记录执行。智能体返回结构化结果：每项检查标为通过、不通过或不确定，并注明所依据的页面。 |
| 有任何疑问：🛑 handoff (交易支持台专员) | 只要不是每项都通过，结果就连同 PDF 一起进入交易支持台队列。 |
| 全部检查通过：把字段写入 Salesforce + 审计轨迹 → 赢单 | 由调用它的程序而不是智能体写入字段和审计记录，并把交易推进到赢单，且只针对全部通过的结果。 |

**检查点：** `handoff`：调用程序把所有并非全部通过的结果送进交易支持台队列。智能体没有写入 CRM 的工具，所以无法把交易标为赢单；只有在全部通过时，程序才以与专员相同的访问权限完成这一步。

**与来源相比：** 唯一的来源出自 2026-01。它是一位公司首席执行官发的帖子，讲 ZoomInfo 的自建系统：视觉模型读取 PDF，推理模型执行检查，中间件负责写入并保留审计轨迹。本搭建方式保留了模型判断与确定性写入程序之间的这种分工。来源用了两个模型；现在一个通用智能体可以在一次运行里读取 PDF 页面并完成检查，但这里没有任何材料表明它能做得同样可靠。AWF-0110 仅处理异常的合同校验描述的是同一个来源和同样的步骤；维护者应考虑合并这两个条目。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 工作流在已签合同从电子签回传时触发；它位于“DocuSign 回传”和“赢单”之间 [[1]](#sources)。
2. 动手构建之前，团队先坐在合同校验专员身边，记录下他们的每项检查和每个升级的原因，以此把手动检查文档化；并把标准定为“准确优先于速度” [[1]](#sources)。
3. 视觉模型读取已签 PDF，识别签名和缩写签名 [[1]](#sources)。
4. 推理模型将合同与 Salesforce 记录交叉核对：签署人权限、对照报价的价格和 ACV、必备的缩写签名和条款 [[1]](#sources)。
5. 🛑 **接手**：智能体只要有任何疑问，交易就转给交易支持台专员；专员只处理可能有问题的交易 [[1]](#sources)。
6. 无误的合同直接通过：由独立的中间件层把字段写回 Salesforce，供财务和法务使用，并保留审计轨迹，采用与人工相同的基于 Okta 的权限和审批路径 [[1]](#sources)。

**产出：** 一条带审计轨迹、已校验的 Salesforce 赢单记录；异常留在专员的队列中。
**失败模式 → 防护：** 无效合同（签署人错误、价格不符、缺少缩写签名）被当作赢单放行 → 任何疑问都升级给人，编排和审计放在确定性的中间件中，与模型的校验逻辑分开。
**与相近工作流的区别：** 最接近的是 AWF-0176 从询价到报价的起草（以及 AWF-0050 通话到 CRM 的 diff 审批）。那两个起草的是报价或 CRM diff，由销售逐项审阅（分段/辅助）；本工作流则在签署之后校验合同，并在没有逐项审批的情况下写入记录系统，只把异常转给专员（抽检）。交付物（已校验的赢单记录）和检查点（异常接手）都不同。
