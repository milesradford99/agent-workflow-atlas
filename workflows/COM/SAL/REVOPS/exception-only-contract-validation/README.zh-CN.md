# 仅处理异常的合同校验

**工具变体：** `salesforce` · `docusign` · `gemini-vision` · `claude-sonnet`

## 背景

收入运营（RevOps）负责从一笔签下的销售到公司账簿之间的系统和检查。其中一项检查发生在客户交回已签合同的时候：在交易被记为赢单之前，要有人确认签字的人有权代表客户签署，价格和年度金额与批准过的报价一致，必需的缩写签字和条款都在。这通常由交易支持专员逐份手工完成；到了季末，大多数合同同时到来，排起的队伍会拖住收入入账。在这里，智能体对每份合同执行检查，没有问题的不经任何人查看就写入 CRM，凡是它存疑的都交给专员。这些情况仍由人处理，因为一份有问题的合同若被记为赢单，会让财务看到失实的收入，还可能让公司受制于没人批准过的条款。

**术语：**
- **收入运营（RevOps）**：负责支撑收入的销售系统、数据和流程的团队。
- **交易支持（deal desk）**：负责核对和批准交易商务条款的团队。
- **签署人权限**：签字的人是否有权让客户公司承担义务。
- **ACV**：年度合同价值，即合同每年的金额。
- **报价**：经批准的报价单，列明产品和价格，合同应与之一致。
- **缩写签字**：签署人在特定页面或条款上签的姓名缩写，表示已阅读并接受。
- **CRM**：记录交易的客户关系管理系统。
- **赢单（closed-won）**：CRM 中表示交易已签署的阶段；财务和法务以它为准开展工作。
- **顺利路径（happy path）**：每项检查都通过的普通情况。
- **中间件**：位于智能体和 CRM 之间的独立程序，负责写入并保留审计轨迹，即检查了什么、写入了什么的记录。
- **模型漂移**：模型的行为随时间变化，例如在一次更新之后。

## 用智能体搭建

**形态：** `service`。每次检查在已签合同回传时启动，现场没有人，人只看到智能体存疑的合同。

**需要：** 电子签服务在合同完成签署时发出的通知，用来启动你自己的程序；通过 MCP 服务器或脚本读取已签 PDF 以及对应的 CRM 记录和报价；一份依据专员检查项和升级原因写成的检查清单文件；交易支持的队列；一个负责写入 CRM 字段和审计记录的独立程序。不要给智能体本身任何写入 CRM 的工具。

| 步骤 | 搭建方式 |
|---|---|
| 已签合同回传 | 电子签服务的通知带着合同标识启动一个 Agent SDK 程序或 `claude -p`。 |
| 视觉模型读取签名 + 缩写签字 | 智能体读取 PDF，签名页和缩写签字页按图像读取。 |
| 交叉核对签署人权限、定价、ACV 与报价、必备条款 | 一个装有检查清单的 skill，对照以只读方式取得的 CRM 记录执行。智能体把每项检查标为通过、不通过或不确定，并注明所依据的页面。 |
| 无问题：将字段写入 CRM + 审计轨迹 | 由调用它的程序而不是智能体写入字段和审计记录，且只在每项检查都通过时才写。 |
| 任何疑问：🛑 handoff (交易支持专员) → 赢单 | 其他结果连同 PDF 一起进入交易支持队列；由专员在 CRM 中把交易推进到赢单。 |

**检查点：** `handoff`：调用程序把所有并非全部通过的结果送进交易支持队列。智能体没有写入 CRM 的工具，所以存疑的合同只能由专员记为赢单；没有问题的合同由程序以与专员相同的访问权限写入。

**与来源相比：** 唯一的来源出自 2026-01。它是一位公司首席执行官发的帖子，讲 ZoomInfo 的自建系统：由 AI 智能体负责检查，由中间件负责写入和审计。本搭建方式保留了这种分工。来源用了一个视觉模型和一个推理模型；现在一个通用智能体可以在一次运行里读取 PDF 页面并完成检查，但这里没有任何材料表明它能做得同样可靠。AWF-0222 已签合同校验描述的是同一个来源和同样的步骤；维护者应考虑合并这两个条目。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 团队先挑最严重的瓶颈（季末已签合同校验）。由一个人坐在专员身边，记录他做的每一项检查，以及他每一次升级的原因 [[1]](#sources)。
2. 团队把标准定为“准确优先于速度”：只要智能体有任何疑问，合同就交给人 [[1]](#sources)。
3. 团队把系统一分为二：负责校验逻辑的 AI 智能体，以及负责 CRM 编排和审计轨迹的中间件层 [[1]](#sources)。
4. 视觉模型读取已签的 PDF（签名、缩写签字）。推理模型对照报价检查签署人权限、定价和 ACV，并对照 CRM 记录检查必备条款 [[1]](#sources)。
5. 无误的合同直接通过：中间件在与人工相同的访问控制、审批和审计路径下把字段自动回写到 Salesforce [[1]](#sources)。
6. 🛑 **接手**：交易支持专员处理智能体标记为可能有误的每一份合同 [[1]](#sources)。

**产出：** 带有已校验合同字段的赢单 CRM 记录，供财务和法务使用，另有一个供专员处理的被标记合同队列。
**失败模式 → 防护：** 审阅人逐份肉眼检查有效合同会拖慢季末 → 只自动化有文档记录的顺利路径 [[1]](#sources)。模型漂移或中间件故障让错误数据进入财务系统 → 独立的审计层，有疑问即升级 [[1]](#sources)。
**与相近工作流的区别：** AWF-0052 提议-确认式管道巡检：其中每次 CRM 回写都由人确认，并每周复核销售管道。本工作流把无误的合同直接写入 CRM，不做逐项批准，只把异常交给人处理（抽检式自主）。产出是已校验的赢单记录，而不是管道异常视图。

## 公开实例

覆盖度（截至 2026-11-06）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [Second collection pass](../../../../../research/2026-11-second-pass.md)。

- [Henry Schuck, ZoomInfo deal desk agent](https://www.linkedin.com/posts/hschuck_in-q4-we-built-an-ai-agent-to-replace-our-activity-7419740825846194176-3GNa) (2026-01-21)。每年约 100,000 笔交易；专员只处理被标记的合同；约 2 个月上线生产。"~85% of signed contract validations are now fully automated"。*第一手：是；可信度：高。*
