# 受控题库的 RFP 应答草稿

**工具变体：** `in-house-agentic-rag` · `conveyor` · `responsive`

## 背景

向大型机构销售的公司会收到征求建议书（RFP）和安全问卷：一长串关于产品、安全性和合规性的问题，答完之后买方才会考虑这家供应商。答案通常由售前工程师汇总，并请产品专家以及安全与合规团队参与。手工做要花上几周，同样的问题被一遍遍回答，而从旧文档里复制来的答案，可能承诺了公司早已不具备的功能或认证，买方日后可能会拿它来要求兑现。智能体只依据一个获批的资料库（收录现行答案和文档）回答每个问题，为每条答案注明来源，并标出资料库答不了的问题。被标记的项由专家核对，最终答复由售前工程师批准，因为每一条答案都是公司要为之负责的陈述。

**术语：**
- **RFP、RFI**：征求建议书，以及更早、更简略的信息征询书，由买方发给潜在供应商。
- **安全问卷**：买方就供应商如何保护数据提出的问题清单，常有几百题。
- **售前工程师（SE）**：销售团队中的技术成员，对答案负责。
- **领域专家（SME）**：被请来回答或核对本领域问题的专家。
- **GRC（治理、风险与合规）**：负责公司安全与合规表述的团队。
- **已验证的资料库（受管控的语料）**：经批准的历史答案、现行产品文档和合规证书的集合，答案只能取材于此。
- **来源追溯（溯源）**：从每条答案指向其所依据的资料库条目的链接。
- **智能体检索**：由智能体分几步搜索资料库，而不是一次性查找。
- **适配性检查**：在接收时确认这份文档是资料库能够回答的。

## 用智能体搭建

**形态：** `skill`。一位售前工程师一次处理一份问卷，并全程在对话中，所以一个旁边放着资料库的 skill 就够了。

**需要：** RFP 或问卷文件；已验证的资料库，作为参考文件放在 skill 旁边，或通过只读的知识库 MCP 服务器访问；买方的模板（电子表格或文档）以及往里写入的手段，例如文档 skill 或脚本；一份各领域被标记问题由谁回答的名单。只使用获准向买方提供的材料，并使用所在机构为此批准的环境。不要给智能体发送邮件或上传到买方门户的工具。

| 步骤 | 搭建方式 |
|---|---|
| 接收 RFP/问卷 → 适配性检查（拒收不对口的文档）→ 拆解成问题 | skill 的第一条指令：检查这份文档是不是资料库覆盖的问卷；如果不是，停下来说明还需要什么。然后把它拆成编号的问题。 |
| 每个问题：从已验证的资料库检索 + 起草并附来源追溯 → 标记无法回答的 | 内置子智能体各负责一组问题，搜索资料库，返回答案、来源和置信度，或者“无来源：已标记”。skill 旁边的脚本退回任何没有来源的答案。 |
| 🛑 review (专家/GRC 处理标记项) | skill 停下，把被标记的问题按需要回答的团队分组写出。 |
| (售前工程师（SE）评论 ⟲ 重新生成) | 在主对话中进行：售前工程师对答案提出意见，智能体依据资料库重写，每条都保留来源。 |
| 🛑 sign-off → 按买方格式导出 | 见“检查点”。 |
| 把获批的修改回流到资料库 | skill 根据获批的答案提出新增或修改的资料库条目；由资料库负责人逐条采纳或舍弃。 |

**检查点：** `review`：skill 列出被标记的问题后停下；专家在对话之外作答，再由售前工程师把答案带回来。`sign-off`：skill 把最终答案写进买方模板后停下；智能体没有发送或上传的工具，所以由售前工程师提交答复。

**与来源相比：** 来源出自 2026-02 至 2026-03。来源 1 描述的是 Palo Alto Networks 内部基于已验证语料做智能体检索的 RFP 助手；来源 2 是一家问卷厂商讲述 Zapier 如何使用它的产品。两者描述的都是接入销售日常工作环境的专用系统。本搭建方式是给一位售前工程师用的单个 skill：来源 2 中在共享工具里把被标记问题转给安全团队的做法，在这里变成一份由售前工程师转发的清单；资料库的日常更新留给它的负责人。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 公司只用经过验证、持续更新的产品文档和合规证书来构建知识库 [[1]](#sources)。Zapier 把 434 条知识条目和 2,675 条历史答复接入同一个资料库 [[2]](#sources)。
2. 销售或售前工程师在销售日常工作的地方上传请求。智能体先检查自己能否回答这份文档，拒收不对口的文档，并告诉销售还需要什么 [[2]](#sources)。
3. 智能体通过智能体检索对照获批语料检查每个问题，并把每条答复追溯到来源。智能体不能编造功能，也不能声称公司并不具备的合规资质 [[1]](#sources)。
4. 🛑 **审阅**：只有真正需要人工把关的地方，才会标记给安全/GRC 团队 [[2]](#sources)。售前工程师对草稿添加评论，AI 重新生成更新版本 [[1]](#sources)。
5. 🛑 **签发**：售前工程师根据客户的目标修改，并批准最终答复。系统从每次互动中学习 [[1]](#sources)。

**产出：** 一份按买方格式完成、可以提交的 RFP、RFI 或安全问卷，以及一个因获批修改而改进的资料库。
**失败模式 → 防护：** 过时或已弃用的规格进入答复 → 只使用受管控的语料，且每条答复都有溯源 [[1]](#sources)。智能体回答超出范围的文档 → 接收时做适配性检查 [[2]](#sources)。过度依赖掩盖缺口 → 把被标记的问题转给安全团队 [[2]](#sources)。
**与相近工作流的区别：** 暂无相近者。AWF-0024 按手册审阅合同（Playbook contract review）依据手册审阅收到的合同；本工作流则基于获批的资料库起草对外的答复。

## 公开实例

覆盖度（截至 2026-11-06）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [New workflows for empty categories](../../../../../research/2026-11-new-workflows.md)。

- [Palo Alto Networks, From Weeks to Minutes](https://www.paloaltonetworks.com/perspectives/from-weeks-to-minutes-how-we-applied-an-ai-first-transformation-to-the-rfp-bottleneck/) (2026-03-26)。内部“头号客户（customer zero）”RFP 副驾；售前工程师修改并重新生成基于已验证语料的 AI 草稿。"delivering RFPs in days instead of weeks"。*第一手：是；可信度：高。*
- [Conveyor, Zapier playbook](https://www.conveyor.com/blog/steal-the-playbook-zapier) (2026-02-24)。Zapier 的 GRC 团队只审阅智能体起草的问卷中被标记的问题。"only 20% of security questions require a security team member which is down from 90%"。*第一手：厂商；可信度：中。*
