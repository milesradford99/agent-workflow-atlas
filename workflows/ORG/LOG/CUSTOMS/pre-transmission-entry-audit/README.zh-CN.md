# 传输前报关单审核

**工具变体：** `flexport-ai-business-rules-engine`

## 背景

报关单是报关经纪人向美国海关与边境保护局（CBP）提交的申报，用来申报进口货物和应缴关税。工作人员根据进口商的单据准备它，里面一个差错，比如税则编码错了、国家代码打错了、货值的小数点放错了位置，都可能导致多缴关税、被罚款或事后更正。传统做法是合规团队只抽查一小部分报关单，而且是在申报之后。这里由智能体在每份已备好的报关单传输之前对照关税规则和客户自己的申报要求逐份检查。无问题的继续往下走；有问题的交给报关专家修正。更正仍由人负责，因为申报是经纪人的法律声明；同时持续进行统计抽检，用来检验智能体自己的准确度。

**术语：**
- **报关单、CBP**：申报进口货物的文件，以及接收它的美国海关与边境保护局。
- **报关经纪人、客户团队**：代进口商申报的持证专业人员；管理客户关系、了解其长期要求的报关行员工。
- **HTS 编码**：协调关税税则（Harmonized Tariff Schedule）编码，用来给产品归类并确定关税；前两位是章，即大的产品类别。
- **估价格式**：申报货值的写法（小数点符号、币种、单位）；该用句点的地方用了逗号，货值可能差出几个数量级。
- **关税叠加**：多项额外关税在基础税率之上同时适用于一件产品，每项有自己的编码。
- **业务规则（SOP 级别的申报指示）**：客户对其报关单应如何申报的长期要求。
- **统计抽检**：申报后让专家复核随机抽取的一部分报关单，以衡量错误率。
- **ACE**：美国海关的系统，进口商可以在其中看到以自己账户申报的报关单数据；来源把所用的数据文件称为 ES-003。
- **PSC、异议**：申报后更正（post-summary correction）是在报关单提交之后提交的修改；异议（protest）是对海关就某份报关单所作决定的正式质疑。

## 用智能体搭建

**形态：** `service`。报关单从制单系统一份接一份到来，每份检查时没有人在场，人只看到分给他们的被标记报关单和抽检样本。

**需要：** 以申报系统能导出的形式读取每份已备好的报关单；每个客户一份规则文件，由客户团队编写并保持最新；当前的关税参考资料（税则文本、额外关税编码及其生效日期），作为有人维护的文件；对话之外用来保存每份报关单的审核结论和后续结果的存储；两个队列，一个给被标记的报关单，一个给抽检样本。不要依靠模型的记忆来掌握当前的关税规则。不要给智能体连接 CBP，也不要给它申报系统中除记录结论之外的写入权限。

| 步骤 | 搭建方式 |
|---|---|
| 客户业务规则由客户团队录入 | 每个客户一份 Markdown 规则文件，用客户团队能自己编辑的平实句子写成。文件的修改走团队正常的审阅流程。 |
| 每份已备好的报关单，传输前：AI 审核 (HTS、国家代码、估价格式、关税叠加、客户规则) | 一个 skill 对照关税参考文件和该客户的规则文件检查一份报关单。脚本负责机械检查（国家代码是否存在、货值格式是否正确）；其余由智能体检查，如 HTS 章节与产品描述是否相符、关税叠加。每条发现都引用对应的规则。由制单系统通过 `claude -p` 或 Agent SDK 程序启动运行，或者由云端定时任务轮询等待审核的报关单队列。 |
| 无问题：传输给 CBP | 智能体把“无问题”结论写入存储。由制单系统而不是智能体传输带有“无问题”结论的报关单。 |
| 发现问题：🛑 review (运营 / 报关专家修正) | 报关单、每条发现及其所依据的规则进入专家队列。在有人标记为已修正之前，这份报关单一直搁置。 |
| 传输 | 由制单系统完成，在智能体之外。 |
| 🛑 sample (统计合规抽检继续进行) | 申报后，固定比例的报关单（包括无问题的）被复制到第二位专家的队列。结果被记录下来，并据此修订规则。 |

**检查点：** `review`：被标记的报关单留在专家队列里，智能体没有释放或传输它的工具；制单系统只发送带有“无问题”结论或经人修正的报关单。`sample`：由脚本随机抽取，而不是智能体来选，所以智能体不能决定自己的哪些结论会被复查。抽检的发现，正是团队了解审核有没有漏掉错误的途径。

**与来源相比：** 来源出自 2025 年至 2026-03，其中两个未注明日期。回溯审计常见问题页面（来源 5）在 2026-11 无法打开，所以依据它的说法只能以条目本身的文字为准。这些来源全部出自 Flexport 自己，或是对其 CEO 言论的报道，错误率数字是它自己的说法。来源描述的是一个平台内的厂商规则引擎；本搭建方式用规则文件、一个 skill 和一个队列完成同样的步骤，不包含该引擎本身，也不包含针对其他经纪人报关单的回溯服务。来源称 2025 年关税规则变化了 53 次，所以必须有人保持参考文件最新；基于过时文件运行的审核会悄悄出错。无需查找更新的记录：最新的来源出自 2026-03。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 客户团队把每个客户的业务规则（SOP 级别的申报指示）录入厂商平台的 AI 业务规则引擎 [[2]](#sources)。
2. AI 审核在申报前对每份报关单都对照监管要求和客户规则做实时检查。覆盖 100% 的报关单，而此前的做法是事后由人工合规复核约 5–10% [[1]](#sources)[[3]](#sources)[[4]](#sources)。
3. 审核能抓到的错误包括：HTS 章节错误（印有马图案的 T 恤被按活马申报）、国家代码差一个字母（TW 与 TV）、逗号与句点混淆导致货值相差几个数量级。Flexport 的 CEO Ryan Petersen 称之为“AI 驱动的拼写检查” [[1]](#sources)。
4. 🛑 **审阅**：有问题的报关单在最终确定前被标记给运营。报关专家修正后再传输。无问题的报关单直接通过 [[2]](#sources)[[1]](#sources)。
5. 🛑 **抽检**：申报后的统计抽检与 AI 审核并行继续（“我们也做那种统计抽样”） [[1]](#sources)。
6. 把报关单错误率作为结果指标来跟踪。Flexport 报告称，在 2024 年 10 月上线后约一个月内，错误率从 1.8% 降到 0.2% [[3]](#sources)[[4]](#sources)。

**产出：** 传输给 CBP 的已修正报关单，以及更低的申报后更正工作量。同一引擎还支撑一项针对其他报关行报关单的回溯审计服务（ACE ES-003 数据、115 条以上叠加规则、PSC 与异议的划分）[5]。
**失败模式 → 防护：** 规则滞后于关税变化（Petersen 称 2025 年有 53 次变化）→ 集中更新规则集，并对每份报关单核对。过度标记淹没运营 → 只标记违反规则或法规的情况，无问题的直接放行。回溯审计本身不检查归类是否正确 [5] → 把归类复核放在上游（AWF-0210 / 0148）。

**与相近工作流的区别：** AWF-0148（报关员复核的报关单准备，Broker-reviewed entry prep）是先制作报关单，再由报关员逐份复核并签发。本工作流的输入是已经备好的报关单，人只看被标记的那些，并保留统计抽检：自主程度是抽检而非分段，交付物是申报前的审核结论。AWF-0210 对新品归类，交付物不同。
