# 邮件转货运订单

**工具变体：** `langgraph` · `azure-openai`

## 背景

发货的公司（托运人）常常仍然用邮件向货运公司提出需求：把一票货运走要多少钱，提供一票货让承运方接下来（装运委托），或者要求约定提货或送货的时间。每封邮件都得有人打开，弄清对方要什么，查出价格或把详情录入运输系统，再回复，而邮件可能在队列里等上几个小时。智能体读每封邮件，判断是哪一类请求，并处理其中的常规部分：发出报价、创建订单或预订时段。它解决不了的请求交给经理，人还要抽查智能体的分类，因为分错类的邮件会在无人察觉的情况下产生错误的报价或订单。人仍然不可缺少，因为订单会动用资金和卡车，而含糊的请求需要了解客户的人来判断。

**术语：**
- **托运人**：有货要运、提出服务需求的公司。
- **报价**：运送一票货的价格，这里取自货运公司自己的定价工具（来源中把他们的叫作 Dynamic Pricing Engine）。
- **装运委托（load tender）**：托运人提供一票货，请货运公司接受，接受后成为其系统中的订单。
- **整车、零担、多式联运、空运**：货物装满一辆卡车；零担（LTL），多家托运人的货物共用一辆卡车；铁路与公路结合的运输；以及航空运输。
- **预约**：在某地点提货或送货的固定时段。
- **运输系统（TMS）**：货运公司记录订单、货载和订舱的系统。
- **异常队列**：智能体未能解决、由经理处理的案例清单。

## 用智能体搭建

**形态：** `service`。邮件全天到来，处理每封时没有人在场，人只看到异常队列和抽检样本。

**需要：** 对接收客户邮件的邮箱的读取权限，以及通过下面所说的工具发送回复的途径；定价工具的访问权限；在运输系统中创建订单和预订时段的访问权限；智能体可以读取的客户历史文件或表格；对话之外用来记录每封邮件、其标签和处理结果的存储；由经理处理的异常队列和抽检队列。客户的邮件和附件含有商业数据，所以要使用公司批准用于这类数据的环境。

| 步骤 | 搭建方式 |
|---|---|
| 客户来信 → 分类 (报价 \| 装运委托 \| 预约 \| 追踪) | 每封新邮件通过 `claude -p` 或 Agent SDK 程序启动一次运行，或者由云端定时任务轮询邮箱。一个 skill 给邮件打标签；一封邮件可能包含多项请求。标签和理由写入存储。 |
| 报价：定价引擎 → 回复 | skill 读取请求，调用包着定价工具的脚本。由回复工具根据定价工具的结果生成并发送邮件，所以智能体无法自己写一个价格。 |
| 委托：跨邮件 + PDF 关联详情，补取缺失信息 → 创建订单 | skill 把邮件及其附件读成一张订单字段表。缺失的字段到客户历史文件和运输系统里查找。脚本检查这张表，订单工具才创建订单。多货载委托中的各个货载可以交给子智能体并行处理。 |
| 预约：预订时段 | skill 提取地点、日期和时间窗口，调用预订工具。 |
| 无法解决：🛑 handoff (团队处理异常) | 邮件、已填的表和已尝试的做法进入异常队列。标为追踪的邮件也进入这里，因为来源的步骤没有给出对它们的处理方式。 |
| 🛑 sample (人工反馈闭环) | 脚本把固定比例已打标签的邮件，连同智能体的处理，复制到抽检队列。标错的标签成为 skill 里的示例。 |

**检查点：** `handoff`：历史记录无法解决的缺失或冲突字段、检查未通过，或标签置信度低，邮件就进入异常队列，既不创建订单，也不发送回复。订单工具和预订工具只有在脚本检查通过之后才会被调用，所以不完整的订单创建不出来。`sample`：抽检队列由脚本随机抽取填充，而不是由智能体来选。抽检结果是衡量智能体分类多久出错一次的唯一依据。

**与来源相比：** 来源出自 2024-10 至 2026-03；其中一篇在目录中未注明日期。2026-03 的新闻稿（来源 6）在 2026-11 无法打开，所以以条目本身的文字为准。这些来源都是该公司自己的发布和博客，或合作方与行业媒体对它的报道。它们描述的是一个建立在厂商云端 AI 服务上的自有系统；本搭建方式用一个 skill、连接器和队列完成同样的步骤，不包含该公司的定价引擎及其庞大的客户知识库，这些需要你自己提供。来源中的速度和数量数字是他们的，不是对本搭建方式的断言。无需查找更新的记录：最新的来源出自 2026-03。

## 步骤

*以下按来源所述。*

1. 智能体按请求类型对收到的邮件分类，包括整车、零担（LTL）、多式联运和空运 [[1]](#sources)[[3]](#sources)。
2. 报价：智能体读取请求，查询 Dynamic Pricing Engine 并回复 [[2]](#sources)。
3. 装运委托：智能体跨邮件和附件（包括手写的 PDF 备注）关联详情，检测并补取缺失数据，然后创建订单；可并行处理 20 个货载 [[1]](#sources)。
4. 预约：智能体提取详情并锁定提货或送货时段 [[1]](#sources)。
5. 🛑 **接手**：工作流这样设计，是为了“so that if something doesn't go right, that's what our managers work on”[[4]](#sources)。
6. 🛑 **抽检**：对分类做一个 'human feedback loop' [[3]](#sources)。

**产出：** 写入运输系统的订单、报价和预约。
**失败模式 → 防护：** 含糊的委托（'I have a load for Tuesday'）→ 用客户历史上下文补全空缺。未能处理的情况 → 交给经理的异常队列。

**近期实践（2026）：**
- 分类：当一封邮件同时要求整车和零担报价时，可以同时路由到两种报价流程（C.H. Robinson，2025-04-16）。[[5]](#sources)

**与相近工作流的区别：** AWF-0021 流程智能体（Procedure agent）回答客户并执行经过身份验证的交易。本工作流没有对话：邮件被转成业务记录，人只处理异常。
