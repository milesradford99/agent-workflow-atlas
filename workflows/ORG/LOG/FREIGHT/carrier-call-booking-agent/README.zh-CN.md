# 承运商电话订舱代理

**工具变体：** `ten8` · `happyrobot` · `parade-codriver`

## 背景

货运经纪公司把有货要运的公司和有运力的卡车公司（承运商）连接起来。它要安排的每一票货叫一个货载。承运商业务员一天里很大一部分时间在打电话：接听就某个已发布货载来电的承运商，给承运商打电话为还没人接的货载找车，确认承运商合法且有保险，谈定价格并订舱。这些工作重复性强，业务员忙时电话没人接，而且没经过核查的承运商或冒牌承运商是真实的风险，货可能被盗或被转给陌生人。智能体接听电话并处理常规的部分：核查承运商，并只在人为每条线路设定的价格范围内议价。智能体解决不了的电话仍由人接手，每次谈定的价格也由团队主管确认后才订舱，因为订舱会动用经纪公司的资金和客户的货物。

**术语：**
- **货载、线路**：要运送的一票货；从提货点到交货点的路线。
- **承运商、MC 号码**：卡车运输公司；在美国监管记录中标识它的 Motor Carrier 号码。
- **货载信息板（load board）**：经纪公司发布货载、供承运商查找的在线市场。
- **TMS**：运输管理系统，经纪公司记录货载、承运商、价格和订舱的系统。
- **合规核查**：确认承运商持有执照、有保险、获准使用。来源中用一款叫 Highway 的工具做这件事。
- **价格下限和上限**：智能体在某条线路上可以同意的最低和最高价格；由人设定。
- **Book Now 价格、Max 价格**：展示给承运商的货载报价，以及经纪公司愿意为它付出的最高价格。
- **重复经纪（double brokering）**：承运商在经纪公司不知情的情况下把货载转给另一家承运商；货运欺诈的一种。
- **价格确认单（rate confirmation）**：记录谈定的承运商、价格和货载的文件。
- **滞留费（detention）**：卡车在提货或交货处被迫等待时产生的费用。

## 用智能体搭建

**形态：** `platform`。核心环节是实时的电话交谈，通用智能体做不到，必须由语音智能体平台来完成。其余步骤通用智能体可以按 `service` 来做：找出就绪的货载、发布和排序、提供语音智能体调用的工具，以及批准后的订舱。

**需要：** 能接听电话号码并拨出电话的语音智能体平台，例如本条目工具变体里的那些；TMS 和货载信息板的访问权限；合规工具的访问权限；每条线路的价格下限和上限，由人设定；供业务员接听转接电话的电话线路；团队主管查看待确认订舱的地方。智能体不得更改承运商的付款或联系信息；有这类请求要交给人处理。在拨出任何电话之前，先确认你在通话录音和告知对方正在与 AI 通话方面的义务。

| 步骤 | 搭建方式 |
|---|---|
| 货载在 TMS 中就绪 → 发布到货载信息板 + 为该线路给承运商排序 | 云端定时任务或自己的调度器运行 `claude -p`，找出标为就绪的货载，有集成的货载信息板就通过集成发布，并用 skill 为该线路给承运商名单排序。 |
| 每个承运商电话 (呼入 \| 呼出)：识别 MC → 合规核查 (Highway) → 匹配货载 → 在线路价格下限/上限内议价 | 通话由语音平台承接。它通过工具连到你的系统：MC 查询、合规核查、按起讫点或参考编号查找货载，以及一个价格工具，返回该线路的下限和上限，并拒绝范围之外的任何价格。 |
| 无法识别 / 超出政策 / 承运商要求：🛑 handoff (业务员，附上下文) | 平台把通话转到业务员的线路，附上 MC 号码和摘要。 |
| 价格谈妥：🛑 sign-off (团队主管确认议价结果) | 语音智能体把一份待确认的订舱（承运商、价格、货载）写成“待定”，自己没有订舱工具。团队主管在你设好的地方批准。 |
| 在 TMS 中订舱 + 发送确认 | 批准之后，由一个小脚本或 skill 在 TMS 中订舱并发送价格确认单。 |

**检查点：** `handoff`：转接是语音平台的一个工具，在承运商或货载无法识别、缺少必填的货载字段、承运商要求转人工或报价满足你的转接规则时触发；业务员会收到 MC 号码和通话摘要。`sign-off`：唯一能在 TMS 中订舱或发送确认的工具，由团队主管批准之后运行的脚本来调用，所以任何一通电话都不会由智能体自行决定而以订舱告终。价格上下限放在价格工具里，智能体无法绕开谈判，而不是只写在语音智能体的指示里。

**与来源相比：** 来源出自 2025-04 至 2026-11。三篇是厂商页面，一篇是对一家经纪公司 CEO 的访谈。它们描述的是厂商产品，步骤只有概述而没有展示，也没有来源展示过用通用部件搭起来的智能体。团队主管确认只在一家经纪公司（Fura）有报道；另一个来源（Circle）报告的是无需人工介入的订舱，所以本搭建方式出于风险考虑保留这道确认，是一种选择，而不是行业惯例。厂商报告的接听率和订舱占比是它们自己的说法，不是对本搭建方式的断言。无需查找更新的记录：最新的来源出自 2026-11。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 货载在 TMS 中就绪后，智能体把它发布到相关的货载信息板，为该线路给经纪公司的承运商网络排序，并同时启动邮件和语音的外呼；已发布货载的承运商来电则全天候 24/7 接听 [[2]](#sources)。
2. 每通电话中，智能体通过 MC 号码识别承运商，在经纪公司的合规工具（Fura 和 Circle 用的是 Highway）中核查资质，并按起讫点或参考编号查找货载 [[1]](#sources)[[2]](#sources)[[3]](#sources)[[4]](#sources)。
3. 它告知货载详情，并在经纪公司按线路设定的价格下限和上限之内议价，与定价算法集成 [[1]](#sources)[[2]](#sources)。欺诈信号（调度员姓名、邮箱域名、银行信息变更）在后台交叉核对 [[2]](#sources)[[3]](#sources)。
4. 🛑 **接手**：当承运商或货载无法识别、缺少必填的货载字段、承运商要求转人工，或报价满足经纪公司的转接条件（例如等于或低于 Book Now / Max 价格）时，通话转给业务员，并附上 MC 号码和上下文摘要 [[2]](#sources)[[4]](#sources)。
5. 🛑 **签发**：在 Fura，智能体把谈完的结果交给团队主管确认后才订舱 [[1]](#sources)。
6. 智能体订下货载，并把每个数据点写回 TMS；运营人员保留对价格参数、滞留费争议和需要判断的货载的处理权 [[2]](#sources)[[3]](#sources)。

**产出：** TMS 中的已订舱货载（承运商、谈定价格、价格确认单），以及未订成货载的通话记录和已获取的报价。
**失败模式 → 防护：** 重复经纪 / 欺诈企图 → 后台合规和欺诈核查（Fura 的第一个月就拦下三起）[2]。承运商听到 AI 语音就挂断，或线路嘈杂 → 提供转接 [4]。智能体同意了不合理的价格 → 由人按线路设定上下限，并由团队主管确认 [1][2]。

**与相近工作流的区别：** 最接近的是 AWF-0150（邮件转订单的货运智能体）：那是托运人一侧（邮件 → 报价/订单/预约，抽检并在异常时接手）。本工作流是承运商采购一侧：实时语音议价，交付物是按谈定价格订下的承运商，并且每次订舱都由团队主管确认。也不同于 AWF-0153（漏提货的补救电话，不涉及订舱）。
