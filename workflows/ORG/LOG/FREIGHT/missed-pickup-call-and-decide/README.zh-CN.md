# 漏提货电话处置


## 背景

在零担（LTL）运输中，一辆卡车在同一趟里从许多托运人那里取货，再送到转运站，在那里分拣到其他卡车上。提货没有按计划发生时，原因可能是货没备好、卡车晚到，或者提货其实已经完成却没人记录，货物会被耽误，而再派一辆车去已经提走货的地方则白跑一趟。一家为众多客户订零担运输的物流公司，过去要靠人去查承运商网站、给承运商打电话、记录答复、通知客户，实在不行就把货件重新发出去等人提货。这里由一个智能体联系承运商，另一个智能体决定下一步怎么办，许多货件同时处理。智能体解决不了的情况仍由人接手，因为一个错误的决定会白派一辆车，或者让客户的货滞留。

**术语：**
- **LTL（零担）**：与其他托运人的货物共用一辆卡车的货运。
- **漏提货**：没有按计划发生的提货，或者完成情况没有被记录的提货。
- **承运商**：负责取货和运输的卡车运输公司。
- **转运站（terminal）**：承运商的集散站，货物在这里汇集并分拣到其他卡车上。
- **重新委托（retender）**：把货件再次提供给承运商，让它再派一辆车。

## 用智能体搭建

**形态：** `platform`。联系承运商要打电话，这是实时的语音交谈，通用智能体做不到，必须由语音智能体平台来完成。决策、系统更新、客户通知和每日数据，可以由通用智能体按 `service` 来运行。

**需要：** 来自货运系统的漏提货事件通知流或队列；能给承运商拨打电话的语音智能体平台，或者对用邮件答复的承运商，用邮件连接器；对货运系统的读写权限，用来更新状态和重新委托；通知客户的途径；对话之外用来记录每个货件的联系、答复和决定的存储；给零担团队的队列。在拨出任何电话之前，先确认你在通话录音和告知对方正在与 AI 通话方面的义务。

| 步骤 | 搭建方式 |
|---|---|
| 零担漏提货通知 | 每个事件通过 `claude -p` 或 Agent SDK 程序启动一次运行，或者由云端定时任务轮询通知流。每个货件一次运行，并行进行。 |
| 每个货件：呼叫智能体联系承运商 | 语音平台拨出电话并返回结构化的答复：已提货、将提货（何时），或无法说明。答复和时间写入存储。 |
| 决策智能体选择后续动作 (改期 \| 重新委托 \| 确认已提货) | 一个 skill，由每个货件一个子智能体来运行，读取记录下来的承运商答复，并按公司对这三种动作的规则处理。货件没有记录承运商答复时，脚本拒绝重新委托。 |
| 更新系统 + 通知客户 | 由工具把结果写入货运系统并发出客户通知。 |
| 未解决：🛑 handoff (零担团队) | 货件、至今的联系和原因进入零担团队的队列。 |
| 日常：向承运商共享漏提货数据 | 云端定时任务每天根据存储为每个承运商生成一份文件，只含货件状态事实，不含客户或价格数据，放在承运商数据推送读取的位置。 |

**检查点：** `handoff`：承运商没有给出可用的答复、答复相互矛盾或没有规则适用于该情况时，skill 把货件交给零担团队，并且不再对它采取任何动作。重新委托工具代价最高，因为它会派出一辆卡车，所以没有记录的承运商答复和 skill 的决定，它就拒绝运行；这条规则放在脚本或 `PreToolUse` 钩子里，而不是只写在 skill 的文字里。

**与来源相比：** 来源出自 2026-01-26；两篇分别是公司的发布稿和转述它的行业媒体文章。它们说一个智能体给承运商打电话、另一个做决定，并报告了同时进行 100 通电话和 100 个决定，但没有展示这两个智能体是怎么搭建的，也没有说货件如何到达零担团队；这里的移交是根据 95% 自动化这个数字推断出来的。本搭建方式保留“联系”和“决定”两个环节的划分，因为只有联系环节需要语音平台。所报告的自动化核查比例是公司自己的数字，不是对本搭建方式的断言。无需查找更新的记录：最新的来源出自 2026-01。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 当提货没有按计划发生时，智能体会自动收到通知 [[1]](#sources)[[2]](#sources)。
2. 一个智能体给承运商打电话或联系承运商；第二个智能体决定后续动作；两者合力能 '100 calls and 100 decisions simultaneously' [[1]](#sources)。
3. 公司的系统随之更新，客户收到通知；此前是由人去查承运商网站、打电话、记录进展并重新委托 [[1]](#sources)[[2]](#sources)。
4. 🛑 **接手**：未能自动化的那部分（95% 的核查已自动化）仍由团队处理；资料来源没有详细描述这一分流 [[1]](#sources)。
5. 公司每天与承运商共享漏提货数据 [[2]](#sources)。

**产出：** 每个漏提货都得到解决或升级，外加每日的承运商数据推送。
**失败模式 → 防护：** 错误的重新委托把卡车派到尚未备好的货物处 → 智能体先与承运商确认状态。注：移交路径只是由资料来源暗示的。

**与相近工作流的区别：** AWF-0005 告警补充与裁定（Alert enrich and adjudicate）会自动关闭无害告警。本工作流中，智能体在现实世界中行动（对承运商外呼、重新委托），产出是已解决的货件，而不是一个判定。
