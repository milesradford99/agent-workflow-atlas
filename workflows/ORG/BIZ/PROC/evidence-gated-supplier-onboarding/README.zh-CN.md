# 凭证把关的供应商准入

**工具变体：** `lio` · `box-ai-agents`

## 背景

公司要付钱给一家新供应商之前，得先在会计系统里为它建一条供应商记录，并确认这家公司真实存在、不在名单里，还能拿出它这类业务所要求的材料：例如处理客户数据的供应商，必须持有安全证书。很多公司实际上跳过了这一步：供应商在收到第一张发票时，由任何有权限的人建出来，所以检查在钱花出去之后才做，同一家供应商还可能出现很多次。智能体读取采购员手头的材料，判断供应商的品类，查重，只向供应商索取该品类所需的凭证，逐份校验，并给出风险评分。新记录仍由人批准，先是中央采购，再是主数据团队，因为这个批准是一道控制：它决定公司可以向谁付款，必须有人为此负责。

**术语：**
- **供应商记录（主数据）**：供应商在会计系统中的条目，含名称、税号和付款信息，之后每次付款都要用到。
- **ERP**：公司主要的财务与运营系统；来源中用的是 SAP S/4HANA。
- **主数据团队**：负责 ERP 中供应商等核心记录质量的人员。
- **税号、注册信息**：供应商的税号和官方公司登记册；两者都能识别一家公司，也能发现重复。
- **供应商品类**：一种分组，例如一次性供应商或处理客户数据的供应商，决定需要哪些凭证。
- **证书**：由第三方出具的文件，例如安全认证，供应商必须持有并按期更新；证书有有效期。
- **重新评估（requalify）**：按现行要求重新检查现有供应商。
- **GRC（治理、风险与合规）**：制定并检查公司规则和风险的团队。
- **审计日志**：记录人或智能体每一次操作，供日后审查。

## 用智能体搭建

**形态：** `service`。请求由采购员提交文件触发，供应商几天后才回复，证书到期靠定时器盯着，所以这项工作是一系列现场无人的运行，人只会看到审批请求。

**需要：** 一个状态存储，每个供应商一条记录（品类、已收到的凭证、已通过的检查、审批情况）；通过连接器（MCP）或脚本，读取 ERP 中现有的供应商记录和公开的公司登记册；一个接收供应商文件的地方；各品类的凭证要求，作为参考文件，由采购部门编辑；一个供中央采购和主数据团队使用的审批队列。不要给智能体创建或修改 ERP 记录的工具。供应商文件（例如安全证书）属于机密：只放在所在机构批准的系统里。

| 步骤 | 搭建方式 |
|---|---|
| 采购员提交报价或发票 → 智能体读取并指定供应商品类 | 提交动作启动一个 Agent SDK 程序或 `claude -p` 运行。skill 读取文件，并依据品类参考文件提出一个品类。 |
| 查重 (税号、注册信息) | 一个脚本在 ERP 供应商列表和公开登记册里按税号和名称查找并返回匹配项；发现可能重复就停下，交给主数据团队。 |
| 品类决定所需凭证 → 用公开来源预填供应商表单 | skill 列出该品类要求的文件，并依据登记册预填供应商的表单；供应商收到链接。 |
| 每个文档：校验类型、公司、有效期 | 每次上传启动一次运行：skill 检查证书类型对不对、公司对不对、有没有过期，并把结果记入状态存储。 |
| 风险评分 + 安全审查 | 一个子智能体读取状态存储里的凭证，写出评分和理由；另一个没有看过前者工作的子智能体审查文件中的安全问题。 |
| 🛑 sign-off (中央采购，然后主数据团队) | 见“检查点”。 |
| 在 ERP 中创建供应商 | 由主数据团队在第二次批准之后运行的脚本；智能体不运行它。 |
| 监控并重新索取即将过期的证书 | 云端定时任务，或你们自己的调度器运行 `claude -p`，扫描状态存储中临近过期的证书，并向供应商发出标准的重新索取。 |

**检查点：** `sign-off`：运行结束时，把凭证摘要、风险评分和理由发到中央采购的审批队列；该批准记录后，新的一次运行再把它发给主数据团队。智能体没有 ERP 写入工具，所以除非第二位审批人操作，否则任何东西都进不了 ERP，而且创建记录的脚本在状态存储里没有两次批准时拒绝运行。

**与来源相比：** 来源 2 出自 2025-09，来源 1 未注明日期。两者都是厂商的说法：来源 1 是 Lio 对一家未具名零售商的案例，来源 2 是 Box 对三星半导体的报道，只涉及步骤 3 中的评分和安全审查，不是整个流程。之后的搜索发现，ERP 和工作流厂商如今已原生提供同样的功能，例如 SAP Business Network 上的 SAP Supplier Onboarding Agent（2026-02 上架，[SAP](https://www.sap.com/assetdetail/2026/02/34307b42-407f-0010-bca6-c68f7e60039b.html)）；它的页面只是简短介绍，没有步骤，所以这里没有因此改动任何内容。来源是产品介绍，不是通用智能体的运行记录：这套搭建是本目录为同一流程做的设计。它不包括厂商的供应商门户、制裁名单筛查，以及对整个供应商库的一键重新评估。如果能用上 ERP 厂商自己的准入智能体，它可能取代这里的脚本和表单。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 准入从采购员手头已有的材料开始，可以是报价或发票；智能体读取后指定供应商品类，并在创建任何记录之前，对照税号和注册数据检查是否重复 [[1]](#sources)。
2. 品类决定供应商需要证明什么：一次性供应商填写简短表单；处理客户数据的供应商必须提供证书。供应商会收到一个链接，指向智能体已用公开来源预填的表单 [[1]](#sources)。
3. 智能体在每份文档到达时即时校验（证书类型对不对、公司对不对、有没有过期）[[1]](#sources)。在三星半导体（Samsung Semiconductor）的 GRC 流程中，智能体从供应商文档中提取元数据并计算风险评分，通过的供应商再由第二个智能体审查文档中的安全问题 [[2]](#sources)。
4. 🛑 **签发**：审批依次经过公司指定的相关人员，先是中央采购，最后是主数据团队，因此未走完流程的记录进不了 SAP [[1]](#sources)。在三星，由 GRC 团队决定是否使用该供应商 [[2]](#sources)。
5. 供应商在 SAP S/4HANA 中创建；每一次人或智能体的操作都记入日志以备审计。现有供应商按品类重新评估，智能体会在旧证书过期前索取新证书 [[1]](#sources)。

**产出：** ERP 中一条经批准、已去重的供应商主记录，附有已校验的凭证和审计日志；并持续监控证书。
**失败模式 → 防护：** 供应商在首张发票时被随意创建并重复（同一个供应商出现 15 次）→ 未走完流程不得创建记录，且先查重 [1]。过期证书无人察觉 → 智能体在到期前重新索取 [1]。结果只来自厂商的说法 → 把提速的说法当作厂商材料对待。
**与相近工作流的区别：** AWF-0083（有边界的长尾采购谈判）是 PROC 类中唯一的已有条目：它在采购员的限额内与现有供应商谈判价格和条款。本工作流则是评估并新建供应商。交付物是供应商记录，而不是谈妥的条款，签发是分阶段的审批链。

## 公开实例

覆盖度（截至 2026-11-13）：**薄弱**：只有匿名、与厂商相关或经记者转述的说法。收集与复核见 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [Box, Samsung Semiconductor vendor assessment](https://blog.box.com/samsung-semiconductor-cuts-vendor-assessment-time-90-using-box-ai-agents) (2025-09-04)。GRC 负责人具名介绍智能体对供应商文档的评分和安全审查。"reducing vendor security assessments from 3-5 days to approximately 4 hours"。*第一手：厂商；可信度：中。*
- [Lio, global retail leader](https://www.lio.ai/customers/global-retail-leader) (undated)。按品类确定凭证、查重，并在创建 SAP 记录前分阶段审批。"its roughly 100 critical IT suppliers"。*第一手：厂商；可信度：低。*
