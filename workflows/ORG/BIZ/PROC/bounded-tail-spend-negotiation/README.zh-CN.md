# 限额内的长尾采购谈判

**工具变体：** `pactum`

## 背景

一家公司向成千上万家供应商采购，而采购员只会认真和最大的几家谈判。长尾上的小供应商（车队服务、购物车、小型设备）沿用多年前定下的付款条款和价格，因为没有哪个采购员有时间一家家去谈。人工来做，就是几百个邮件往来，拖上几周。在这里，采购员为某个品类一次性设定目标和限额，智能体与所有供应商并行展开谈判，在这些限额内用一项条款去换另一项。限额仍由人来设定和批准，因为它关系到公司的资金和现金状况，涉及财务、资金和法务；凡是智能体无法在限额内谈定的，都转给采购员，只有采购员才能突破限额。

**术语：**
- **长尾采购**：向众多小供应商的零散采购，合起来金额不小，但很少有人花力气去谈。
- **付款条款**：发票开出后多少天付款；条款越长，现金在公司留存的时间越久。
- **资金部（treasury）**：管理公司现金和融资的财务团队。
- **限额（授权范围）**：智能体可以同意的范围，例如付款天数区间、最低折扣和服务水平。
- **服务水平**：供应商承诺的交付或支持标准。
- **谈判活动（campaign）**：同时与许多供应商谈同一个目标，例如延长付款条款。
- **ERP**：公司主要的财务与运营系统，供应商条款记录在这里。
- **升级**：因为超出智能体可以决定的范围，把事项交给人处理。

## 用智能体搭建

**形态：** `service`。供应商要隔几天才回复，所以这项工作是由收到的回复触发的许多次短运行，现场没有人；采购员只会看到被升级的案例。

**需要：** 每个品类一份谈判活动文件，由采购员编写并批准（目标、限额、取舍、截止时间、升级规则），智能体可读不可改；供应商清单（联系人、现行条款、采购额）；一个只限于本次活动的供应商的邮箱或消息连接器；一个状态存储，保存每个供应商的报价、还价和状态；一个接收升级案例的队列。不要让智能体接触 ERP，也不要给它签署工具。供应商联系方式和采购额属于商业机密：只放在所在机构批准的系统里。

| 步骤 | 搭建方式 |
|---|---|
| 采购员按品类设定目标、限额和取舍 | 谈判活动文件，由采购员编写。 |
| 🛑 plan | 见“检查点”。 |
| 上传供应商清单 | 一个脚本读取清单，在状态存储里为每个供应商建一条记录；一个 skill 依据现行条款和谈判活动文件估算节省金额，供采购员在启动前查看。 |
| 每个供应商：机器人在限额内谈判 | 每收到一封回复，或由云端定时任务找出该发首条消息或跟进的供应商，就为每个供应商启动一次运行：一个 Agent SDK 程序或 `claude -p`，加载该供应商的记录，通过 skill 读取谈判活动文件，并写出下一次报价。 |
| 超出限额：🛑 handoff (采购员) | 运行停下，并在队列里新增一项，附上往来邮件、供应商的报价和被突破的限额。 |
| 达成一致：签署协议 → 把条款推送到 ERP | 一个脚本把谈定的条款写入一条记录，供采购员走合同和 ERP 流程；签署和 ERP 录入按你们自己的流程办。 |

**检查点：** `plan`：智能体没有办法启动谈判活动；只有当谈判活动文件带有采购员、财务、资金和法务给出的批准，并由启动脚本核实后，才会开始。`handoff`：每一条发出的报价都要经过一个脚本（或发送工具上的 `PreToolUse` 钩子），与谈判活动文件里的限额比对，只要有任何条款超出就拦下，所以 skill 里的指令跳不过去；被拦下的案例连同证据进入采购员的队列。只有采购员能通过修改谈判活动文件来放宽限额。

**与来源相比：** 来源均未注明日期；来源 1 引用了 2022-11-08 的 HBR 文章和 2023-05-01 的 Talking Logistics 文章，来源 2 是厂商的产品页面。撰写本节时无法重新打开来源 1（403），其中的 HBR 原文也需要付费。同一做法已有更新的记录：Pactum 2026-07-31 的一篇博客介绍了 Ahold Delhaize USA 和 Honeywell 在既定防护范围内进行自主谈判（[Pactum](https://pactum.com/blog/how-enterprise-procurement-leaders-use-ai)）；那是厂商自己的说法，并不改变这些步骤。来源描述的是一个带有自己谈判引擎和面向供应商界面的厂商平台，没有展示它如何谈判。这套搭建让通用智能体在限额内写出每条消息，是针对同一流程的设计，不是厂商的方法。Pactum 的联系人校验、翻译和看板都没有包含在内。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 采购团队选择条款很少被谈判的长尾供应商（沃尔玛的试点中是车队服务、购物车、零售设备）[[1]](#sources)。
2. 采购员确定谈判活动的目标（付款条款、折扣幅度、截止时间），并按地区或品类设定规则、阈值和升级路径 [[2]](#sources)。
3. 🛑 **计划**：采购员会同财务、资金和法务，在启动前商定谈判方案。试点中有 5 名采购员以及这几个部门参与 [[1]](#sources)。审批机制来自厂商文档 [[2]](#sources)。
4. 采购员上传供应商清单（联系人、现行条款、采购额）。平台会预览预计节省的金额 [[2]](#sources)。
5. 聊天机器人与每个供应商并行谈判，在设定的限额内权衡付款天数、折扣和服务水平 [[2]](#sources)。
6. 🛑 **接手**：任何超出限额的报价都升级给采购团队 [[2]](#sources)。
7. 达成一致的条款经签署后推回采购系统，并记录备查 [[2]](#sources)。

**产出：** 载明新商务条款（付款条款、折扣）的已签署供应商协议，送入 ERP/合同记录。
**失败模式 → 防护：** 机器人超出授权 → 设硬性限额并加升级机制。供应商不愿参与 → 再次联系，并把目标定得切合实际（试点中的目标为 20%）。节省金额的数字来自厂商或二手来源 → 对照自己的采购数据核实。HBR 的来源需要付费，我只见过别处的引述。
**与相近工作流的区别：** AWF-0022 发票提取-匹配-分派（Invoice extract-match-route）处理的是采购之后的发票。本工作流则是在采购之前，于人设定的限额内谈判商务条款。产出物和检查点都不同。
