# 经理批准的招聘流程操作

**工具变体：** `claude-code` · `waas-mcp` · `ashby-mcp` · `gmail` · `slack`

## 背景

小公司的招聘经理会同时在好几个地方收到应聘：邮箱、招聘网站和招聘管理系统。每位应聘者都要对照岗位要求来读，然后拒绝、追问，或者推进，而且每个系统最后都要显示同样的结果。这是几个小时重复的阅读和写作，也很容易在一个地方拒绝了某人，而他在另一个地方仍显示为进行中。智能体对照经理写好的标准阅读每位应聘者，给出处理建议并起草消息。每一批在发送或归档之前仍要经理批准，因为拒信是发给真实的人的，而录用谁的决定带有法律责任，这些责任属于雇主，不属于工具。

**术语：**
- **ATS（招聘管理系统，applicant tracking system）**：公司用来保存候选人及其招聘进度的软件。来源中用的是 Ashby。
- **WAAS（Work at a Startup）**：创业公司发布岗位、接收应聘的招聘网站，自带消息功能。
- **岗位手册（playbook）**：针对一个岗位的文件，包含硬性要求、强信号、自动归档规则和邮件模板。
- **分级**：把应聘者分到某一组；这里分为归档、索要作品示例、推进。
- **归档**：把候选人从进行中的招聘流程里移出，并附原因代码。
- **工作许可**：在该岗位所在国家合法工作的资格。
- **纽约 LL144、欧盟 AI 法案**：针对招聘中使用自动化工具的规定。纽约市的 Local Law 144 和欧盟 AI 法案都涉及这类工具；欧盟法案把这类系统列为高风险。

## 用智能体搭建

**形态：** `skill`。一位招聘经理在对话中处理自己的应聘者，也在对话里批准，所以一个 skill 加上放在旁边的岗位手册就够了。

**需要：** 邮箱、招聘网站和 ATS 的连接器（MCP），以及日历的读取权限；每个在招岗位一份岗位手册，由经理编辑；每份手册里每个阶段一个消息模板。应聘者资料属于个人数据：只放在所在机构批准用于这类数据的系统里，并在使用任何排序之前，先弄清上面提到的招聘法规有什么要求。

| 步骤 | 搭建方式 |
|---|---|
| 分流：收件箱 + WAAS + Ashby + 日历 | skill 的第一条指令：通过各自的连接器读取每个系统，并把事项分组（排期、流程决定、新申请、噪音）。 |
| 每个应聘者：对照岗位手册分级 | 智能体打开该岗位的手册文件，为每位应聘者分级。应聘者多时，子智能体每个负责几位，返回一张表：应聘者、级别、所依据的规则。工作许可或所在地不明确的，只做标记，不归档。 |
| 向经理给出建议 (终端或 Slack) | skill 在对话中列出建议。也可以用聊天连接器把建议发到一个频道。 |
| 🛑 action | 见“检查点”。 |
| 按阶段定制每位候选人的消息 | 取该候选人所处阶段的手册模板，再为每人加一句定制内容，以草稿形式展示。 |
| 在 Gmail、WAAS、Ashby 中发送并归档 | 连接器的写入调用，只在批准之后进行。 |
| 重新查询各系统以核实 | skill 的最后一条指令：重新读取每个系统，只报告已经生效的操作。 |

**检查点：** `action`：skill 展示起草好的消息和归档方案，然后停下，等经理回答；经理可以批准整批（“reject all of these”），也可以逐个批准。发送和归档会影响公司之外的人，所以发送消息、归档候选人的连接器工具在权限规则里设为“询问”，并提醒经理不要把它们改成始终允许。这样即使跳过了 skill 里的某条指令，也仍会弹出确认。

**与来源相比：** 来源出自 2026-03。撰写本节时无法重新打开它们（页面读取器收到该站点的 403），所以本节依据的是条目自己的文字。来源本身就是一组 Claude Code skill，和这套搭建方式一致：每个岗位一份手册、任何写入之前先审批、最后重新查询。按定时器运行、把建议发到 Slack 的后台模式没有包含在内；这套搭建在经理提出要求时才运行。术语里提到的招聘法规义务（告知、审计、人工复核），这套搭建没有处理，需要雇主自己满足。

## 步骤

*以下按来源所述。*

1. 配置：招聘经理复制用户、Ashby 和各岗位的岗位手册模板。手册包含硬性要求、强信号、自动归档规则和邮件模板 [[1]](#sources)。
2. 分流：智能体扫描收件箱、Work at a Startup (WAAS) 的应聘者、Ashby 候选人、日历、已发邮件和草稿，然后把事项分组（排期、流程决定、新申请、噪音）[[1]](#sources)。
3. 审阅应聘者：智能体拉取完整资料，对照手册为每人分级。如果工作许可或所在地不明确，就标记该候选人待审，而不是自动归档 [[2]](#sources)。
4. 可选的后台模式：`/loop 10m /recruit-watch` 会让智能体把每个新事项的建议发到 Slack。经理在帖子下回复 👎、'skip' 或 'ask' [[3]](#sources)。
5. 🛑 **操作**：招聘经理批准每个写操作，可逐个也可批量。技能先展示起草好的拒信和归档方案，然后等待（'Present for approval — DO NOT CREATE YET'）。其规则包括 'NEVER send or archive without explicit approval' [[2]](#sources)。
6. 执行：智能体通过 Gmail 或 WAAS 消息发送每封个性化拒信（标准模板加每人一句定制内容），并在 Gmail、WAAS 和 Ashby 中带原因代码归档候选人 [[1]](#sources)[[2]](#sources)。
7. 核实：智能体重新查询 Gmail、Ashby 和 WAAS，每个操作确认生效之前不报告成功 [[2]](#sources)。

**产出：** 候选人在 ATS、WAAS 和 Gmail 中得到一致的通知与归档，反馈备注记录在 ATS 中。经理的招聘流程中已决定的事项被清空。
**失败模式 → 防护：** 因数据缺失（所在地或签证）而拒绝 → 手册规则强制标记，而不是自动归档。某个系统中写入静默失败 → 汇报前必须重新查询。骚扰式群发 → README 明确声明不做批量垃圾邮件。因为智能体对候选人分级，所以会涉及招聘相关法规风险（纽约 LL144、欧盟 AI 法案的高风险类别）。
**与相近工作流的区别：** AWF-0029 寻访-筛选-排期式招聘（Source-screen-schedule hiring）中，智能体撰写证据摘要，且“no reject decision”，由人在最后做决定。本工作流中，智能体对候选人分级，建议归档和拒绝，并在经理下令后自己发送拒信、归档候选人。检查点是按批次的操作审批，产出是已发出的消息和 ATS 变更，而不是面试材料包。
