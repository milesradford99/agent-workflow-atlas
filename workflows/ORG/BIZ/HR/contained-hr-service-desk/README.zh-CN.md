# 自主闭环的 HR 服务台

**工具变体：** `watsonx-orchestrate`

## 背景

在大公司里，HR（人力资源）部门要回答员工关于薪酬、福利、休假和职业发展的问题，还要替员工和经理办理日常事务：开一封在职证明、批一次休假、把某人调到新经理名下、走晋升流程中的一个环节。每件事都从员工或经理提出请求开始。靠人工做，就意味着电话热线、邮箱，以及 HR 员工一遍遍查同样的政策、把同样的改动敲进好几个系统，而且各国的答案还不一样。这里由智能体做唯一的入口：它依据当地政策和本人的记录作答，并直接在 HR 系统里办完常规事务。智能体办不了的事，以及所有敏感事项（例如绩效差或违纪），仍由 HR 的人来接手，因为这些决定关系到一个人的工作和收入，公司对员工负有法律义务，需要有人来权衡具体情况。

**术语：**
- **HR 伙伴（HR partner）**：为经理和员工处理需要判断的个案的 HR 专业人员。
- **记录系统**：其数据被视为正式版本的系统，这里指人事、薪酬和费用系统。
- **事务（transaction）**：智能体在记录系统里做的一次改动，例如一次休假申请或一次调动。
- **闭环率（containment）**：在助手内部办完、无需转给人的请求所占的比例。
- **在职证明信**：证明某人在公司任职的信函，租房或贷款时常常需要。
- **LLM（大语言模型）**：负责读懂请求并写出答复的 AI 模型。
- **多智能体编排**：一个智能体把任务的各部分交给其他智能体，再把它们的结果合起来。
- **CSAT / NPS**：来自用户调查的满意度分数；NPS（净推荐值）衡量用户愿意推荐这项服务的程度，可以是负数。

## 用智能体搭建

**形态：** `service`。每个请求从聊天入口进来，智能体这边没有人值守；HR 伙伴只看到转交给他们的个案。

**需要：** 一个聊天入口，把每条消息连同登录者的身份交给一个 Agent SDK 程序；连到人事、薪酬和费用系统的 MCP 连接器，以提出请求的那个人自己的权限操作，而不是管理员权限；各国的 HR 政策，作为由 HR 维护的参考文件；每个 HR 领域（福利、薪酬、职业发展）一个 skill，列出它可以办理的事务；一个供 HR 伙伴领取转交个案的队列。薪酬、健康福利、绩效和违纪记录都是个人数据，而且往往是敏感数据：只放在所在机构批准的系统里，不要让智能体把一个人的记录给另一个人看。

| 步骤 | 搭建方式 |
|---|---|
| 员工或经理在聊天中提出请求 | 聊天入口带着消息和本人身份启动 Agent SDK 程序。 |
| 分类并路由到 HR 领域 (福利、薪酬、职业发展) | 智能体选用对应领域的 skill；也可以每个领域一个子智能体，让各领域的指令互不干扰。 |
| 依据本地政策和个人记录作答 | skill 读取本人所在国家的政策文件，并通过连接器读取本人的记录。 |
| 在 HR 系统中办理事务 (证明信、休假、调动、晋升环节) | 每种获批的事务对应一个连接器工具。`canUseTool` 先向请求人展示将要改动的内容，请其确认后才执行；HR 系统本身要求的审批仍然照常进行。 |
| 敏感或超范围：🛑 handoff (HR 伙伴) | 智能体停下，告诉对方会由谁来联系，并把个案和已收集的信息发到 HR 伙伴的队列。 |
| 满意度调查 → 增加自动化 | 聊天入口发出调查；HR 查看结果和转交记录，决定下一步增加哪项事务。 |

**检查点：** `handoff`：skill 列出敏感话题（绩效、违纪、投诉、任何涉及另一位具名员工的事），要求智能体遇到就停下。这里漏掉一次停顿就会波及员工本人，可能影响其工作或收入，所以还要用 `PreToolUse` 钩子在个案被标为敏感时拦住所有事务工具；连接器也只提供获批的事务，其他任何事都只能转交。除这些事务之外，智能体没有任何能改动薪酬或雇佣状态的工具。

**与来源相比：** 来源时间为 2024-07 至 2026-07。它们描述的是 IBM 自己的 HR 助手，搭在 IBM 自家的智能体平台上（`watsonx-orchestrate`，在 2026-07 的来源中仍在使用）。来源报告了结果和所处理请求的类型，但没有说明每项事务如何确认、敏感个案如何识别；本搭建方式中的确认步骤和钩子是本目录的设计，不是 IBM 报告的做法。来源中的入口还取代了 HR 电话热线和邮箱；那是组织层面的决定，不属于搭建本身。2026-11 复核时，来源 4（Fortune）拒绝访问，所以违纪这个例子依据的是此前对它的阅读。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 员工和经理通过同一个聊天入口（AskHR）办理 HR 事务；IBM 关闭了 HR 电话热线和邮箱，使其成为唯一入口 [[1]](#sources)[[3]](#sources)。
2. 助手的 LLM 对提示词分类，并路由到相应的 HR 领域（福利、薪酬、职业与技能）[[2]](#sources)。
3. 对于提问，助手结合本地薪酬和 HR 政策给出个性化答复；对于任务，它直接在记录系统（Workday、SAP SuccessFactors、Concur）中办理：在职证明信、休假申请、经理发起的员工调动、季度晋升中的环节、薪酬和组织变更 [[2]](#sources)[[3]](#sources)。2025 年起，助手为多步骤的 HR 事务编排多个智能体 [[3]](#sources)。
4. 🛑 **接手**：助手把它无法闭环处理的请求，以及低绩效或违纪等敏感事项，转交人类 HR 伙伴 [[1]](#sources)[[4]](#sources)。
5. HR 团队跟踪满意度（CSAT/NPS）并不断增加新的自动化；目前已有近 90 项 [[1]](#sources)[[3]](#sources)。

**产出：** 已回答的 HR 问题和在记录系统中办结的 HR 事务；其余情况转给 HR 伙伴。
**失败模式 → 防护：** 强制推行使满意度一度下滑（NPS -35）→ 不断改进答复并增加可办理的事务，直到 NPS 回升 [1]。机器人处理了敏感案例 → 按政策转交人工 [4]。办错事务 → 仅在发起请求的经理于 AskHR 内下达指令时才执行（确切的确认步骤未公开说明）。
**与相近工作流的区别：** AWF-0144（经理批准的招聘流程操作）和 AWF-0029（寻访-筛选-排期招聘）都是招聘类工作流，按批次或按决定审批。本工作流属于 HR 的员工服务一侧：智能体端到端办结大部分请求，人只接手 6% 的转交。交付物和自主程度都不同。
