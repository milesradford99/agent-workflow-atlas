# 数据驱动的项目状态报告

**工具变体：** `ganttly`

## 背景

项目经理（PM）负责推进项目，并向依赖这个项目的人（客户或干系人）说明进展。每周，项目经理要从做事的人那里收集更新，对照计划，判断哪些延误、哪些有风险，再按每位客户要的格式写出来。整理和改格式占去一周的大部分时间；而如果依据的是过时的数据，一份读起来很顺的报告也可能是错的。智能体读取项目数据，把工作分为正常、延误、有风险，并起草报告和甘特图。报告发出前仍由项目经理阅读和修改，因为它是项目经理向客户就自己项目作出的说明，而数据里漏掉什么，只有项目经理知道。

**术语：**
- **状态报告**：定期发给客户或干系人的说明，讲项目是否正常、有什么风险、接下来做什么。
- **干系人**：对项目结果有利害关系的人，例如客户或出资方。
- **甘特图**：把任务画成沿时间线排列的横条的图。
- **依赖关系、关键路径**：依赖关系指一项任务要等另一项完成才能开始；关键路径是决定最早完成日期的那条依赖任务链，这条链上的延误会拖延整个项目。
- **风险提示**：被标出的、可能使项目延期或超支的事项。

## 用智能体搭建

**形态：** `skill`。一位项目经理一次生成一个项目的报告，并且在对话中修改，所以一个 skill 加上放在旁边的报告模板就够了。

**需要：** 对项目任务列表和时间线的读取权限，通过项目工具的连接器（MCP），或由项目经理放进来的导出文件；每种客户格式一份报告模板，由项目经理编写；绘制甘特图的办法，例如放在 skill 旁边的脚本，根据任务数据输出图片或 HTML 文件。不要接入邮件工具。项目数据里可能有客户和外包人员的名字：只放在所在机构批准的系统里。

| 步骤 | 搭建方式 |
|---|---|
| 拉取任务、时间线和项目数据 | skill 的第一条指令：通过连接器或导出文件读取任务列表和时间线；缺少需要的字段（日期、负责人、依赖关系）就停下。 |
| 分类为正常、延误、有风险 | 智能体把每项任务的日期和状态与计划对照，写出一张表：任务、类别、能说明问题的数据。 |
| 起草摘要、指标、风险提示、甘特图 | 智能体依据这张表填写客户的模板；指标由脚本计算，不在文字里估算；另一个脚本画出带依赖关系和关键路径的甘特图。 |
| 🛑 review (项目经理修改) | 见“检查点”。 |
| 发送给客户或干系人 | 项目经理从自己的邮箱发出。 |

**检查点：** `review`：skill 最后展示报告草稿、分类表和每项指标背后的源数据，然后停下；由项目经理修改草稿。智能体没有邮件工具，所以除非项目经理发出，否则不会有任何东西到客户手里。

**与来源相比：** 唯一的来源（也是唯一的公开实例）是一篇标注为“Apr 20”但没有年份的帖子；作者的账号创建于 2026-04，所以大概率出自 2026-04。它是作者为自己的付费报告工具（`ganttly`）做的宣传，只给出四个简单的步骤：连接数据、让 AI 分类、生成报告、选择格式。它没有展示提示词、模板，也没有说明工具如何核对数据，所以这套搭建是本目录为同样四个步骤做的设计，不是对该工具的复制。工具里可交互的甘特图在这里没有复现；由脚本画一张静态图。帖子中的时间数字是作者自己的说法，这套搭建不作任何此类承诺。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 项目经理连接项目数据源（任务列表、时间线）[[1]](#sources)。
2. 模型读取数据，标出哪些正常、哪些延误、哪些有风险，以及哪些事项是干系人关心的 [[1]](#sources)。
3. 生成报告：文字摘要、计算出的指标、标出的风险，以及带依赖关系和关键路径的甘特图 [[1]](#sources)。
4. 🛑 **审阅**：项目经理在发送前阅读并修改草稿 [[1]](#sources)。
5. 项目经理按客户要求的格式（PDF、HTML 或邮件摘要）发送，由每月一次改为每周一次 [[1]](#sources)。

**产出：** 发送给客户或干系人的每周状态报告。
**失败模式 → 防护：** 报告看似规整但状态有误 → 项目经理发送前对照源数据核对。报告格式含糊或前后不一致 → 先定好统一模板。证据只是工具作者的一份自述，所以节省时间的说法未经验证。
**与相近工作流的区别：** 没有相近的工作流。AWF-0031 每日收件箱分拣（Daily inbox triage）处理的是收到的邮件，本工作流则是根据项目数据生成对外的项目状态。
