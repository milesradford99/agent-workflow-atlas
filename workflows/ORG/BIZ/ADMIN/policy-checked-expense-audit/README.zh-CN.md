# 按政策审核报销

**工具变体：** `make-gemini-workday-monday` · `appzen`

## 背景

员工为出差、餐饮或活动花了公司的钱，要提交附有收据的报销单来报销。钱报回去之前，一个人数不多的差旅与费用团队要对照公司的书面政策逐行检查，员工的经理还要批准这份报销单。一家每月有几千行报销的公司，行数远远超过几位专员能仔细看完的量：收据格式五花八门、币种各不相同，政策又经常变。智能体负责跑固定规则、对照政策读每张收据，把合规的报销单直接转给经理。凡是违反规定的报销单仍由人来判断，付款也仍由经理批准，因为这是员工的钱，错误的驳回对员工不公平，而怀疑有人挪用资金，是对一位同事的判断，公司必须说得出理由。

**术语：**
- **T&E（差旅与费用）**：公司在员工出差、餐饮和活动上的支出，以及管这些支出的团队和政策。
- **报销单**：员工申请报销的单据，由若干行组成，每行附一张收据。
- **报销时效**：花钱之后过了多久才报销；政策通常不受理超过一定期限的报销。
- **品类限额**：每类支出（例如一顿饭、一场活动）的金额上限。
- **Webhook**：某件事一发生，一个系统就立刻发给另一个系统的消息，这里指报销单提交时。
- **审核看板**：一份共享的任务列表，每份报销单是其中一个条目，带有团队能看到、能修改的状态。
- **LLM（大语言模型）**：负责阅读收据和政策文本的 AI 模型。
- **确定性检查**：写成代码的固定规则，每次给出的结果都一样。
- **自动通过**：这里指不经专员查看、把合规的报销单转给经理；它不是付款决定。
- **采购订单（PO）**：公司向供应商发出的正式订单，付款前要拿发票与它核对。
- **并行运行**：在一段时间内让新流程和旧流程同时运行并比较结果，然后才依赖新流程。

## 用智能体搭建

**形态：** `service`。每份报销单都会触发一次运行，现场没有人；人只看到违规项和经理的审批请求。

**需要：** 通过 MCP 连接器或小脚本，读取费用系统中已提交的报销单和收据，并且只能设置一种状态（审核通过，或需要审核）；T&E 政策、限额和阈值，作为由 T&E 团队编辑的参考文件；一个存放违规项的审核队列，例如团队的看板或工单队列；一套经批准的反馈模板。员工记录和收据属于个人数据：只放在所在机构批准用于这类数据的系统里。不要给智能体任何批准付款、驳回报销单或给员工写信的工具。

| 步骤 | 搭建方式 |
|---|---|
| 提交报销单 | 费用系统的 webhook 启动一个 Agent SDK 程序或 `claude -p`；也可以用云端定时任务每隔几小时收集一次新报销单。 |
| 规则检查 (金额、日期、时效、品类限额) | skill 旁边的一个脚本按政策文件里的限额逐行检查，返回每一行的结果。 |
| LLM 对照政策阅读收据 | skill：智能体对照政策文件阅读每张被标记的收据，并记下所依据的条款。长的报销单可以分给几个子智能体。 |
| 币种检查 | 另一个脚本把收据上的币种和金额与报销行比对。 |
| 合规：自动通过 → 🛑 sign-off (经理) | 智能体通过连接器把报销单设为审核通过；费用系统把它转给经理。 |
| 违规：🛑 handoff (T&E 专员) | 智能体设为需要审核，并在队列里新增一个条目，附上每条未通过的规则、收据和一份建议使用的反馈模板。 |
| 向员工发送模板化反馈 | 专员选用或修改模板，从费用系统里发出。 |

**检查点：** `sign-off`：经理在费用系统里审批；连接器不提供任何审批或付款操作，`PreToolUse` 钩子会拒绝任何要把状态设成那两种以外的调用。`handoff`：每份有违规的报销单都带着已收集的证据进入专员的队列；智能体没有驳回报销单或发邮件的工具，所以员工只会收到专员的消息。政策文件对智能体是只读的，只有 T&E 团队能改规则。

**与来源相比：** 唯一的来源（也是唯一的公开实例）出自 2025-11。它是一篇厂商的客户案例：客户在一个无代码自动化平台上用一组场景搭出这个流程，读收据时调用一次模型，检查每隔几小时运行一次。这套搭建方式用通用智能体跑同样的步骤，并保留“先固定规则、后模型判断”的顺序。它不包括来源里定制的退回页面，也不包括团队当时还只是在考虑的“明显违规自动驳回”。来源中的并行运行和逐步放开自主度是上线时的做法，不属于搭建本身。`variants` 里列出的 `appzen` 是一款商业报销审核产品，来源没有描述它。来源报告的准确率是厂商自己的数字。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 员工在人事与财务系统（Workday）中提交报销单。Webhook 在 T&E 团队的审核看板（monday.com）上创建一个条目 [[1]](#sources)。
2. 自动化流程运行规则检查：条目金额、日期、报销时效，以及餐饮、活动等品类限额 [[1]](#sources)。
3. 对需要进一步审查的条目，自动化流程把政策、收据和员工数据发给 LLM（Vertex AI 上的 Gemini）。LLM 提取收据细节，并对照政策作出判断 [[1]](#sources)。
4. 自动化流程再做一些确定性检查，例如币种是否一致 [[1]](#sources)。
5. 自动化流程分派报销单。合规的报销单自动通过，并在 Workday 中转给经理（🛑 **签发**：经理）。违规的进入“需要审核”（🛑 **接手**：由 T&E 专员判断）[[1]](#sources)。
6. 对需要修改的报销单，T&E 专员选用预先写好的违规说明，通过邮件或 Workday 发给员工 [[1]](#sources)。
7. T&E 团队在看板上编辑政策清单和阈值。这些内容按需同步，并在每周日同步 [[1]](#sources)。
8. 上线前，团队让它与旧流程并行运行 60–70 天。上线 30–40 天之后，团队才扩大自主度 [[1]](#sources)。

**产出：** Workday 中已通过或已退回的报销单，外加审核队列和异常情况的审计轨迹。
**失败模式 → 防护：** 政策版本不对 → 由团队自己维护政策库，每周同步。过度信任模型 → 并行运行，逐步放开自主度。明显违规的仍需要人来处理（目前只是在考虑自动驳回）。准确率（“接近 100%”）是厂商自报的。
**与相近工作流的区别：** AWF-0022 发票提取-匹配-分派（Invoice extract-match-route）把供应商发票与采购订单匹配后付款。本工作流则是对照内部差旅与费用（T&E）政策检查员工的报销，并向员工发送指导性反馈。产出物和检查点的负责人都不同。
