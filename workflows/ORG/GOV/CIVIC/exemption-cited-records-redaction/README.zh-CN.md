# 引用豁免条款的公开记录遮蔽

**工具变体：** `common-sense-ai` · `atea-masking-service`

## 背景

议会、政府机构等公共机构依法必须在公众提出要求时提供其记录（美国依据公共记录法和 FOIA，瑞典依据公开原则）。公开之前，工作人员要找出申请涉及的每一条记录，这些记录可能分散在文档、邮件和许可系统里；要逐份判断它是否在申请范围内；还要把法律保护的内容（例如个人数据）遮盖起来，并注明法律依据。文件成千上万时，这既慢又重复。智能体负责检索、给每份文件归类，并提出遮蔽建议和法律条文出处。每一处遮蔽仍要由记录官员批准：漏掉个人数据就是侵犯隐私，遮得过多则是扣下了公众有权看到的内容，而且按瑞典监管机构的指引，决定哪些内容属于保密的是官员本人。

**术语：**
- **公共记录申请（FOIA）**：向公共机构申请获得其记录副本。
- **相关（responsive）**：在申请要求的范围之内；无关（non-responsive）的记录不在公开之列。
- **豁免（exempt）**：在申请范围内，但受某项具体法律规定保护而不予公开。
- **遮蔽（redaction）**：公开之前，把文件中受保护的部分遮盖起来。
- **个人数据（直接和间接标识符）**：能指明某个人或可能指向某个人的信息。
- **记录官员**：负责决定哪些内容可以公开的工作人员。
- **DPIA**：数据保护影响评估，以新方式处理个人数据之前必须做的书面风险检查。

## 用智能体搭建

**形态：** `skill`。记录官员一次处理一份申请，并且全程在对话中；同一份申请里的大量文件，可以在同一个 skill 内由内置子智能体并行归类。

**需要：** 申请原文；通过 MCP 连接器对存放记录的系统（文档管理、邮件、许可）的只读访问，范围限于该申请涉及的内容；一份参考文件，写明所在辖区的豁免条款和遮蔽规则，以及每一条的法律出处；一个放智能体工作副本的位置，与原件和任何公开文件夹分开；一套经批准可处理个人数据的环境，最好在任务结束后删除文档。不要给智能体邮件工具，也不要给它公开文件夹的写入权限。

| 步骤 | 搭建方式 |
|---|---|
| 收到记录申请 → 与申请人澄清范围 | 官员把申请交给 skill。skill 起草澄清问题，由官员发出。厂商放在申请人面前的公开聊天不在这套搭建之内。 |
| 在文档、邮件和许可系统中检索 | skill 检索每个已连接的系统，把候选文件清单写入一份结果文件。 |
| 每份文件：归类为 相关 \| 无关 \| 豁免（附法律条文） | 内置子智能体各领一批文件，返回一张表：文件、类别、所引豁免条款。它们只能引用参考文件中的豁免条款。哪条都对不上的文件，标记为“不确定”交给官员。 |
| 提出遮蔽建议（个人数据、州法豁免） | 智能体把每处拟议的遮蔽写成一条记录（文件、页码、文字、理由、出处），并生成加了标记的工作副本。原件始终不动。 |
| 🛑 review (记录官员批准每一处遮蔽) → 公开给申请人 + 审计日志 | 见“检查点”。由钩子把每次工具调用追加到审计日志。 |

**检查点：** `review`：skill 最后列出每一处拟议的遮蔽，以及每份豁免或不确定的文件及其出处，然后停下。官员对每一项批准、修改或驳回。公开这一步没有搭建出来：智能体没有邮件工具，权限规则拒绝写入公开文件夹，所以由官员依据已批准的清单整理并发出公开包。

**与来源相比：** 来源的时间为 2024-12 至 2025-12；厂商产品页没有日期。来源 1 是厂商页面，来源 2 是监管机构的摘要（PDF 能打开但没有得到可读的文本，所以没有重读），来源 3 是新闻报道，部分内容在付费墙之后。它们都没有详细展示智能体的步骤。这套搭建是一位官员处理一份申请的设计，省去了厂商对常规申请的自动公开（会跳过审阅），也省去了它的付款和身份核验功能。这里不作任何效果上的断言。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 受理：在工作人员看到之前，由 AI 聊天先请申请人澄清含糊的申请 [[1]](#sources)。
2. 智能体在机构的文档管理、Outlook/SharePoint、许可等系统中搜索相关记录，并把申请的各部分分派给相应部门 [[1]](#sources)。
3. 智能体把每份文档分类为 responsive（相关）、non-responsive（无关）或 exempt（豁免），并附上豁免所依据的法律条文 [[1]](#sources)。
4. 智能体提出遮蔽建议：个人数据（直接和间接标识符）以及辖区规则所涵盖的内容；瑞典市政版本按服务领域使用模板 [[1]](#sources)[[2]](#sources)[[3]](#sources)。
5. 🛑 **审阅**：责任官员在公开前检查并批准每一处拟议的遮蔽；按瑞典监管机构的指引，该工具“纯粹是辅助”，由官员决定哪些内容属于保密 [[1]](#sources)[[2]](#sources)。
6. 记录交给申请人；系统保留一份日志，记载搜索了什么、返回了什么、保留了什么 [[1]](#sources)。

**产出：** 给申请人的遮蔽后公开包，以及搜索、保留和豁免的审计轨迹。
**失败模式 → 防护：** 漏掉个人数据或过度遮蔽 → 官员审阅每一处遮蔽，并采纳数据保护机构建议的 DPIA 和日志记录 [2]。厂商对“常规”申请自动办结会跳过审阅 → 配置哪些申请类型可以自动公开，敏感的仍走完整审阅 [1]。厂商处理个人数据 → 使用受限环境，任务结束后删除文档 [3]。
**与相近工作流的区别：** 最接近的是 AWF-0082（模型分诊的记录公开）：它批量分类已归档的电报以便解密，人只处理“不确定”的记录并抽查模型的判断。本工作流是端到端处理一份进来的申请（搜索、豁免分类、遮蔽），并且每一处遮蔽都由人批准；交付物是给单个申请人的遮蔽后公开件。

## 公开实例

覆盖度（截至 2026-11-13）：**薄弱**：只有匿名、与厂商相关或经记者转述的说法。收集与复核见 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [Common Sense AI, Los Altos Hills request](https://www.commonsensetech.ai/products/public-records) (undated)。一份大型市政申请经分诊并预先准备好遮蔽，只剩少量文档需要细看。"Los Altos Hills brought us 8,483 documents in one request. We saved them 99 hours and $7,900 of staff time, leaving only 30 documents requiring close human review."。*第一手：厂商；可信度：中。*
- [Techtidningen, Ronneby kommun](https://techtidningen.se/blev-tre-ganger-snabbare-ronneby-gick-fran-papper-och-penna-till-ai-pa-sex-manader/) (2025-12-08)。市政府采用 Lidingö/Atea 的遮蔽工具；上传、AI 给出建议、承办人审阅。"Nu har man infört ett AI-baserat system som gör att det går tre gånger snabbare."。*第一手：访谈；可信度：中。*
