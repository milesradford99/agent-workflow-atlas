# 意见征询主题分析与签核

**与相近工作流的区别：** AWF-0030 议题树研究（Issue-tree research）产出的是假设驱动的研究简报。本工作流则是依照一份由人签核的主题清单，对固定的公开语料做归类，并由分析师抽检归类结果。产出物和检查点都不同。
**工具变体：** `iai-consult`

## 背景

意见征询是把一项提案摆到公众面前，就几个开放问题请大家作答，而回答是自由文本回来的：几万条网页表单和邮件，其中许多是照着动员模板复制的近似重复，许多只有一句话，也有少数是唯一一条有专业依据的反对意见。接下来得有人说清楚这些回复到底说了什么。便宜的办法是读一个样本再外推，快，但永远会被人质疑样本漏掉了要点；彻底的办法是全部读完，把每条回复按一份主题清单编码，这要按"分析师周"计，也正是抽样成为惯例的原因。本工作流把活儿重新切分：机器读完全部回复，同时提出主题和归类；人保留真正需要判断的部分——哪些主题算数、归类在原文面前是否站得住、结论是什么。主题清单在任何归类开始之前就要签核，因为一份由模型编出来、政策团队从没看过的清单，会悄悄地决定这次征询"是关于什么的"，而之后再怎么复核也发现不了。

**术语：**
- **意见征询（consultation）**：政府公布一项提案、就设定的问题公开征集书面意见的正式程序。
- **自由文本回复（free-text response）**：受访者自己敲进去的回答，区别于勾选项或动员模板信件。
- **主题（theme）**：一批回复共同涉及的一个话题，由分析来界定。
- **归类（mapping）**：把一条回复指派给一个或多个主题，也称编码（coding）。
- **签核（sign-off）**：政策团队对主题清单的批准，必须在归类开始前完成。
- **双人复核（double review）**：两名分析师编码同一批回复，用来衡量两个人之间的一致程度。
- **F1**：兼顾准确率与召回率的单一分数，这里用于把工具的归类与人的归类作比较。
- **平等性分析（equality analysis）**：检查错误率在不同受访群体之间是否有差异。
- **看板（dashboard）**：把主题计数和支撑这些计数的原始回复并排显示的审阅界面。

## 用智能体搭建

**形态：** `service`。征询按各自的节奏从许多团队送来，每一批都是几万条回复，处理完、写完报告就丢弃；事后没有人维护按次征询的资产，而语料量也远超一次对话能装下的规模。这是无人值守的批量处理，中途有三道关口由人接手，所以是一项服务——不是某个团队会话里跑一次的 skill，也不是一份常设语料的 project。

**需要：** 按问题导出的回复，带稳定的受访者 ID，正文里不包含这次征询本身没有采集的信息；照原样提出的问题集，因为主题是按问题生成的，问题改写就会得到另一份清单；能在征询时间表内完成签核的政策团队，因为不签核就无法开始归类；一个把回复原文和为其提出的主题并排显示的审阅界面，因为分析师没法对着自己读不到的内容勾选归类；事先定好的抽样规则（每个问题抽多少、其中多少做双人复核），否则事后的一致率数字毫无意义；以及公开发布用的分析模板。智能体不能自己写结论，也不能裁定一份主题清单是否够用：这两件事属于分析师和政策负责人。

| 步骤 | 搭建方式 |
|---|---|
| 每个问题的回复 | 按问题分别导入；来自动员模板的重复回复被标出而不是合并，因为"完全相同的回复有多少条"本身就是一项发现。 |
| 每个问题：从全部回复中归纳主题 | 对全集而不是样本做主题建模，返回一份刻意偏长的清单：签核时能删掉一个主题，但没人能签核一个从未被提出来的主题。 |
| 🛑 sign-off（政策团队修改主题清单） | 流程停下，把每个问题的清单摆给政策团队增、并、改名或删除；签核后的版本固化为一个文件供归类读取，此后再改动就以变更的形式可见。 |
| 每个回复：归入一个或多个主题 | 一个 Dynamic workflow 按回复批次扇出，每个工作者返回主题 ID 和它所依据的原文片段，这样审阅人能对着原文核对归类，而不必凭空相信。 |
| 🛑 sample（分析师核验归类） | 抽样按事先定好的规则执行；界面记录每一次勾选与取消，正是这些记录产生了用来衡量工具的人与人基线。 |
| 主题计数与原始回复的看板 | 计数由已记录的归类算出，绝不取自模型对自己结果的复述；每个计数都能追到其背后的回复。 |
| 分析师综合结论 | 见检查点：结论由人看着看板写出；被标记为"不属于任何主题"的回复退回主题清单，而不是塞进最接近的那个主题。 |
| 🛑 review（政策负责人） | 搭建没有任何从分析通往政府回应的路径；负责人在这些内容被使用之前审阅主题和归类方式，来源也说这一步始终会发生。 |

**检查点：** `sign-off`：主题清单就是这次征询对"自己在问什么"的定义，所以由主办这次征询的团队批准，而归类步骤读的是批准的版本，不会重新生成主题。`sample`：分析师对能读到全文的回复重新编码，其中做过双人复核的那部分给出人与人的一致率——没有它，工具的一致率分数就没有标尺。`review`：在分析结果进入政府回应之前，官员要审阅主题以及回复的归类方式；搭建本身没有发布能力，所以这是一道真正的关口，而不是一条通知。

**与来源相比：** 来源出自 2025-05 到 2026-02，实例本身都在 2025 年：两份 i.AI 评估、一份 GOV.UK 新闻稿，以及苏格兰政府的评估报告。两份评估 PDF、新闻稿和报告本轮没有重新打开；本月打开的是 [GOV.UK 的 Consult 页面](https://www.gov.uk/government/publications/consult-register-your-interest/consult-ai-tool)、[一份议会书面答复](https://questions-statements.parliament.uk/written-questions/detail/2026-10-09/33320)和[一份厂商基准页](https://www.blits.ai/ai-use-cases/public-consultation-response-analysis)。此后有这些变化：约束条件已经从"能不能做"变成"能不能拿到权限"——GOV.UK 2026-07-22 的页面说需求超出容量，以候补名单方式管理，全面跨政府推广计划在 2027 年，所以在 2026 年团队并不能随手采用。2026-10-30 的一份书面答复把 Consult 列入投产使用的工具，Consult、Extract、Minute 与 Parlex 四个合计每周记录超过 1,000 次登录——这是四个工具的数字，不能当作 Consult 单品的用量。现在还存在第二个实际运行的搭建：交通部与艾伦·图灵研究所共建的 Consultation Analysis Tool，用模型集成提出主题，由人在随机样本上验证主题集，再把全部回复归类；它报告已分析 200,000 条回复、超过 8,000,000 词，与人工编码者的原始一致率 92%，盲测 F1 为 0.75，在测试的三个问题上未发现系统性偏差，按族裔的差异在 3 个百分点以内且有利于少数群体。它自己的那句告诫正是本条目需要的：若不经人工验证主题集，它只能找到约 75% 的人工主题——这恰恰是签核这一步存在的理由，而不是它的脚注。这里有两个数字仍是建模而非实测——交通部 50% 到 70% 的节省是相对"全部人工编码"的反事实，IWC 那次 240 英镑与 22 个专家小时同理。最新的实践细节仍是 IWC 那一条：每条回复的审阅时间中位数为 16 秒，12% 的回复被审阅人添加了"New theme"。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 把每个征询问题的自由文本回复载入 Consult（i.AI）。它对全部回复（而非抽样）做主题建模，并为每个问题提出一份较长的主题清单 [[1]](#sources)。
2. 🛑 **签发**：负责这次征询的政策团队逐个问题审阅生成的主题清单，在归类开始前可以增加、修改或删除主题 [[1]](#sources)。
3. 由 LLM 把每条回复归入一个或多个已签核的主题 [[1]](#sources)。
4. 🛑 **抽检**：分析师在审阅界面中打开单条回复，勾选或取消主题。在 DWP 的评估中，125 名审阅人每个问题最多核对了 5,000 条回复，其中每个问题有 1,000 条由两人重复审阅，用来衡量两个人之间的一致程度 [[1]](#sources)。在首次正式使用（苏格兰政府）中，专家审阅了每一条回复 [[2]](#sources)。
5. 检查缺失的主题：审阅人可以标记某条回复不属于任何主题，这能暴露签核后的清单是否漏掉了一大类回复 [[1]](#sources)。
6. 政策制定者借助看板（主题频次加原始回复）撰写结论 [[1]](#sources)[[2]](#sources)。
7. 🛑 **审阅**：在分析结果进入政府回应之前，官员始终要审阅主题以及回复的归类方式 [[2]](#sources)。

**产出：** 按问题整理的主题框架，附计数和关联的原始回复，用于撰写公开发布的征询分析和政府回应。
**失败模式 → 防护：** 签核后的主题清单漏掉一大类回复 → 审阅人标记“没有合适的主题”，并重新审视清单。不同回复群体之间存在偏差 → 按自报的残障状况做平等性分析（DWP 的实例中未发现偏差）[[1]](#sources)。过度信任归类结果 → 用两人重复审阅得到的人与人基线（F1 0.710）来对照 Consult（F1 0.816）[[1]](#sources)。

## 公开实例

覆盖度（截至 2026-11-06）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [New workflows for empty categories](../../../../../research/2026-11-new-workflows.md)。更多实例补充于 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [i.AI, Consult Evaluation: DWP Pathways to Work](https://assets.publishing.service.gov.uk/media/68f63fe01c9076042263f0bd/evaluation-report.pdf) (2025-08-27)。DWP 的正式征询：125 名审阅人核对了 Consult 的主题归类；并与人与人之间的一致程度作了对比。"The reviewer made no changes to Consult's mapped themes for 73% of responses.". *第一手：是；可信度：高。*
- [GOV.UK, Humphrey AI tool reviews consultation responses](https://www.gov.uk/government/news/government-built-humphrey-ai-tool-reviews-responses-to-consultation-for-first-time-in-bid-to-save-millions) (2025-05-14)。苏格兰政府化妆品征询，2,000 多条回复，六个问题；专家完善了主题并审阅了每一条回复。"an F1 score (a common measure of alignment for AI tools) of 0.76"。*第一手：是；可信度：中。*
- [i.AI, Consult Evaluation: Independent Water Commission Call for Evidence](https://ai.gov.uk/evaluations/consult-evaluation-independent-water-commission-call-for-evidence/) (2025-10)。第三次正式使用；50,000 多条回复；两组审阅人与 Consult 作对比。"for 64%–69% of responses, reviewers made no changes to Consult’s theme suggestions"。*第一手：是；可信度：高。*
- [GOV.UK, Ground-breaking use of AI saves taxpayers’ money](https://www.gov.uk/government/news/ground-breaking-use-of-ai-saves-taxpayers-money-and-delivers-greater-government-efficiency) (2025-10-16)。IWC 实例的成本和专家核查时间。"The AI tool categorised responses into themes in around 2 hours, costing £240 and experts only needed 22 hours to check the results.". *第一手：是；可信度：高。*
