# 差异审阅式笔记库维护

**工具变体：** `claude-code-obsidian`

## 背景

很多人把个人笔记（会议笔记、阅读笔记、项目页面）以纯文本文件的形式放在一个文件夹里，这个文件夹叫笔记库（vault），并且要花不少时间整理：归档新笔记、建立链接、把昨天会议的转写稿放进去。智能体可以根据口述的指令做这些整理工作，但它并不总是完全照要求去做，还可能编造日期，或者改动了本该保持原样的内容。所以笔记的主人在每处改动被保留之前都要先看一遍，用的是 git：一种记录文件夹里每一处改动、以便对比和撤销的工具。智能体负责修改，主人阅读 diff 并说明要改什么，只有主人决定什么能成为笔记的一部分；笔记是主人自己的记录，其中悄悄混进的错误可能几个月都没人发现。

**术语：**
- **笔记库（vault）**：以纯 Markdown 文件存放的一个笔记文件夹，这里用笔记应用 Obsidian 打开。
- **git**：记录文件夹里每一处改动的工具，可以恢复早先的版本。
- **diff**：一次改动新增和删除的行的清单。
- **提交（commit）**：把审阅过的一组改动保存成 git 历史中的一个永久节点。
- **行内批注**：主人直接写在文件里的备注，这里写成 HTML 注释（`<!-- USER-COMMENT: ... -->`），供智能体找到并处理。
- **口述**：对着设备说出指令，由语音转文字打成文本。
- **摩擦点**：智能体反复出错或让主人反感的某种做法，例如编造日期、跳过步骤。
- **`CLAUDE.md`**：一份常驻指令文件，智能体在每次会话开始时读取。

## 用智能体搭建

**形态：** `skill`。一个人在自己在场的对话里编辑自己的笔记库，并且在保存每处改动之前先审阅，所以 skill 加上笔记库里的 `CLAUDE.md` 就够了；除一项权限设置之外，不需要额外的工作者或强制规则。

**需要：** 以 git 仓库形式存在的笔记库，并在库之外做备份（外置硬盘或系统备份）；笔记库里的一份 `CLAUDE.md`，写明库的约定（文件夹结构、笔记格式、“绝不编造日期，留占位符”）；每项重复性工作一个 skill，例如归档笔记，或从会议记录工具的本地文件同步会议转写稿；主人的口述工具或键盘。会议转写稿和个人笔记里可能含有他人的信息：把笔记库放在主人自己的机器上。

| 步骤 | 搭建方式 |
|---|---|
| 口述指令 | 主人在智能体会话里说出或输入请求。 |
| 智能体通过技能编辑笔记库 (同步转写稿、归档笔记) | 每项重复性工作一个 skill，按名称调用（例如 `/sync-meetings`），再加上 `CLAUDE.md` 里的约定。 |
| (智能体处理行内批注 ⟲ 🛑 review (git diff)) | 主人在 git 里打开 diff，加上 `<!-- USER-COMMENT: -->` 批注，让智能体读取并处理；重复到 diff 可以接受为止。见“检查点”。 |
| 提交 | 审阅之后由主人提交。 |
| 从会话日志中挖掘摩擦点 → 更新智能体指令 | 主人不时运行的一个 skill：读取主人机器上保存的对话日志，列出反复出现的纠正并引用原话，提出对 `CLAUDE.md` 的修改，由主人决定是否采纳。 |

**检查点：** `review`：skill 在每次编辑任务结束时说明改了什么，然后停下；主人在 git 里阅读 diff。把 `git commit` 设为需要询问（或者直接拒绝，由主人在自己的终端里提交）的权限规则，意味着智能体不能自己把改动保存成提交；git 历史加离线备份，让错误的修改可以撤销。开启详细输出可以看到智能体读取了哪些文件。

**与来源相比：** 来源出自 2026-01。来源用 Claude Code 的 skill、口述、本地会议记录工具和 Obsidian 搭出这套做法；它自己的配置只是一个人的配置，所以这套搭建方式是依据它做出的设计。来源提到 Claude Code 里 skill 和斜杠命令现已合一，意思是 skill 可以像命令一样按名称运行。摩擦点分析依赖于智能体的对话历史保存在主人的电脑上；你的环境是否保留这份历史，需要自己确认。来源的作者说摩擦点的发现会反馈到对 `CLAUDE.md` 的修改；这套搭建方式不对其效果作任何断言。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 主人通过口述（用 Wispr Flow 口述工具）把指令输入智能体会话 [[1]](#sources)。
2. 智能体（Claude Code）通过技能处理 Obsidian 笔记库，例如把 Granola 的会议转写稿连同时间戳和元数据同步成笔记 [[1]](#sources)。
3. 🛑 **审阅**：主人在 git 中打开智能体的改动并阅读 diff，因为“智能体并不会完全照我说的去做”[[1]](#sources)。
4. 主人在 diff 上留下行内 `<!-- USER-COMMENT: -->` 批注，让智能体逐条处理。重复这一过程，直到 diff 通过 [[1]](#sources)。
5. 主人做好备份（git、外置硬盘、Time Machine），并开启详细输出，以便看到智能体读取了哪些文件 [[1]](#sources)。
6. 主人定期让智能体分析会话消息中的摩擦点（编造日期、跳过步骤），把发现转成对 CLAUDE.md 的修改 [[1]](#sources)。

**产出：** 一个更新后、有版本记录的笔记库，以及供下一次运行使用的修订后的智能体指令。
**失败模式 → 防护：** 智能体无视指令或编造日期 → 用行内批注做 diff 审阅，并把摩擦点分析的结果反馈到 CLAUDE.md。笔记丢失或被覆盖 → git 加离线备份。
**与相近工作流的区别：** AWF-0030 议题树研究（Issue-tree research）产出研究简报，AWF-0031 处理收件箱。本工作流维护的是个人笔记库，智能体的每一处改动都以 diff 形式审阅。
