# 按置信度分流的会议工单

**工具变体：** `n8n` · `jira` · `slack-huddles` · `granola`

## 背景

团队开完会，总得有人把商定的事项变成团队跟踪系统里的工单，每张都有负责人、截止时间，以及足够让别人开工的细节。这件事挤在两场会议之间做，所以任务常常被漏掉，或者写得太单薄，上下文就丢了。这里由智能体读会议转写稿，提取待办，到代码和已有工单里找上下文，再写出工单。负责人和承诺都明确的条目直接变成工单。负责人不清楚或时间含糊的条目则等人批准，因为负责人写错，会把别人的活派到不该派的人头上，而随口一句“我们大概应该……”也未必是一项承诺。

**术语：**
- **huddle**：Slack 等聊天应用里简短、随意的语音通话，结束后可以发布转写稿。
- **待办（action item）**：会上有人答应去做的任务。
- **工单（ticket）**：在 Jira 等跟踪系统里记录一项工作的条目，有负责人和状态。
- **验收标准（acceptance criteria）**：这项工作必须满足什么条件才算完成。
- **故事点（story points）**：团队对一项工作大小的粗略估计。
- **few-shot 示例**：放在提示词里的少量范例，向智能体示范对这个团队来说什么算待办、什么不算。
- **负责人置信度**：提取结果对“谁负责”有多大把握：明说了（明确）、可以推断（隐含），或根本没提（未分配）。

## 用智能体搭建

**形态：** `service`。转写稿一发布就启动一次运行，现场没有人，人只看到模糊条目的审批卡片，以及工单被改写的通知。

**需要：** 一种在转写稿出现在指定频道时启动运行的方式，例如由工作流工具或小型 webhook 处理的 Slack 事件；聊天应用的连接器（MCP 服务器），用来读转写稿、发审批卡片；跟踪系统的连接器，用来搜索和创建工单；代码仓库的读取权限；用于解析姓名的团队名单；一份纳入版本控制的 few-shot 示例文件。转写稿记录了人们在会上说的话：只在成员本来就能看到它们的频道里运行。

| 步骤 | 搭建方式 |
|---|---|
| huddle 结束，转写稿发布 → 跳过 3 分钟以内的 huddle | 触发器只在 huddle 持续 3 分钟及以上时才启动一次 `claude -p` 或 Agent SDK 运行，并把名单传进去。 |
| 提取待办（负责人置信度、截止时间、原文引句） | 一个 skill，里面有提取字段结构和 few-shot 示例，返回结构化的条目。 |
| 每个待办：搜索代码和已有工单 → 信息完整的工单（验收标准、链接、估时） | 内置子智能体，每个条目一个，通过连接器搜索仓库和跟踪系统，返回工单草稿。 |
| 负责人和承诺都明确：在 Jira 中创建 \| 模糊：🛑 action | 由脚本而不是智能体，根据负责人置信度字段来判定。它创建明确的工单，并把每个模糊的条目作为 Slack 卡片发出。见“检查点”。 |
| 跟踪已创建工单的修改 | 第二个定时任务（云端定时任务，或由自己的调度器启动 `claude -p`），把每张已创建的工单与它后来的状态做对比。 |
| 大幅改写：🛑 review (优化提示词) → 更新 few-shot 示例 | 向提示词的维护人发一条 Slack 通知，由他修改示例文件。 |

**检查点：** `action`：模糊的条目以 Slack 卡片发出，有四个选项（原样创建、分配给我、修改、丢弃），在有人选定之前不创建任何工单。这类条目的创建工单凭据只在脚本手里；智能体能发卡片，不能创建工单。`review`：对比发现大幅改写时，维护人收到通知，去修改提示词或示例；智能体不会自己改自己的示例。

**与来源相比：** 来源出自 2025-12 至 2026-10。来源 1 用工作流工具（n8n）调用语言模型来搭建这条流水线；这套搭建方式用的是通用智能体，沿用同样的提取字段结构和 few-shot 示例，并把分流放在一个脚本里。来源 2 描述的是另一种安排：技术项目经理把转写稿粘贴到内部应用里，每张建议的工单创建前都要审阅，所以那是辅助版本，不是这里的分流。2026-11 时，来源 1 的页面只能部分读出文字（代码清单被折叠了），公开实例里的数字没有重新核对。这套搭建方式不声称任何审批占比或节省的时间。来源 1 所述每季度更新示例的做法，留给维护人按自己的节奏安排。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 当 Slack huddle 的转写稿发布到指定频道时，触发一个自动化工作流（n8n）；3 分钟以内的 huddle 会被跳过，发言轮次会被合并，并拉取团队名单用于姓名解析 [[1]](#sources)。
2. 带有团队专属 few-shot 示例的语言模型（LLM）把具体的待办提取成结构化字段：带置信度的负责人（明确、隐含、未分配）、截止时间和紧急程度、依赖、类型，以及转写稿中的原文片段 [[1]](#sources)。
3. 对每个条目，流水线（工作流中的自动化步骤）搜索代码库和已有工单，生成信息完整的 Jira 工单：摘要、描述、3-5 条验收标准、技术说明、相关文件和工单、标签、故事点 [[1]](#sources)。
4. 🛑 **操作**：模糊的提取结果（负责人不明、时间含糊）不直接创建，而是发到 Slack 审批卡片，可选择原样创建、分配给我、修改或丢弃；这一步能拦下约 15% 的提取结果 [[1]](#sources)。有把握的条目直接在 Jira 中创建。
5. 🛑 **审阅**：流水线把已创建的工单与其后来被编辑的状态做对比；大幅改写会触发 Slack 通知，提示审阅提示词，few-shot 示例则每季度根据失败案例更新 [[1]](#sources)。

**产出：** 链接到会议片段和相关代码的 Jira 工单，以及一个等待审批的模糊条目队列。
**失败模式 → 防护：** 含糊的闲聊（“我们大概应该……”）产生幽灵任务 → 用 few-shot 示例把这类话标为非待办，低置信度条目走 Slack 审批 [1]。负责人错误 → 设负责人置信度字段，未分配的条目进入审批 [1]。质量漂移 → 用编辑距离做反馈闭环 [1]。希望每张工单都经过审阅的团队使用辅助版本（RADAR：创建任何工单前先审阅、编辑、选择）[2]。
**与相近工作流的区别：** 最接近的是 AWF-0086（模板驱动的会议纪要）：它产出的纪要由人在传阅前修正。本工作流的交付物是直接写进跟踪系统的工单。智能体自己创建有把握的条目，人只处理模糊的约 15%，以及被大幅修改的工单。
