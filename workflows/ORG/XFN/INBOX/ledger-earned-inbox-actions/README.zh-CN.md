# 账本赢得授权的邮箱操作

**工具变体：** `claude-scheduled-task` · `gmail` · `outlook`

## 背景

没读的邮箱是一件做不完的杂务：大部分邮件是垃圾或例行的，只有少数真正重要，而误删一封的代价比省下的几分钟大得多。让智能体来清理邮箱，就带来一个问题：该信任它到什么程度。这里的智能体只负责提请求，自己从不碰邮箱。每个请求的操作（删除邮件、标为已读、存一份回复草稿）都交给另一个持有邮箱凭据的闸门，由负责人在手机上批准或拒绝。账本按操作类别记录这些决定：负责人一直批准的类别，就赢得不必询问、自动执行的资格；一直被拒绝的类别，则退回逐次询问。每一种新的请求仍由负责人把关，每次升级都要负责人确认，每封回复都由负责人亲自发送，因为删除邮件无法撤销，回复又代表负责人本人说话。

**术语：**
- **闸门（gate）**：一个小程序，持有唯一的邮箱凭据，接收智能体的请求，只在允许时才执行。
- **账本（ledger）**：负责人每一次批准和拒绝的记录，按每个邮箱里的每类操作分别保存。
- **级别（L0、L1、L2、L3）**：智能体不经询问可以做多少。L0 时每个请求都要等负责人；L1 时常规请求自动通过（例如来自负责人之前批准过的发件人的删除请求），新的请求仍要等待。L2 是草稿所能达到的最高级别，所以回复始终由负责人发送；L3 是删除和标为已读将来某天可能达到的悄悄执行的级别。
- **升级与降级**：一类操作在获得足够多批准后升一级，或在被拒绝太多次后退回逐次询问。
- **标为已读**：把邮件标记为已读，使它离开未读列表。
- **上限（cap）**：一类操作每小时、每天最多可以执行多少次请求的限制。

## 用智能体搭建

**形态：** `service`。运行按计划启动，现场没有人，负责人只看到审批请求和简报。

**需要：** 你自己写的一个闸门：一个小型 MCP 服务器或程序，持有 Gmail 和 Outlook 的凭据，只向智能体开放三个请求工具（删除、标为已读、存草稿）。一个由闸门写入的账本，例如一张数据库表，按邮箱、按操作类别、每个决定一条记录。一个能联系到负责人手机的渠道，例如带批准和拒绝按钮的聊天或推送消息。不给智能体邮箱凭据，不给发送工具，也不给修改账本的工具。

| 步骤 | 搭建方式 |
|---|---|
| 定时运行：读取未读邮件 (Gmail, Outlook) | 云端定时任务，或者用自己的调度器启动 `claude -p` 或一个 Agent SDK 程序，每天运行几次。智能体通过闸门的读取工具读邮件。 |
| 回读上次运行以来负责人的决定 → 更新发件人规则 | skill 的第一条指令：读取闸门返回的决定和备注，把它们变成 skill 旁边一个文件里的规则。 |
| 每封邮件：请求删除 \| 标为已读 \| 存为草稿 | 一个 skill，为每封邮件选定三种请求之一，并调用对应的闸门工具。 |
| 任务处于 L0 或发件人为新：🛑 action → 任务处于 L1 且发件人已知：闸门在每小时和每日上限内执行 → 账本记录每个决定 | 闸门自己的代码，不是智能体：它在账本里查出级别，发出手机请求，或在上限内直接执行，并记录结果。 |
| 最近 100 次中拒绝 ≤2 次：🛑 sign-off → 最近 10 次中拒绝 3 次：降回逐次询问 | 两个计数都由闸门计算。它把某类操作标为有资格升级并请负责人确认；降级则自动进行。 |
| 运行结束的简报与账本核对 | 简报由 skill 写出；闸门把其中的数量与账本核对。 |
| 草稿：🛑 action (负责人亲自发送) | 见“检查点”。 |

**检查点：** `action`：请求停在闸门，直到负责人在手机上批准或拒绝；智能体没有邮箱凭据，没有这一步就无法行动。草稿最高只到 L2，智能体也没有发送工具，所以每封回复都由负责人在自己的邮件客户端里发出。`sign-off`：只有负责人确认之后，闸门才会提升某类操作的级别。级别、计数和上限都在闸门的代码和账本里，而不在 skill 的指令里，所以智能体改不了它们。

**与来源相比：** 来源 1 出自 2026-11，描述的是 Claude 里的一个定时任务，配有自己的闸门和账本，作者自 9 月下旬起运行。无需另外查找更新的记述。闸门和账本是作者自己的组件，不在本目录的构件之列；这套搭建方式只是说明你得自己写。来源报告的是一个人的实验：它说 100 次决定的门槛适合请求很多的删除，不适合很少出现的草稿，作者打算调整。这套搭建方式没有规定门槛的具体数字。来源里说存在智能体自己记忆中的规则，在这里是 skill 旁边的一个文件。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 一个定时的 Claude 任务（即智能体）每天在 Gmail 和 Outlook 中读取几次未读邮件。对每封邮件，它从三种操作中选一种：删除、标为已读，或存一份回复草稿。它不能发送，也不持有邮箱密钥 [[1]](#sources)。
2. 每个变更请求都交给闸门，只有闸门持有凭据。在 L0 级别，每个请求都要等待。🛑 **操作**：负责人在手机上批准或拒绝 [[1]](#sources)。
3. 账本记录每个决定，按任务、按邮箱分别保存。只有明确的批准、拒绝或“标记为错误”才算数；沉默不计入 [[1]](#sources)。
4. 🛑 **签发**：某个任务（某个邮箱里的某一类操作）最近 100 次决定中被拒绝的不超过 2 次，就有资格升一级，并由负责人确认。在 L1 级别，常规请求（例如来自已批准发件人的删除）自动通过；新发件人仍要等待。最近 10 次中被拒绝 3 次，该任务退回逐次询问 [[1]](#sources)。
5. 每个任务在每个级别都有每小时和每日的上限，由闸门执行 [[1]](#sources)。
6. 每次运行开始时，智能体回读上次运行以来的决定和备注，把它们变成规则（例如某个发件人保持未读）。它也从负责人发出的邮件和对草稿的修改中学习 [[1]](#sources)。
7. 每次运行以一份简报收尾，说明查看了什么、做了什么、在等什么。闸门把数量与账本核对。🛑 **操作**：草稿最高只到 L2，所以回复始终由负责人亲自发送 [[1]](#sources)。

**产出：** 一个邮箱：已赢得授权的任务（目前只有删除）自行运行，其余的等待批准；另有按任务记录的账本，决定每个任务的自主级别。
**失败模式 → 防护：** 一个全局信任设置对大多数任务都不合适 → 按任务建账本，并设升级与降级规则。数量失控 → 每小时和每日上限（“37 封 Gmail 删除请求被上限拦下”）。简报与实际脱节 → 闸门交叉核对数量。罕见任务（草稿）永远达不到 100 次决定的门槛 → 负责人打算按任务频率调整门槛。
**与相近工作流的区别：** 最接近的是 AWF-0031 每日邮箱分诊（Daily inbox triage，辅助：每封邮件由人发送，每个邀请由人接受，智能体只起草）。本工作流中智能体通过闸门直接操作邮箱，每类操作凭负责人的决定记录赢得自主权，并有升级签发和自动降级。检查点安排和自主程度不同，交付物也不同（邮箱确实被清理了，而不是简报加草稿）。AWF-0145 是日历审计，与邮件无关。
