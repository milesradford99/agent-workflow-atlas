# 可决策的投保件分诊

**工具变体：** `cytora` · `kalepa`

## 背景

企业想为某项风险投保，比如一家工厂或一支车队，通常要通过经纪人，由经纪人向保险公司发送投保件（submission）：一封附有附件、表格和电子表格的邮件，描述要投保的对象。保险公司的核保员决定是否承接这项风险以及定什么价。核保员看到之前，得有人先阅读投保件，把关键事实录入保险公司的系统，补充外部信息，再判断它是否符合保险公司承保的范围。这很慢，而且团队能看多少投保件，取决于有多少人来读。这里由智能体把每份投保件转成结构化数据，补充信息，评估契合程度，排进一个按优先级排序的队列，对智能体拿不准的件由人来核对。每个风险仍由核保员评估、定价、承保或拒保，因为这个决定动用的是保险公司的资金。

**术语：**
- **经纪人（broker）**：替客户向保险公司安排风险的中介。
- **投保件（submission）**：经纪人提交的、描述风险的一整套文件。
- **ACORD**：一种广泛使用的标准保险表格。
- **险种（line of business）**：保险的一个类别，如财产险或海运险，每个险种有自己的数据字段（数据模式）。
- **核保员（underwriter）**：决定是否承接风险以及承保条件的人。
- **承保偏好（appetite）**：保险公司愿意承保的风险类型及条件。
- **报价、承保、拒保**：给出价格；接受风险并使保障生效；拒绝。
- **补充（enrich）**：在投保件所述之外，加入保险公司自己的记录和外部来源的数据。
- **核保工作台**：核保员的工作界面和队列。

## 用智能体搭建

**形态：** `service`。投保件到达收件箱时没有人守在键盘前，人只看低置信度的件和排好序的队列。

**需要：** 对投保件收件箱的读取权限；每个险种一份数据模式文件，列出要提取的字段；由核保团队维护、作为参考文件的承保偏好和优先级规则；连接保险公司自己记录和所用外部数据的连接器或脚本；让结构化投保件落地的队列或核保工作台。不要给智能体任何报价、承保或拒保的工具，也不要让它回复经纪人。投保件包含客户的商业和个人数据，所以要使用经批准可处理这类数据的环境。

| 步骤 | 搭建方式 |
|---|---|
| 经纪人投保件 → 数字化为险种数据模式 | 云端定时任务，或你自己的程序启动 `claude -p` 或 Agent SDK 程序，取走新到的投保件。一个 skill 按对应险种提取字段（包括其他语言的文档），并为每个字段记录出自文档的哪里以及置信度。 |
| 补充内部 + 外部数据 | MCP 连接器或脚本，每个数据源一个，由 skill 调用。 |
| 承保偏好 + 优先级评分 | skill 套用承保偏好文件，写出评分和理由。 |
| 高置信度：直接进入队列 \| 低置信度：🛑 review | 脚本把每个字段的置信度与阈值比较。高于阈值的写入队列，其余进入验证队列。 |
| 🛑 sign-off (核保员评估、报价、承保或拒保) | 见“检查点”。 |

**检查点：** `review`：低置信度的投保件被挡在核保队列之外，连同提取出的字段和对应的原文段落一起发到验证队列；由人更正后放行。阈值写在脚本里，所以智能体无法调低。`sign-off`：智能体没有报价、承保或拒保的工具，所以由核保员在下游系统里完成。

**与来源相比：** 有日期的来源出自 2025-11 至 2026-11，另有三份没有日期。多数来源是厂商或承保机构对产品（Cytora、Kalepa）的叙述，这些产品在自己的平台里用自己的模型、数据源和与核保系统的集成完成这项工作；这套搭建方式用通用智能体加数据模式和承保偏好文件，并不重现它们。它们的数字见“公开实例”，不是对这套搭建方式的说明。智能体为每个字段报出的置信度只是一个估计，在信任某个阈值之前，应当用一批被人工更正过的样本去核对它。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 系统接收非结构化的投保件，按承保机构的数据模式转换为结构化的、'decision-ready' 的风险 [[1]](#sources)[[2]](#sources)。
2. 系统补充外部数据，并按承保偏好和策略排序 [[3]](#sources)[[4]](#sources)。
3. 系统让高置信度的投保件直接进入核保队列 [[2]](#sources)。
4. 🛑 **审阅**：低置信度的投保件停在 'human-in-the-loop validation checkpoints'，由人在投保件进入队列前核对提取出的数据 [[2]](#sources)。
5. 🛑 **签发**：核保员在下游系统中评估、报价并承保（或拒保）[[1]](#sources)[[4]](#sources)。

**产出：** 核保工作台中按优先级排序的结构化投保件队列。
**失败模式 → 防护：** 提取错误流入定价 → 置信度阈值和验证检查点。核保员只看到收件箱的一小部分 → 全收件箱分诊（Paragon）和拒保分流。

**近期实践（2026）：**
- 步骤 2：Hiscox 英国高净值客户模型按风险偏好对经纪人投保件分类，以简化核保员的工作流（Hiscox 2025 年报）。[[5]](#sources)
**与相近工作流的区别：** 上文的 Hiscox 报价起草会产出带定价的报价。本工作流的产出是排好序的投保件队列，每个风险仍由核保员定价。AWF-0022 形态相近，但产出的是应付款项，而不是核保决定。

## 公开实例

覆盖度（截至 2026-11-06）：**部分**：第一手实例只覆盖流程的一部分，或检查点设在别处。收集与复核见 [Second collection pass](../../../../../research/2026-11-second-pass.md)。

- [Ivans, Arch Insurance submission intake](https://www.ivans.com/blog/posts/arch-insurance-ai-submission-intake-cytora/) (2026-05-26)。四条业务线在不到三个月内上线。"from two to three days down to two hours"。*第一手：厂商；可信度：中。*
- [Cytora, Zurich scales Agentic AI](https://cytora.com/risk-flow-center/blog/zurich-scales-agentic-ai-to-5-countries-in-90-days-proving-the-target-model-for-itsglobal-rollout) (n.d.)。在 Zurich 各国分支推广。"manual triage time falling from 75 minutes to 15 minutes"。*第一手：厂商；可信度：中。*
- [Markel, AI can accelerate underwriting](https://www.markel.com/insights-and-resources/insights/ai-can-accelerate-underwriting-people-must-remain-accountable) (2026-11-02)。承保机构自己的叙述；核保员最终确定每一份报价。"a 65% quote-to-submission ratio"。*第一手：是；可信度：高。*
- [Kalepa, Paragon case study](https://kalepa.com/case-studies/paragon-doubled-quote-to-bind-rate) (n.d.)。整个收件箱在 90 天内全部经过分诊；引述 Paragon 管理层的话。"somewhere around 98 to 99% accurate now"。*第一手：厂商；可信度：中。*
