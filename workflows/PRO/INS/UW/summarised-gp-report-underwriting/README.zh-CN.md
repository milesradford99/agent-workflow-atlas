# 全科医生报告摘要核保

**工具变体：** `aviva-in-house` · `vitality-in-house`

## 背景

保障类保险（如寿险、重疾险）在客户身故或确诊严重疾病时赔付。有人投保时，保险公司可能要向其家庭医生（GP，全科医生）索取一份体检报告。核保人（underwriter）是保险公司里决定是否承保以及承保条件的专业人员，他要在报告里找出会改变风险的病况和检查结果。这类报告可能超过 90 页，其中大部分内容与决定无关，所以读起来费时，也可能漏掉关键细节。这里由 AI 模型过滤无关细节，并归纳关键医学事实。核保人阅读摘要，每个案件都由核保人作出决定，因为这个决定关系到一个人能否获得保障；事后还要对保险公司的工作进行审计。

**术语：**
- **保障类保险（protection insurance）**：在身故、严重疾病或丧失工作能力时赔付的保险，而不是对财产损失赔付。
- **重疾险和严重疾病险（CI）**：确诊所列病况时一次性给付保险金的保险。
- **全科医生（GP）体检报告**：申请人的医生出具的、关于其病史的报告。
- **核保人（underwriter）**：决定是否承保以及承保条件的人。
- **顾问（adviser）**：替客户办理投保的中介人，也是接收决定的人。
- **投保后审计**：事后对已作出的决定进行复查，检查决定是否妥当。

## 用智能体搭建

**形态：** `skill`。一位核保人一次处理一份申请，并且全程在对话中，所以一个为这位核保人摘要一份医学报告的 skill 就够了。曾与 `service` 比较过，因为报告可以在到达时就摘要；但无论哪种做法都由人阅读每份摘要，所以保留较小的形态。

**需要：** 作为文件的全科医生报告；保险公司针对各产品列出的、需要关注的病况和检查结果，作为参考文件放在 skill 旁边；核保人已在使用的核保手册。健康数据是最敏感的个人数据之一：只使用经所在机构批准、可处理这类数据的环境，不要给智能体邮件或顾问通信工具，也不要给它保单系统的写入权限。

| 步骤 | 搭建方式 |
|---|---|
| 个人保障类保险申请 → 收到全科医生（GP）体检报告 (多达 90+ 页) | 核保人把一份申请的报告文件交给 skill。 |
| GenAI 过滤无关细节 + 归纳关键医学事实 | skill 通读整份报告，按固定标题（病况、用药、检查与结果、生活方式、转诊）写出摘要，每条事实都标明出自哪一页，并在末尾列出它判断为无关而略去的部分。报告特别长时，由内置子智能体各取一段页码，返回其中的事实。 |
| 🛑 review (核保人阅读摘要并作出最终决定) → 把决定告知顾问 | 见“检查点”。 |
| 🛑 sample (投保后审计 + 定期质量复核) | 见“检查点”。 |

**检查点：** `review`：skill 以摘要和被略去部分的清单收尾，然后停下。它从不写出决定；由核保人在保单系统里作出决定，并从那里告知顾问，智能体两件事都没有工具可用。`sample`：审计不属于当次案件。由复核人抽取一批已决定的案件，运行 skill 的检查模式，把保存下来的摘要与完整报告对照，列出报告里有而摘要漏掉的病况；结果由复核人判断。

**与来源相比：** 来源出自 2025-11 至 2026-04。Aviva 和 Vitality 是自研摘要工具，并报告在上线前经过 18 个月测试和准确性验证，Vitality 先从风险较低的案件开始；这套搭建方式没有这样的测试，所以使用前应在已知结果的案件上试用，并与核保人自己的阅读结果对比。Aviva 报告其工具也用于投保后审计。来源没有说明各自的提示词或模型。关于时间和报告长度的数字见“公开实例”，不是对这套搭建方式的说明。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 保险公司对个人寿险、重疾险或严重疾病险的申请需要一份全科医生体检报告 [[1]](#sources)[[2]](#sources)[[3]](#sources)。
2. 生成式 AI 模型分析报告，过滤无关细节并突出关键信息，把「有时超过 90 页」的报告压缩成简明摘要 [[1]](#sources)。
3. 保险公司先从风险较低的案件开始推广，再扩大使用 [[3]](#sources)。
4. 🛑 **审阅**：「Aviva 的核保人将审阅这些摘要并作出最终决定」 [[1]](#sources)。
5. 🛑 **抽检**：投保后审计，以及「定期质量复核和持续监督」 [[2]](#sources)[[3]](#sources)。

**产出：** 对保障类保险申请的核保决定，告知顾问和客户。
**失败模式 → 防护：** 摘要漏掉重大病况 → 经过 18 个月测试，在扩展到重疾险之前对各类病况做准确性验证，从低风险案件开始，持续做质量复核 [1][2][3]。
**与相近工作流的区别：** AWF-0149 是把经纪人提交的案件分诊为带评分的队列；AWF-0155 是起草带定价的经纪人报价邮件。本工作流中智能体浓缩一位申请人的医学证据，每个案件都由核保人决定（辅助）：交付物（基于医学证据的个人风险决定）和检查点都不同。这使 UW 类下有三个各不相同的工作流。

## 公开实例

覆盖度（截至 2026-11-13）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [Aviva, AI underwriting tool launch](https://www.aviva.com/newsroom/news-and-research-overview/news-releases/2025/11/aviva-to-launch-groundbreaking-ai-underwriting-tool/) (2025-11-18)。经过 18 个月测试后推广寿险核保；每个案件由核保人决定。"already processed 1,000 cases in an active test phase"。*第一手：是；可信度：高。*
- [Aviva, extends to Critical Illness](https://www.aviva.com/newsroom/news-and-research-overview/news-releases/2026/03/aviva-extends-industry-first-ai-underwriting-tool-to-critical-illness-cover/) (2026-03-18)。扩展到重疾险；也用于投保后审计。"reduced the time underwriters spend reviewing each case by around half"。*第一手：是；可信度：高。*
- [IFA Magazine, Vitality AI underwriting](https://ifamagazine.com/vitality-launches-ai-powered-underwriting-to-speed-up-adviser-case-decisions/) (2026-04-15)。自研 LLM 生成全科医生报告摘要，试点 18 个月，先做低风险案件。引述了 CEO 的话。"an 81% reduction in GP report length"。*第一手：厂商；可信度：中。*
