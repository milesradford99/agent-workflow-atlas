# 代位追偿线索分诊

**工具变体：** `shift-subrogation` · `megaputer-subrocheck`

## 背景

保险公司赔付一宗理赔之后，如果另一方负有部分或全部过错，可以设法向对方或对方的保险公司追回这笔钱，这叫代位追偿（subrogation）。例如，一位司机因另一位司机造成的车祸获得赔付，保险公司可以向另一位司机的保险公司索赔。要发现这类案件，得读每宗理赔的数据和经办人的自由文本备注，再套用事故发生地所在州的法律；经办人常常忘记转介，追偿时效也可能在不知不觉中过去。这里由智能体在后台扫描每一宗理赔，无论未结还是已结，给每宗打分并写明理由。哪些线索值得追，由追偿专员决定；向对方提出索赔则由理赔经办人去做，因为那是以保险公司名义提出的法律主张。

**术语：**
- **代位追偿（subrogation）**：保险公司赔付自家客户之后，向有过错的一方追回这笔金额的权利。
- **理赔经办人（claims handler）**：负责管理一宗理赔的保险公司员工。
- **追偿专员**：处理代位追偿转介的人。
- **比较过失（comparative negligence）**：由各州规定的规则，在双方之间划分过错，并按受损方自己的过错份额减少可追回的金额。
- **PIP（人身伤害保障）和 MedPay**：车险中不论谁造成事故，都先付保单持有人医疗费用的保障。保险公司能否追回这笔钱因州而异。
- **诉讼时效**：超过这个期限就不能再提起索赔。
- **召回清单**：公布的因缺陷而被撤回的产品清单，可能指向制造商的过错。
- **出租/网约车辆（livery / rideshare vehicle）**：用于营运的车辆。在纽约，这是追回 PIP 的条件之一。
- **索赔函（demand）**：书面要求对方或其保险公司付款。
- **线索（alert）**：系统标出的、有追偿可能的理赔。

## 用智能体搭建

**形态：** `service`。扫描按计划覆盖全部理赔，没有人守着，人只看带评分的线索。

**需要：** 对理赔系统结构化字段和经办人备注的只读权限；团队所用各州规则（比较过失、PIP 和 MedPay、诉讼时效）的参考文件，由追偿团队保持更新；外部数据（召回清单、车辆登记数据）的连接器或脚本；一个在对话之外的存储，记录哪些理赔已评分及其结果；一个让线索进入追偿专员手中的队列。不要给智能体任何联系第三方或写入理赔记录的工具。理赔中可能有医疗信息，所以要使用经批准可处理个人健康数据的环境。

| 步骤 | 搭建方式 |
|---|---|
| 每个未结/已结理赔：读取结构化数据 + 理赔员备注 | 云端定时任务，或你自己的调度器启动 `claude -p` 或 Agent SDK 程序，从状态存储中取出尚未评分或上次运行后有变动的理赔。动态工作流（dynamic workflow）为每宗理赔分派一个子智能体，读取字段和备注。 |
| 套用各州过失与 PIP 法律、召回及外部数据 | 每个子智能体读取各州规则的参考文件，并调用外部数据的连接器或脚本。 |
| 估算责任 + 可追偿金额 → 给线索打分并说明理由 | 子智能体返回评分、估算的责任和可追偿金额，以及驱动评分的理由，每条理由都注明所依据的规则或记录。脚本检查每个诉讼时效日期都是由理赔的日期算出的。 |
| 🛑 review (追偿专员接受或驳回线索) | 见“检查点”。 |
| 🛑 action (经办人推进索赔/追偿) | 见“检查点”。 |

**检查点：** `review`：运行结束时把线索及其理由写入追偿专员的队列；被接受和被驳回的线索写入状态存储，后续运行不再重复。评分较低的理赔也按固定比例抽出一部分放进队列，追偿专员的判断会反馈到评分阈值上。`action`：智能体没有发送索赔函、联系对方或开立追偿案件的工具，所以由经办人在理赔系统里去做。

**与来源相比：** 来源出自 2024-07 至 2026-07。三份来源都是 Shift Technology 自己的案例和访谈，所以本条目说的是一个厂商产品，来源并未展示其内部步骤。Shift Subrogation 在自己的平台里用自己的模型和数据源给理赔评分；这套搭建方式用通用智能体、参考文件和连接器重建这些步骤，并不声称能达到该产品的效果。保持各州规则文件的正确是追偿团队要持续做的工作。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 系统扫描每份理赔档案，包括结构化字段和理赔员的自由文本备注（用 GenAI 归纳），弄清发生了什么、涉及哪些人、其他方是否可能有过错 [[1]](#sources)[[2]](#sources)。
2. 系统套用外部数据：各州比较过失和 PIP/MedPay 规则、诉讼时效、产品召回清单、车辆登记数据（例如确认某辆车是网约车/出租车辆，以适用纽约 PIP） [[1]](#sources)[[3]](#sources)。
3. 系统估算责任和潜在追偿金额，生成带评分的线索，并附上驱动评分的理由和细节摘要 [[1]](#sources)。
4. 🛑 **审阅**：追偿人员审阅线索，而不是逐宗理赔：「我们不再需要审阅每一宗理赔」 [[2]](#sources)。
5. 🛑 **操作**：理赔经办人推进追偿；经办人仍会手动转介理赔，由工具兜住遗漏 [[2]](#sources)。

**产出：** 带责任估算和支撑理由的、按优先级排序的代位追偿转介单，由追偿团队跟进。
**失败模式 → 防护：** 经办人忘记转介导致漏追 → 后台扫描全部理赔，包括已结案的。诉讼时效已过 → 在线索中套用各州规则。理赔员不信任 → 定位为辅助并培训团队 [2]。
**与相近工作流的区别：** AWF-0094、AWF-0095 和 AWF-0096 是决定或沟通保险公司向自家客户赔付多少。本工作流是赔付之后向第三方追回款项；智能体无人值守地筛查全部理赔，人只看线索。交付物和自主程度都不同。
