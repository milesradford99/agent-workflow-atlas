# 基于保单条款的理赔函件

**工具变体：** `voltaire`

## 背景

有人就财产险提出理赔时，保险公司必须书面告知它会赔多少；如果全部或部分拒赔，还要说明依据的是保单中的哪一条措辞。内勤理赔员（desk adjuster，不去现场勘查，而是坐在办公桌前依据档案处理理赔的人）根据理赔档案和保单写这些函件。保单很长：基础条款、各州的修订条款，以及改变其他页面中定义的批单，所以很容易引错版本。写错的函件可能被保险公司退回，甚至引发纠纷。这里由智能体根据理赔文件起草函件，并引用所依据的保单措辞，对于找不到依据的拒赔则拒绝撰写。内勤理赔员修改函件，保险公司批准后才发出，因为作出保障范围决定的是保险公司。

**术语：**
- **内勤理赔员（desk adjuster）**：依据档案远程处理理赔的理赔员，在灾害期间常是临时聘用的。
- **保险公司（carrier）**：出具保单并承担风险的保险公司。
- **保单声明页（dec sheet）**：保单中载明被保险人、保险标的、限额和免赔额的一页。
- **批单（endorsement）**：对保单标准措辞作出修改的附加条款。
- **估损单（estimate）**：对这次损失的维修费用估算。
- **拒赔、部分拒赔**：拒绝整件理赔的函件，或拒绝其中一部分的函件。
- **巨灾事件**：飓风等造成理赔量激增的灾害。

## 用智能体搭建

**形态：** `skill`。一位理赔员一次处理一件理赔，并且全程在对话中，所以一个装有函件流程和保险公司函件格式的 skill 就够了。

**需要：** 以文件形式提供给智能体读取的理赔档案、保单声明页、估损单，以及带批单的完整保单文本；放在 skill 旁边、作为参考文件的保险公司函件格式；一个小脚本，检查草稿中引用的每一句保单原文是否逐字出现在保单文本里；一套经所在机构批准、可处理投保人个人数据的环境。不要接入邮件工具。

| 步骤 | 搭建方式 |
|---|---|
| 理赔档案 + 保单声明页 + 估损单 → 生成引用保单条款的函件 | skill 读取这些文件和保单，选出对应的函件格式，起草函件，每项陈述都对应一段被引用的保单原文及其页码。 |
| 没有支持条款：拦截 ('no relevant policy language found') | skill 运行引文检查脚本。如果拒赔或部分拒赔没有脚本能在保单中找到的引文，skill 就停下来，输出“no relevant policy language found”，不写函件。 |
| 🛑 review (内勤理赔员) → 🛑 sign-off (保险公司批准) → 发出 | 见“检查点”。 |

**检查点：** `review`：skill 最后把草稿连同旁边的引文一起呈现，然后停下；由内勤理赔员修改。`sign-off`：skill 里没有发送步骤，智能体也没有邮件工具，所以由理赔员把函件送交保险公司批准，保险公司在自己的流程中批准。

**与来源相比：** 来源和公开实例出自 2025-11，来自厂商对一场网络研讨会的回顾。Voltaire 的工具在自己的产品里生成函件，内置各保险公司的专用格式；这套搭建方式用通用智能体，把格式放进参考文件，再加一个引文检查脚本，并不重现该产品的行为。来源没有说明该工具如何找到支持条款，所以引文检查是本目录的设计。保险公司的批准是人的步骤，不在智能体的工具范围内。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 生成工具分析理赔档案、保单声明页和估损单，然后从头生成拒赔、部分拒赔或赔付函件 [[1]](#sources)。
2. 如果内勤理赔员试图在没有有效保单条款的情况下拒赔，工具会返回“no relevant policy language found”[[1]](#sources)。
3. 🛑 **审阅**：内勤理赔员修改函件 [[1]](#sources)。
4. 🛑 **签发**：由保险公司批准函件；在使用该工具之前，函件常因保单措辞或语法有误而被“退回”[[1]](#sources)。

**产出：** 经保险公司批准、发给投保人的保障范围函件。
**失败模式 → 防护：** 引用了错误的保单措辞 → 生成器拒绝生成它无法找到依据的拒赔。巨灾期间业务激增、新入职的内勤理赔员多 → 内置各保险公司专用的格式。
**与相近工作流的区别：** AWF-0024 依据审查手册的合同审阅（Playbook contract review）是对照审查手册给合同做批注。这里的产出是以保单为依据、对外发出的保障范围函件，检查点是保险公司的批准。
