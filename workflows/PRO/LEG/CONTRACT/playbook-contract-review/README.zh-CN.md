# 依手册审阅合同

**工具变体：** `harvey` · `spellbook` · `luminance` · `claude-playbook-skill`

## 背景

公司在签署一份由对方起草的合同（供应商的条款、客户的保密协议）之前，要由律师逐条对照公司自己的规则来读：哪些可以接受，哪些不行。这些规则写成一份审查手册。律师的大部分时间花在最后被证明可以接受的条款上，以及一遍遍写同样的修改和说明。智能体负责逐条比对、提出修改后的措辞，并解释每一处改动。凡是偏离手册的条款，仍由律师判断，最后也只能由律师发出，因为律师对这份法律意见负有职业责任，对方会把发出的内容当作公司的立场。

**术语：**
- **审查手册（playbook）**：针对每类条款，写明公司的首选措辞、被对方坚持时可以接受的退让措辞，以及低于它就不签的底线。
- **绿 / 黄 / 红**：条款符合首选立场 / 落在退让范围内 / 越过底线或缺失。
- **修订痕迹（redline）**：记录在 Word 文件里的修改，对方能看到每一处增删。
- **定义术语**：合同中被赋予固定含义的词；改动一个条款，可能使另一个使用同一术语的条款出问题。
- **责任上限与赔偿条款**：一方最多要向另一方承担多少，以及承诺补偿对方损失的条款。两者必须对照着读，因为赔偿条款可能不受上限约束。

## 用智能体搭建

**形态：** `skill`。一位律师一次审一份合同，并且全程在对话中，所以一个装有流程和审查手册的 skill 就够了。

**需要：** `.docx` 格式的合同；作为参考文件放在 skill 旁边的审查手册，每种协议类型一份；能往 Word 文件里写修订痕迹的手段，例如处理文档的 skill 或放在 skill 旁边的脚本；一套经所在机构批准、可以处理保密和受特权保护的客户文件的环境。不要接入邮件工具。

| 步骤 | 搭建方式 |
|---|---|
| 合同 → 判断类型 → 加载审查手册 | skill 的第一条指令：读合同，说出类型，打开 `playbooks/<type>.md`。没有匹配的手册就停下来说明。 |
| 每个条款：对照立场 (绿/黄/红) | 短合同在主对话中完成。长合同由内置子智能体各负责一组条款，返回一张表：条款、手册立场、评级、建议措辞。 |
| 修订痕迹 + 批注 | 由脚本或文档 skill 把修改写进文件的副本，绝不改原件，每处修改配一条批注，说明手册依据。 |
| 一致性检查 | 在主对话中对整份修订稿再过一遍：定义术语、交叉引用、责任上限与赔偿条款。 |
| 🛑 review → 🛑 sign-off → 发出 | 见“检查点”。 |

**检查点：** `review`：skill 最后列出所有黄色和红色条款，附手册立场和建议修改，然后停下；由律师修改修订稿。`sign-off`：skill 里没有发送步骤，智能体也没有邮件工具，所以由律师从自己的邮箱发出。

**与来源相比：** 本条目列出的工具（`harvey`、`spellbook`、`luminance`）是法律行业产品，在 Word 或它们自己的审阅界面里完成这些步骤。通用智能体加一个 skill 是在文件上完成同样的步骤，不在 Word 界面内工作。本条目的步骤没有引用来源，唯一的公开实例讲的是一家律所对起草类工具的一般性试用，不是这套搭建方式。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 智能体判断协议类型并加载对应的审查手册（每个条款的标准立场、退让方案和底线）。
2. 智能体把合同切分为条款，把每个条款对应到手册中的条目，并标出手册要求但合同里没有的条款。
3. 智能体并行地把各条款与手册比对，并给每个条款评为绿、黄或红。
4. 智能体写出 Word 修订痕迹，并用页边批注说明每处修改的原因。
5. 智能体检查修订稿的内部一致性：定义术语、交叉引用、责任上限与赔偿条款是否相互匹配。
6. 🛑 **审阅**：律师审阅黄色和红色事项。
7. 🛑 **签发**：由律师发出。
