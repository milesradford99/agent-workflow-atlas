# 样本调优的合同要素提取

**工具变体：** `hebbia` · `elevate-elm` · `ironclad` · `contractpodai-leah`

## 背景

大型公司往往在共享文件夹里存着成千上万份已签署的合同，却没有一份可检索的记录说明每份合同写了什么：当事方是谁、什么时候到期、是否自动续约、能否转让给他人。合同生命周期管理系统（CLM）正是把这些事实存成字段，所以在公司启用 CLM 之前，律师或合同人员要把全部存量合同读一遍，再把答案逐项录入。这既慢又枯燥，而且两个人读同一条款，记录结果常常不一致。在这个工作流中，智能体读取每份合同，提出字段取值、支撑它的条款原文和一段通俗摘要，并且每一项都链接回原文。律师仍要决定哪些字段重要、在样本上调优指令、对照原文核对结果，并理清相关文件之间的关系，因为公司将依据导入的数据做续约、发通知和风险决策。

**术语：**
- **CLM**：合同生命周期管理系统（contract lifecycle management），用来存放合同并跟踪其关键日期和条款的软件。
- **存量合同（legacy contracts）**：已经签署并归档的协议，区别于正在起草的协议。
- **要素提取（abstraction）**：把合同中的关键事实和条款提取到结构化字段里。
- **去重（dedupe）**：剔除草稿、副本和未签署版本，使每份协议只算一次。
- **主从关系（合同族）**：一份主协议，以及修改它的修订协议和订单；从属文件中的内容可能会覆盖主协议。
- **SME**：领域专家（subject matter expert），这里指对某类条款足够熟悉、能说出正确字段取值的律师。

## 用智能体搭建

**形态：** `project`。只用一个 skill 不够：这项工作要在整个合同组合上并行进行，每个结果都必须以无法跳过的方式对照原文核对，字段定义又是每次运行都要用到的固定知识。

**需要：** 以文件形式存放的合同，放在经所在机构批准、可以处理保密商业文件的环境里；律师编写的字段与风险要求清单，作为参考文件，附上 CLM 的导入格式；每个 CLM 字段一份提示词，作为文件放在 skill 旁边；一张电子表格或数据表，智能体按合同逐份记录每个字段的取值、引用的条款原文及其在文件中的位置；让审阅人能把引用的原文和每个取值并排打开的办法。不要给智能体 CLM 的写入权限。

| 步骤 | 搭建方式 |
|---|---|
| 律师定义字段和风险要求 | 由律师编写的参考文件：字段、什么算风险，以及 CLM 的导入格式。 |
| 盘点并去重存量合同 | 由脚本列出文件，并按名称和内容标出草稿、副本和未签署版本。律师确认范围内的清单。 |
| 为每个 CLM 字段编写提示词 | 一个 skill，每个字段一份提示词，并写明 CLM 可导入的输出格式。 |
| (在代表性样本上提取 ⟲ 🛑 review (律师优化提示词)) | skill 在律师选定的样本上运行，把结果与原文并排展示，并采纳他们对提示词的修改。重复到他们批准为止。见“检查点”。 |
| 每个合同：条款原文 + 通俗摘要 + 标准编码，并链接到原文 | 用动态工作流，或每批合同一个子智能体，套用这个 skill，每份合同返回一行。脚本检查每条引用的条款是否逐字出现在文件中，凡不符的行一律退回。 |
| 🛑 review (律师监督的团队校验) | 见“检查点”。律师还要根据一张“哪份文件修订哪份文件”的表来理顺合同族。 |
| 🛑 sample (准确率指标 + 一致性检查) | 由脚本运行一致性检查（例如结束日期早于开始日期），并抽出样本供审阅。见“检查点”。 |
| 导入 CLM | 由人用已批准的导出文件执行导入。 |

**检查点：** `review`：样本每测完一轮，skill 就停下来，把结果与原文并排展示；律师修改提示词并批准之后，才开始全量运行。全量运行之后，审阅团队打开每个取值的原文链接并更正该行。动态工作流在运行中途不能接收输入，所以这些停顿设在它之前和之后，不在其中。`sample`：由脚本按固定比例抽出若干行交律师核对，根据他们的判断计算约定的准确率指标，并对整个数据集运行一致性检查。这些结果记录之前不生成导出文件；智能体也没有任何能写入 CLM 的工具，所以导入由人来做。

**与来源相比：** 来源出自 2026-04 至 2026-05。这套搭建方式中的智能体承担来源所说的 AI 辅助首轮提取，审阅步骤和来源一样仍由人来做。来源用具名平台（本条目列出 `hebbia`、`elevate-elm`、`ironclad`、`contractpodai-leah`）完成提取和导入；这套搭建方式用文件、脚本和动态工作流取代提取平台，并把 CLM 导入留给人。两个来源都没有公布自己的提示词，所以本搭建方式中的提示词文件要由各团队自己编写。公开实例中的准确率数字是来源自己的，与这个设计无关。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 企业律师确定哪些条款和属性重要（当事方、所在地、期限、续约选项、转让、其他关键条款） [[1]](#sources)。
2. 团队盘点合同库，剔除草稿、重复件和未签署版本，缩小到范围内的文件（例如约 98,000 个文件缩减到 60,000） [[2]](#sources)。
3. 团队配置与具体 CLM 字段对应的 AI 提示词，输出符合 CLM 平台导入格式的结果 [[1]](#sources)。
4. 🛑 **审阅**：团队先在有代表性的合同样本上测试，并在规模化之前优化提示词和输出 [[1]](#sources)；即「基于样本的手册验证」和领域专家校准 [[2]](#sources)。
5. 对每份合同，AI 提取条款原文，写出通俗易懂的摘要，并套用标准化编码 [[1]](#sources)。
6. 🛑 **审阅**：在律师监督下，审阅人从每个数据点点击跳转到原文来校验；律师理顺合同族中的主从关系 [[1]](#sources)[[2]](#sources)。
7. 🛑 **抽检**：迁移前依据质量框架，使用明确的准确率指标、反馈循环和自动一致性检查 [[2]](#sources)。

**产出：** 经校验、带原文链接、已导入客户 CLM 系统的合同元数据。
**失败模式 → 防护：** 提示词漏掉字段细微差别 → 规模化之前先做样本试点。主从层级出错（修订协议与主服务协议） → 由律师主导的合同族核对。提取错误悄无声息 → 提供原文链接和准确率指标。
**与相近工作流的区别：** AWF-0024 手册式合同审阅是针对一份来件合同做修订以供谈判；AWF-0092 是起草新的低风险文件。本工作流的交付物是覆盖整个存量合同组合的结构化元数据，带样本校准循环和组合层面的质控；交付物和检查点都不同。

## 公开实例

覆盖度（截至 2026-11-13）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [Troutman Pepper Locke, Accelerating CLM Implementation](https://www.troutman.com/insights/accelerating-clm-implementation/) (2026-04-20)。律所自己的实例：1,000 多份燃气公用事业存量合同，样本测试提示词，律师监督下校验。"roughly half of what a traditional manual review would have taken"。*第一手：是；可信度：高。*
- [Elevate, CLM-ready contract repository](https://elevate.law/case-studies/how-ai-enabled-review-delivered-a-clm-ready-contract-repository/) (2026-05-27)。法律服务提供商自己的项目：分流 98K 个文件，提取 60K 个，迁移到 Ironclad。">99% accuracy across extracted metadata"。*第一手：厂商；可信度：中。*
