# 抽检式数据主体访问披露

**与相近工作流的区别：** AWF-0035 经验证的 GenAI 初审是在诉讼中判断文档是否相关，并由人签发召回率；AWF-0036 是构建义务登记表。本工作流的交付物是向个人作出的法定披露，带第三方遮蔽质检和一个月的期限；检查点（与请求人确定范围、遮蔽质检）和交付物都不同。
**工具变体：** `relativity-air-for-review` · `cds-vision-ai` · `relativity-redact` · `aiimi`

## 背景

任何人都可以问一家机构"你手里有我哪些信息"，在英国和欧盟，这个答复要在一个月内给出。这件事看起来像一次小规模的诉讼披露，但有一处更难：期限是法定的、而且短，所以一个请求没法等"下周不忙的时候"，而收集来的东西来自邮箱、共享盘和聊天工具，别人的个人信息就混在同一批文件里。两项义务方向相反。请求人有权拿到自己的数据，所以过滤必须紧到不把人家要的东西扣下；第三方也有权利，所以同事与客户的姓名、联系方式、可识别细节，在寄出之前必须去掉。AI 审阅对两半都有用——按"是否含请求人的个人数据"排序并给出理由，以及识别第三方标识以便遮蔽——但两边都不由它决定，因为漏掉一份文件是合规失败，漏遮一个名字是数据泄露。让这件事站得住的设计是：对系统丢弃的东西抽样，而且在期限之前抽而不是在被投诉之后抽；对每一处遮蔽有人过一遍；开局就把范围决定记录下来，因为真要起争议，争的就是这个决定。

**术语：**
- **DSAR / SAR**：数据主体访问请求，个人索取自己的个人数据。
- **个人数据（personal data）**：与已识别或可识别的个人有关的信息。
- **第三方数据（third-party data）**：混在同一批文件里的他人个人数据，必须遮蔽。
- **豁免（exemption）**：可以扣留的法定理由，例如法律特权或他人权利。
- **范围（scope）**：为这个请求确定的保管人、日期区间与检索词。
- **漏检抽样（elusion sampling）**：对系统丢弃的文档抽样，以估计漏掉了什么。
- **特权（privilege）**：法律职业特权，须由律师评估的豁免之一。
- **审计记录（audit trail）**：范围、抽样与遮蔽决定的记录，监管机构来问时它就是抗辩。

## 用智能体搭建

**形态：** `service`。请求持续从公众和员工那里到来，每一个都带着自己那一个月的时钟；收集、排序与遮蔽对每一个请求都无人值守地运行，人出现在范围、抽样与遮蔽质检三处。这里没有按请求人累积、可由 project 持有的东西，也没有一次对话装得下一只邮箱。

**需要：** 接入范围所点名的邮箱、网盘与聊天工作区，并记录收集时间，因为文件在收集那一刻的状态才是你能辩护的；去重与邮件串联，因为同一封邮件会出现在五个保管人的信箱里；按司法辖区定制的提示词，因为豁免规则不同；写下来、并且尽可能与请求人确认过的范围决定，因为请求过宽是答复迟到最常见的原因；对"不相关"集合事先定好的抽样规则；按当地语言调好的标识类别；以及一个能适用豁免（含特权）的人来做的质检环节。智能体不能以豁免为由扣留任何东西，也不能认证披露已经完整：两者都是法律决定，期限不是压缩它们的理由。

| 步骤 | 搭建方式 |
|---|---|
| 收到 DSAR（法定期限） | 时钟从收到时起算，是案件上的一个字段而不是某人收件箱里的一条备注；之后每一步都对它打时间戳。 |
| 🛑 plan（与请求人确定保管人、日期、关键词的范围） | 一份范围记录，最好经请求人确认，它成为"搜过什么"的定义——答复被质疑时第一件要看的正是它。 |
| 收集 + 去重 + 邮件串联 | 自动收集，记录来源、收集时间与去重移除了什么，因为把同一封邮件交出五次是遮蔽风险，不是周全。 |
| 按请求和司法辖区定制提示词 | 排序指令点名请求人、时间区间与该辖区的豁免，于是模型给出判断的理由可以对着范围核查。 |
| AI 对文档按其含数据主体个人数据的程度排序并给出理由 | 每份文档得到排序与引用原文的理由；低置信文档按相关处理，因为多收一份的代价是遮蔽时间，少收一份的代价是泄露。 |
| 🛑 sample（抽样质检"不相关"文档） | 在期限之前由人读一份丢弃集的样本，样本量按风险而不是按剩余时间定；发现问题就重开该类别的排序。 |
| 自动检测并遮蔽第三方个人身份信息 | 标识检测按文档提出遮蔽建议，每条建议都以"决定"的形式可见而不是静默执行，好让质检者看得出遮了什么、没遮什么。 |
| 🛑 review（律师助理/律师质检遮蔽、豁免、特权） | 工作人员核查遮蔽并适用豁免，特权部分单独留给律师；搭建不能最终确定一项扣留。 |
| 披露 + 审计记录 | 披露包与范围、抽样、遮蔽、豁免的记录一起发出，那正是监管机构会要的那份卷宗。 |

**检查点：** `plan`：范围在开局时确定，因为答得太窄会变成投诉、答得太宽会变成泄露风险，而这个决定必须站得住，不能临到期才凑。`sample`：丢弃集在披露之前抽样，这是唯一能抓住"过滤调得太紧"的检查——也是月份不够时最常被跳过的那一项。`review`：每一处遮蔽与每一项豁免都由人决定，特权保留给律师，搭建本身没有任何把披露包发出去的路径。

**与来源相比：** 来源出自 2025-11 到 2026-01，另加一份未标日期的厂商故事。Gravity Stack 与 CDS 的两篇本轮没有重新打开；打开的是监管机构公布的案件数据。此后有这些变化：本工作流的主题已经成为监管机构最大的单一投诉类别。在信息专员公署公布的 2026/27 财年第一季度已办结案件摘录中，访问权相关条款是 24,132 件案件里 11,731 件的主要问题，占 48.6%，上一季度为 40.7%——这是已公布案件的占比，不是收到的请求数量，所以应当读作争议的趋势而不是量的趋势。对这套搭建有两个后果。第一，最后一步的审计记录不再只是勤勉，它就是应对投诉的那份材料：范围、抽样与遮蔽决定正是办案人员会要的，而一份产出很快却没有这些记录的披露包，会把"快速答复"变成"立案调查"。第二，风险的位置变了——投诉量集中在这里，被惩罚的失败是"看起来合理但不完整"的答复，而这正是不做抽样的排序所产出的东西。条目的其他数字未变，仍是单一案件的轶事：一个案子去重后剩约 1,500 份，另一个从 75,000 份降到 11,671 份，以及一次在 48 小时内完成的答复。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 🛑 **计划**：确定请求的范围（保管人、日期区间、定向关键词），最好与请求人沟通后确定；把参数记录下来以备辩护 [[1]](#sources)。
2. 从 M365/Google/Slack 收集，去重并做邮件串联以压缩体量（例如某案最后剩约 1,500 份；另一案从 75,000 份降到 11,671 份）[[1]](#sources)[[2]](#sources)。
3. 用按请求范围与司法辖区定制的 DSAR 专用提示词运行生成式审阅，对文档排序并给出理由与引用 [[1]](#sources)[[3]](#sources)。
4. 🛑 **抽检**：在放大之前，对"不相关"文档做定向抽样质检，以验证 AI 判断；某次运行中做了"两个小规模验证样本" [[1]](#sources)[[2]](#sources)。
5. 自动检测并遮蔽第三方的个人数据（姓名、邮箱、电话、地址）[[2]](#sources)。
6. 🛑 **审阅**：律师助理或客户方人员质检遮蔽后的集合，并追加保密性遮蔽；可能涉及特权的命中单独留给有经验的律师质检 [[2]](#sources)[[3]](#sources)。
7. 在一个月的法定窗口内产出披露，并保留审计记录 [[1]](#sources)。

**产出：** 遮蔽后的披露集与给数据主体的答复，附范围、质检与遮蔽的审计记录。
**失败模式 → 防护：** 请求过宽（姓名缩写与常用词相撞）→ 在收集前谈定范围。AI 漏掉相关文档 → 对"不相关"做漏检式抽样。披露了第三方数据或特权意见 → 自动个人信息检测加人工遮蔽与特权质检。

- [Relativity, Baker McKenzie aiR](https://www.relativity.com/resources/customers/baker-mckenzie-relativity-air/)（未标日期）。一周内处理两个 DSAR，使用定制提示词；律师验证输出。"One DSAR was completed in just 48 hours"。*第一手：厂商；可信度：中。*
