# 合规义务清单构建

**与相近工作流的区别：** AWF-0025 有据可查的法律备忘录（Grounded legal memo，RESEARCH）回答单个法律问题。本工作流则构建并维护一份与控制措施对应的长期清单，并按周对比变更。
**工具变体：** `llm-xml-ingest-pipeline`

## 背景

一家受监管机构所受的规则，多到没有一个人能装下：法条、实施条例、说明条例将如何被解读的监管指引，以及声称同时满足这三者的内部政策。把这些放在同一个视图里，就是合规义务清单的工作——每条规则拆解成"你必须做什么"，映射到"哪项控制措施做到了它"，再由一个有资格判断控制是否充分的人审阅。费力之处在拆解和盯梢：规则以 PDF 和扫描函件的形式到来，跨司法辖区互相重叠，而且一次只改几个条款，这意味着真正要紧的工作是发现"改动的那几个条款里，哪些触及了你已经承诺履行的义务"。模型可以做读的部分——抓取、拆解、标注、关联，并产出带影响说明的每周差异——但做不了判断，因为"控制措施是否充分"是一个法律与运营上的结论，取决于文件里没有的事实。因此让这套工作流可信的两件事都不性感：结构化的表示，使变更表现为"某个字段变了"而不是"某段话看起来不一样"；以及两端各有一位律师，一位核查抽取，一位签核充分性。

**术语：**
- **合规义务清单（obligations register）**：结构化的"机构必须做什么"清单，每项义务附其来源。
- **分级（tiering）**：按效力给来源排序——法条、条例、指引、内部政策——因为它们会互相冲突。
- **义务（obligation）**：从规则中拆出的一项独立职责，是清单的构成单位。
- **控制措施（control）**：满足某项义务的内部流程或政策。
- **充分性（adequacy）**：律师关于"该控制措施确实满足了该义务"的判断。
- **主题审阅（thematic review）**：把一组义务放在一起读，看控制措施是否覆盖了整个主题，而不只是逐条对应。
- **前瞻扫描（horizon scanning）**：跟踪提案与分阶段生效日，区别于对已发布内容的监测。
- **停表（stop-the-clock）**：不改变规则本身、只推迟适用日期的立法延期。

## 用智能体搭建

**形态：** `project`。清单是一份有历史的常设资产：每项义务都带着创设它的法律文件、生效版本、应对它的控制措施，以及律师最后一次认可它的日期。每周差异只有对着这份留存的历史才有意义，所以这是一个由团队维护的仓库，不是跑一次的 skill，也不是按需应答的服务。

**需要：** 在导入之前就按效力分好级的来源清单，否则清单会把指引当法律来引；客户自己的模板，因为无法导入 GRC 工具的清单没人会用；内部的控制措施、标准与政策文本，因为映射步骤得有东西可映；每一版法律文件都要带日期，**包括设定该日期的日期**，因为"被挪动的生效日"是最容易被漏掉的那类变更；以及为两件不同的活排好的律师时间——核查抽取、判断充分性——它们不是同一次审阅，不该合并。智能体不能判定充分性，也不能判定某项变更是编辑性的：这两个判断正是清单存在的目的。

| 步骤 | 搭建方式 |
|---|---|
| 确定范围并为来源分级 | 一份来源台账，每条带效力层级与辖区，审一次、做版本化，因为两份文本冲突时由层级决定谁赢。 |
| 抓取为结构化 XML | 确定性导入客户模板，把法律文件、版本及其生效日期存为字段而不是散文。 |
| 拆解并标注义务 | 模型把每份文件拆成独立职责，按主题标注，并保存每条职责的原文段落，好让律师对着条款核查抽取。 |
| 关联相关规则 | 跨文件、跨辖区的语义关联，以带理由的边存储，这才使主题审阅能看见同一项义务出现在三个地方。 |
| 🛑 review（律师核查输出） | 律师逐条把抽出的义务与其段落对照；提示词与领域专家共同迭代；无法回溯到条款的抽取一律退回。 |
| 为每项义务汇总控制措施 | 模型把机构的控制措施、标准与政策汇总成一个视图并做主题审阅，标出没有明显控制措施的义务。 |
| 🛑 sign-off（律师审查充分性） | 律师判断控制措施是否充分，这一步才让清单成为法律工作成果，而不是模型输出。 |
| 每周新旧文本对比 → 影响简报 | 差异在结构化字段上计算而不是靠文本相似度，所以"日期被挪动"与"某句被改写"是两类不同事件；简报点名受影响的义务与业务影响。 |
| 🛑 review | 律师在每份简报送到客户之前核查，下一周差异里的误报也是在这里被剔除的。 |

**检查点：** `review`：每一条抽取都对着原文段落核查，而之所以查得动，只因为段落被存了下来——这道关口挡住了"一段合理的转述变成一项义务"。`sign-off`：充分性是律师关于机构控制措施的结论，而不是关于规则的结论；在它被记录下来之前，这份清单不能用于审计；搭建本身没有任何把义务标成"已覆盖"的路径。

**与来源相比：** 来源出自 2026-03-25，本轮没有重新打开。此后有这些变化：清单最难的失败模式有了一个教科书式案例，而它是一个日期。欧盟《人工智能法》的高风险义务原定 2026-08-02 适用；2026-07-24 公布的 (EU) 2026/1744 号条例把附件三的期限挪到 2027-12-02、把嵌入受监管产品的高风险组件挪到 2028-08-02，而[第 50 条的透明度义务仍留在原定日期](https://www.legalfly.com/post/horizon-scanning-guide)，自 2026-08-02 起适用，对已在市场上的生成式系统另给到 2026-12-02 的标识过渡期。同一时期，企业可持续尽职调查的时间表动了两次：一项"停表"指令把首次适用推到 2028 年，2026-02-26 的 Omnibus I 指令又推到 2029 年并提高了员工门槛。对这套搭建有两点教训。第一，只读了"AI 法被延期"这个标题的团队会漏掉 8 月仍然生效的那部分，而这恰恰是每周文本差异最容易招来的错误：延期与未变的条款出现在不同法律文件里，只有把"每个日期由哪份文件设定"存下来的清单才能分辨二者。第二，每个日期字段都需要自己的出处——设定它的文件以及设定时间——因为一份只记了期限、不记由谁设定的清单，会一直围绕一个已经不成立的日期做规划，而重新规划才是最贵的部分，不是读。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 划定范围并按层级对监管来源分级。一条定制流水线把 HTML、PDF 与扫描文本抓取成客户模板中的结构化 XML [[1]](#sources)。
2. LLM 识别、概括并标注各条义务，把文本拆解为映射到主题的独立条款，并通过语义检索关联相关规则与指引 [[1]](#sources)。
3. 🛑 **审阅**：律所律师核查 LLM 的全部输出。提示词与领域专家共同迭代 [[1]](#sources)。
4. 对每项义务，LLM 把机构的控制措施、标准与政策汇总成单一来源，并做主题审阅 [[1]](#sources)。
5. 🛑 **签发**：律师判断每项义务的控制措施是否充分，由此产出合规义务清单 [[1]](#sources)。
6. 每周自动更新：LLM 读取新旧法规文本，概括变更及其业务影响，用于向利益相关方简报 [[1]](#sources)。
7. 🛑 **审阅**：每份简报在送到客户之前由律师核查 [[1]](#sources)。

**产出：** 一份经法律审阅、映射到内部控制措施的合规义务清单，并以每周变更摘要保持更新。它可用于控制映射、前瞻扫描与 GRC 工具。
**失败模式 → 防护：** 分辨真实的法律变更与编辑性改动，以及跨来源、跨辖区的数据重叠 → 结构化导入加对每一项输出的律师审阅 [[1]](#sources)。
