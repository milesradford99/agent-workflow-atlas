# 有护栏的课程辅导助手

**与相近工作流的区别：** 最接近的是 AWF-0042 辅导员批准的 AI 回合（TUTOR），那是辅助模式：辅导员批准每一轮 AI 回复后学生才能看到。本工作流中学生直接与辅导助手对话。人在论坛回答发布之后检查，助教在样本上评判提示词或模型版本，因此自主程度（抽检）和检查点安排不同。
**工具变体：** `cs50-ai-azure-gpt4o`

## 背景

一门有 200,000 名学生的课没法逐个回答问题。答疑时间变成队列，队列变成一小时的等待，而最需要开口问的学生恰恰最不愿意排。常见的解法是论坛，它帮到的是自信的人和耐心的人。AI 辅导助手改变了这道算术：每个学生在凌晨三点都能得到回答，用他自己的话，就在他正在写代码的那个编辑器里。风险同样明显。把答案直接交出去的辅导助手，抹掉的正是这道练习本来要制造的那种挣扎，而且它在规模上会同时对所有人抹掉。所以设计问题不是让模型更有帮助，而是让它比聊天机器人**故意更没帮助**，并且这种"没帮助"要挡得住成千上万个换个说法再问一遍的沮丧的人。由此有两点。护栏必须既在提示词里、也在代码里，因为被明令不要给代码的模型，仍会有一定比例照给。而教学人员保留两件模型接不了的事：检查公开发布的回答，以及判断新版本是否比旧版本更好——后者要求读同一问题的两份回答，而不是读一个分数。

**术语：**
- **小黄鸭（rubber duck）**：你把问题讲给它听、往往因此自己找到答案的东西；这里指只提问不解答的辅导助手。
- **RAG（检索增强生成）**：从课程材料而非通用知识中取答案。
- **系统提示词（system prompt）**：定义辅导助手角色与边界的那段常驻指令。
- **护栏（guardrail）**：在代码层面限制模型输出的检查，而不是只在提示词里请求它遵守。
- **指令稀释（instruction dilution）**：提示词过长，靠后的指令不再被遵守。
- **成对比较（pairwise comparison）**：把对同一问题的两份回答摆给评判者，问哪份更好。
- **模型评分评测（model-graded evaluation）**：用模型而非人来打分，只有在与人的判断核对过之后才可用。
- **助教（teaching fellow, TF）**：带讨论课和答疑的研究生教职人员。

## 用智能体搭建

**形态：** `service`。它为一个远大于任何教职团队能服务的规模持续运行，没有人来启动一次运行：提问进来、回答出去，唯一的真人介入都在事后——教职人员处理论坛回答，助教处理版本比较。这是一项服务，不是某个学生跑一次的 skill，也不是一个带每用户语料的 project。

**需要：** 课程材料作为检索语料，因为靠通用知识作答的辅导助手会去教"互联网版本"的这门课；一段定义角色与拒绝方式的系统提示词，外加在交付前检查回答并重试的代码，因为光靠提示词撑不住；入口处的个人信息剥离；按学生按时间单位的使用上限，否则最需要思考的学生会把思考外包出去；一个论坛回答的审阅界面，让教职人员能事后认可、修改或删除；足够细的日志，让漂移能按模式而不是按投诉被发现；以及一批排好时间的助教，用于成对比较——这是唯一能告诉你"新版本更好"的步骤。

| 步骤 | 搭建方式 |
|---|---|
| 课程系统提示词 + 课程材料 RAG | 编辑器、网页、论坛共用一套后端，课程语料是唯一的检索来源，提示词像代码一样做版本管理。 |
| 去除个人信息 | 每次提问的前置处理，因为学生会不假思索地把自己的姓名、同伴的代码和学号粘进对话框。 |
| 每个学生提问：给出引导式回答，而非完整解答 | 模型以辅导者身份作答：给提示、反问、指回某一讲。生成之后的检查会扫一遍回答里有没有代码块和直接给答案的措辞，命中就重试，然后才给学生看。 |
| 论坛回答：🛑 review（教职人员认可、修改或删除） | 回答立即发布，教职人员就在论坛里审阅；界面必须让修改是一次动作，否则在量上审阅根本不会发生。 |
| 日志分析（代码块、直接给答案的措辞） | 定期扫日志，按版本、按教学周统计那些破绽——围栏代码块、"完整解法如下"——这是在学生投诉之前发现漂移的办法。 |
| 候选提示词或微调 | 每个修法都是候选而不是上线：一次提示词修订，或在若干经过整理的学生-助教对话上做微调。 |
| 🛑 sample（助教两两比较新旧版本） | 助教看到同一个学生问题被两个版本分别作答，选一个并写下理由；搭建持续收集这些选择，直到足以构成证据。 |
| （模型评分评测 ⟲ 与助教选择的一致度） | 模型评判者先对着助教的选择校准，之后才在规模上被采信，用来给助教没读到的那些案例打分。 |

**检查点：** `review`：论坛回答是公开的，所以教职人员的检查在事后、按例外进行——认可、修改或删除——它能成立，只是因为需要改的回答少到找得出来。`sample`：助教成对比较版本并留下理由；这个判断就是模型评分评测的基准，所以这个闭环先在人身上校准，再在量上采信，任何版本都不能只凭一个分数到达学生面前。

**与来源相比：** 来源出自 2024 与 2025，即两篇 SIGCSE 论文；公开实例是 2025 那篇。两篇论文本轮都没有重新打开；本月打开的是 2026-09-25 的一篇哈佛公报访谈。此后有这些变化：团队公开了护栏实际是怎么做的，而它不是提示词。Malan 描述了团队自己写的代码，会[在学生看到之前评估一份回答，并有时拒绝或重试](https://dev.news.harvard.edu/gazette/story/2026/09/taming-the-duck-for-starters)，因为光有指令"往往不够"。他也确认本条目当作指标记录的那个失败仍然存在——小黄鸭被明令不要用代码块作答，仍有高达四分之一的情况照给——并把原因归于采样的随机性，以及训练数据里技术回答本来就长成代码的样子。有两处机制是本条目原搭建里没有的：上文那个生成后过滤器，以及一个借自游戏的用量上限——"生命值"系统，在团队看到有学生一次问出约 200 个问题的长尾之后，限制每个时间单位内只能问几个问题。后果现在也看得见了：答疑需求大幅下降（此前等待曾长达一小时），成绩上升，课程因此回到监考考试，并加上短时口试抽查。最后这一变化对本工作流的评测闭环很要紧：如果辅导助手确实有效，它所服务的测评就必须跟着动，否则"进步"会表现为一次成绩上涨，而它量的是辅导助手，不是学习。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 所有工具共用一套后端。它剥离学生提问中的个人信息，并把提问包进一段课程专用的系统提示词，要求模型扮演 CS50 助教，做引导而不是给答案 [[1]](#sources)。
2. 论坛提问使用对课程事实的 RAG 以减少幻觉。小黄鸭在 IDE、网页和 Ed 论坛上直接回答学生 [[1]](#sources)。
3. 🛑 **审阅**：Ed 上每一条小黄鸭的回答都可以由教职人员认可、修改或删除 [[1]](#sources)。
4. 团队挖掘日志寻找漂移，例如出现代码块，或出现"这是一个示例"之类直接给出完整解法的措辞 [[2]](#sources)。
5. 他们制作候选修法：少样本提示，或在 50 段经整理的学生-助教对话上做微调 [[2]](#sources)。
6. 🛑 **抽检**：助教对同一批学生提问比较两个版本的回复并留下书面反馈。模型评分评测在放大之前，先与助教的选择核对 [[2]](#sources)。

**产出：** 与学生 24/7 使用的课程对齐 AI 辅导助手；论坛回答有人监督，每次提示词或模型变更之前都有一轮助教验证过的评测。
**失败模式 → 防护：** "指令稀释"，即模型忽略过长的提示词；从 GPT-4 换到 GPT-4o 后，含代码块的消息从 20% 升到 25% → 上线前做成对助教评测与微调 [[2]](#sources)。过于热心、反而削弱学习的回答 → 引导式回答提示，加上对直接给答案措辞的监控 [[2]](#sources)。
