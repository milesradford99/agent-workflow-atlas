# 审稿意见回复与稿件修订

## 背景

"退修重投"是一篇论文能收到的最好消息，也是作者最难熬的两周。三位审稿人写下四十条意见，其中一些互相矛盾，而每一条都需要三样东西：一个决定（接受、反驳或部分让步）、稿子里的一处改动、以及回复信里说明"改了什么、改在哪里"的一句话。这些工作在机械与不机械之间摇摆：一处改动会挪动出现在四个地方的同一个数字，一次新分析会重新生成正文描述的那张图，一次让步会让讨论里某个句子失效，而为回答一条意见新加的引用必须能解析。模型擅长机械的那部分，恰在边界上危险，因为修订稿必须内部自洽——每个数字都对得上重新生成的输出，每句断言都对得上论文现在说的话——而一封听起来合理的回复信，并不等于一封真实的回复信。所以人保留三个决定：让步到什么程度、反驳怎么写、以及最终这一包东西是不是自己愿意署名的。

**术语：**
- **退修重投（revise and resubmit）**：邀请提交修订稿与逐条回复的决定。
- **回复对照表（response matrix）**：每条审稿意见一行，记着计划改动与落点。
- **反驳（rebut）**：不改稿而回答一条意见，并给出理由。
- **重新分析（reanalysis）**：因审稿人质疑方法或统计而重跑分析。
- **latexdiff**：由两次编译生成的、标出全部改动的稿件版本。
- **回复信（response letter）**：逐条回应意见、随修订稿提交的文件。
- **披露（disclosure）**：说明工作中如何使用 AI 的声明，许多期刊现在要求在稿件正文中给出。

## 用智能体搭建

**形态：** `skill`。一位通讯作者、一份稿件、一组审稿意见，在一次对话里处理，对照表、diff 与回复信以文件留存。论文本身是持久产物，住在作者自己的仓库里；智能体在一份副本上工作，而署名的是作者。

**需要：** 审稿意见的文本，这样对照表是被建出来的而不是被概括出来的；稿件源文件及其构建方式，因为真正要紧的检查是一次重新编译；分析代码与数据，这才让"重新分析"成为可能，而不是只写一句"我们重新分析了"；经得起审阅的"意见—改动"映射，因为只有 diff 支撑得住，回复信才可信；目标期刊的 AI 政策，因为修订稿现在要带披露声明，而各刊对放在哪里规定不同；以及一个会读智能体碰过的每一节的人。智能体不能决定让步、不能用作者不会用的口吻写信、也不能认证数字已经对上——最后这项检查正是要在末尾放一个人的原因。

| 步骤 | 搭建方式 |
|---|---|
| 审稿意见 → 回复对照表 | 每条意见变成一行，带审稿人原话、决定、计划改动及其位置；定位不到的意见保持"未结"状态，而不是被悄悄删掉。 |
| 🛑 plan | 作者在任何修改开跑之前逐行定下接受、反驳或部分接受——这是唯一一步真正涉及论文论点的环节，而不是它的文字。 |
| 每个意见：（修改或重新分析 ⟲ 编译、重跑、引用检查） | 子智能体按意见分工：改文字、重跑分析并重新生成图表、补引用。循环以"干净编译"和"重跑复现所报告数字"为结束条件。 |
| latexdiff + 回复信 | diff 由两次构建生成，所以不可能漏掉一处改动；回复信对着对照表起草，所以每一条都指向一处真实改动。 |
| 🛑 review | 作者从语气与实质两方面修改反驳，让步在这里被软化，或者分歧在这里被说清楚。 |
| 🛑 sign-off | 通讯作者把稿件、diff 与回复信作为一包一起批准；搭建没有投稿通路。 |

**检查点：** `plan`：接受/反驳/部分接受由作者决定，并且在动工之前定下，因为"先拼出一份修订再补理由"论证的是模型的主张，不是论文的主张。`review`：反驳由人从语气与实质上修改——回复信是一份说服性文书，它的分寸不可外包。`sign-off`：一个人把稿件、diff 与回复信作为一套批准，这也正是"AI 使用披露"必须为真的那个时刻。

**与来源相比：** 本条目没有引用来源：它的步骤没有引注，公开实例只是一个没有任何修订记录的模板仓库。正因如此，它被写下之后发生的变化比平常更要紧。ICMJE 在 2026 年 1 月更新了推荐规范，新增一节专讲出版中的 AI，其中两项要求正好落在本工作流上：作者必须**在提交的作品本身**披露 AI 使用，而不只是在投稿信里；AI 工具不得作为来源出现在参考文献中。未披露可能被认定为学术不端，而各刊对声明放在哪一节的规定不同，所以披露要按目标期刊分别写，不能写一次通用。实际后果是本条目形状里没有体现的一项搭建要求：修订产出包含一份披露声明，写明所用工具及其用途——起草、语言润色、重新分析——而签发处的那个人除了核数字，也在核这份声明。另一项变化是本条目一直暴露在外的那个风险：当回复信本身也成了一必须"关于它是怎么产生的"也说真话的文件，一个擅长起草有力反驳的智能体，其产出就需要检查有没有 diff 支撑不住的断言——和以前的检查是同一个，只是多了一个理由去跑它。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下步骤是本条目原有的描述。没有任何来源记录它们，见 **与来源相比**。*

1. 把审稿意见解析进 `response.md`（意见 → 计划的修改 → 位置）。
2. 🛑 **计划**：作者对每条意见决定接受、反驳还是部分接受。
3. 为每条意见分别运行子智能体：修改文字、重跑分析并重新生成图表、补充引用。
4. 编译，并生成 `latexdiff` 版本。
5. 核实每个数字都与重新生成的输出一致，每个引用键都能解析。
6. 起草回复信。
7. 🛑 **审阅**：作者从语气和实质内容两方面修改反驳。
8. 🛑 **签发**：通讯作者在重新投稿前批准修订稿、`latexdiff` 和回复信。
