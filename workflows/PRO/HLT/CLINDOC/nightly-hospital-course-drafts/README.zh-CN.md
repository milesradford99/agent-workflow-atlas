# 夜间住院经过草稿

**工具变体：** `gemini-2-5-pro` · `epic-fhir` · `gpt-4-1-ehr-template`

## 背景

患者出院时，主治医师要为接手的医生写一份出院小结。其中的住院经过部分讲述这次住院的来龙去脉：患者为什么入院、发现了什么、做了什么、还有哪些事没了结。住院时间一长，这意味着要读医生、护士、药师、治疗师等许多人写的记录，而且常常是在出院当天匆忙完成，重要的内容很容易漏掉。在这里，一个任务每晚运行，读取每位住院患者的记录，起草住院经过，每条陈述都附上指向来源记录的引用，让医师早上就能拿到草稿。用不用它由医师决定；医师对照所引的记录核对，并签署出院小结，因为签署后的出院小结是下一位临床医生据以行事的医疗记录，其中的遗漏或错误陈述可能伤害患者。医师还会对一部分草稿评定危害程度，让团队判断这个工具能否继续用下去。

**术语：**
- **主治医师、住院部医师（hospitalist）**：对患者的诊疗负总责的上级医生；hospitalist 是只在住院病房工作的主治医师。
- **出院小结、住院经过**：患者出院时写的文件，以及其中讲述这次住院经过的部分。
- **EHR（电子病历）**：医院保存每位患者病历的系统；这里用的是 Epic。
- **FHIR**：其他程序从 EHR 读取健康记录所用的一种标准接口。
- **H&P、病程记录、多学科记录**：入院时的病史与体格检查；每天的记录；护士、药师、治疗师、营养师、个案管理和灵性关怀人员写的记录。
- **智能体式工作流**：这里指让模型分几个阶段来构建并核对摘要，而不是只用一次提示词。
- **行内引用**：每条陈述后面指向其来源记录的标注。
- **一句话概述、按问题组织的摘要**：用一句话描述患者；按医学问题分条组织的摘要。
- **AHRQ Common Format Harm Scale**：美国一家联邦机构制定的标准量表，用来评定一个错误可能造成多大的危害。
- **遗漏、不准确、幻觉**：漏掉了重要内容；陈述有误；陈述了任何记录里都没有的内容。

## 用智能体搭建

**形态：** `service`。草稿在夜间生成，现场没有人；医师早上只看到为自己每位患者写好的草稿。

**需要：** 通过 MCP 服务器或一个小脚本、经医院批准的只读 FHIR 访问，可以读取本病区在院患者的记录；与住院部医师商定的输出格式，作为参考文件放在 skill 旁边；一个状态存储，记录哪些患者已起草、已发送；医院允许传送患者信息的安全内部渠道；一份反馈表，其答案落到团队能读取的存储里。这些记录属于患者记录：服务只能运行在医院批准处理它们的环境中（在美国，即受业务伙伴协议覆盖的环境）。不要给智能体任何写入 EHR 的工具。

| 步骤 | 搭建方式 |
|---|---|
| 夜间：通过 FHIR 拉取入院记录 (H&P、病程记录、多学科记录) | FHIR 接口能从云端访问时，用云端定时任务；否则在医院网络内由医院自己的调度器启动 `claude -p` 或一个 Agent SDK 程序。由脚本取回每次住院的记录。 |
| 3 阶段智能体式摘要 + 核验，附行内来源引用 | 一个装有输出格式的 skill。每位患者交给一个子智能体，根据记录起草；另一个没见过起草过程的子智能体，逐条对照所引的记录核对陈述，并标出找不到依据的条目。 |
| 每位患者一封加密邮件草稿，上午 9 点前送达 | 由脚本通过批准的渠道给主治医师每位患者发一条消息，并记入状态存储。这次运行到此结束。 |
| 🛑 review (主治医师采用、修改或弃用) → 粘贴进 EHR 中的出院小结 | 由医师在 EHR 中完成。 |
| 🛑 sample (医师反馈危害与错误) | 随每份草稿附上的反馈表。之后的一次运行把答案汇总给团队。 |

**检查点：** `review`：草稿以消息的形式送到医师手上，而不是病历中的一条记录。智能体没有任何写入 EHR 的工具，所以除非医师把它粘贴进去并签署出院小结，否则什么都不会进入病历。`sample`：医师通过反馈表，对自己挑选的草稿评定潜在危害和错误类型；答案进入团队的存储，智能体在草稿发出后也没有任何修改它的途径。

**与来源相比：** 来源和公开实例出自 2026-04 至 2026-08。斯坦福团队围绕一个模型搭建了定制的三阶段流水线，并用邮件发送草稿；上面的搭建方式保留了用消息送达的做法，并用一个单独的子智能体做逐条核对。论文在补充材料中描述了这三个阶段，本条目没有转述，所以拆成起草和核对两步是本目录的设计，不是来源的做法。第二个公开实例是通过 EHR 自身的集成，把草稿放进 EHR 自带的出院小结模板；这条路需要 EHR 厂商的工具，不在本搭建方式之内。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 每晚，流水线通过 FHIR 从 EHR 中取回该次住院的临床文档，包括医师、药学、护理、治疗、营养、个案管理和灵性关怀的记录 [[1]](#sources)。
2. 一个 3 阶段的智能体式工作流（Gemini 2.5 Pro）迭代地构建并核验摘要，而不是单次提示，每个阶段都保持以原始记录为依据 [[1]](#sources)。
3. 团队与住院部医师共同设计了输出格式：患者一句话概述、叙述式住院经过、按问题组织的摘要，每条陈述都带指向来源记录的行内引用 [[1]](#sources)。
4. 上午 9:00 前，流水线给每位主治医师按患者各发一封加密邮件，草稿为交互式 HTML 文件，附一个复制按钮，会去掉引用以便粘贴进 Epic [[1]](#sources)。
5. 🛑 **审阅**：医师可以 'free to use, edit, or discard summaries at their discretion'；出院小结由医师签署 [[1]](#sources)[[2]](#sources)。
6. 🛑 **抽检**：医师对一部分摘要填写反馈表，对潜在危害程度（AHRQ Common Format Harm Scale）和错误类型（遗漏、不准确、幻觉、引用错误）打分 [[1]](#sources)[[2]](#sources)。

**产出：** 出院小结中的住院经过部分，由医师在 EHR 中修改并签署。
**失败模式 → 防护：** 遗漏（占已评分摘要的 25%）和不准确（20%）→ 使用前由医师对照所引来源审阅；长时间住院超出上下文长度 → 分阶段拆解；采用了却没有节省时间 → 跟踪 EHR 时间日志和职业倦怠，而不只看使用率。
**与相近工作流的区别：** AWF-0088 预先起草的影像报告（Pre-drafted radiograph reports）是在听写模板内起草单次检查的报告；AWF-0026 医患对话环境记录员（Ambient scribe）是根据录音起草就诊记录。本工作流的产出是整个住院期间的住院经过，由多位作者的记录综合而成，每晚批量生成，供医师选择性使用，且每句话都有来源引用。产出和输入都不同，互换测试不通过。

## 公开实例

覆盖度（截至 2026-11-13）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [Grolleau et al., Stanford, JAMA Netw Open](https://jamanetwork.com/journals/jamanetworkopen/fullarticle/2848785) (2026-05-08)。为期 10 周的前瞻性试点，384 例出院，医师可选择是否使用草稿；其中 100 份评定了危害。"Physicians used artificial intelligence (AI) content in 219 cases (57.0%)"；"Physicians rated 88 unedited summaries (88.0%) as having no harm potential"。*第一手：是；可信度：高。*
- [Suarez et al., ACI](https://doi.org/10.1055/a-2962-8004) (2026-08-01)。GPT-4.1 在强制使用的出院小结模板内起草住院经过；8,298 名成人；测量了编辑时间。"the AI tool was associated with a 32% increase in edit time"。*第一手：是；可信度：高。*
