# 按例外分流的自动编码

**与相近工作流的区别：** AWF-0032 依据标准把关的预授权（Criteria-gated prior auth）是最接近的一个，它是辅助级的：工作人员审阅每封信函并提交每项申请。这里，已覆盖病历的编码不经人工审阅直接进入计费，人只处理例外情况和审计抽样。
**工具变体：** `nym-autonomous-coding`

## 背景

每一次就诊最终都要以一张带编码的理赔单离开医院：诊断了什么、做了什么、在哪里做。持证编码员读病历、分配编码，这项工作慢、专精、且长期缺人——招不到编码员的医院只能压着理赔单，而压着的单子就是已经花出去的钱。编码又特别适合自动化，因为问题很窄、证据就在文档里：某段文字要么支持某个诊断，要么不支持。一个读遍所有病历、并为每个编码给出依据的引擎，因此能承担大部分工作——但只能在文档确实支持的地方。让它安全的设计不是更高的准确率，而是逐份病历的分流决定。引擎看得懂的病历原样进计费；看不懂的——文档自相矛盾、缺一份记录、缺医师签名、某个编码没把握——连同原因一起交给一个人。然后对全部病历（无论自动与否）抽样审计，把发现喂回引擎的知识库。留给人的仍是本来就属于人的部分：确定这家机构的编码理念，以及在付款方问起"这个编码凭什么"时守住这张单。

**术语：**
- **ICD / CPT / E&M**：诊断、操作与就诊复杂度三套编码体系。
- **病历（chart）**：一次就诊的临床记录，这里是编码的单位。
- **编码理念（coding philosophy）**：机构就"文档含糊时该怎么编码"写下来的立场。
- **覆盖率（coverage）**：引擎不经人手即完成编码的病历占比。
- **被剔除病历（dropped chart）**：带着原因转给编码员的病历。
- **置信阈值（confidence threshold）**：超过该分数，引擎就把编码送去计费而不再复核。
- **HCC / 风险调整（risk adjustment）**：决定按价值付费与 Medicare Advantage 合同支付的诊断捕获。
- **审计链（audit trail）**：把某个已分配编码回溯到支撑它的文档与规则的那条逐码链接。
- **高编（upcoding）**：分配的编码比文档支持的程度更重，正是付款方审计要找的东西。

## 用智能体搭建

**形态：** `service`。病历从电子病历系统持续流入，没有人来启动一次运行，多数病历在无人介入下完成编码并送往计费，例外则排进编码员的队列；此外还有定期审计对整个流抽样。这在构造上就是一项服务：无人值守、由队列驱动、以覆盖率而非任何单份产出论成败。

**需要：** 结构化的病历文本及其元数据，包括缺失的签名或记录是否真的缺失；在配置之前就写下来的机构编码理念，因为引擎必须按合规团队的方式解决歧义；一套取自本机构历史病历、由本机构审计员编好的验证集，因为厂商的准确率是在别人的人群上测的；分流规则与四种剔除理由，明确到编码员拿到病历就知道该查什么；一套有抽样比例和明确责任人的审计流程；以及在理赔层面可取的审计链，因为第一次被付款方质询时就会要它。智能体不能靠推断去化解文档冲突，也不能为了提高支付而抬高编码的严重度：这两件事正是把效率项目变成追偿通知的失败模式。

| 步骤 | 搭建方式 |
|---|---|
| 记录编码理念与机构指南 | 一套写成文字、做版本管理的规则集，引擎配置由它推出、审计对着它衡量——没有它，每一次分歧都会变成关于模型的争论。 |
| 🛑 plan（配置并验证引擎） | 用本机构的历史病历对着本机构的审计员做验证，准确率与覆盖率都有明示的门槛；编码员被训练成核对引擎的推理，而不是从头重编。 |
| 每个病历：引擎分配 ICD/CPT/E&M 编码，并为每个编码附理由 | 逐码保存所依据的段落与所适用的规则，而不只是保存编码——正是这份理由让编码员的核对与付款方的抗辩都成为可能。 |
| 覆盖检查 | 逐份病历对照明示条件作出的分流决定，而不是一个全局置信分：四种剔除理由就是规格说明。 |
| 已覆盖：编码送计费 | 直通过去，不逐份复核，这既是全部的经济性所在，也正是审计抽样必须真实的原因。 |
| 🛑 handoff（编码员） | 被剔除的病历带着理由到达；编码员的更正当作训练信号留下，而不是一次性的修补。 |
| 🛑 sample（定期编码审计） | 一条常设的抽样，跨专科、跨服务线抽取，由审计员对照文档打分，发现回流进知识库。 |

**检查点：** `plan`：引擎按机构自己的编码理念配置，并在任何病历不经复核就进计费之前，用本机构的病历对本机构的审计员做过验证——来源明确说，编码员必须被训练成能核验输出，而不是被输出取代。`handoff`：四种剔除理由是安全阀；引擎只懂一半的病历必须离开自动通路，而理由要随它一起走。`sample`：定期审计是"直通计费"站得住脚的前提，也是引擎唯一能得知"它自信地做错了"的途径。

**与来源相比：** 来源是一份未标日期的厂商会议讲稿，本轮没有重新打开。此后有这些变化：这一类从试点走进了采购，数字开始署名公布。一份对 KLAS 2026-04 市场报告的二度转述把自动编码排在美国医疗 AI 用例首位，按专科计的免手动率为 62% 到 87%，对照盲审人工专家组的准确率为 92.5% 到 96.4%，而该专家组自身的一致性约为 92.5%（KLAS 报告仅对订阅者开放，转述只能当二手材料看）。厂商现在会公布具名部署：Your Health 于 2025-10 上线 Fathom，[首日即有 95.5% 的就诊完成编码，准确率从 96.3% 升到 98.3%](https://fathomhealth.com/insights/your-health-deploys-fathom-autonomous-medical-coding-to-achieve-95-5-automation-rate-at-98-3-accuracy-rate-across-all-service-lines)；Nym 的上线门槛是在启动前用客户自己的历史病历复核达到 95% 的准确率，超过声明的置信阈值才送往计费。这些数字要配两条告诫。第一条来自同一份 Your Health 通稿自己报的：平均风险调整因子一年内从 1.12 升到 1.78，营收基准测算从 35M 美元升到 70M 美元。这要么是编码员此前漏掉的 HCC 捕获，要么是高编；在审计链证明是前者之前，付款方审计会按后者处理——所以逐码引用不是锦上添花的功能，它就是抗辩本身。第二条是独立性仍然薄弱：一份第三方能力评测发现，Nym 并未完整公开其人工监督与护栏文档，两家头部厂商也都没有公布独立的准确率验证。条目的证据等级因此仍为 B。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 记录本机构的编码理念与指南，并据此配置引擎 [[1]](#sources)。
2. 🛑 **计划**：在依赖引擎结果之前先做验证。训练人类编码员核验它的输出并给出反馈 [[1]](#sources)。
3. 电子病历系统把病历送给引擎。它在几秒内完成编码，并为每个编码给出理由 [[1]](#sources)。
4. 已覆盖病历上的编码直接进入计费，不逐份复核 [[1]](#sources)。
5. 🛑 **接手**：被剔除的病历交给人类编码员。四种剔除原因是引擎的理解缺口、文档冲突、某个编码置信度低，以及文档缺失（例如缺急诊记录或缺医师签名）[[1]](#sources)。
6. 🛑 **抽检**：对自动编码的病历定期做审计与质量检查。审计发现回流进引擎的知识库 [[1]](#sources)。

**产出：** 送往计费的已编码理赔单，以及给编码员的例外病历队列。
**失败模式 → 防护：** 有缺口或冲突的病历会被编错 → 每一类都作为被剔除病历分流出去。覆盖率是部分的（主要是门诊专科）→ 按被剔除的份额保留编码员编制。
