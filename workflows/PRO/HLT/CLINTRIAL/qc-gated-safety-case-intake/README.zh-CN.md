# 质控把关的安全病例录入

**工具变体：** `arisglobal-lifesphere-navax` · `bayer-mygenassist` · `indegene-naem`

## 背景

药企必须收集关于其药品可能造成伤害的每一份报告，不论来自医生、患者还是本公司员工，并在规定时限内把每一份都作为结构化的病例报告提交给监管机构。这项工作叫作药物警戒。工作人员阅读收到的表单、邮件或通话记录，把细节录入安全数据库，就缺失的信息去函询问报告人，再由医生审核每个病例的医学含义。病例量大时手工录入很慢，而一个字段填错，或者自由文本里的严重事件被漏掉，都属于合规失误。在这里，生成式 AI 把病例细节提取进数据库，并起草随访函。提取出的数据仍由人按双人原则核对，每封函件由药物警戒专员修改并发送，医学审核由安全部门的医生完成，因为公司要对提交的每个病例、以及能否从中发现安全问题承担法律责任。

**术语：**
- **不良事件（AE）**：服药者身上出现的任何有害或不希望发生的医学事件，不论是否由药物引起。
- **药物警戒（PV）、药物警戒专员**：药品上市使用后对其安全性的监测；处理病例、联系报告人的工作人员。
- **来源文件**：病例的原始报告，由表单、邮件或电话内容汇编而成。
- **安全数据库**：公司用来记录和提交病例、经过验证的系统。
- **ICSR（个例安全报告）、E2B**：提交给监管机构的单个病例报告；E2B 是它的国际电子格式。
- **病例处理、双人原则（Four Eyes）**：录入和核对病例，常由外部供应商完成；每项工作都由第二个人核对的规则。
- **随访函（文件函）**：向报告人索取病例缺失信息的函件。
- **药物警戒质量管理规范**：监管机构对药物警戒工作的规定，包括应多久联系一次报告人。
- **GenAI、LLM**：生成式 AI，即生成文本的模型；大语言模型是其中一种。
- **幻觉**：模型陈述了来源中没有的事实。
- **QC（质量控制）**：对提取出的数据进行的核对。
- **流程确认、验证**：按监管对计算机系统的规定，测试系统是否按要求工作；范围是整个流程，而不只是 AI 环节。
- **医学审核、获益-风险分析**：医生对病例的评估；权衡药品的获益和风险。
- **CSR（临床研究报告）**：一项已完成试验的完整报告。
- **严重事件**：在安全报告中，指导致死亡、住院、残疾或其他严重后果的事件；这类病例的时限更短。

## 用智能体搭建

**形态：** `platform`。病例保存在经过验证的安全数据库中，也从这里提交给监管机构；在这些来源中，提取功能是该数据库厂商的一个模块。经过验证的系统，通用智能体替代不了。它可以以 `skill` 的形态承担随访函（一位专员、一个病例、全程在对话中），也可以以 `service` 的形态准备提取草稿，但自己绝不写入数据库。

**需要：** 随访函 skill 需要表格形式的病例数据和待问问题，以及作为参考文件放在 skill 旁边的函件模板和联系次数规则；提取服务需要一个收件来源文件的队列，以及每个病例一份暂存文件，由病例处理团队在质控后导入；一套经公司验证团队批准、可以处理个人健康数据的环境。不要接入邮件工具，也不要让智能体访问安全数据库。

| 步骤 | 搭建方式 |
|---|---|
| 不良事件来源文件（表单、邮件、通话记录） → GenAI 将病例字段提取进安全数据库 | 安全数据库的录入模块。通用智能体只能写一份字段暂存文件，每个字段附上其来源段落，交由团队核对后导入。 |
| 🛑 review (病例处理团队双人质控) | 由病例处理团队在安全数据库中完成。 |
| 数据缺失：起草给报告人的随访函 | skill：根据病例表格和问题清单填写函件模板，每个缺失项对应一个问题。 |
| 🛑 review (药物警戒专员修改并发送) | 由药物警戒专员从自己的邮件系统发出。 |
| 🛑 sign-off (医学审核) → 提交 ICSR (E2B) | 由安全部门的医生在安全数据库中完成，提交也由该数据库发出。 |

**检查点：** `review`：对提取数据的质控在安全数据库中进行，不经过智能体；随访函 skill 给出草稿后停下，智能体没有邮件工具，由专员修改并发送。`sign-off`：医学审核和 E2B 提交都在经过验证的系统中进行，智能体无权访问，所以任何内容都不会经由智能体到达监管机构。

**与来源相比：** 来源和公开实例出自 2025-03 至 2025-10。一篇 2026-06 的行业文章回顾了 AI 在病例处理中的应用，提到 2025–2026 年的 AI 监管原则，以及 ICH E2D(R1) 和 M14 下的结构化报告格式，但没有报告这个工作流的新实例（[Pharmaceutical Commerce, 2026-06-11](https://pharmaceuticalcommerce.com/view/how-automation-and-ai-can-transform-pharmacovigilance)）。截至 2026-11 未找到更新的第一手记录。这些来源是一份厂商新闻稿、一篇关于同一部署的访谈，以及一项药物警戒专员使用公司内部基于 ChatGPT 的助手起草函件的研究；没有一个来源报告由智能体来运转整条流程，因此上面的搭建方式只覆盖随访函和暂存草稿。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 工作人员把通过电话、邮件或电子方式到达的报告，汇编为药物警戒数据库中的来源文件 [[2]](#sources)。
2. GenAI「Advanced Intake」模块把病例表单数据提取到安全系统的各字段；流程确认环节要检查「字段是否提取到了系统中正确的数据点」 [[1]](#sources)[[3]](#sources)。
3. 🛑 **审阅**：病例处理供应商按「Four Eyes」原则（第二双眼睛）对提取出的数据做质量控制 [[1]](#sources)。
4. 病例信息不完整时，LLM 根据病例数据和问题表格，起草发给报告人的文件（随访）函 [[2]](#sources)。
5. 🛑 **审阅**：药物警戒专员在发送前审阅并修改函件草稿；第二次联系尝试遵循药物警戒质量管理规范的规则 [[2]](#sources)。
6. 🛑 **签发**：安全团队对已处理的病例进行医学审核和获益-风险分析 [[3]](#sources)。

**产出：** 安全数据库中已完成的 ICSR，可供监管提交。
**失败模式 → 防护：** 集成后字段映射到错误的数据点 → 对整个流程重新验证，而不仅是 AI 环节 [1]。AI 编造病例事实 → 双人质控并就 AI 风险培训用户 [1]。严重事件藏在非严重的自由文本里 → 从自由文本叙述中提取 [1]。
**与相近工作流的区别：** AWF-0033 协调员审阅的预筛选是把患者与试验标准做匹配，AWF-0091 是起草临床研究报告（CSR）。本工作流的交付物是受监管的单病例安全报告，带双人质控和向报告人随访的闭环；交付物和检查点都不同。

## 公开实例

覆盖度（截至 2026-11-13）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [Bayer France PV, MyGenAssist cross-over study](https://pmc.ncbi.nlm.nih.gov/articles/PMC11933758/) (2025-03-10)。为期 4 个月的前后对照研究；专员审阅 LLM 起草的随访函；回复率不变。"An average of 23.3% (95% CI 13.8%-32.8%) of time saving was made"。*第一手：是；可信度：高。*
- [ArisGlobal, Boehringer Ingelheim NavaX go-live](https://www.arisglobal.com/media/press-release/boehringer-ingelheim-harnesses-genai-to-transform-case-intake-with-lifesphere-navax/) (2025-07-08)。GenAI 录入已用于 ICSR，保留质控环节；引述了 BI 药物警戒负责人的话。"up to 90% average data extraction accuracy"。*第一手：厂商；可信度：中。*
- [Journal of mHealth, BI PV Q&A](https://thejournalofmhealth.com/lessons-in-ai-use-what-worked-for-boehringer-ingelheim-in-a-pv-context/) (2025-10-09)。BI 药物警戒运营负责人谈验证、供应商质控和双人审阅；没有新数字。"We have adopted the “Four Eyes” principle (a second set of eyes)"。*第一手：访谈；可信度：中。*
