# 只看例外的对账

**与相近工作流的区别：** AWF-0038 底稿匹配式结账智能体：由会计主管在账簿锁定前审阅全部内容（分段）。本工作流中常规项目无需人工审阅即可清除，只有例外项才到人手上（抽检），交付物是例外报告，而不是结账底稿和记账凭证。
**工具变体：** `claude-code-skills` · `ledge`

## 步骤

1. 构建之前先定义流程：输入、匹配规则、输出，以及哪些例外需要人处理。流程确定后，Graph Digital 的搭建用了不到一天 [[1]](#sources)。
2. 每次运行从显式的存储中加载状态（未决例外、以往决定、已约定的阈值、处理历史），而不是依赖对话窗口 [[1]](#sources)。
3. 通过单一用途的 CLI 封装读取三个源系统（ERP、银行流水、费用管理），返回干净的结构化数据。作者称，这项工作中使用 MCP 连接反而增加了运行时间、成本和误报例外 [[1]](#sources)。
4. 按既定规则（金额、类别、时间、交易对手）交叉核对交易，找出系统之间不一致或数据超出预期范围的地方 [[1]](#sources)。
5. 常规且匹配置信度高的项目直接通过，无人查看。🛑 **接手**：智能体无法有把握归类的项目进入结构化的例外报告，交由财务处理 [[1]](#sources)。在一个厂商部署中，权限边界限制了可自动清除的范围：单笔金额上限、不含关联方或核销项目、不重述已关闭的期间。低于阈值的项目连同溯源材料交给指定的高级对账负责人 [[2]](#sources)。
6. 记录每次运行：决定、可用的上下文、调用的工具和输出。为下一次运行更新状态存储 [[1]](#sources)。审阅人的处理结果可以反馈到匹配置信度中，并根据人工推翻率重新校准阈值 [[2]](#sources)。

**产出：** 一份结构化的例外报告，每个被标记的项目都附有证据。它取代了 BI 看板和例外管理类 SaaS，财务在结账前或结账中处理这些项目。
**失败模式 → 防护：** 误报例外太多（人工工作更多而不是更少） → 精简工具接口、调优阈值。运行之间丢失上下文 → 显式的状态存储。自动清除了不该清除的项目 → 硬性权限边界（金额上限、排除关联方），并每季度根据人工推翻率重新校准 [2]。

## 公开实例

覆盖度（截至 2026-11-13）：**部分**：有第一手实例，但只覆盖流程的一部分，或检查点位置不同。收集与复核见 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [Stefan Finch, Graph Digital reconciliation agent](https://graph.digital/guides/ai-agents/replace-saas-with-ai-skill) (2026-04-18)。创始人自己的生产环境对账智能体，覆盖 ERP、银行和费用数据；只有例外项交给人。"Six months of continuous production. Zero failures."。*第一手：是；可信度：中。*
- [Grids and Guides, Autonomous reconciliation at the sub-ledger](https://gridsandguides.com/case-studies/autonomous-reconciliation) (n.d.)。未具名客户，四个子分类账；权限边界内自动清除，其余交给指定审阅人。"94% of monthly line items matched with zero human touch"。*第一手：厂商；可信度：低。*
