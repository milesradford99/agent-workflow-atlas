# 只看例外的对账

**工具变体：** `claude-code-skills` · `ledge`

## 背景

对账是一项记账核对：同一笔交易，在每个本该记录它的系统里都出现，而且金额相同。这些系统包括财务系统、银行对账单，以及员工用来报销的工具。财务团队在每月结账前做这件事。大部分精力花在确认大量相符的项目上，为的是找出少数不相符的。在这里，智能体按计划定时做匹配，凡是它有把握匹配上的都直接放行，所以人只看到不一致的或它无法归类的项目。这些项目仍由人来处理。判断两条记录为什么不同（时间差、差错、不当行为），以及用哪笔分录来更正，是一项会计判断，必须有人能向审计师说明理由。

**术语：**
- **ERP**：公司主要的财务与运营系统。
- **结账**：月末把账簿定稿的过程；结账之后，该期间的数字就固定了。
- **例外**：匹配规则没能清除的交易。
- **误报**：被标为例外、其实没有问题的项目。
- **状态存储**：智能体对话之外的一个文件或数据库，保存以往各次运行的决定。
- **CLI 封装**：只做一件事的小型命令行脚本，例如取回昨天的银行流水，并输出结构化数据。
- **MCP**：把智能体连接到外部系统的工具和数据的一种标准方式。
- **权限边界**：对智能体可以自行清除哪些项目的硬性限制，例如单笔金额上限。
- **关联方项目、核销**：与有关联的公司或个人之间的交易；决定不再指望收回某笔款项。两者都会受到审计师更严格的审查。

## 用智能体搭建

**形态：** `service`。每次运行按计划启动，现场没有人，人只看到例外报告。

**需要：** 对 ERP、银行流水和费用系统的只读访问，每个系统一个小脚本，或者通过 MCP 连接器；一个运行时可读可写的状态存储（仓库里的一个文件或一张数据库表），用来保存未决例外、以往决定和阈值；例外报告的落点，例如工单队列或共享文件夹。不要给智能体任何向总账过账的途径。

| 步骤 | 搭建方式 |
|---|---|
| 定时运行 | 这些系统能从云端访问时，用云端定时任务；否则用自己的调度器启动 `claude -p` 或一个 Agent SDK 程序。 |
| 从状态存储加载以往例外和阈值 | skill 的第一条指令：读取状态文件。不从以前的对话里继承任何内容。 |
| 读取 ERP + 银行流水 + 费用系统 | skill 旁边每个系统一个脚本，各自返回结构化的行。 |
| 每笔交易：交叉核对规则 | 规则放在 skill 旁边的参考文件里。完全相符的由脚本清除；剩下的由智能体逐项处理。 |
| 匹配有把握：直接通过 | 写入运行日志。不需要人参与。 |
| 有差异或置信度低：🛑 handoff | 加入例外报告，附上各系统的记录和未通过的规则。 |
| 例外报告 → 写入运行日志和状态 | skill 的最后一步。由调用它的程序或 `Stop` 钩子确认状态文件已写入，这次运行才算完成。 |

**检查点：** `handoff`：例外报告是这次运行唯一发给人的东西，智能体也没有任何能改动总账的工具，所以每个例外都由人在 ERP 里处理。他们的决定写入状态存储，供下一次运行使用。对“哪些可以不经人手清除”的限制（金额上限、不含关联方或核销项目）应当放在匹配脚本或钩子里，那里跳不过去；不要只写在 skill 的文字里。

**与来源相比：** 来源 1 归在工具 `claude-code-skills` 之下，这套搭建方式沿用了它报告的设计：显式的状态存储、每个系统一个脚本、输出只限于例外。云端定时任务（截至 2026-11 仍是研究预览）现在可以提供定时触发，不必自建调度器。来源 2 描述的是一款厂商产品；它根据审阅人推翻智能体的频率来重新校准阈值，这一点不在本搭建方式之内。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 搭建之前，团队先定义流程：输入、匹配规则、输出，以及哪些例外需要人处理。流程确定后，Graph Digital 的搭建用了不到一天 [[1]](#sources)。
2. 每次运行开始时，智能体从显式的存储中加载状态（未决例外、以往决定、已约定的阈值、处理历史），而不是依赖对话窗口 [[1]](#sources)。
3. 智能体通过单一用途的 CLI 封装读取三个源系统（ERP、银行流水、费用管理），返回干净的结构化数据。作者称，这项工作中使用 MCP 连接反而增加了运行时间、成本和误报例外 [[1]](#sources)。
4. 智能体按既定规则（金额、类别、时间、交易对手）交叉核对交易，找出系统之间不一致或数据超出预期范围的地方 [[1]](#sources)。
5. 常规且匹配置信度高的项目直接通过，无人查看。🛑 **接手**：智能体无法有把握归类的项目进入结构化的例外报告，交由财务处理 [[1]](#sources)。在一个厂商部署中，权限边界限制了可自动清除的范围：单笔金额上限、不含关联方或核销项目、不重述已关闭的期间。低于阈值的项目连同溯源材料交给指定的高级对账负责人 [[2]](#sources)。
6. 智能体记录每次运行：决定、可用的上下文、调用的工具和输出。它为下一次运行更新状态存储 [[1]](#sources)。审阅人的处理结果可以反馈到匹配置信度中，并根据人工推翻率重新校准阈值 [[2]](#sources)。

**产出：** 一份结构化的例外报告，每个被标记的项目都附有证据。它取代了 BI 看板和例外管理类 SaaS，财务在结账前或结账中处理这些项目。
**失败模式 → 防护：** 误报例外太多（人工工作更多而不是更少） → 精简工具接口、调优阈值。运行之间丢失上下文 → 显式的状态存储。自动清除了不该清除的项目 → 硬性权限边界（金额上限、排除关联方），并每季度根据人工推翻率重新校准 [2]。
**与相近工作流的区别：** AWF-0038 底稿匹配式结账智能体：由会计主管在账簿锁定前审阅全部内容（分段）。本工作流中常规项目无需人工审阅即可清除，只有例外项才到人手上（抽检），交付物是例外报告，而不是结账底稿和记账凭证。

## 公开实例

覆盖度（截至 2026-11-13）：**部分**：有第一手实例，但只覆盖流程的一部分，或检查点位置不同。收集与复核见 [Third collection pass](../../../../../research/2026-11-third-pass.md)。

- [Stefan Finch, Graph Digital reconciliation agent](https://graph.digital/guides/ai-agents/replace-saas-with-ai-skill) (2026-04-18)。创始人自己的生产环境对账智能体，覆盖 ERP、银行和费用数据；只有例外项交给人。"Six months of continuous production. Zero failures."。*第一手：是；可信度：中。*
- [Grids and Guides, Autonomous reconciliation at the sub-ledger](https://gridsandguides.com/case-studies/autonomous-reconciliation) (n.d.)。未具名客户，四个子分类账；权限边界内自动清除，其余交给指定审阅人。"94% of monthly line items matched with zero human touch"。*第一手：厂商；可信度：低。*
