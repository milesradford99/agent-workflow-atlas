# 负责人确认的采购订单预提

**工具变体：** `amazon-bedrock-agentcore` · `strands-agents` · `sap-s4hana`

## 背景

公司已经收到了货物或服务但还没收到账单时，会计规则仍要求把这笔成本记在它发生的那个月。这笔分录叫预提。对于一张涵盖长期工作的采购订单（PO），比如要做一到两年的定制工装，财务必须弄清交付进展到哪里，算出多少成本属于当期，然后入账。这些事实掌握在下单的人手里，所以财务要发邮件问订单负责人，等回复，再做一张表格。在这里，智能体从每张需要预提的采购订单出发，询问订单负责人，读取回复，按公司的书面流程算出金额，并准备好分录但不过账。订单负责人必须确认事实，因为别人不知道；每笔分录过账前由财务经理批准，因为一旦过账就改变了审计师要检查的账簿。

**术语：**
- **采购订单（PO）**：公司向供应商下的订单，写明买什么和约定的价格。
- **预提**：在费用发生的当月入账、早于发票到达的费用。
- **按时间比例的直线法预提**：把成本平均分摊到交付期内，只记入落在当月的那一份。
- **会计分录**：账簿里关于借记和贷记什么的记录。**暂存**分录已保存在 ERP 中，但还没有过账到账簿。
- **ERP、SAP**：公司主要的会计系统；SAP 是这类产品之一。
- **SOP（标准操作规程）**：公司针对某项工作的书面规则，这里指何时、如何预提。
- **重要性**：金额要多大才值得更仔细地处理。金额小的项目可以走较简单的路径。
- **GAAP**：公司账簿必须遵循的会计准则。
- **审计轨迹**：每一步何时发生、由谁（或什么）完成的记录，外部审计师会阅读。

## 用智能体搭建

**形态：** `service`。每次运行由事件触发，也就是某张采购订单需要预提，现场没有人在键盘前；它还要等好几天才能等到负责人回复，所以状态保存在对话之外，人只看到给负责人的提问和暂存的分录。

**需要：** 对 ERP 中采购订单的读取权限，以及创建暂存分录但不能过账的权限；作为参考文件的预提 SOP 和重要性阈值；一个公司自己控制的、可以收发邮件的邮箱；一个状态存储（数据库表或文件），保存每张订单的状态、负责人的回复和步骤日志；一个给财务经理的审阅队列。

| 步骤 | 搭建方式 |
|---|---|
| SAP 事件：采购订单需要预提 | 一个定时任务向 ERP 查询需要预提的采购订单，并为每张订单启动一次运行，用云端定时任务，或自己的调度器启动 `claude -p` 或一个 Agent SDK 程序。 |
| 从知识库加载订单数据 + 预提 SOP → 按重要性阈值分流 | skill 的第一条指令：读取订单和 SOP 参考文件。由脚本套用阈值；规则没有定论的部分由智能体处理。 |
| 邮件通知订单负责人：🛑 handoff | 智能体通过邮件连接器起草并发出提问，并在状态存储中记下“等待负责人回复”。这次运行结束；负责人的回复启动下一次运行。 |
| 解析回复 → 按直线法按时间比例预提 | 智能体读取回复，提取交付时间，由脚本计算直线法的金额。 |
| 创建暂存会计分录 | 脚本在 ERP 中创建暂存分录，所用的凭据没有过账权限。 |
| 🛑 action (财务经理在过账前批准) | 分录及其计算过程进入财务经理的队列。 |
| 过账到 SAP + 审计轨迹 | 经理在 ERP 中过账。运行把每一步连同时间戳写入状态存储。 |

**检查点：** `handoff`：运行向订单负责人发出一个提问后就停下；在回复被记录之前，什么都不会往下走，没有回复的负责人会一直在状态存储中可见。`action`：智能体的凭据能创建暂存分录，不能过账，所以由财务经理过账。这条限制应当设在 ERP 的权限里，不要只写在 skill 的文字里。

**与来源相比：** 来源 1 出自 2026-08，公开实例就是同一篇文章。它是与云厂商合写的客户案例，讲的是它自己的技术栈，所以上面的搭建方式是依据它的步骤做出的设计，不是照搬。来源中的智能体运行环境、无服务器任务、知识库和数据库，在这里换成了带参考文件的 skill、一个调度器和一个状态存储。云端定时任务截至 2026-11 仍是研究预览。来源报告的结果（每个周期省去 15 天手工工作）不适用于这套搭建方式。把边缘情况回填到 SOP 这一点，留给财务经理去编辑参考文件。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 无服务器任务（Lambda）轮询 SAP S/4HANA（OData 事件），查找需要预提的定制工装采购订单；工装周期 12–24 个月，发票可能在订单下达 18 个月以后才到 [[1]](#sources)。
2. 智能体从知识库检索预提 SOP（金额阈值、订单特征、交付时间、GAAP 规则），并按重要性把每张订单分流到相应的校验路径 [[1]](#sources)。
3. 智能体通过 MCP 服务器用 Amazon SES 发送邮件并解析回复；被它取代的手工流程需要邮件询问订单负责人以确认交付日期。🛑 **接手**：由订单负责人提供确认 [[1]](#sources)。
4. 智能体按直线法计算按时间比例的预提，并在 SAP 中创建暂存会计分录；每一步都带时间戳记录在 DynamoDB 中 [[1]](#sources)。
5. 🛑 **操作**：任何会计分录过账前，最终批准权仍在财务经理手中；他们发现的边缘情况会回填到 SOP 文档 [[1]](#sources)。

**产出：** 每张采购订单一笔已批准并过账的预提会计分录，并附完整的审计轨迹供外部审计师使用。
**失败模式 → 防护：** 硬编码规则脆弱 → 业务逻辑放在可编辑的 SOP 中；未经审阅就过账 → 分录在经理批准前一直保持暂存；SOP 有缺口 → 经理审阅时找出边缘情况，用于完善 SOP [1]。
**与相近工作流的区别：** AWF-0038（以底稿匹配的结账智能体）按月批量准备所有结账领域，由一位财务主管统一审阅；AWF-0164 对账交易并转交异常。本工作流按采购订单由事件触发，向订单负责人询问事实，并要求每笔分录过账前单独批准。替换测试在交付物（单笔预提分录）和检查点（负责人接手 + 逐笔操作）上不通过。
