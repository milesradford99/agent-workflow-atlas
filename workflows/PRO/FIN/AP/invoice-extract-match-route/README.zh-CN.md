# 发票提取、匹配与分流

## 背景

应付账款（AP）是财务团队里负责支付公司收到的账单的那一部分。每张供应商发票都要读一遍，对照实际订购和收到的东西核对，记到账簿里正确的科目，由有权批准这笔金额的人批准，然后付款。发票版式和语言五花八门，人要一遍遍重复录入同样的字段，重复发票或被篡改的发票也很容易漏过。欺诈往往表现为供应商银行账户被悄悄改掉。在这里，智能体读发票、做核查、与订单匹配并编码，人只看到对不上的部分。每个异常仍由人处理，每个付款批次仍由有付款权限的人批准，因为钱要从公司流出去，批准的人要为此负责。

**术语：**
- **发票、采购订单（PO）、收货单**：供应商的账单；公司的采购订单，写明订了什么；货物或服务已经到达的记录。
- **三单匹配**：核对发票、采购订单和收货单在品种、数量和金额上是否一致。
- **总账科目编码（GL coding）**：为发票的每一行选定记入的总账科目（账簿里的类别）。
- **供应商主数据**：公司认可的供应商名单及其资料，包括银行账户。
- **OCR**：把扫描页面转成文字的软件。
- **ERP**：公司主要的财务与运营系统，获批的应付款在其中过账并付款。
- **授权矩阵（delegation-of-authority matrix）**：规定谁可以批准多大金额支出的表，按发票金额和类型划分。
- **SOX**：美国法律，要求上市公司对财务报告保持内部控制并留存审计轨迹。

## 用智能体搭建

**形态：** `service`。发票在供应商发来时通过邮件和门户到达，处理时没有人在键盘前，人只看到例外和付款批次。

**需要：** 对发票所在的收件箱或门户的读取权限；通过脚本或 MCP 连接器，对 ERP 中的供应商主数据、未结采购订单和收货单的读取权限；一份放总账科目编码规则和授权矩阵的参考文件；一个位于对话之外的存储，保存每张发票提取的字段、核查结果和状态；一个让例外和付款批次等人处理的队列。不要给智能体任何释放付款或修改供应商银行账户信息的工具。

| 步骤 | 搭建方式 |
|---|---|
| 发票 → 提取字段并给出置信度 | 云端定时任务，或自己的调度器启动 `claude -p` 或一个 Agent SDK 程序，来接手每张新发票。OCR 由脚本完成；智能体读取文字，返回表头字段和明细行，并给每个字段一个置信度。 |
| 核查供应商、重复、银行账户信息 | 脚本把提取出的供应商、发票号和银行账户信息，与供应商主数据和以往发票比对。银行账户信息变更绝不由智能体自行放行。 |
| 三单匹配 → 总账科目编码 | 脚本匹配发票、采购订单和收货单，清除在设定容差内的差异；智能体根据编码参考文件提出总账科目，并为没能匹配的项目写出建议修复方案。 |
| 已匹配：排入付款队列 | 发票在状态存储中记为可进入付款批次。 |
| 异常：🛑 handoff | 发票、提取的数据、证据和建议修复方案进入审阅队列。 |
| 🛑 sign-off (付款批次) | 智能体为指定的审批人整理好付款批次，然后停下。 |

**检查点：** `handoff`：每个异常，以及每一次银行账户信息变更（不论有无异常），都带着已收集的证据进入审阅队列；由人在 ERP 中处理，决定记入状态存储。`sign-off`：智能体没有付款或释放付款的工具，所以由授权矩阵指定的审批人在付款系统中操作。“银行账户信息变更或超过限额的金额必须交给人”这条规则，应当放在匹配脚本或 `PreToolUse` 钩子里，不要只写在 skill 的文字里。

**与来源相比：** 来源出自 2025-04 至 2025-11。来源 1（Uber 工程团队的文章，2025-04）在撰写本节时无法打开；这套搭建方式依据的是本条目的步骤和来源 2，后者是一篇厂商文章（2025-11），介绍的是产品，没有展示其内部做法。来源描述的是专门构建的流水线：OCR、微调或托管的模型，以及定制的审阅界面；上面的搭建方式用读取 OCR 文字的智能体取代了模型这一步，并且不包括审阅界面、根据历史学习总账科目，以及按字段准确率重新训练。通用智能体不能签发付款批次，PDF 与数据并排显示的界面是你所选审阅工具的功能。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

**规则：** 银行账户信息变更*一律*交给人处理，因为这是欺诈信号。付款审批遵循授权矩阵（delegation-of-authority matrix）。完整的审计轨迹为 SOX 合规而保留。

1. 供应商门户（针对采购订单提交）和邮件接收发票，邮件会生成工单；接入服务提取附件 PDF。系统对低分辨率扫描件和手写内容做预处理，并统一多页文档的格式 [[1]](#sources)。
2. 系统提取字段：先 OCR（Uber 的 Vision Gateway），再用 LLM 提取表头字段和明细行。Uber 选择 GPT-4，因为微调模型处理明细行的效果不佳。团队按字段跟踪准确率，把准确率低于阈值的供应商送去做画像和标注 [[1]](#sources)。
3. 系统核查供应商、重复和银行账户信息：后处理的业务规则与现有数据库交叉比对 [[1]](#sources)。审批前，欺诈智能体会标记“unverified bank details, mismatched vendor domains, or edited invoice copies”，向新账户或未验证账户支付超过 $5,000 的付款会暂停，等待人工复核 [[2]](#sources)。任何银行账户信息变更都交给人处理（见规则）。
4. 系统对发票、采购订单和收货单做三单匹配。智能体会清除可接受的小差异，例如数量略有变动、合理的运费和提前到货。任何未解决的问题都会成为带上下文和建议修复方案的异常 [[2]](#sources)。
5. 智能体逐行套用总账科目编码，编码依据组织的历史付款和会计数据学习得出 [[2]](#sources)。已匹配的发票排入付款队列；异常则分流给人处理。
6. 🛑 **接手**：应付账款审阅人在 PDF 与提取数据并排显示的界面中处理每个异常，提醒和软警告集中显示在一处 [[1]](#sources)，并参考智能体给出的上下文和建议修复方案 [[2]](#sources)。银行账户信息变更一律进入这一步。
7. 🛑 **签发**：由授权矩阵指定的审批人对付款批次签发。审批路径按发票金额、供应商类型或类别配置，审批智能体会汇总供应商历史、合同条款、采购订单匹配情况和过往发票 [[2]](#sources)。获批的发票送入 ERP 付款 [[1]](#sources)。

**产出：** 获批的应付款过账到 ERP 进入付款批次，每个操作、决定和异常都记录在审计轨迹中 [[2]](#sources)。
**失败模式 → 防护：** 凭空生成的值，尤其是明细行 → 业务规则检查加人工复核 [[1]](#sources)。新格式、25 种以上语言、手写内容和准确率漂移 → 预处理、给低准确率的供应商做标注、跟踪准确率并定期重新训练 [[1]](#sources)。供应商主数据混乱或编码历史不一致会拖慢学习 → 上线前先清理，并在“30 to 90 days”的学习期内配合人工复核和纠正 [[2]](#sources)。付款被改道到变更过或未验证的银行账户 → 欺诈信号加自动暂停等待人工复核 [[2]](#sources)；通过基于角色的访问权限实现职责分离 [[2]](#sources)。
