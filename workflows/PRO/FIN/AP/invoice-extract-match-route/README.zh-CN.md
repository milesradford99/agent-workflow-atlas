# 发票提取、匹配与分流

**规则：** 银行账户信息变更*一律*交给人处理，因为这是欺诈信号。付款审批遵循授权矩阵（delegation-of-authority matrix）。完整的审计轨迹为 SOX 合规而保留。

## 步骤

1. 从供应商门户（针对采购订单提交）和邮件接收发票，邮件会生成工单；接入服务提取附件 PDF。对低分辨率扫描件和手写内容做预处理，并统一多页文档的格式 [[1]](#sources)。
2. 提取字段：先 OCR（Uber 的 Vision Gateway），再用 LLM 提取表头字段和明细行。Uber 选择 GPT-4，因为微调模型处理明细行的效果不佳。按字段跟踪准确率，准确率低于阈值的供应商送去做画像和标注 [[1]](#sources)。
3. 核查供应商、重复和银行账户信息：后处理的业务规则与现有数据库交叉比对 [[1]](#sources)。审批前，欺诈智能体会标记“unverified bank details, mismatched vendor domains, or edited invoice copies”，向新账户或未验证账户支付超过 $5,000 的付款会暂停，等待人工复核 [[2]](#sources)。任何银行账户信息变更都交给人处理（见规则）。
4. 对发票、采购订单和收货单做三单匹配。智能体会清除可接受的小差异，例如数量略有变动、合理的运费和提前到货。任何未解决的问题都会成为带上下文和建议修复方案的异常 [[2]](#sources)。
5. 逐行套用总账科目编码，编码依据组织的历史付款和会计数据学习得出 [[2]](#sources)。已匹配的发票排入付款队列；异常则分流给人处理。
6. 🛑 **接手**：应付账款审阅人在 PDF 与提取数据并排显示的界面中处理每个异常，提醒和软警告集中显示在一处 [[1]](#sources)，并参考智能体给出的上下文和建议修复方案 [[2]](#sources)。银行账户信息变更一律进入这一步。
7. 🛑 **签发**：由授权矩阵指定的审批人对付款批次签发。审批路径按发票金额、供应商类型或类别配置，审批智能体会汇总供应商历史、合同条款、采购订单匹配情况和过往发票 [[2]](#sources)。获批的发票送入 ERP 付款 [[1]](#sources)。

**产出：** 获批的应付款过账到 ERP 进入付款批次，每个操作、决定和异常都记录在审计轨迹中 [[2]](#sources)。
**失败模式 → 防护：** 凭空生成的值，尤其是明细行 → 业务规则检查加人工复核 [[1]](#sources)。新格式、25 种以上语言、手写内容和准确率漂移 → 预处理、给低准确率的供应商做标注、跟踪准确率并定期重新训练 [[1]](#sources)。供应商主数据混乱或编码历史不一致会拖慢学习 → 上线前先清理，并在“30 to 90 days”的学习期内配合人工复核和纠正 [[2]](#sources)。付款被改道到变更过或未验证的银行账户 → 欺诈信号加自动暂停等待人工复核 [[2]](#sources)；通过基于角色的访问权限实现职责分离 [[2]](#sources)。
