# 引用政策条款的费用审核

**工具变体：** `ramp-policy-agent`

## 背景

员工用公司的卡消费，或通过报销单把自己垫的钱要回来。财务人员要对照公司书面的费用政策（可以买什么、限额多少、要什么凭证）逐笔核对，批准，再把它记入会计账簿。大部分条目明显符合政策，全靠手工逐笔去读既慢，还是会漏过被篡改的收据。在这里，智能体对照政策读每一笔费用，把明显低风险的批准并记下依据的是哪一条，只把异常项交给审批人。每个异常项仍由人来裁定，已批准的费用仍由人标记就绪并同步到总账，政策本身要不要修改也仍由人决定，因为政策是公司的规则，账上写了什么由财务负责。

**术语：**
- **费用政策**：公司关于员工可以花钱买什么、限额多少、必须保留什么凭证的书面规则。
- **异常项**：智能体无法按政策明确批准的费用。
- **审计轨迹**：每项决定、由谁（或什么）作出、依据是什么的记录。
- **总账（GL）**：公司主要的会计记录。同步一笔费用，就是把它过账到这里。
- **标记就绪并同步**：复核人的最后一步，确认已批准的费用并把它送入总账。

## 用智能体搭建

**形态：** `service`。费用在刷卡和提交报销时全天到来，检查时没有人在键盘前，人只看到异常项和政策修改建议。

**需要：** 放在 skill 旁边、作为参考文件的文本或 PDF 费用政策；通过脚本或 MCP 连接器，对费用系统中的交易、收据、备注和员工信息的读取权限；一个位于对话之外的存储，保存每项决定、理由和所引用的条款；一个让异常项等审批人处理的队列。不要给智能体任何标记就绪、向总账过账或修改政策的工具。

| 步骤 | 搭建方式 |
|---|---|
| 上传费用政策 PDF | 政策文件作为参考文件放在 skill 旁边；政策变化时由财务替换。 |
| 每个费用：对照政策检查并附条款引用 | 云端定时任务，或自己的调度器启动 `claude -p` 或一个 Agent SDK 程序，来接手每笔新费用。skill 让智能体把它与政策对照，返回决定、理由和所引用的条款。 |
| 低风险：通过并附理由 | 决定、理由和条款写入状态存储，作为审计轨迹。智能体可以批准的金额上限或类别由脚本把关。 |
| 异常或可疑收据：🛑 handoff | 费用、智能体的建议和理由进入审批人的队列。 |
| 🛑 action (复核人标记就绪并同步) | 复核人在费用系统里完成；智能体没有这样的工具。 |
| 建议政策修改 → 🛑 review | skill 把引发升级的条款汇总成一份建议文件，交给财务。 |

**检查点：** `handoff`：每个异常项带着建议和理由进入审批人的队列，审批人的决定写回状态存储。`action`：智能体没有标记就绪或向总账过账的工具，所以由复核人手工完成。绝不允许自动通过的金额上限和类别，应当放在脚本或 `PreToolUse` 钩子里，不要只写在 skill 的文字里。`review`：skill 写完政策修改建议后停下；它改不了政策文件，由财务决定。

**与来源相比：** 来源出自 2025-07（回复到 2025-10）。两个来源讲的都是 Ramp 自己的智能体产品，所以这些步骤是厂商的说法，看不到内部做法；上面的搭建方式是一个依据政策文件工作的智能体，不是该产品的复刻。Ramp 较新的一篇文章（2026-01-13，[Policy Agent now available to all Ramp Plus customers](https://ramp.com/blog/ramp-policy-agent-ga-launch)）称，Policy Agent 给出批准、拒绝或复核的建议，并由财务主管选择哪些费用可以由它自动批准。来源没有界定低风险和异常项的阈值；这套搭建方式把阈值留给你来定。它不包括短信答疑，也不包括根据使用情况和反馈来学习。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 财务上传公司的 PDF 费用政策，智能体开始执行该政策 [[2]](#sources)。
2. 智能体全天候检查每一笔员工费用，并结合交易明细，标记可疑的收据和发票 [[1]](#sources)[[2]](#sources)。
3. 智能体自动通过低风险费用。每项决定都记录理由和所依据的政策条款，并写入审计轨迹 [[1]](#sources)[[2]](#sources)。
4. 🛑 **接手**：智能体把真正的异常项连同它的建议和理由交给人工审批人 [[1]](#sources)[[2]](#sources)。
5. 🛑 **操作**：智能体不会把费用标记为就绪，也不会把它们同步到总账；这一步仍由复核人手工完成 [[2]](#sources)。
6. 智能体通过短信回答员工的政策问题，并根据使用情况和反馈建议修改政策 [[1]](#sources)[[2]](#sources)。🛑 **审阅**：由财务决定是否修改政策。

**产出：** 附政策条款引用的已通过或已升级的费用决定，供复核人标记就绪并同步到总账（GL）。
**失败模式 → 防护：** 两个来源都没有界定低风险和异常的阈值 → 保留人工的标记就绪/同步这一步，并抽查审计轨迹。准确率的说法由厂商自报（“99% accuracy”）→ 先测算自己的人工推翻率，再依赖自动通过 [[1]](#sources)[[2]](#sources)。
**与相近工作流的区别：** 最接近的是 AWF-0022 发票提取-匹配-分派（Invoice extract-match-route，应付账款），它提取供应商发票并做三单匹配，最后由付款批次的签发收尾。本工作流则是依据书面政策裁定员工费用。智能体自动通过低风险条目，不需要人逐笔批准，人只看到升级上来的情况以及“标记就绪/同步”这一步，因此产出物和检查点都不同。
