# 专家审批的应税规则

**工具变体：** `openai-rft`

## 背景

销售商品或服务的公司，必须在每个销售地征收正确的销售税或增值税。一件产品是否应税、税率多少、税款应在哪里缴纳，取决于当地的法律，而这些法律和官方指引一直在变。因此，结账时计算税款的软件（税务引擎）需要为每个辖区的每种产品类型配一条规则，传统上由税务专家阅读法律并逐条手写。在这里，智能体阅读来源并提出每条规则，附上推理和引用，并留意会影响现行规则的新指引。税务专家对每一份提案批准、修改或驳回之后，它才会进入引擎，因为错误的规则会被用于每一笔交易，公司要对多收或漏收的税款负责。

**术语：**
- **应税性（taxability）**：某种产品在某地是否征税，以及税率多少。
- **辖区（jurisdiction）**：有自己税法的州、国家或其他主管机构。
- **成文法、条例、指引、私人信函裁定**：法律本身；依据法律制定的细则；税务机关发布的解释；以及税务机关就某个具体问题对单个纳税人作出的裁定。
- **来源地、分摊（sourcing, apportionment）**：确定一笔销售属于哪个辖区，以及涉及多个辖区时税款如何分摊。
- **减免（abatement）**：对本应适用的税款的减轻或免除。
- **税务引擎**：把规则应用到每笔交易并返回应缴税额的软件。
- **混合索引（稠密 + 稀疏）**：既按含义、又按原词匹配的搜索索引，使查询能找到对应的法律条文。
- **微调（fine-tuning）**：用机构自己的例子（这里是专家的修改）进一步训练模型。
- **无需修改的准确率**：专家不作任何修改就批准的提案所占的比例。

## 用智能体搭建

**形态：** `service`。新的指引到来时没有人在场，所以监控和提案按计划运行，人只看到待审阅的提案和提醒队列。

**需要：** 一个存放各项依据（成文法、条例、指引、裁定）的库，每项都标注辖区、生效日期和依据类型，并配一个既能按含义也能按原词查找段落的搜索索引；一份产品与辖区任务清单，写明目标、该辖区的征税方式、已知的模糊点和现有处理；一个保存以往专家决定及理由的状态存储（文件或数据库表）；供税务专家处理的审阅队列。不要给智能体任何写入生产税务引擎的权限。

| 步骤 | 搭建方式 |
|---|---|
| 摄取法规、条例、指引、裁定 | 云端定时任务，或自己的调度器启动 `claude -p` 或一个 Agent SDK 程序，每个主管机构网站运行一个脚本，抓取新增或变更的文件。 |
| 规范化 + 切分 + 打标签 → 混合索引 | 脚本按文件自身的标题切分，标注辖区、生效日期和依据类型，然后装入索引。智能体通过 MCP 服务器访问索引。 |
| 每个产品 × 辖区：检索依据 + 以往审阅信号 | 脚本旁边的 skill 在每次运行开始时读取任务，并从状态存储中读取该辖区以往的专家决定。 |
| 提出应税性、税率、来源地判定及推理和引用 | skill 为每个任务写出一份结构化提案：判定、推理摘要，以及每一点的引用。脚本会拒绝任何缺少引用的提案。 |
| 🛑 review | 见“检查点”。 |
| 获批：版本化规则进入生产税务引擎 | 由另一个脚本（不是智能体）把每份获批的提案变成版本化的规则文件并载入。 |
| 反馈回流到检索 + 微调 → 新指引：标记受影响的判定 | 专家的决定和理由保存到状态存储，供之后的运行读取。摄取一步发现某项依据有变更时，会有一次运行重新检查引用它的规则，并向队列添加提醒。 |

**检查点：** `review`：每份提案和提醒都连同推理和被引用的段落进入审阅队列，专家批准、修改或驳回，并附简短理由。智能体没有写入税务引擎的工具，晋升脚本只读取标记为已批准的项目，所以未经审阅的提案不可能生效。

**与来源相比：** 唯一的来源及其公开实例出自 2025-11-23；这是厂商对自己流水线的说明，所以没有拿别的说法对照。来源报告了一个用专家反馈微调过的模型，以及一个表现更差的、用现成模型的标准检索方案（无需修改的准确率不足 65%）。这套搭建方式没有微调这一步，因为上面的构件里没有；它改为把专家以往的决定传入每次运行，所以不应假定它能达到来源中的准确率。来源自建了爬取工具和审阅看板，这里对应的是脚本和一个队列。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 网页自动化系统持续摄取并监控成文法、条例、指引、公告、判例和私人信函裁定 [[1]](#sources)。
2. 材料先规范化，再切分成章节（规则加 LLM 切分），标注辖区、依据类型、生效日期和层级，然后建立稠密 + 稀疏索引 [[1]](#sources)。
3. 对每个任务（某辖区的某个产品，或一个产品分类），系统会获得目标、该辖区的征税方式、已知的模糊点、现有处理、检索到的依据，以及以往专家审阅留下的信号 [[1]](#sources)。
4. 微调过的推理模型提出结构化的判定（应税性、税率、减免、来源地/分摊），并附推理摘要和引用 [[1]](#sources)。
5. 🛑 **审阅**：内部税务专家在审阅看板上查看提案、推理和依据，批准、修改或驳回，任何改动都要简短说明理由 [[1]](#sources)。
6. 获批结果成为版本化规则，推送到生产税务引擎；审阅人的说明回流到检索和微调数据集；看板还会对受新指引影响的现有判定发出提醒 [[1]](#sources)。

**产出：** 带引用的、版本化且机器可读的应税性/税率/来源地规则，已在税务计算引擎中生效。
**失败模式 → 防护：** 现成的 RAG 无需修改的准确率不足 65%，每次审阅约 2 分钟 → 用专家反馈做微调，并传入以往审阅信号；指引变化后规则过期 → 监控会标记受影响的判定以便重新审阅 [1]。
**与相近工作流的区别：** AWF-0165（分议题拆分的通知函回复）起草的是给客户的函件；AWF-0041（1040 申报表准备）准备的是单份申报表。本工作流的交付物是每个产品 × 辖区的可复用税务规则，每一条都经专家审阅后才进入生产引擎，并带有反馈回路。替换测试在交付物上不通过。
