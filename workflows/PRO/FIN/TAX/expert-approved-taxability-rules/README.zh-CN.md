# 专家审批的应税规则

**与相近工作流的区别：** AWF-0165（分议题拆分的通知函回复）起草的是给客户的函件；AWF-0041（1040 申报表准备）准备的是单份申报表。本工作流的交付物是每个产品 × 辖区的可复用税务规则，每一条都经专家审阅后才进入生产引擎，并带有反馈回路。替换测试在交付物上不通过。
**工具变体：** `openai-rft`

## 步骤

1. 网页自动化持续摄取并监控成文法、条例、指引、公告、判例和私人信函裁定 [[1]](#sources)。
2. 材料先规范化，再切分成章节（规则加 LLM 切分），标注辖区、依据类型、生效日期和层级，然后建立稠密 + 稀疏索引 [[1]](#sources)。
3. 对每个任务（某辖区的某个产品，或一个产品分类），系统会获得目标、该辖区的征税方式、已知的模糊点、现有处理、检索到的依据，以及以往专家审阅留下的信号 [[1]](#sources)。
4. 微调过的推理模型提出结构化的判定（应税性、税率、减免、来源地/分摊），并附推理摘要和引用 [[1]](#sources)。
5. 🛑 **审阅**：内部税务专家在审阅看板上查看提案、推理和依据，批准、修改或驳回，任何改动都要简短说明理由 [[1]](#sources)。
6. 获批结果成为版本化规则，推送到生产税务引擎；审阅人的说明回流到检索和微调数据集；看板还会对受新指引影响的现有判定发出提醒 [[1]](#sources)。

**产出：** 带引用的、版本化且机器可读的应税性/税率/来源地规则，已在税务计算引擎中生效。
**失败模式 → 防护：** 现成的 RAG 无需修改的准确率不足 65%，每次审阅约 2 分钟 → 用专家反馈做微调，并传入以往审阅信号；指引变化后规则过期 → 监控会标记受影响的判定以便重新审阅 [1]。

## 公开实例

覆盖度（截至 2026-11-13）：**充分**：有详细的第一手实例，与流程的大部分环节一致。收集与复核见 [Fourth collection pass](../../../../../research/2026-11-fourth-pass.md)。

- [Sphere, Building TRAM](https://www.getsphere.com/blog/building-tram) (2025-11-23)。自有生产流水线；记录了无需修改的准确率和专家每条判定审阅时间的变化。"median review time has dropped by ~92 percent, from nearly 120 seconds to under 10 seconds per determination". *第一手：是；可信度：高。*
