# 按问题拆分的税务通知回复

**工具变体：** `shorthills-copilot`

## 背景

税务机关会向企业发出书面通知，质疑某份申报、要求补充资料，企业必须在期限内回复。一份通知往往包含好几个各自独立的问题。会计或咨询公司里的顾问（此处称顾问）要阅读通知，查找客户以往的申报资料、此前的回复以及相关的法律和判例，再写出逐个问题、附有证据的回复。这件事靠手工很慢，问题多、证据量大时还可能漏掉一点。在这里，智能体把通知拆成各个问题，为每个问题收集证据，并按公司的模板起草带引用的回复。回复发出之前，由顾问修改并批准，因为公司要为代表客户向税务机关所说的话承担职业责任。

**术语：**
- **税务通知**：税务机关发出的书面文件，质疑某份申报、要求提供资料或提出调整。
- **问题（issue）**：通知中一个独立的疑问或主张，需要单独回答。
- **顾问**：公司里负责准备并批准客户回复的专业人员。
- **客户申报资料**：公司为客户保存的申报表和佐证记录。
- **通告（circular）**：税务机关发布的官方解释或指示。
- **判例（precedent）**：对类似问题以往作出的裁定或法院判决。
- **审计记录（audit trail）**：记录起草了什么、由谁起草、谁批准的留痕。

## 用智能体搭建

**形态：** `skill`。一位顾问一次回复一份通知，并且全程在对话中，所以一个装有回复模板和研究流程的 skill 就够了。

**需要：** PDF 形式的通知；作为文件的客户申报资料和以往回复；公司由法律、通告、判例和模板组成的知识库（作为参考文件，或通过连接器）；公司的回复模板；一套经公司批准、可以处理保密的客户税务记录的环境。不要接入邮件工具。

| 步骤 | 搭建方式 |
|---|---|
| 上传通知 PDF → 提取并结构化每个问题 | skill 读取 PDF，写出编号的问题清单，每个问题附通知原文的措辞，以及涉及的金额或期间。 |
| 每个问题：检索客户申报资料、以往回复、法律/通告、判例 | 内置子智能体各负责一个问题，返回客户文件和知识库中对应的段落，各附文件名和位置。 |
| 按 13 点模板起草回复并附证据引用 | 主对话根据子智能体返回的表格填写公司的模板。没有引用段落支撑的论断标为待定，不作论证。 |
| 🛑 review (顾问修改并批准) | 见“检查点”。 |
| 发出 | 由顾问在智能体之外完成。 |
| 反馈回流到系统 | 顾问的修改被保存为一份备注，供加入 skill 的参考文件，由顾问决定采纳或丢弃。 |

**检查点：** `review`：skill 最后给出草稿，列出每个问题、其证据和引用，然后停下；由顾问修改并批准。智能体没有邮件工具，所以由顾问从自己的系统发出回复。

**与来源相比：** 唯一的来源是一家厂商的案例页面，没有日期，它的公开实例就是同一个页面。它写明所用的是基于 Azure 的 GPT-4 和自建的检索流水线，这套搭建方式改用 skill 加子智能体处理文件。来源给出的初稿耗时和准确率是针对它自己的系统，不是对这套搭建方式的说法。来源没有说明反馈一步如何改进系统，所以表中最后一行只是一个建议。

*以上是依据本条目的步骤和截至 2026-11 的工具文档做出的设计，不是已报道的实例。*

## 步骤

*以下按来源所述。*

1. 有人把政府税务通知以 PDF 上传。LLM 识别税务机关提出的每个问题，并将其结构化，以便分别研究和起草 [[1]](#sources)。
2. 对每个问题，系统检索客户的申报资料、以往回复、内部的法律/法案/通告、判例和模板，使每个论点都有引用的证据支撑 [[1]](#sources)。
3. 系统按固定的 13 点模板起草回复，由模板组织论点和引用 [[1]](#sources)。
4. 🛑 **审阅**：顾问在发出前审阅、修改并批准草稿；所有操作都作为审计记录留痕 [[1]](#sources)。
5. 审阅人的反馈用于改进系统，使其跟上规则变化 [[1]](#sources)。

**产出：** 一份经批准的、给税务机关的回复，带客户记录和法律的引用，并附在项目的审计记录中归档。
**失败模式 → 防护：** 多问题通知且证据量大，容易漏掉一点 → 先拆分为问题，再按问题套用模板。法律会变 → 基于持续维护的内部知识库检索。引用错误 → 发送前由顾问批准。
**与相近工作流的区别：** AWF-0041 可审阅的 1040 准备：那是根据客户原始文件准备并提交申报表，带字段校验和二次审阅。本工作流的交付物是对税务机关通知的回复，逐个问题起草并附法律引用，由顾问一次性批准。交付物不同，检查点只有一个。
